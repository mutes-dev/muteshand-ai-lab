## CORE PRINCIPLE

**Orchestrator controls flow — core pipeline controls truth.**

The HAND (Orchestrator) Layer sits ABOVE system_entry.
It does NOT replace or modify any core pipeline layer.
Core pipeline remains the sole execution authority.

# LAYER DEFINITIONS

---

## 1. TASK CLASSIFIER (AUTONOMY GATE)

**Responsibility:**

* Analyze incoming tasks and produce classification signals (risk, complexity, confidence) to guide execution decisions.

**Behavior:**

* Hybrid classification:
  - Rule-based patterns (deterministic, fast)
  - LLM-assisted analysis (nuanced understanding)
* Risk-based classification (primary signal)
* Complexity as secondary signal
* Confidence threshold for auto-execution
* Conservative default: when uncertain, require approval

**Output:**

```python
{
  "risk_level": "low" | "medium" | "high",
  "complexity": "low" | "medium" | "high",
  "confidence": float,  # 0.0–1.0
  "reasoning": string
}
```

---

## EXECUTION DECISION LOGIC

Execution decisions are determined by the orchestrator using classification signals.

Rules:

- If confidence < threshold → approval REQUIRED
- If risk_level == "high" → approval REQUIRED
- If risk_level == "medium" → approval REQUIRED
- If risk_level == "low":
    - If complexity == "high" → approval REQUIRED
    - Else → auto execution allowed

These rules are deterministic and must be applied consistently.

**Rules:**

* MUST err on side of caution (default to approval)
* MUST NOT block execution indefinitely
* Classification influences but does not override user control

### AUTHORITY CONSTRAINT

- Task Classifier provides RECOMMENDATIONS ONLY.

- It MUST NOT:
  - block execution
  - enforce approval independently
  - act as final authority

- Orchestrator controls flow decisions but MUST NOT override SYSTEM_CONTRACTS or HARNESS validation.
- User (override)

## 2. ORCHESTRATOR PLANNER (WORKFLOW PLANNER)

**Responsibility:**

* Decompose user goal → workflow (steps[])
* Define WHAT needs to be done
* NOT how (agents define implementation)
* Create initial step sequence

**Behavior:**

* Hybrid planning model:
  - Deterministic patterns for known workflows
  - LLM-assisted for novel goals
* Proposes plan OR auto-executes based on task classification
* Plans are DYNAMIC — evolve during execution

**Output:**

```python
{
  "status": "success",
  "workflow": {
    "id": string,
    "name": string,
    "goal": string,           # original user intent
    "steps": [
      {
        "id": string,
        "name": string,
        "purpose": string,    # what this step achieves
        "agent": string,      # which agent handles it
        "estimated_complexity": "low" | "medium" | "high"
      }
    ],
    "approval_required": bool
  }
}
```

**MUST NOT:**

* Call tools or execute anything
* Generate tool arguments (parser/resolver responsibility)
* Assume step order is fixed (may change at runtime)

### PLANNING RESPONSIBILITY BOUNDARY

- Orchestrator Planner is responsible for:
  - initial decomposition of user goal
  - strategic workflow definition

- Workflow Runtime is responsible for:
  - tactical adjustments ONLY
  - executing and refining steps within current workflow

- Runtime MUST NOT:
  - redefine overall workflow structure independently
  - override planner-defined goal

- Runtime MAY:
  - request planner to generate new steps when needed

## 3. WORKFLOW RUNTIME (STATE MACHINE + PROCESS ENGINE)

**File:** `orchestrator_runtime.py`

**Responsibility:**

* Manage workflow lifecycle (ACTIVE, PAUSED, COMPLETED, FAILED, BLOCKED)
* Manage step lifecycle (PENDING, RUNNING, COMPLETE, FAILED, BLOCKED)
* Enforce retry logic with max_retries ceiling
* Handle state transitions deterministically
* Route step execution to appropriate executor (agent or system_entry fallback)
* **Process-driven execution loop** (Agile-style iteration)

**Process-Driven Execution Model:**

Workflows are NOT fixed sequences. They evolve dynamically.

```
Execution Loop:
1. PLAN next step (orchestrator planner)
2. EXECUTE step (agent → system_entry)
3. VALIDATE result (intent validator)
4. CHECK alignment with original goal (governance layer)
5. ADJUST next step (add/modify/remove steps as needed)
6. REPEAT until goal complete or blocked
```

**OUTPUT FORMAT:**

```python
{
  "id": string,
  "name": string,
  "status": "ACTIVE" | "PAUSED" | "COMPLETED" | "FAILED" | "BLOCKED",
  "goal": string,              # original user intent (preserved)
  "steps": [
    {
      "id": string,
      "name": string,
      "agent": string,
      "status": "PENDING" | "RUNNING" | "COMPLETE" | "FAILED" | "BLOCKED",
      "retries": int,
      "max_retries": int,
      "input": any,
      "output": any,
      "error": string | null,
      "created_at_runtime": bool  # true if step added dynamically
    }
  ],
  "drift_detected": bool,        # governance flag
  "user_paused": bool            # user control flag
}
```

**RULES:**

* MUST trigger EXACTLY one system_entry call per step (atomic execution)
* MUST NOT batch multiple steps into single execution
* MUST increment retries only on failure
* MUST escalate to BLOCKED when retries exhausted
* MUST NOT modify pipeline data
* MUST allow step creation at runtime (dynamic workflows)
* MUST enforce validation before continuation
* MUST prevent drift from original goal (via governance check)

**MEANINGFUL PROGRESS:**

Meaningful progress is defined as:

- advancement toward the original goal
- successful completion of a step with valid output
- transition of workflow state toward completion

The following do NOT count as progress:

- repeated ineffective retries
- cyclic step execution patterns
- outputs that fail validation or do not advance the goal

**NO-PROGRESS ESCALATION:**

If no meaningful progress is detected across a bounded number of iterations:

- execution MUST escalate to the user
- autonomous execution MUST NOT continue indefinitely

The threshold for escalation is configurable and MUST NOT be hardcoded in architecture.

**STATE TRANSITIONS (VALID ONLY):**

```
PENDING → RUNNING
RUNNING → COMPLETE
RUNNING → FAILED
FAILED → RUNNING (retry, if retries < max_retries)
FAILED → BLOCKED (if retries >= max_retries)
PENDING → BLOCKED
RUNNING → BLOCKED
COMPLETE → terminal
BLOCKED → terminal
PAUSED → RUNNING (user resume)
PAUSED → BLOCKED (user abort)
```

## 3A. PARALLEL EXECUTION (CONTROLLED)

**Responsibility:**

* Enable concurrent execution of independent steps
* Improve performance without compromising determinism or control
* Ensure outputs remain traceable and non-ambiguous

---

**Rules:**

* Parallel execution is ONLY allowed when steps are independent and have no data dependency
* Each parallel step MUST:
  - follow atomic execution (EXACTLY one system_entry call)
  - maintain full execution trace
* system_entry rules remain unchanged and MUST be enforced per step

---

**Output Handling:**

When multiple agents execute in parallel:

* Each agent produces an independent output
* Outputs MUST NOT be merged directly

---

**Resolution Strategy:**

If multiple outputs exist, the system MUST choose ONE of the following:

1. **Selection**
   - Orchestrator selects the output best aligned with the goal

2. **Resolution Step**
   - Orchestrator creates a new step to resolve conflicting outputs
   - Assigned to an appropriate agent

3. **User Escalation**
   - If conflict or uncertainty is high, escalate to user

---

**Governance Integration:**

* Governance layer evaluates:
  - alignment with original goal
  - consistency between outputs
* Governance determines whether:
  - selection is safe
  - resolution is required
  - escalation is necessary

---

**Constraints:**

* The system MUST NOT:
  - merge outputs into a synthesized response
  - infer or average conflicting results
  - create implicit combined answers

* All final outputs MUST be:
  - traceable to a single execution path
  - verifiable against system contracts

## 4. GOVERNANCE / ALIGNMENT CONTROL

**Responsibility:**

* Detect drift from original goal
* Validate agent suggestions
* Approve / reject plan changes
* Enforce plan alignment throughout execution

Governance is the final authority for execution decisions.

It resolves all signals from:

- Intent Validator
- Agent suggestions
- Runtime conditions

**Drift Detection:**

* Compare current execution path vs original goal
* Detect scope creep, tangent execution, goal substitution
* Flag when agent output diverges from intended outcome

**Approval Authority:**

* Orchestrator controls workflow and execution flow decisions, but MUST operate within SYSTEM_CONTRACTS and HARNESS validation constraints.
* Agents may suggest improvements
* Orchestrator approves/rejects agent suggestions (flow control only, not validation overrides)

**Output:**

```python
{
  "drift_detected": bool,
  "drift_type": "scope_creep" | "tangent" | "goal_substitution" | "none",
  "severity": "low" | "medium" | "high",
  "recommendation": "continue" | "adjust" | "escalate",
  "user_notification_required": bool
}
```

**Rules:**

* MUST NOT allow silent deviation from goal
* MUST escalate high-severity drift to user
* MUST maintain original goal as north star
* Suggestions from agents are advisory only

**Conflict Resolution:**

If signals conflict between components:

- Governance decisions take precedence over all advisory signals
- No component may override Governance decisions

## 5. AGENT EXECUTOR (LLM SANDBOX — HOW, NOT WHAT)

**File:** `agent_executor.py`

**Responsibility:**

* Execute agent steps with LLM integration
* Detect USE_TOOL: prefix in LLM output
* Route tool calls through system_entry (NOT direct tool access)
* Format tool output via LLM formatter (advisory only)
* Handle LLM_ERROR as failure signal
* Return structured agent output contract
* **Define HOW to achieve step purpose, not WHAT to do**

**Agent Interaction Model:**

**Agents define HOW, Orchestrator defines WHAT:**

| Authority | Responsibility |
|-----------|---------------|
| Orchestrator | WHAT needs to be done (step purpose, goal alignment) |
| Agent | HOW to achieve it (implementation, tool selection, reasoning) |

**Agents may:**
* Suggest improvements to plan
* Propose alternative approaches
* Request additional steps
* Recommend tool selection
* Suggest at most ONE structural workflow change per step

**Agents MUST NOT:**
* Decide workflow flow
* Approve their own suggestions
* Execute without orchestrator routing
* Override governance decisions

**Agent Suggestion Flow:**
```
Agent proposes change → Orchestrator evaluates → Governance check
→ [if aligned] Approve and modify workflow
→ [if drift detected] Reject or escalate to user
```

**OUTPUT FORMAT:**

```python
# Success
{
  "status": "success",
  "result": {
    "agent": string,      # agent name
    "role": string,       # agent role
    "reasoning": string,  # explanation or tool used
    "output": string,     # final formatted response
    "executed_input": string | None,  # USE_TOOL: call if any
    "execution_result": dict | None,  # raw system_entry result
    "suggestions": [      # optional improvements proposed
      {
        "type": "add_step" | "modify_step" | "tool_change",
        "description": string,
        "reasoning": string
      }
    ]
  }
}

# Failure
{
  "status": "failure",
  "reason": string
}
```

**Rules:**

* MUST route ALL USE_TOOL: calls through system_entry (line 77, 234)
* MUST NOT execute tools directly outside sandbox
* MUST return failure on LLM_ERROR (not silent success)
* MUST NOT control workflow flow (returns result only)
* MUST validate output via agent_output_validator
* Suggestions are advisory — orchestrator approves/rejects
* Repeated suggestions without measurable progress MUST trigger escalation
* Suggestions MUST NOT cause unbounded workflow expansion
* Formatter output is NON-AUTHORITATIVE (advisory display only)

## 6. ESCALATION & RETRY CONTROL

**Responsibility:**

* Manage hybrid retry model:
  - Limited retries (bounded by max_retries)
  - Intelligent retry attempts (memory-aware)
* Define escalation triggers
* Route to user when internal resolution fails

**Escalation Triggers:**

| Trigger | Condition | Action |
|---------|-----------|--------|
| Repeated failure | Same error across retries | Escalate to user |
| Uncertainty | Low confidence in any path | Request guidance |
| Conflicting outputs | Agents disagree on approach | User resolution |
| Drift detected | Goal alignment lost | User approval required |
| Critical operation | Destructive action pending | Mandatory approval |

**Retry Model:**

```
Step fails → Apply memory → Retry (increment retry count)
→ [if success] Continue
→ [if max_retries exhausted] Escalate to user
```

**Rules:**

* Retry internally first (with memory application)
* Escalate to user if threshold exceeded
* MUST NOT loop infinitely
* MUST track retry history
* User escalation is not failure — it's controlled handoff

## 7. USER APPROVAL MODEL

**Responsibility:**

* Require approval for sensitive operations
* Define approval scope
* Enable user override at any time

**Approval Required For:**

* **Installations** — new packages, dependencies, tools
* **External actions** — API calls, webhooks, external services
* **Destructive operations** — delete, overwrite, irreversible changes
* **Scope expansion** — workflow growing beyond original intent
* **Low-confidence classifications** — uncertain task assessment

**Approval Levels:**

```python
{
  "operation": string,
  "risk_level": "low" | "medium" | "high" | "critical",
  "approval_required": bool,
  "user_can_override": bool,
  "timeout_seconds": int | null,  # null = indefinite wait
  "default_action": "ask" | "allow" | "deny"  # "ask" = default
}
```

**Rules:**

* Default = ask unless explicitly pre-approved
* User can override at any time
* Pre-approved operations logged for audit
* Timeout handling: queue for user or abort with notification

## 10. MEMORY-AWARE BEHAVIOR

**Responsibility:**

* Influence planning based on execution history
* Apply learned patterns to improve success rate
* Distinguish small improvements from major changes

**Memory Application Model:**

```
Small improvements (automatic):
- Noise token removal (execution_patterns.json)
- Retry with cleaned input
- No approval required

Major changes (approval required):
- Workflow structure modification
- New step creation
- Agent reassignment
- Goal redefinition
```

**Memory Influences:**

| Area | Influence | Approval |
|------|-----------|----------|
| Planning | Prefer previously successful patterns | Auto if low risk |
| Decision making | Use historical success rates | Auto |
| Noise removal | Apply learned tokens | Auto |
| Workflow structure | Suggest based on similar goals | Required |

**Rules:**

* Small improvements → automatic application
* Major changes → require approval
* Memory NEVER overrides user explicit instruction
* Memory poisoning prevention (numeric/path filters already in place)

### MEMORY SAFETY CONSTRAINTS

- Memory MUST NOT:
  - alter original user goal
  - override explicit user instructions
  - introduce new steps without orchestrator approval

- Memory influence is strictly advisory.

- All memory-driven changes MUST pass:
  → Governance check (Section 4)

## 11. STEP DEFINITION (DYNAMIC — CREATED AT RUNTIME)

**Step Characteristics:**

* **Atomic** — EXACTLY one system_entry call
* **Dynamic** — created at runtime, NOT pre-defined
* **Purpose-driven** — each step has clear purpose toward goal
* **Independent** — steps can be added, removed, reordered during execution

**Step Lifecycle:**

```
PLANNED → CREATED → RUNNING → COMPLETE/FAILED → [next step planned dynamically]
```

**Output Format:**

```python
{
  "id": string,                    # unique step identifier
  "name": string,                  # human-readable name
  "purpose": string,               # what this step achieves
  "agent": string,                 # assigned agent
  "status": "PENDING" | "RUNNING" | "COMPLETE" | "FAILED" | "BLOCKED",
  "retries": int,
  "max_retries": int,
  "input": any,                    # step input (from orchestrator)
  "output": any,                   # agent output
  "error": string | null,
  "created_at_runtime": bool,      # true if dynamically created
  "created_during_step": string | null,  # parent step that spawned this
  "execution_log": [...]           # history of attempts
}
```

**Dynamic Step Creation:**

Steps may be created during execution when:
* Agent suggests additional steps (approved by orchestrator)
* Governance detects need for correction step
* Workflow reveals hidden complexity
* User requests plan modification

**Rules:**

* One step = EXACTLY one system_entry call (unchanged)
* Steps created dynamically MUST still follow atomic rule
* Orchestrator maintains full control over step lifecycle
* No agent may create steps without orchestrator approval

### CONSTRAINTS (CRITICAL)

- Each execution iteration MAY create AT MOST one new step unless explicitly approved by user or orchestrator override.
- Total steps per workflow MUST be bounded by a configurable limit (max_steps_per_workflow).
- Orchestrator MUST detect non-progress loops:
  - repeated identical steps
  - no state change across iterations
- Orchestrator MUST detect cyclic step patterns, even if step definitions differ superficially
- Detection should consider step purpose and outcome, not only step identity
- If loop detected → trigger escalation (Section 6).

# DATA FLOW (DYNAMIC WORKFLOW MODEL)

```
User Request
↓
[1] TASK CLASSIFIER
    → Analyze task → produce classification signals (risk, complexity, confidence)
    → Set approval requirement based on decision logic
↓
[2] ORCHESTRATOR PLANNER (if complex/critical)
    → Decompose goal → initial steps[]
    → Create workflow with goal preservation
↓
[3] WORKFLOW RUNTIME — Process Loop
    │
    ├─► PLAN next step (orchestrator planner)
    │
    ├─► GOVERNANCE CHECK
    │   → Validate alignment with original goal
    │   → Detect drift, scope creep
    │
    ├─► [if approval required] USER APPROVAL
    │   → Wait for user, timeout handling
    │
    ├─► AGENT LOOKUP (agent_registry.py)
    │
    ├─► AGENT EXECUTOR (agent_executor.py)
    │   → LLM Registry → LLM Executor → LLM Response
    │   → [if USE_TOOL: detected]
    │       → system_entry(tool_call) → Core Pipeline Execution
    │   ← Execution Result
    │   → Intent Validator → Accept/Retry/Escalate Decision
    │   → Agent Output Validation
    │   ← Structured Agent Output (+ suggestions)
    │
    ├─► ESCALATION CHECK
    │   → Repeated failure? → Escalate to user
    │   → Drift detected? → User approval
    │   → Max retries? → BLOCKED
    │
    ├─► MEMORY APPLICATION
    │   → Apply learned patterns (if retry)
    │   → Update execution_patterns.json
    │
    ├─► ADJUST NEXT STEP
    │   → Add/modify/remove steps based on results
    │   → Process suggestions from agent (orchestrator approves)
    │
    └─► REPEAT until goal complete or blocked

Execution decision flow:

- Intent Validator produces recommendation
- Governance evaluates alignment and context
- Orchestrator applies final execution decision within system constraints

↓
[4] PERSISTENCE (if COMPLETED or PAUSED)
    → Store workflow state
    → Log execution history
← Workflow Result
```

# FAILURE MODEL

| Failure Type | Response |
|-------------|----------|
| **LLM_ERROR** | failure status, triggers retry with memory |
| **Intent contradiction** | retry or escalate based on confidence |
| **Max retries exhausted** | escalate to user or BLOCKED |
| **Drift detected** | governance check → adjust or escalate |
| **Approval timeout** | queue or abort with notification |
| **Invalid agent output** | validation failure, logged |
| **Persistence failure** | logged, execution continues |
| **User abort** | immediate stop, cleanup, log state |
| **system_entry rejection** | MUST retry, adjust, or escalate — no alternative paths |

**Escalation is not failure** — it's controlled handoff to user judgment.

## REJECTION HANDLING CONSTRAINT

If system_entry rejects execution:

- the system MUST retry, adjust input, or escalate to the user
- it MUST NOT attempt alternative execution paths
- it MUST NOT bypass validation under any circumstance
