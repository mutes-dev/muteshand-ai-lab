# AI LAB — CANONICAL PROJECTION MODEL V1

## PURPOSE

Defines the canonical projection architecture used for workflow rendering, synchronization, continuity, and interaction.

This contract formalizes:

* orchestrator-owned projections
* frontend projection rendering
* projection identity
* projection lifecycle
* projection mutation flow
* projection transport semantics
* canonical read-model ownership

Projection synchronization follows the commit ordering defined in:
ORCHESTRATION_AND_EXECUTION_SEQUENCE_CONTRACT_V1

Projection mutation legality boundaries are governed by:
MUTATION_LEGALITY_AND_RUNTIME_ISOLATION_CONTRACT_V1

Projection persistence semantics are governed by:
PERSISTENCE_AND_DURABILITY_CONTRACT_V1

Runtime coordination is governed by:
RUNTIME_REGISTRY_AND_EXECUTION_COORDINATION_CONTRACT_V1

Execution identity and replay semantics are governed by:
EXECUTION_IDENTITY_AND_REPLAY_CONTRACT_V1

---

## CORE PRINCIPLE

Canonical projections are orchestrator-owned synchronized read models.

Canonical projections provide:

* stable workflow visibility
* synchronized rendering
* editable plan visibility
* deterministic continuity behavior

Canonical projections are NOT:

* execution truth
* lifecycle authority
* execution state ownership

Lifecycle Authority remains the authoritative source of lifecycle truth.

Projections synchronize AFTER authority commit per:
ORCHESTRATION_AND_EXECUTION_SEQUENCE_CONTRACT_V1

Projections NEVER participate in mutation legality decisions per:
MUTATION_LEGALITY_AND_RUNTIME_ISOLATION_CONTRACT_V1

Projections NEVER participate in lifecycle sequencing authority.

---

# 1. PROJECTION OWNERSHIP

Canonical projections are owned by:

* Orchestrator Runtime

Frontend consumes projections.

API transports projections.

Neither frontend nor API owns projection truth.

The system MAY expose:

* Workflow Projection
* Plan Projection
* Step Projection
* Control Projection
* Output Projection
* Trace Projection

All rendered workflow state MUST originate from canonical projections.

# 3. SEMANTIC OBSERVABILITY RELATIONSHIP

Canonical projections MAY expose:

* semantic expectation metadata

Canonical projections MUST NOT:

* redefine semantic expectations

SEMANTIC_EXPECTATION_MODEL_CONTRACT_V1

# 4. PROJECTION IDENTITY

Every canonical projection MUST include:

* workflow_id
* projection_version
* projection_timestamp
* projection_type

Projection identity MUST remain stable across:

* reload
* reconnect
* hydration
* streaming interruption

### WORKFLOW IDENTITY RELATIONSHIP

Canonical projections synchronize FROM authoritative workflow identity.

Canonical projections:

* do NOT define workflow existence
* do NOT define workflow identity truth
* do NOT restore canonical workflow authority

Projection identity continuity exists to preserve:

* synchronized visibility
* continuity rendering
* hydration continuity

Workflow identity continuity remains governed by:

* Lifecycle Authority
* Persistence Layer

---

# 5. PROJECTION VERSIONING

Canonical projections MUST support deterministic ordering.

Newer valid projections supersede older projections.

Late or stale projections MUST NOT overwrite newer synchronized projections.

Projection versioning MAY use:

* timestamps
* sequence counters
* monotonic version numbers

Implementation choice is flexible.

Deterministic ordering is REQUIRED.

---

# 6. PROJECTION EMISSION MODEL

Canonical projections MUST be emitted when:

* workflow initializes
* lifecycle changes
* steps update
* outputs update
* plans mutate
* synchronization refresh occurs
* continuity reconciliation occurs

Projection emission follows the canonical ordering defined in:
ORCHESTRATION_AND_EXECUTION_SEQUENCE_CONTRACT_V1

Projections MUST NOT be emitted before the corresponding lifecycle authority commit.

Projection emission MUST remain workflow-scoped.

---

# 7. PROJECTION LIFECYCLE

Canonical projections MAY exist in states such as:

* ACTIVE
* STALE
* INVALIDATED
* TERMINAL

Projection lifecycle is separate from:

* workflow lifecycle
* execution lifecycle

Projection lifecycle governs synchronization visibility only.

## CONVERGENCE ISOLATION

Canonical projections are synchronized read models only.

Projection systems MUST NOT:

* gate lifecycle convergence
* block terminalization
* prevent authoritative recovery stabilization

Projection failures MUST remain isolated from lifecycle authority convergence.

System-wide sequencing is governed separately by:
SYSTEM_CONVERGENCE_AND_RECOVERY_CONTRACT_V1

---

# 8. PROJECTION MUTATION FLOW

Frontend MUST NOT directly mutate canonical projections.

Projection changes occur through:

1. Intent/action request
2. API validation
3. Orchestrator validation
4. Governance/dependency validation
5. Runtime update
6. Projection regeneration
7. Projection re-emission
8. Frontend re-render

This flow obeys mutation legality windows per:
MUTATION_LEGALITY_AND_RUNTIME_ISOLATION_CONTRACT_V1

Projection regeneration follows the sequencing defined in:
ORCHESTRATION_AND_EXECUTION_SEQUENCE_CONTRACT_V1

---

# 9. PLAN PROJECTION MODEL

Editable plans operate through canonical plan projections.

Frontend MAY:

* request edits

* request modifications

Frontend MUST NOT:

* directly rewrite canonical plan projections
* bypass orchestrator validation

All plan edits MUST:

* pass dependency validation
* pass governance validation
* trigger projection regeneration

# 14. MULTI-WORKFLOW SUPPORT

Canonical projections MUST remain isolated per workflow_id.

Cross-workflow contamination is prohibited.

Projection synchronization MUST remain workflow-scoped.

### MULTI-WORKFLOW RESTORATION

Canonical projections MUST support:

* simultaneous multi-workflow restoration
* workflow-scoped projection regeneration
* workflow-scoped synchronization continuity

Projection restoration MUST remain isolated per workflow_id.

Projection restoration MUST NOT:

* merge workflow identity
* infer workflow authority
* synthesize workflow existence
