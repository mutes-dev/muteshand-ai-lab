Planner includes deterministic normalization:

* converts implicit chaining → explicit
* no regex
* no interpretation

Status: ACTIVE
Reason: improve usability without breaking determinism

---

## DECISION — NORMALIZATION MODEL

Normalization uses:

* structural matching
* strict positional rules

Status: ACTIVE
Reason: maintain deterministic behavior

---

## DECISION — REGEX USAGE CONSTRAINT

Regex usage is FORBIDDEN in:

- input normalization
- argument parsing
- semantic inference
- planner reasoning

Regex usage is ALLOWED ONLY in:

- deterministic semantic mapping

CONSTRAINTS:

- patterns must be explicit and fixed
- one pattern maps to exactly one tool
- patterns must not overlap
- no ambiguity allowed
- tool must exist in registry before routing
- no argument extraction allowed at planner level

Purpose:

Enable controlled semantic access without introducing drift or inference.

Status: ACTIVE
Reason: controlled determinism vs blanket prohibition

---

## DECISION — EXECUTION EMBEDDED IN MANAGER

Execution remains inside manager (transitional).

Status: ACTIVE
Reason: avoid premature modularization

---

## DECISION — REMOVE PLANNER-LEVEL VALIDATION

Planner MUST NOT call validation.

Status: ACTIVE (FINAL)
Reason:

* Planner does not own arguments
* Prevents pre-pipeline failure
* Restores correct pipeline order

# ⚠️ TEMPORARY DECISIONS (CONTROLLED DEVIATIONS)

---

## DECISION — RUNTIME CHAIN RESOLUTION

Chain Resolver executes inside the execution loop.

- PREVIOUS_RESULT is a runtime dependency
- Resolution requires actual execution results
- Therefore cannot occur in structural phase

Status: ACTIVE

Reason:
Runtime dependency resolution requires access to execution results.
Moving this earlier introduces invalid data and breaks determinism.

Conclusion:
Chain resolution is a runtime concern and MUST remain inside execution.

## DECISION — SEMANTIC MAPPING LAYER

Planner includes deterministic semantic pattern matching:

Execution Order:
1. Normalize input
2. Direct tool match
3. Semantic pattern match
4. Else → structured failure

Pattern Rules:
- Explicit regex patterns only
- One pattern maps to exactly one tool
- Patterns must not overlap
- Tool must exist in registry
- No argument extraction

Status: ACTIVE
Reason: Enable direct tool accessibility without unsafe fallbacks

---

## DECISION — FALLBACK REMOVAL

Unsafe fallback behavior REMOVED.

Previous behavior:
- Any input could be treated as tool name
- No validation of tool existence

Current behavior:
- Only valid tool names from registry allowed
- Unknown inputs return structured failure

Status: ACTIVE
Reason: Prevent execution of arbitrary/invalid tools

---

## DECISION — DETERMINISTIC ROUTING

Planner routing is now FULLY deterministic for known inputs:

Direct match → immediate return
Semantic match → immediate return
Unknown input → immediate failure

Only math operations use LLM (by design).

Status: ACTIVE
Reason: Reduce LLM dependency for common operations

---

## DECISION — SEMANTIC ROUTING WITHOUT ARGUMENT EXTRACTION

- Planner routes semantic inputs only
- Argument extraction remains resolver responsibility
- No inference allowed at planner level
- input_text preserved unchanged

Status: ACTIVE
Reason: Maintain layer separation, no planner argument generation

---

## DECISION — VALIDATION FAILURE IS ACCEPTABLE FOR SEMANTIC INPUTS

- Missing arguments cause validation failure
- System must NOT guess values
- Explicit failure is correct behavior
- Resolver enhancement will address in Phase 3

Status: ACTIVE
Reason: Prevent silent inference, enforce explicit argument handling
