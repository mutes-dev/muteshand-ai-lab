1. Argument ownership moved from Planner → Resolver  
   Reason: enforce deterministic architecture  

2. Parser reduced to tokenization only  
   Reason: strict layer separation  

3. Failure model changed to explicit failure objects  
   Reason: prevent silent failure  

4. Logging temporarily allowed in execution  
   Reason: debugging visibility (to be removed later)  

5. Execution fallback guard introduced
   Reason: prevent fallback logic from overriding "PREVIOUS_RESULT" tokens and breaking deterministic chaining

6. Duplicate chaining logic removed from manager layer
   Reason: enforce Chain Resolver as single source of truth and eliminate conflicting logic paths

7. Execution layer remains embedded in manager (transitional state)
   Reason: modularization not yet complete; premature separation would risk architecture drift

8. Input normalization layer introduced in planner
   Reason: convert implicit chained instructions into explicit deterministic form without modifying planner intelligence

9. Structured matching model adopted for normalization
   Reason: resolve conflict between literal equality and dynamic values while preserving deterministic architecture

10. Regex and pattern matching explicitly prohibited in normalization layer
    Reason: prevent interpretation and maintain strict deterministic behavior

### DECISION — DUPLICATE DETECTION CONTROL FLOW

Duplicate planner output is treated as a retry failure condition.

It MUST:

* NOT exit via success path
* NOT proceed to execution
* fall through retry loop and be handled by retry exhaustion

Rationale:
Prevents undefined state and enforces deterministic failure behavior.
