## 3. ARCHITECTURAL PROGRESSION MODEL

### 3.1 Layer-Locked Construction

The system is built as a stack of architectural layers.

Each layer:

1. MUST be defined before construction begins
2. MUST declare its authority contracts before implementation
3. MUST verify its contracts before locking
4. MUST NOT be considered complete without harness evidence

### 3.2 Lock Criteria

A layer is LOCKED only when:

- Its responsibility matches ARCHITECTURE_V2 exactly
- It does NOT perform any other layer's responsibility
- It is fully testable in isolation
- It produces deterministic outputs (where applicable)
- It passes both manual tests and harness tests

Once locked:

- The layer MUST NOT be modified unless a P0 issue is found
- Any change must be explicitly approved at Head Dev level

### 3.3 Stabilization Before Expansion

Expansion to the next layer is NOT permitted until:

- Current layer is locked
- Cross-layer contracts are defined
- Integration tests between adjacent layers pass
- No known P0 or P1 issues remain in current layer

### 3.4 Governance Decision Rule

Retry or rework at any layer MUST ONLY occur when governance explicitly returns 'retry'.

Any retry triggered outside governance decision is an architectural violation.

## 4. PHASE STATUS CLASSIFICATION SYSTEM

### 4.1 Status Definitions

| Status | Definition |
|--------|------------|
| NOT STARTED | No design, no implementation, no verification. Layer exists only as architecture intent. |
| PARTIAL | Design exists OR partial implementation exists OR partial verification exists. Not yet lock-eligible. |
| IMPLEMENTED | Implementation exists matching architecture, but not yet verified by harness or audit. |
| VERIFIED | Implementation exists AND passes harness tests AND contract audit. Ready for stabilization review. |
| STABILIZED | Verified AND locked per Architecture Law #4. Layer is frozen; modifications require Head Dev approval and P0 justification. |
| DEFERRED | Explicitly postponed. Must include deferral reason and unblocking conditions. |
| EXPERIMENTAL | Under active exploration. May violate architecture temporarily for learning purposes. MUST be sandboxed. MUST NOT merge to production without re-architecture. |
| BLOCKED | Progress is halted. Must identify blocking dependency, blocking contract, or blocking verification gap. |

### 4.2 Status Transition Rules

- NOT STARTED → PARTIAL: Design or implementation initiated
- PARTIAL → IMPLEMENTED: Implementation matches architecture; internal tests pass
- IMPLEMENTED → VERIFIED: Harness passes; contract audit passes
- VERIFIED → STABILIZED: Head Dev approval; no P0/P1 issues; layer locked
- ANY → DEFERRED: Explicit decision with documented rationale
- ANY → BLOCKED: Dependency or verification failure identified
- BLOCKED → PARTIAL: Blocking condition resolved
- STABILIZED → PARTIAL: P0 found; Head Dev unlocks for emergency fix

### 4.3 No False Progress

A layer MUST NOT be reported at a higher status than its weakest component.

If any subcomponent is NOT STARTED, the layer is at best PARTIAL.

### LAYER 3 — Dependency + Scheduling Enforcement

#### Objective

Enforce execution structure through dependency DAG and scheduling contracts. Ensure parallel execution is safe, deterministic, and conflict-free.

#### Intended Architecture

A deterministic dependency DAG with explicit depends_on semantics. Scheduling is a DERIVED layer — execution groups are ephemeral runtime constructs, NOT persisted in the plan. The scheduler reads plan steps, evaluates dependencies and conflicts, and dynamically forms execution groups at runtime. The plan remains a flat list of steps. Execution groups share a scheduling boundary, execute under the same parallelism rules, and complete before the next group begins. Scheduler uses live step state as authoritative source, with snapshots as cache/fallback only. Fail-fast policy is explicitly defined.

#### Intended Responsibilities

- Maintain DAG structure with explicit dependency edges (no inference from natural language or purpose)
- Derive execution groups dynamically at runtime (NOT persisted, NOT modifying plan structure)
- Evaluate execution group eligibility for parallel scheduling
- Detect resource conflicts before parallel execution
- Enforce pre-flight step mutation cycle
- Prioritize live step state over stale scheduler snapshots
- Re-evaluate dependencies at each execution iteration before group formation
- Invalidate dependent steps when upstream dependencies fail, are retried, or are invalidated
- Prevent stale dependency execution (dependent steps MUST NOT continue using outdated results)

#### Intended Capabilities

- Deterministic dependency resolution (no LLM inference, no heuristic ordering)
- Explicit DAG semantics: nodes = steps, edges = dependencies; graph MUST be acyclic, resolvable, with at least one valid execution path
- Ephemeral execution group formation with parallel eligibility rules
- Resource conflict detection pre-execution
- Step state pre-flight mutation and validation
- Explicit fail-fast vs independent parallel policy definition
- Runtime dependency re-evaluation at each scheduling iteration
- Dependency invalidation propagation (retry, failure, or completion invalidation triggers downstream re-evaluation)
- Stale dependency prevention (system MUST NOT allow dependent steps to execute using outdated dependency results)
- Conflict-aware scheduling that adapts group composition based on conflict severity (LOW allow, MEDIUM sequentialize, HIGH exclude)

#### Intended Enforcement Requirements

- Scheduling is DERIVED; execution groups are ephemeral runtime constructs NOT persisted in the plan
- Scheduler MUST NOT modify plan structure, persist group definitions, or introduce new step entities
- Scheduler MUST NOT make governance decisions, execute steps directly, or override conflict resolution
- Scheduler MUST NOT infer dependencies from step purpose or natural language
- Parallel execution allowed ONLY if no dependency AND no shared state conflict
- NEVER parallel: installs, system changes, environment changes, destructive file actions
- Scheduler snapshots are cache/fallback ONLY; live step state MUST override stale snapshot state
- Dependency resolver MUST be deterministic and model-agnostic
- Fail-fast policy MUST be explicitly defined in scheduling contract
- Runtime MUST re-evaluate all PENDING steps at each execution iteration before group formation
- System MUST NOT allow dependent steps to execute using outdated dependency results
- Dependency invalidation MUST trigger downstream step re-evaluation

#### Intended Stabilization Requirements

- Dependency correctness MUST be verified under mutation and retry
- Parallel execution safety MUST be validated for all conflict categories
- Conflict detection MUST be enforced before execution, never after
- Scheduler snapshot staleness MUST NOT cause false blocking
- Scheduling derivation purity MUST be maintained (groups derived at runtime, not persisted)
- Dependency invalidation propagation MUST be deterministic and complete
- Stale dependency execution MUST be impossible under all runtime conditions

#### Intended Verification Requirements

- Dependency correctness under plan mutation and retry

- Conflict detection enforcement pre-execution
- Stale snapshot rejection behavior
- Scheduling derivation purity (groups ephemeral, plan unmodified)

### LAYER 4 — Projection Continuity + Read Models

#### Objective

Build the synchronized read-model and runtime continuity infrastructure for visibility. Projections are STRICTLY DERIVED from authoritative lifecycle authority; they MUST NEVER become authority. Projections synchronize TO authority; authority NEVER synchronizes FROM projections.

#### Intended Architecture

Projection continuity is RUNTIME CONTINUITY INFRASTRUCTURE — NOT GUI read-model support, NOT lifecycle authority, NOT a source of truth. A pure read-model projection layer derives ALL state from authoritative lifecycle authority. Projections support workflow identity continuity, hydration continuity, event continuity, websocket continuity, projection versioning with monotonicity, stale rejection, and continuity across pause/resume and restart. Terminal projection protection prevents overwriting completed or failed states. The stream registry functions as EPHEMERAL projection cache ONLY — it NEVER stores lifecycle truth (status). The frontend is projection-derived ONLY with ZERO lifecycle synthesis. Temporary projection divergence is acceptable; permanent divergence is PROHIBITED. Projections MUST eventually converge to authoritative runtime/lifecycle state. Convergence is DOWNWARD-AUTHORITY-ONLY: authority → projections, never projections → authority.

#### Intended Responsibilities

- Hydrate read models from AUTHORITATIVE lifecycle authority ONLY — projections NEVER synthesize, originate, or infer lifecycle truth
- Accumulate and merge events into coherent projection state
- Maintain projection identity and monotonic version counters
- Invalidate derived execution artifacts after semantic mutation
- Reject stale projections and trigger refresh or rehydration
- Preserve workflow identity continuity across restart, reconnect, hydration, projection regeneration, and stream rebuild
- Maintain hydration continuity (continuous, monotonic, non-restarting across pause/resume/completion)
- Maintain event continuity (event accumulation and merge semantics without recreation)
- Maintain websocket/polling continuity (transport only, never owning lifecycle state)
- Ensure stream registry functions as EPHEMERAL projection cache ONLY — it NEVER stores status, NEVER becomes lifecycle authority, NEVER competes with runtime authority

#### Intended Capabilities

- Progressive hydration from authoritative state (continuous, monotonic, non-restarting)
- Event accumulation with merge semantics (preserved across pause/resume, no bulk repopulation)
- Projection versioning with monotonicity across restart (version counter never decreases)
- Stale projection detection and rejection (runtime truth always wins)
- Terminal projection protection (COMPLETED/FAILED immutable, cannot be overwritten by non-terminal projections)

### 6.5 Runtime Authority Boundaries

The following runtime authority boundaries MUST be preserved across all layers:

- **Lifecycle Authority centralization:** Exactly ONE layer owns lifecycle truth. No distribution, no mirroring with authority claims.
- **Projection non-authority:** Projections, stream registry, frontend, and transport layers are strictly read-model / cache / transport. They MAY NOT originate, synthesize, or override lifecycle truth.
- **Scheduler derivation-only:** Scheduling groups are ephemeral runtime constructs. Scheduler MUST NOT mutate plan, persist groups, own governance, or infer dependencies.
- **Governance isolation:** Governance decisions are deterministic and independent of validator signals, semantic noise, and projection state.
- **Runtime mutation legality:** Mutation during ACTIVE execution or ACTIVE retry is prohibited. Concurrent conflicting mutations are prohibited. Terminalization is authoritative independent of downstream sync.
- **Stream registry ephemerality:** Stream registry is projection cache only. It caches projections and event snapshots, NEVER lifecycle truth (status). It MUST NOT compete with runtime authority.
- **Recovery authority:** Recovery reconciles to lifecycle authority. Persistence is mirror-only. Projections are NOT recovery authority. Recovery restores state, does NOT replay execution.
- **Downward-authority-only convergence:** Convergence is strictly downward-authority-only. Derived layers (projections, persistence, streams, frontend, transport, caches, observability) NEVER reconcile upward into lifecycle authority. Authority flows downward exclusively: authority → projections, authority → persistence, authority → streams. NEVER projections → authority, NEVER persistence → authority, NEVER streams → authority.

## 15. ARCHITECTURAL AUDIT PREPARATION

### 15.1 Purpose

The formal implementation audit phases are defined in Section 9.

This section defines LIKELY ARCHITECTURAL AUDIT FOCUS AREAS within those phases. These are NOT implementation accusations; they are architectural targets that the audit process should verify against the intended architecture defined in this roadmap.

### 15.2 Authority Leakage Audit Targets

- **Lifecycle authority centralization:** Verify exactly ONE layer owns lifecycle truth. Detect any distribution, mirroring, or delegation with authority claims.
- **Projection authority contamination:** Verify projections NEVER originate, synthesize, or override lifecycle truth. Detect any projection-to-authority feedback loops.
- **Stream registry lifecycle ownership:** Verify stream registry stores ONLY projections and event snapshots, NEVER status or lifecycle truth.
- **Frontend lifecycle synthesis:** Verify frontend derives ALL state from authoritative projection with ZERO synthesis, ZERO inference, ZERO origination of workflow identity.
- **Transport layer authority:** Verify websockets and polling are transport-only with no lifecycle ownership, no state restoration, no authority reconciliation.

### 15.3 Convergence and Recovery Audit Targets

- **Terminalization synchronization coupling:** Verify lifecycle terminalization remains authoritative INDEPENDENT of projection, stream, or frontend synchronization success or failure.
- **Convergence sequencing drift:** Verify convergence operations follow explicit, deterministic, auditable sequence with downward-authority-only directionality.
- **Recovery replay restrictions:** Verify recovery restores authoritative state WITHOUT replaying execution, WITHOUT deriving from projections.
- **Stale-state quarantine semantics:** Verify cold start normalizes ambiguous lifecycle state to quarantine and NEVER allows stale disk to overwrite runtime authority.
- **Persistence authority boundary:** Verify persistence functions as mirror/recovery support ONLY, never claiming lifecycle authority.

### 15.4 Mutation and Scheduling Audit Targets

- **ACTIVE immutability enforcement:** Verify mutation is PROHIBITED during ACTIVE execution and ACTIVE retry under all concurrency conditions.
- **Retry mutation race conditions:** Verify retry as NEW execution attempt with proper isolation, no concurrent mutation, no lifecycle resurrection semantics.
- **Scheduler persistence leakage:** Verify execution groups are ephemeral runtime constructs; scheduler NEVER mutates plan, NEVER persists groups, NEVER makes governance decisions.
- **Stale dependency execution:** Verify system rejects execution of dependent steps using outdated dependency results; invalidation propagates downstream deterministically.
- **Dependency inference prohibition:** Verify scheduler NEVER infers dependencies from step purpose or natural language.

### 15.5 Governance and Observability Audit Targets

- **Governance isolation:** Verify governance decisions remain deterministic and independent of validator signals, semantic noise, and projection state.
- **Semantic observability governance leakage:** Verify semantic drift signals have ZERO influence on governance determinism, ZERO runtime mutation authority, ZERO autonomous trigger capability.
- **Validator signal authority:** Verify validator signals are advisory-only and NEVER directly trigger retry autonomously.
- **Retry legality boundaries:** Verify retry eligibility is governed by execution failure, governance decision, recoverable BLOCKED, or authorized recovery — NOT by validator signals alone.

### 15.6 Contract Drift Audit Targets

- **Implementation-to-contract drift:** Verify every layer's implementation behavior aligns with its declared contracts. Detect silent drift where code behavior has diverged from contract specification without explicit architectural revision.
- **Runtime-to-contract reconciliation:** Verify runtime semantics (state transitions, retry behavior, convergence rules) match contract-defined semantics. Detect runtime assumptions that contradict authoritative contracts.
- **Authority-boundary drift:** Verify authority boundaries (lifecycle ownership, projection non-authority, scheduler derivation-only) are preserved in implementation. Detect any leakage where derived layers have gained implicit authority.
- **Convergence-behavior drift:** Verify convergence sequences and recovery behavior match contract-defined rules. Detect unauthorized convergence paths or upward-reconciliation patterns.
