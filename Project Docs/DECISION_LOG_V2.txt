### Runtime No-Progress Ceiling and BLOCKED Non-Terminality Clarification

**Date:** 2026-06-03

**Decision:**
Runtime max-iteration / no-progress safety ceiling is classified as BLOCKED, not FAILED.

max_iterations_exceeded / no_progress_ceiling represents a recoverable orchestration stall requiring operator/governance intervention. It does not, by itself, prove unrecoverable workflow failure or terminal execution failure.

BLOCKED remains recoverable, mutable, non-terminal, actionable, and Task Hub eligible unless later archived/dismissed or explicitly transitioned by Lifecycle Authority.

Projection systems must not synthesize FAILED truth, failure metadata, retry targets, or terminal FAILED semantics for BLOCKED, PAUSED, ACTIVE, or other non-FAILED workflows.

Failure metadata and retry-target projection fields are valid only when lifecycle_status == FAILED.

**Reason:**
The BLOCKED Semantic Authority Audit found that current runtime/projection behavior had drifted from contracts by treating BLOCKED workflows as terminal FAILED in some paths and by allowing projection code to synthesize failure metadata for non-FAILED workflows.

The audit found that most semantics were already answered by Project Docs:
- BLOCKED is recoverable, mutable, and non-terminal.
- Dependency-victim steps remain BLOCKED.
- Governance escalation / no-progress paths result in BLOCKED.
- FAILED is terminal for the current execution instance but recoverable through authorized retry/re-execution lineage.
- Projections must not synthesize semantic/lifecycle truth.

The only unresolved question was whether the orchestrator runtime loop ceiling should be treated as FAILED or BLOCKED. SA resolved this by classifying runtime max-iteration / no-progress ceiling as BLOCKED.

**Architectural Clarifications:**
- BLOCKED is not terminal FAILED.
- BLOCKED must not be auto-terminalized as FAILED merely because automatic orchestration cannot safely continue.
- Runtime safety ceilings are protective no-progress stalls, not explicit unrecoverable system termination.
- "system termination" → FAILED applies only to explicit unrecoverable terminal failure authority, not protective no-progress ceiling.
- Lifecycle Authority must commit BLOCKED for max_iterations_exceeded / no_progress_ceiling unless a separate explicit terminal FAILED condition exists.
- Non-terminal BLOCKED projection updates must still be emitted for operator visibility.
- Projection failure metadata is read-only display data and must not originate failure truth.
- Task Hub remains the correct surface for actionable/recoverable BLOCKED workflows.
- History is not the default surface for BLOCKED/no-progress workflows.

**Verified Outcomes:**
- orchestrator_runtime.py corrected BLOCKED-as-terminal paths.
- max_iterations_exceeded remains BLOCKED.
- dependency-victim downstream steps remain BLOCKED.
- governance escalation / retry exhaustion paths preserve BLOCKED where contracts require BLOCKED.
- BLOCKED projections are non-terminal with projection_state=ACTIVE.
- projection_schema.py guards failure metadata and retry target computation to lifecycle_status == FAILED only.
- PAUSED/BLOCKED/ACTIVE workflows no longer synthesize failure metadata or retry targets.
- genuine FAILED workflows still expose failure_reason, failed_step_id, retry_target_step_id, retry_eligible, and recoverable FAILED metadata.
- Manual validation confirmed normal execution, mixed BLOCKED/COMPLETED behavior, and genuine FAILED division-by-zero behavior remain operational.

**Explicitly NOT Introduced:**
- no new lifecycle state
- no FAILED_TERMINAL or FAILED_IRRECOVERABLE lifecycle state
- no lifecycle authority change
- no governance authority change
- no projection authority change
- no retry semantic redesign
- no Task Hub / History semantic change
- no frontend authority change
- no SSE/event transport change
- no replay architecture
- no adaptive orchestration
- no old workflow migration

**Impact:**
This decision closes the semantic ambiguity around runtime no-progress safety ceilings and restores alignment between lifecycle authority, runtime governance, projection non-authority, and Task Hub actionability.

It prevents protective orchestration stalls from being misclassified as unrecoverable workflow failure while preserving genuine FAILED workflow recovery semantics.

**Status:** COMPLETE + SA-AUTHORIZED + IMPLEMENTED + VALIDATED

### Sprint 7 Pre-Step Planner Failure Handling and Timeout Deferral

**Date:** 2026-06-07

**Decision:**
Reject the ISSUE-092A application-level LLM timeout/circuit breaker implementation and defer future timeout work until failure-semantics handling is validated end-to-end through GUI/runtime paths.

Adopt graceful pre-step planner failure handling for planner failures that occur before executable steps exist.

Pre-step planner failures must use the existing FAILED lifecycle state with enriched execution/stream result metadata. They must not introduce a new lifecycle state, fabricate failed steps, or fabricate failed_step_label.

For pre-step planner failures:
- status remains FAILED
- steps=[]
- outputs=[]
- workflow_output=null
- failed_step_id=null
- retry_target_step_id=null
- retry_eligible=false
- failed_recoverable=false
- retry_disabled_reason is populated
- machine-readable reason/failure_reason remains preserved
- failure_display_message provides user-facing natural language display text

Frontend may clear Planning/loading state based on terminal backend result, including terminal FAILED without projection, but must not synthesize lifecycle truth.

Projection remains non-authoritative. A pre-step FAILED projection is not required for graceful handling if the backend execution/stream result already provides terminal truth.

Retry Failed Step must not be shown unless backend-provided failed_step_id and retry_target_step_id exist and retry is eligible.

**Reason:**
ISSUE-091 PERF-036 measurement showed LLM latency is the dominant performance factor, but ISSUE-092A's timeout wrapper caused unacceptable GUI/runtime regressions despite passing unit tests. Manual validation proved unit tests alone were insufficient for timeout/failure behavior validation.

ISSUE-092B validation showed that planner/pre-step failures can occur before run_workflow emits a projection. The correct architectural response is not frontend lifecycle synthesis or projection authority escalation, but backend-authored enriched terminal FAILED result handling and frontend cleanup based on backend terminal state.

This preserves the distinction between:
- pre-step planner failure with no failed step and no retry target;
- real execution-step failure with failed_step_id, retry_target_step_id, and retry eligibility.

**Architectural Clarifications:**
- FAILED remains the existing lifecycle state for pre-step planner failure.
- No FAILED_PLANNING or other lifecycle state is introduced.
- execution/stream result may carry terminal failure truth for display when projection is absent.
- Projection absence during pre-run_workflow failure is not itself projection corruption.
- Frontend may stop showing Planning when backend terminal FAILED is received.
- Frontend must not invent lifecycle truth.
- Retry legality remains backend-authored.
- failed_step_label must not be fabricated when no step exists.
- failure_display_message is display-only and does not replace reason/failure_reason machine codes.

**Verified Outcomes:**
- ISSUE-092A timeout implementation rejected and reverted through ISSUE-092A-R.
- llm_executor direct invocation baseline restored.
- Normal workflows restored after rollback.
- Pre-step planner failures now fail gracefully with enriched FAILED metadata.
- Invalid Retry Failed Step suppressed when no failed step/retry target exists.
- Planning clears on terminal FAILED without requiring projection.
- Valid failed-step workflows remain retryable when failed_step_id and retry_target_step_id exist.
- Natural-language planner failure display added through failure_display_message while raw reason/failure_reason are preserved.

**Explicitly NOT Introduced:**
- no LLM timeout/circuit breaker
- no fast-path
- no greeting/conversational support guarantee
- no new lifecycle state
- no projection authority change
- no frontend lifecycle authority
- no governance change
- no retry/recovery redesign
- no fake failed step or failed_step_label
- no planner prompt optimization
- no _format_tool_output change
- no AG1 behavior change

**Impact:**
Sprint 7 failure handling is now safer for planner/pre-step failures. Future timeout/circuit breaker work remains valid but must be reattempted only after failure-semantics paths are validated end-to-end through GUI/runtime integration, not unit tests alone.

**Status:** ISSUE-092A REJECTED + REVERTED; ISSUE-092B COMPLETE + VALIDATED

## PROJECTION + CONTINUITY

### Projection-Only Frontend Model
**Decision:** Frontend must be pure projection renderer. Must derive ALL state from authoritative projection only. Must NOT synthesize lifecycle truth.
**Reason:** Frontend ownership of lifecycle state (isExecuting, activeWorkflowId) caused authority drift.
**Status:** ACTIVE ARCHITECTURE RULE

### Projection Continuity Formalization
**Decision:** Projection continuity is eventual-consistency architecture. Temporary lag is valid. Divergence is a bug only when convergence fails.
**Reason:** Projection systems are transport/projection layers, not lifecycle authority.
**Status:** ACTIVE ARCHITECTURE RULE

### Derived Execution Artifact Reclassification
**Decision:** tool_call, scheduler snapshots, projection caches, and stream projections are mutable operational state. NOT semantic truth. MUST invalidate after semantic mutation.
**Reason:** tool_call persistence bug proved compiled artifacts can diverge from canonical semantic truth.
**Status:** ACTIVE ARCHITECTURE RULE

### Resume Continuity Model
**Decision:** Resume MUST continue same workflow, same projection lifecycle, same hydration lifecycle. Must NOT create new lifecycle authority or competing workflow identity.
**Reason:** Recreating projection ownership caused stale lifecycle states and hydration freezes.
**Status:** ACTIVE ARCHITECTURE RULE

### Runtime Truth Supersedes Projection Interpretation

**Decision:** Formalize runtime inspection and lifecycle authority as authoritative debugging truth sources over projection/UI interpretation.

**Reason:** Runtime survivability audits proved projection divergence and eventual consistency lag were incorrectly interpreted as orchestration corruption during validation.

**Architectural Clarification:**
- Projection layers remain eventual-consistency read models
- Temporary divergence is legal architecture behavior
- Convergence failure is the actual failure condition
- Foreground workflows intentionally differ from projection-backed continuity semantics
- Runtime inspect endpoints are authoritative observability tooling

**Impact:**
Future debugging, validation, dashboard, and websocket evolution must prioritize authoritative runtime truth over projection interpretation.

**Status:** COMPLETE + VERIFIED

### Interrupted ACTIVE Restore/Checkpoint Handling

**Date:** 2026-06-04 / 2026-06-05

**Decision:**
Interrupted/restored ACTIVE steps without authoritative execution failure must not be normalized to FAILED.

Persistence restore interruptions and checkpoint restore interruptions should mark affected ACTIVE steps as BLOCKED with the relevant interruption reason, not FAILED.

Use:
- persistence_restore_interrupted → BLOCKED
- checkpoint_restore_interrupted → BLOCKED

**Reason:**
SA clarified that an interrupted execution identity is not equivalent to a genuine execution failure. Marking interrupted ACTIVE steps as FAILED polluted workflow terminalization and could cause workflows to appear failed even when no execution_result failure existed.

**Architectural Clarifications:**
- FAILED requires explicit execution/governance failure authority.
- Interrupted execution identity is recoverable/operator-actionable blockage, not terminal execution failure.
- BLOCKED preserves recoverability without synthesizing failure truth.
- Projection must not synthesize FAILED metadata or retry targets from restore-interruption markers.
- The minimal fix was chosen to reduce regression risk.

**Explicitly NOT Introduced:**
- no lifecycle authority change
- no projection authority change
- no retry semantic change
- no governance change
- no Task Hub / History semantic change
- no broad post-loop status-gate rewrite
- no replay/recovery redesign

**Impact:**
The restore/checkpoint interruption path is now safer and better aligned with lifecycle authority. A broader post-loop gate ordering risk remains deferred and should be handled only if reproduced.

**Status:**
COMPLETE + IMPLEMENTED + VALIDATED MINIMAL FIX

## 2026-06-08 — ISSUE-095B Sprint 7 AG1-Only Operator-Memory Advisory Bridge

**Date:** 2026-06-08

**Decision:**
Adopt an AG1-only operator-memory advisory bridge as the first active memory usage path.

Sprint 6 ISSUE-079 closed memory as storage/API/GUI/guardrail foundation only, with no active runtime memory usage. Sprint 7 ISSUE-095B now activates the first bounded runtime memory bridge.

The bridge may inject operator-managed memory into AG1/tool-selection context only.

Memory remains read-only, advisory-only, source-labeled, bounded, and non-authoritative.

Planner memory remains deferred.

Learning/adaptation remains deferred.

Legacy `global_memory.py` / `global_memory.json` / `memory_adapter.py` / `preference_tracker.py` remain separate and dormant.

The bridge reads from operator-managed `memory_store.py` only.

Memory may influence AG1 wording/tool-selection context as advisory information, but must not become a deterministic guardrail or authority layer.

Explicit current user/step instruction remains higher priority than memory.

Memory content is treated as data, not executable instruction.

Deterministic eligibility rules:
- `source="user"` only
- categories `behavior` / `preference` / `context`
- category `pattern` excluded
- `confidence >= 0.5`
- `GLOBAL` memory included
- `PROJECT` memory included only when a project/workflow lookup key is available
- `workflow_id` may be used as project lookup key for this slice when no separate `project_id` exists
- max entries and prompt length bounded

Observability decision:
`MEMORY_CONTEXT_USED` must be emitted when advisory memory context is used.
`MEMORY_CONTEXT_USED` must include safe metadata only:
- `count`
- `scopes_used`
- `categories_used`
- `project_id_present` / `project_id_used`
- `memory_ids`
- `bridge_status`

Raw memory values must not be logged in `MEMORY_CONTEXT_USED` metadata.

`MEMORY_CONTEXT_USED` is also emitted to the event bus for operator-visible History / Execution History Events display.

**Reason:**
OPERATIONAL_ROADMAP_V2 moves Sprint 7 toward product capability activation, with memory activation as a first capability milestone.
The safest first activation point is AG1/tool-selection rather than planner because AG1 is already bounded, advisory-only, and system_entry-routed, while planner memory could affect workflow structure.
This provides runtime memory usage without altering lifecycle, governance, projection, retry, recovery, execution_result, or Task Hub/History authority.

**Architectural Clarifications:**
- Memory is advisory context, not execution truth.
- Memory is not governance authority.
- Memory is not lifecycle authority.
- Memory is not retry/recovery/replay/replan authority.
- Memory is not projection truth.
- Memory is not Task Hub / History eligibility authority.
- Memory is not FAILED actionability authority.
- Memory is not automatic learning.
- Memory is not a tool legality layer.
- AG1 remains advisory-only.
- AG1/tool-selection remains LLM-controlled and may still be fragile; ISSUE-095B does not claim deterministic tool-selection guardrails.
- Future memory-assisted guardrails/tool legality must be separately designed.

**Verified Outcomes:**
- New isolated advisory bridge implemented in `system/memory/advisory_bridge.py`.
- Bridge reads `memory_store.py` directly.
- Bridge does not use `global_memory.py`.
- Bridge does not use `memory_adapter.py`.
- Bridge does not activate `preference_tracker.py`.
- Advisory memory is injected into AG1/tool-selection context.
- Planner was not modified.
- `MEMORY_CONTEXT_USED` appears in persisted trace JSON.
- `MEMORY_CONTEXT_USED` appears in UI Events after visibility follow-up.
- Manual validation confirmed operator memory could influence AG1/finalize_output response for "What is your name?"
- Manual validation also confirmed local AG1 tool-selection can still misroute independently of memory correctness.
- Focused ISSUE-095B tests passed after test-safety remediation.

**Explicitly NOT Introduced:**
- no planner memory
- no automatic learning
- no preference adaptation
- no trace/journal-driven memory ingestion
- no memory_store/global_memory unification
- no memory_adapter reactivation
- no preference_tracker activation
- no memory authority over execution_result
- no memory authority over governance
- no memory authority over lifecycle
- no memory authority over retry/recovery/replay/replan
- no memory authority over projection
- no memory authority over Task Hub / History
- no memory authority over FAILED actionability
- no deterministic tool-selection guardrail
- no AG1 authority escalation
- no adaptive orchestration

**Impact:**
ISSUE-095B marks the first active, bounded runtime use of operator-managed memory.
