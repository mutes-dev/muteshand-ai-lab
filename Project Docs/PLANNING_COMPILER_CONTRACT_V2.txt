## Amendment 2026-07-05 — Planner-First Tool-Gated Hybrid Architecture

### 0.1 Planner-first role (clarified)

The planner is the primary workflow decision-maker for non-trivial workflows.

- Capability routing and AG1 remain advisory.
- Capability routing may recommend a tool/profile context but may not replace the planner's decision authority.
- The planning compiler may accept, repair, or reject capability-emitted candidate workflows exactly as it does for planner-emitted workflows.

### 0.2 Scoped tool/profile context

- The planner and AG1 must receive scoped tool/profile catalogs where profile context is available.
- Tool binding / candidate narrowing must respect the active profile.
- The full tool universe must not be exposed when a narrower profile is active.
- Profile definitions are in `TOOL_PROFILE_GATING_CONTRACT_V1`.

### 0.3 Document Q&A quarantine

- Document Q&A output must be structured as `found | not_found | ambiguous | unsupported` plus answer, evidence snippets/chunk IDs, source document identity, and limitations/warnings.
- `semantic_transform` `answer_question` and Slice 007 Q&A behavior are not approved as a planner/compiler target.
- Evidence-backed single-document Q&A may be opened as a bounded future Sprint 11 MVP only after quarantine and profile plumbing are stable.
- Multi-document Q&A is deferred to Sprint 15+.

### 0.4 Capability router demotion

- The capability router is a deterministic closed-form fast path and tool/profile recommender only.
- It does not own workflow planning authority for non-trivial or uncertain workflows.

### 0.5 Structured-data analysis planning boundary

- F5 structured-data analysis steps require active StructuredDataAnalysisProfile membership and a supported operation grammar.
- The planner/compiler must not treat arbitrary table questions ("analyze this spreadsheet") as supported analysis.
- Aggregate/filter/sort/numeric analysis tools must not be silently added to DocumentReadProfile, ComputeProfile, or GeneralFallbackProfile.
- If implementation requires planner/system/AG1 prompt changes, planner-visible schema changes, or lifecycle/governance changes, STOP and escalate.

## 1. Document Purpose

Define the Planning Compiler / Planning Stabilization layer.

**Purpose:**
Convert user intent and/or planner output into a verified, dependency-complete, tool-grounded, output-aware execution plan before handoff to existing runtime/governance/system_entry.

This contract defines:
- intent classification
- capability/tool grounding
- plan skeleton handling
- deterministic dependency binding
- plan verification
- final synthesis dependency binding
- same-resource file sequencing binding
- tool candidate narrowing for AG1
- workflow output aggregation policy
- narrow purpose/output false-success validation
- SAME retry no-prior-tool handling
- document-intelligence planning pattern
- optional dependency / partial-failure design boundary

Explicitly stated:
- This contract does not implement adaptive orchestration.
- This contract does not replace planner, governance, runtime, lifecycle authority, projection, or system_entry.
- This contract does not grant frontend authority.
- This contract does not grant AG1 unrestricted authority.
- This contract does not grant semantic validation broad authority.

---

## 2. Core Principle

Planning intelligence must be stabilized before execution.

A plan is not execution authority.

Planner output is candidate structure, not trusted runtime truth.

The planning compiler may reject, repair within deterministic rules, or require replan before execution.

The existing runtime/governance/system_entry stack remains execution authority.

Planning compiler is not lifecycle authority, governance authority, runtime coordination authority, projection authority, memory authority, or execution truth.

**Correct authority chain:**
```
user intent / planner / capability candidate
-> planning compiler stabilization
-> dependency binding
-> plan verification
-> tool/capability grounding
-> workflow validator
-> runtime/governance/system_entry
-> execution_result truth
-> output aggregation / projection / display
```

**Forbidden authority chain:**
```
planner text
-> direct execution without dependency/tool/output verification
```

---

## 3. Relationship to Existing Authorities

Lifecycle Authority owns lifecycle truth.
Governance owns runtime decisions.
Runtime Registry owns execution coordination state.
execution_result owns execution truth.
system_entry remains sole execution gateway.
Projection remains non-authoritative.
Frontend remains non-authoritative.
Memory/adaptive systems remain advisory only.
AG1 remains tool-selection support, not planning authority.

**Planning Compiler may:**
- validate plan structure
- bind explicit dependencies
- reject partial dependency declarations
- narrow candidate tool classes
- require a final synthesis/output aggregation step
- mark plan as invalid before execution

**Planning Compiler may not:**
- execute tools
- mutate lifecycle truth
- mark steps complete
- rewrite execution_result
- bypass governance
- bypass system_entry
- infer arbitrary semantic dependencies from broad prose
- create adaptive orchestration loops

## 4. Stage Model

This draft defines the proposed planning compiler stage model:

1. **Intent classifier** — classify task shape before planning/execution
2. **Capability/tool grounding** — know available capability classes before tool execution
3. **Plan skeleton** — high-level steps from planner, not trusted until verified
4. **Deterministic dependency binder** — extract and bind all explicit step references
5. **Plan verifier** — reject invalid partial declarations, self/future references
6. **Tool binding / candidate narrowing** — bind steps to narrowed tool classes
7. **Executor handoff** — hand verified plan to existing runtime/governance/system_entry
8. **Output aggregation contract** — define how workflow output is produced
9. **Purpose/output false-success validation** — bounded deterministic gate for obvious false success

Each stage is an architecture rule candidate pending Bryan/SA acceptance.

Runtime must not infer missing dependencies from natural language.

- folder_list
- web_search
- webpage_read
- text_synthesis
- final_output
- compare
- summarize
- transform/rewrite

**Rules:**

## 7. Plan Skeleton

The planner may generate high-level steps.

The plan skeleton is not trusted until dependency binding, verification, and tool grounding pass.

Plan skeleton must not assume dependencies are solved merely because the planner wrote natural language.

---

## 8. Deterministic Dependency Binder

Explicit step references must be extracted deterministically.

**Supported references must include at least:**
- step_1
- step 1
- result of step_1
- result of step 1
- output of step_1
- output of step 1

**Rules:**
- collect all explicit references, not only first match
- support multi-parent dependencies
- deduplicate references
- preserve stable order
- reject self references
- reject future references
- reject nonexistent references
- do not infer broad semantic dependencies from arbitrary prose unless separately approved

**Acceptance examples:**
```
Purpose references result of step_1 and result of step_2
=> depends_on must contain step_1 and step_2

Purpose references result of step_1, step_2, and step_3
=> depends_on must contain all three
```

---

## 9. Partial Dependency Validation

If purpose/output instructions explicitly reference step_N, every referenced prior step must appear in depends_on.

**Rules:**
- validation must reject partial dependency declarations
- validation should not silently repair at execution time
- failure reason should be explicit, such as partial_dependency_declaration or referenced_dependency_missing

**Acceptance example:**
```
purpose = "combine result of step_1 and result of step_2"
depends_on = ["step_1"]
=> plan invalid before execution
```

## 10. Final Synthesis Dependency Binding

Define final synthesis steps as first-class dependency consumers.

**Synthesis indicators:**
- final answer
- summarize
- compare
- combine
- merge
- brief
- report
- recommend
- list both results
- use all previous results
- create final output
- write summary from sources

**Rules:**
- synthesis steps must depend on all required source steps
- final synthesis over multiple branches must receive all branch outputs
- document brief/report steps must depend on all relevant read steps
- synthesis must not execute with missing source dependencies

Do not allow final synthesis to rely on global hidden state or frontend/projection context.

## 11. Same-Resource File Sequencing Binding

### Purpose

The Planning Compiler may deterministically inject missing dependencies between existing steps that operate on the same concrete local file path when the operation order is required for safe execution.

This addresses same-resource file operation sequences that the planner may omit due to lack of explicit step_N reference patterns in natural language inputs such as "write to file X, then read it" or "write 'A' to file, write 'B' to same file".

### Authority Boundary

This is pre-runtime planning compiler repair only.

It must happen before validator/runtime/governance/system_entry handoff.

Compiler deterministic repair is pre-runtime only and must not become broad semantic inference.

Same-resource file sequencing must not bypass dependency validation, governance, mutation legality, system_entry, or tool safety.

Runtime/scheduler must not infer or repair these dependencies during execution unless a later contract explicitly approves runtime resource safety.

### Allowed Repair

The compiler may add `depends_on` entries between existing steps only when all are true:

1. Both steps already exist.
2. Both steps reference the same concrete normalized file path.
3. The prior step appears earlier in the plan.
4. The later step operates on the same resource in a way that requires ordering.
5. The repair only adds a dependency from later step -> earlier step.
6. Existing dependencies are preserved and deduped.
7. The repair is idempotent.
8. The repaired workflow still passes normal validation.

### Approved Same-Path Sequencing Patterns

The compiler may repair the following deterministic patterns:

- write same path -> read same path
- write same path -> edit same path
- edit same path -> read same path
- write same path -> write same path
- edit same path -> edit same path

Optional / conservative:

- read same path -> edit same path

should be allowed only when user phrasing indicates an intentional sequence, such as "then", "after reading", "read it first", or similar explicit sequencing language.

If uncertain, the compiler should not over-repair and should instead leave validation/governance/operator review to catch the issue.

### Explicit Non-Goals / Prohibitions

This does not allow:

- creating new steps
- deleting steps
- changing step purpose
- changing tool selection
- changing execution_result
- mutating lifecycle truth
- bypassing governance
- bypassing system_entry
- frontend/projection authority
- runtime/scheduler inference
- broad semantic dependency inference from prose
- resource locking implementation
- staged planner architecture
- prompt changes
- adaptive orchestration

### Relationship to Dependency Model

DEPENDENCY_MODEL_CONTRACT_V2.txt still prohibits runtime from inferring or auto-correcting missing dependencies during execution.

This Planning Compiler repair is contract-legal only because it is pre-runtime, deterministic, bounded to objective same-path file operations, and verified before handoff.

### Relationship to Prompt

Prompt guidance may teach the planner same-resource sequencing, but compiler repair is the deterministic safety net when the planner omits same-resource dependencies.

Prompt guidance alone is not considered sufficient safety for same-resource write/edit/read/write collision classes.

### Runtime Boundary

Runtime resource locking / scheduler resource conflict enforcement remains deferred and requires separate SA approval.

Current approved approach is planner/compiler-side deterministic pre-runtime dependency binding only.

### Acceptance Examples

Example 1:
```
Input:
Write 'hello' to C:\temp\test.txt, then read it back.

Expected:
step_2 depends_on includes step_1.
```

Example 2:
```
Input:
Write to C:\temp\A.txt, edit C:\temp\A.txt, then read C:\temp\A.txt.

Expected:
step_2 depends_on includes step_1.
step_3 depends_on includes step_2.
```

Example 3:
```
Input:
Write 'X' to C:\temp\file.txt. Write 'Y' to C:\temp\file.txt.

Expected:
step_2 depends_on includes step_1.
Reason:
same-path write/write collision must not be parallelized.
```

### Ambiguity Rule

If path extraction is uncertain, operation type is uncertain, or same-resource relationship is not concrete, do not repair.

The compiler must prefer no repair over broad semantic inference.

## 12. Tool Binding / Candidate Narrowing

Planning compiler may bind a step to a tool class or narrowed candidate set.

AG1 may choose within that narrowed candidate set.

AG1 must not freely choose from the full tool universe when a narrower legal candidate set exists.

**Examples:**
- arithmetic divide step => divide_numbers or compatible arithmetic divide tools only
- specific local file answer => read_file then text_synthesis/final_output
- write artifact from gathered content => text synthesis before or inside write_file, but content must be generated from dependencies

**Rules:**
- finalize_output may not replace a required concrete tool operation.
- list_files may not replace read_file for a specific file path task.
- web_search may not be selected when user explicitly says using only a local file / do not search web.

## 14. Workflow Output Aggregation Contract

Define workflow output as first-class.

**Output mode must be one of:**
- last_step_output
- explicit_final_synthesis_output
- multi_output_aggregate
- partial_result_with_warning
- failed_or_incomplete

**Rules:**
- last_step_output is valid only when the user asked for a single terminal output or a final synthesis step produced the final answer.
- multi_output_aggregate is required when the user asks for multiple independent results and no final synthesis step exists.
- explicit_final_synthesis_output is required when the plan includes a final answer/brief/report/compare/recommendation step.
- partial_result_with_warning is valid only when partial failure semantics are explicitly allowed or contractually defined.
- failed_or_incomplete is required when required outputs are missing.

**Acceptance example:**
```
User asks: "What are 12 plus 8 and 7 times 6? Return them separately."
Steps produce 20 and 42.
Final workflow_output must include both values, not only 42.
```

---

## 15. Narrow Purpose / Output False-Success Validation

Define a bounded deterministic gate.

This is not broad semantic drift authority.

It may reject obvious false success only.

False-success validation must remain narrow and must not rewrite execution_result or fabricate success.

**Checks may include:**
- unresolved placeholders like [result of step_2]
- output says required context is missing
- output says "I cannot answer" when task required an answer and dependencies were expected
- final answer omits explicitly requested outputs
- artifact contains only the original task instruction
- requested multiple outputs but only one output appears
- final synthesis references source steps but omits their outputs
- file written without generated deliverable content

**Rules:**
- This gate must be narrow and explainable.
- It must not become broad subjective quality scoring.
- It must not override execution_result truth by fabricating success.
- It may block completion, trigger retry/replan-required, or mark output incomplete according to governance contract.

## 16. SAME Retry No-Prior-Tool Handling

If retry_strategy=SAME is selected but no prior selected_tool / structured tool_call exists, runtime/compiler must not burn automatic retry attempts repeatedly.

SAME retry handling must align with EXECUTION_IDENTITY_AND_REPLAY_CONTRACT_V2.txt, USER_CONTROL_CONTRACT_V3.txt, GOVERNANCE_CONTRACT_V3.txt, and STATE_TRANSITIONS_CONTRACT_V2.txt.

**Allowed outcomes:**
- mark retry_not_eligible with same_retry_missing_prior_tool
- require replan
- block/escalate for operator action
- downgrade to normal retry only if later contract explicitly allows it

**Default rule:**
For now, SAME retry with no prior selected tool is non-retryable/replan-required, not auto-retryable.

This must align with existing SAME retry enforcement contract.

## 17. Document Intelligence Planning Pattern

Define the required pattern:

For prompts like:
```
Using only <local file path>, answer/summarize/create brief/report X.
```

The plan must normally be:
```
read_file
-> synthesize / summarize / brief from read output
-> optional write artifact if requested
```

**Rules:**
- do not choose list_files for a specific file path
- do not choose web_search when user says using only local file / do not search web
- final synthesis must depend on read_file output
- written artifact content must be generated from source output, not just repeat instruction

**For multi-doc tasks:**
```
read each source
-> synthesize from all read outputs
-> optional write artifact
```

Final synthesis must depend on all read steps.
