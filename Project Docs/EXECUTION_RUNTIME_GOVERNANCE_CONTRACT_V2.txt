## Purpose

Defines authoritative runtime execution behavior/governance semantics for:
- execution behavior
- mutation legality
- retry behavior
- terminal/recoverable state semantics
- orchestration isolation
- runtime concurrency boundaries

This contract formalizes runtime behavior that MUST remain deterministic and race-safe.

This contract defines runtime execution behavior/governance semantics, not ownership of Governance Authority itself.

## 2. Terminal vs Recoverable States

### Terminal States

The following workflow/step states are terminal:
- COMPLETED (immutable terminal)
- CANCELLED (immutable terminal)
- FAILED (recoverable terminal)

COMPLETED and CANCELLED are immutable terminal.

FAILED is recoverable terminal.

Retry/re-execution from FAILED is allowed only through authorized recovery/retry/re-execution contracts and creates new execution lineage.

COMPLETED/CANCELLED must not retry, continue, re-execute, structurally mutate, or resurrect.

### Recoverable States

The following states are recoverable:
- BLOCKED (recoverable non-terminal/wait)
- PAUSED (recoverable non-terminal)
- QUEUED (not terminal)

Recoverable states MAY transition back into active execution flow through legal governance actions.

---

## 3. Blocked State Semantics

BLOCKED is:
- recoverable
- mutable
- non-terminal

BLOCKED indicates:
execution halted pending correction, mutation, approval, or dependency resolution.

BLOCKED MUST NOT be treated as terminal failure.

BLOCKED = recoverable non-terminal/wait.

---

## 3A. Runtime No-Progress Ceiling Semantics

Runtime max-iteration ceiling is a recoverable orchestration stall.

It maps to BLOCKED.

It is non-terminal.

It requires operator/governance intervention.

It must not be treated as terminal FAILED.

Runtime no-progress ceiling maps to BLOCKED by default, not FAILED.

Projection must emit non-terminal BLOCKED update.

The runtime loop ceiling is not, by itself, proof of unrecoverable execution failure.

---

## 4. Failed State Semantics

FAILED is:
- recoverable terminal

FAILED indicates:
execution permanently terminated for the current execution instance.

FAILED -> ACTIVE resurrection is prohibited unless a formally authorized re-execution workflow occurs through authorized recovery/retry/re-execution contracts.

FAILED is recoverable terminal.

Retry/re-execution from FAILED creates new execution lineage.

---

## 5. Active Execution Mutability

ACTIVE execution is immutable.

ACTIVE immutability semantics are governed by:
MUTATION_LEGALITY_AND_RUNTIME_ISOLATION_CONTRACT_V2.txt

During ACTIVE execution:
- mutation is prohibited
- retry mutation is prohibited
- plan mutation is prohibited

This prevents:
- race conditions
- execution corruption
- lifecycle desynchronization

---

## 6. Active Retry Mutability

ACTIVE retry execution is immutable.

Retry isolation semantics are governed by:
MUTATION_LEGALITY_AND_RUNTIME_ISOLATION_CONTRACT_V2.txt

Mutation during ACTIVE retry execution is prohibited.

Mutation attempts during ACTIVE retry MUST be:
- rejected
  OR
- deferred through future queued mutation semantics

Immediate concurrent mutation is prohibited.

---

## 7. Pause Semantics

Pause is deferred.

Pause MUST occur only after the currently executing step completes safely.

Immediate execution interruption is prohibited.

This preserves:
- deterministic execution
- runtime consistency
- execution atomicity

---

## 8. Resume Semantics

Resume restores execution continuity through:
- authoritative runtime state
- canonical projections
- continuity reconciliation

Resume does NOT:
- restart orchestration from scratch
- recompute entire workflow blindly

Resume continues from the last valid runtime state.

---

## 9. Retry Semantics

Retry represents:
- a new execution attempt
- NOT continuation of previous execution

Retry creates a new execution instance per:
EXECUTION_IDENTITY_AND_REPLAY_CONTRACT_V2.txt

Retry MAY:
- regenerate execution artifacts
- regenerate tool_call
- regenerate execution inputs

Retry behavior MAY be adaptive rather than deterministic replay.

Retry during ACTIVE or BLOCKED execution follows legal runtime retry flow within the existing lifecycle window unless terminalization occurs.

Retry/re-execution from FAILED is a recoverable-terminal recovery path and must create new execution lineage under EXECUTION_IDENTITY_AND_REPLAY_CONTRACT_V2.

Governance does NOT own replay semantics.

Replay vs reconstruction semantics are governed by:
EXECUTION_IDENTITY_AND_REPLAY_CONTRACT_V2.txt

Retry does NOT imply lifecycle resurrection.

Retry remains governed by:
- lifecycle authority
- state transition legality
- runtime governance rules

---

## 9A. SAME Retry Runtime Enforcement

When governance/runtime receives retry_strategy=SAME, runtime must preserve the same selected_tool / execution route where possible.

Runtime may reconstruct arguments freshly from current legal workflow state and dependency outputs.

Runtime must not perform unrestricted AG1/tool selection for SAME retry if a prior selected_tool or structured tool_call exists.

If the prior selected_tool cannot legally be reused, runtime must fail safely by BLOCK, ESCALATE, or return retry_not_eligible / retry_disabled_reason according to existing governance contracts.

Runtime must not silently substitute finalize_output or any other semantically different tool.

SAME retry remains a new execution attempt and must obey:
- execution_generation / retry_generation handling
- retry isolation
- artifact invalidation
- dependency invalidation
- stale-owner suppression
- lifecycle authority validation
- mutation legality
- trace/audit requirements

Note: Direct raw tool_call replay is not required for this slice. The minimum runtime model is same selected_tool with fresh argument reconstruction.

## 17. Concurrent Operation Rules

Concurrent operation rules are governed by:
MUTATION_LEGALITY_AND_RUNTIME_ISOLATION_CONTRACT_V2.txt

The following concurrent combinations are prohibited:
- mutation + ACTIVE execution
- mutation + ACTIVE retry
- terminalization + retry continuation
- conflicting lifecycle transitions

Unsafe transition windows MUST reject conflicting runtime operations.

## 18. Projection Relationship

Projection systems MAY temporarily diverge from runtime state.

Projection continuity MUST eventually converge to authoritative runtime/lifecycle state.

Temporary projection lag is acceptable.

Permanent divergence is prohibited.

---

## 19. User-Control Force Retry Runtime Semantics

User-control force retry is a new execution attempt.

It must obey:
- execution identity boundaries
- retry isolation
- runtime locks
- mutation legality
- artifact invalidation
- dependency invalidation
- stale owner suppression
- lifecycle authority validation
- trace/audit requirements

It may not run during ACTIVE execution, ACTIVE retry, terminalization, or illegal mutation windows.

It must increment the appropriate execution_generation / retry_generation according to existing retry/re-execution mechanisms.

It must not reuse stale execution artifacts.

It must not treat the previous failed execution as successful.

Runtime governance must not bypass USER_CONTROL_CONTRACT_V3.txt or USER_APPROVAL_CONTRACT_V2.txt where approval/control is required.
