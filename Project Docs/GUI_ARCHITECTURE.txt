# AI LAB — GUI ARCHITECTURE V2

## PURPOSE

Defines GUI structure aligned with orchestrator and contracts.

Runtime coordination is governed by:
RUNTIME_REGISTRY_AND_EXECUTION_COORDINATION_CONTRACT_V1

Execution identity and replay semantics are governed by:
EXECUTION_IDENTITY_AND_REPLAY_CONTRACT_V1

GUI consumes execution visibility but does NOT define execution identity.

GUI does NOT infer replay state.

GUI does NOT reconstruct runtime coordination.

---

## CORE PRINCIPLE

GUI = thin, context-aware interaction layer

---

## ARCHITECTURE

User → GUI → API → Orchestrator → system_entry

---

## KEY RULE

ALL interactions MUST be workflow-scoped.

## STREAMING MODEL

---

### STREAM AUTHORITY BOUNDARY

Streams are:

* transport-only
* transient synchronization layers
* non-authoritative

GUI MUST NOT derive:

* workflow existence
* lifecycle authority
* workflow ownership

from stream continuity alone.

---

### PURPOSE

Defines how the GUI handles streaming responses from the orchestrator.

The system supports incremental updates during execution.

---

### CORE PRINCIPLE

Streaming is event-based and context-scoped.

GUI MUST process updates incrementally and bind them to the correct workflow.

---

### STREAM EVENT STRUCTURE

Each stream event MUST include:

* workflow_id
* event_type
* payload

---

### EVENT TYPES

MESSAGE

* chat response content

STEP_UPDATE

* step state changes

OUTPUT

* execution output from tools

TRACE

* debug or trace information

COMPLETE

* indicates end of stream

---

### GUI BEHAVIOR

GUI MUST:

* process events in order received
* update UI incrementally
* bind all updates to workflow_id
* update only affected components

GUI MUST NOT:

* wait for full response before rendering
* mix events between workflows
* overwrite unrelated UI state

---

### STATE CONSISTENCY

Final GUI state MUST match orchestrator state after COMPLETE event.

---

### MULTI-PROJECT RULE

Streaming events MUST always be scoped to workflow_id.

GUI MUST isolate updates per project.

---

### ERROR HANDLING

If stream fails:

* GUI MUST display error state
* GUI MUST NOT assume completion
* GUI MUST allow retry via control actions

---

# FINAL RULE

Streaming extends data flow but does NOT change authority model.

* Orchestrator remains source of truth
* GUI remains non-authoritative

## OBSERVABILITY LAYER SEPARATION

### DASHBOARD LAYER VS FOCUSED WORKFLOW LAYER

The GUI architecture recognizes TWO distinct observability surfaces:

**Layer 1 — Passive Dashboard / Observability Layer**

* observes runtime state passively
* subscribes to websocket/event streams
* groups, filters, visualizes, and aggregates
* remains read-only and non-authoritative

**Layer 2 — Focused Workflow Interaction Layer**

* explicitly attached to a specific workflow
* scoped to operator interaction
* supports pause/resume/retry/mutation requests
* does NOT auto-discover arbitrary runtime workflows

---

### PASSIVE OBSERVABILITY SEMANTICS

Dashboard and observability surfaces MAY:

* render runtime state projections
* display orchestration topology
* group workflows, projects, and agents
* aggregate runtime visibility

Dashboard and observability surfaces MUST NOT:

* synthesize lifecycle truth
* infer workflow ownership
* derive orchestration authority
* reconcile authority conflicts locally

---

### EXPLICIT WORKFLOW ATTACHMENT SEMANTICS

Focused workflow screens are:

* explicit attachment surfaces
* workflow-scoped
* interaction-oriented

Focused workflow screens are NOT:

* global runtime discovery dashboards
* auto-discovery surfaces
* authority inference layers

Frontend workflow attachment MUST remain:

* explicit (started, restored, or selected)
* operator-initiated
* context-bound

---

### WEBSOCKET / EVENT SUBSCRIPTION BOUNDARIES

Websocket and event streams are:

* transport layers
* synchronization layers
* projection delivery layers

Frontend websocket consumers MAY:

* subscribe
* visualize
* group
* aggregate
* render

Frontend websocket consumers MUST NOT:

* synthesize workflow truth
* derive lifecycle authority
* infer orchestration ownership
* resolve authority conflicts locally

---

### FRONTEND NON-AUTHORITY PRESERVATION

Frontend observability MAY become rich and dynamic.

Frontend authority MUST remain thin and non-authoritative.

Visibility does NOT imply authority.
