# AI LAB — GUI ARCHITECTURE V2

## PURPOSE

Defines GUI structure aligned with orchestrator and contracts.

Runtime coordination is governed by:
RUNTIME_REGISTRY_AND_EXECUTION_COORDINATION_CONTRACT_V1

Execution identity and replay semantics are governed by:
EXECUTION_IDENTITY_AND_REPLAY_CONTRACT_V1

GUI consumes execution visibility but does NOT define execution identity.

GUI does NOT infer replay state.

GUI does NOT reconstruct runtime coordination.

---

## CORE PRINCIPLE

GUI = thin, context-aware interaction layer

---

## ARCHITECTURE

User → GUI → API → Orchestrator → system_entry

---

## KEY RULE

ALL interactions MUST be workflow-scoped.

---

## DATA FLOW

INPUT TO GUI:

{
"projects": [...],
"active_project_id": "...",
"steps": [...],
"state": "...",
"outputs": [...],
"trace": [...]
}

GUI consumes PLAN STEP representation.
Execution STEP is internal and not required for initial display.

OUTPUT FROM GUI:

{
"action": "<action_type>",
"workflow_id": "...",
"step_id": "optional"
}

---

## STREAMING MODEL

---

### STREAM AUTHORITY BOUNDARY

Streams are:

* transport-only
* transient synchronization layers
* non-authoritative

GUI MUST NOT derive:

* workflow existence
* lifecycle authority
* workflow ownership

from stream continuity alone.

---

### PURPOSE

Defines how the GUI handles streaming responses from the orchestrator.

The system supports incremental updates during execution.

---

### CORE PRINCIPLE

Streaming is event-based and context-scoped.

GUI MUST process updates incrementally and bind them to the correct workflow.

---

### STREAM EVENT STRUCTURE

Each stream event MUST include:

* workflow_id
* event_type
* payload

---

### EVENT TYPES

MESSAGE

* chat response content

STEP_UPDATE

* step state changes

OUTPUT

* execution output from tools

TRACE

* debug or trace information

COMPLETE

* indicates end of stream

---

### GUI BEHAVIOR

GUI MUST:

* process events in order received
* update UI incrementally
* bind all updates to workflow_id
* update only affected components

GUI MUST NOT:

* wait for full response before rendering
* mix events between workflows
* overwrite unrelated UI state

---

### STATE CONSISTENCY

Final GUI state MUST match orchestrator state after COMPLETE event.

---

### MULTI-PROJECT RULE

Streaming events MUST always be scoped to workflow_id.

GUI MUST isolate updates per project.

---

### ERROR HANDLING

If stream fails:

* GUI MUST display error state
* GUI MUST NOT assume completion
* GUI MUST allow retry via control actions

---

# FINAL RULE

Streaming extends data flow but does NOT change authority model.

* Orchestrator remains source of truth
* GUI remains non-authoritative

---

## PROJECTION CONTINUITY MODEL

GUI consumes synchronized projections rather than synthesizing state locally.

GUI MUST:

* render continuity projections
* preserve workflow continuity during streaming/polling
* reconcile from authoritative projection refreshes

GUI MUST NOT:

* derive lifecycle truth locally
* replace valid continuity with stale projections
* infer terminal execution state

---

## CANONICAL PROJECTION MODEL

GUI consumes orchestrator-owned canonical projections.

GUI rendering MUST originate from canonical projections rather than local synthesized state.

GUI interactions operate through:

* intent requests
* projection refresh
* projection re-render

GUI MUST remain projection-render-only.

---

## HYDRATION AUTHORITY RULES

Frontend hydration MUST consume:

* authoritative lifecycle state
* canonical projections

Frontend hydration MUST NOT:

* derive authority from stream registry
* synthesize workflow truth locally
* reconstruct lifecycle authority

Hydration sequencing is governed separately by:
SYSTEM_CONVERGENCE_AND_RECOVERY_CONTRACT_V1

GUI hydration consumes execution visibility per:
RUNTIME_REGISTRY_AND_EXECUTION_COORDINATION_CONTRACT_V1

GUI does NOT restore replay state per:
EXECUTION_IDENTITY_AND_REPLAY_CONTRACT_V1

---

## CONTROL FLOW

User action
→ GUI attaches context
→ API validates
→ Orchestrator processes
→ State updates
→ GUI re-renders

---

## CONTEXT MODEL

GUI MUST:

* maintain active_project_id
* bind all actions to project

GUI MUST NOT:

* operate globally
* send context-less requests

### WORKFLOW SELECTION BOUNDARY

Frontend workflow selection is:

* UI interaction state only
* non-authoritative
* operator-scoped

active_project_id represents:

* currently viewed workflow
* currently selected UI context

active_project_id does NOT represent:

* authoritative workflow existence
* lifecycle authority
* canonical workflow ownership

Frontend MUST NOT:

* infer workflow existence heuristically
* synthesize workflow identity
* assume singleton workflow recovery
* restore workflow authority locally

Workflow authority originates ONLY from:

* Lifecycle Authority
* Persistence-backed workflow identity
