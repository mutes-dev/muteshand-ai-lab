# AI LAB — GOVERNANCE CONTRACT V2 (DECISION ENGINE)

---

## SCOPE

This document defines the GOVERNANCE layer of the system.

Applies to:
- step-level decision making
- retry logic
- completion evaluation
- escalation logic
- approval triggering
- confidence evaluation
- validation interpretation

Does NOT apply to:
- core execution (system_entry)
- tool execution logic
- parser/resolver/validation (core pipeline)

---

## CORE PRINCIPLE

GOVERNANCE = deterministic decision engine

Governance:
- decides what happens AFTER execution
- controls step progression
- enforces safety and correctness
- remains explainable and debuggable

---

## AUTHORITY MODEL

DECISION = strict inputs (deterministic)  
INFLUENCE = adaptive inputs (advisory only)

---

### DECISION INPUTS (AUTHORITATIVE)

Governance decisions MUST be based ONLY on:
- execution_result
- validation_result
- risk_level
- retry_count
- step_importance
- backend-validated user_control_override_request / force_execution_request (only when authorized under USER_CONTROL_CONTRACT_V2)

---

### INFLUENCE INPUTS (ADVISORY ONLY)

These may influence behavior but MUST NOT decide outcome:
- memory (learned behavior)
- historical patterns
- contextual signals

---

## DECISION OUTPUTS

Governance MUST return EXACTLY one:
- COMPLETE
- RETRY
- FAIL
- BLOCK
- ESCALATE

---

## STEP COMPLETION RULE

A step is COMPLETE ONLY if:

execution_result = success  
AND validation_result = pass  
AND purpose_met = true  

If ANY condition fails → NOT COMPLETE

---

## RETRY STRATEGY

Retry 1 → same input  
Retry 2+ → variation  

---

### VARIATION RULES

Variation may include:
- parameter adjustment
- tool refinement
- prompt refinement

Variation MUST NOT:
- change step purpose
- expand scope
- violate constraints

---

## retry_strategy=SAME Enforcement

retry_strategy=SAME is not display-only metadata.

retry_strategy=SAME must be enforced by runtime.

SAME means the retry preserves the same intended execution route/tool where possible.

For a step with a prior selected_tool or structured tool_call, SAME retry must not freely re-enter unrestricted AG1/tool_selection_agent and select a semantically different tool.

The minimum required enforcement model is:

- preserve the prior selected_tool / execution route
- reconstruct arguments freshly from current legal workflow/dependency state
- revalidate arguments before execution
- reject or escalate if the prior tool is unavailable, unsafe, stale, incompatible, or no longer legal
- do not fall back to finalize_output merely because the original tool failed

SAME retry does not mean:
- planner re-entry
- semantic reinterpretation
- arbitrary tool reselection
- output finalization as replacement for tool execution
- treating failed execution as successful

### Retry Strategy Variants

SAME:
- same selected_tool / execution route where possible
- fresh argument reconstruction allowed
- no unrestricted tool reselection

CONSTRAINT_REFINED:
- may refine parameters/prompts/constraints while preserving step purpose and compatible tool intent

REFINED / FALLBACK / SAFE_ALTERNATIVE:
- future expansion only unless explicitly implemented and contract-authorized

### Current Behavior Classification

Unrestricted tool reselection during retry_strategy=SAME is an architecture bug, even if earlier git history allowed it.

---

## finalize_output Retry Boundary

finalize_output is allowed for valid text-producing, summarization, formatting, explanation, or output-shaping steps, including intermediate workflow steps where the step purpose is text synthesis.

Do not blanket-ban finalize_output for all intermediate steps.

However, finalize_output is not valid as a replacement for concrete tool-required semantic operations, such as:
- arithmetic calculation
- divide_numbers / multiply_numbers / add_numbers style numeric steps
- file write/delete/mutation
- API execution
- browser/read_webpage/tool-specific action
- shell/system operation
- any step whose semantic_expectation/output_shape requires a specific non-finalization tool behavior

Error-looking finalize_output text remains failure-classified / advisory-rejected.

finalize_output may not transform a failed execution into a successful execution unless the step purpose is legitimately finalization/text synthesis and validation passes.

---

## RISK MODEL

RISK = base_risk + context_adjustment

---

### BASE RISK (BY STEP TYPE)

- ANALYZE → LOW
- RESEARCH → LOW
- GENERATE → LOW
- EXECUTE_API → MEDIUM
- EXECUTE_FILE → MEDIUM
- EXECUTE_INSTALL → HIGH
- EXECUTE_SYSTEM_SETTINGS_SERVICES → HIGH
- EXECUTE_ENVIRONMENT → MEDIUM

---

### CONTEXT ADJUSTMENT

Increase risk if:
- destructive action
- sensitive location
- cost involved
- irreversible change
- multi-target impact

Decrease risk if:
- reversible
- safe scope
- known safe pattern

---

## VALIDATION MODEL

Two validation layers exist:

---

### CORE VALIDATION (AUTHORITATIVE)

- structural only
- performed in core pipeline
- determines if execution is allowed

---

### ORCHESTRATOR VALIDATION (SEMANTIC)

- evaluates correctness of outcome
- checks purpose fulfillment
- influences governance decisions

---

### RULES

- core validation = gatekeeper (execution allowed or not)
- orchestrator validation = decision modifier
- orchestrator validation MUST NOT override execution_result
- orchestrator validation MAY:
  - block completion
  - trigger retry
  - trigger escalate

---

## CONFIDENCE MODEL

CONFIDENCE = execution_result + validation + history

---

### SIGNAL SOURCES

Execution:
- success → increase
- failure → decrease

Validation:
- pass → increase
- warning → decrease
- fail → strong decrease

History:
- consistent success → increase
- repeated failure → decrease
- inconsistent → strong decrease

---

### CONSTRAINT

Confidence MUST NOT:
- override execution_result
- force completion
- bypass validation

Memory influences confidence ONLY.

Memory MUST NOT:

- directly influence decisions
- override execution_result
- bypass validation

Flow:

memory → confidence → governance decision

---

## APPROVAL MODEL

Approval is checked BEFORE execution.

---

### APPROVAL RULE

ASK if:
- cost involved
- high risk
- irreversible action
- low confidence
- unusual vs learned behavior

---

### HARD REQUIREMENTS (MUST ASK)

- cost involved
- irreversible actions
- high-risk system changes

---

### SOFT REQUIREMENTS (SHOULD ASK)

- low confidence
- conflicting signals
- unusual behavior

---

### AUTO EXECUTION

Allowed if:
- low risk
- reversible
- high confidence
- known safe pattern

---

### APPROVAL EFFECT

If approval required:
→ decision = BLOCK  
→ step does NOT execute  

---

## LEGACY OVERRIDE_STATE RULING

The legacy `override_state` concept is not valid implementation authority.

Do not implement raw:

```text
override_state = ON -> FAIL + CONTINUE
```

The replacement model is a backend-validated, scoped user-control request defined by `USER_CONTROL_CONTRACT_V2.txt`.

Governance may consider an accepted `user_control_override_request` or `force_execution_request` only as a structured decision input after backend validation confirms:

- workflow_id / step_id scope
- requested_action
- current lifecycle legality
- mutation legality
- dependency validity
- tool/privacy/safety legality
- staleness/expiry status
- execution_generation / retry_generation match where applicable
- trace/audit requirements

A user-control request may authorize legal retry, replan, continuation after warning, or risk acceptance.

A user-control request may not:

- bypass governance
- bypass lifecycle authority
- bypass mutation legality
- bypass dependency requirements
- change execution_result truth
- fabricate success
- resurrect terminal workflows
- continue from projection/frontend state alone
- bypass privacy/tool safety hard blocks

---

## FAILURE MODEL

If execution_result = failure:

---

### RETRY CONDITION

Normal autonomous governance retry remains bounded by max_retries.

IF retries < max_retries:
→ RETRY

User-control force retry is not ordinary autonomous governance retry.

A backend-validated force_step_retry may authorize one separately bounded re-execution attempt only under USER_CONTROL_CONTRACT_V2 rules.

This does not mean governance retry is unbounded.

This does not allow raw override_state behavior.

This does not allow FAIL + CONTINUE when dependencies require the failed output.

This does not allow failed execution to be treated as successful.

---

### RETRIES EXHAUSTED

After normal retries are exhausted, governance may not autonomously retry.

IF a backend-validated user_control force_step_retry request authorizes a legal continuation path AND backend confirms recoverability and retry target legality:
→ apply the authorized governance outcome (for example one bounded RETRY, replan handoff, or controlled FAIL + CONTINUE where dependencies do not require the failed output)

ELSE:
    IF step_importance = HIGH:
        → BLOCK
    ELSE:
        → FAIL + CONTINUE

Rules:
- user-control override may not mark failed execution as successful.
- user-control override may not ignore failed dependencies.
- user-control override may not bypass mutation legality, lifecycle legality, privacy/tool hard blocks, or execution_result truth.
- A legal backend-validated user-control force_step_retry may hand off to the retry/re-execution mechanism only within the separate force retry budget and only if recoverability and retry target legality are confirmed.

---

## VALIDATION FAILURE FLOW

If execution_result = success AND validation_result ≠ pass:

IF risk = HIGH:
→ ESCALATE

ELSE:
→ RETRY

---

## LOW CONFIDENCE FLOW

If confidence = LOW:

IF risk = HIGH:
→ ESCALATE

ELSE IF retries < limit:
→ RETRY

ELSE:
→ ESCALATE

---

## ESCALATION MODEL

ESCALATE when:
- retries exhausted AND uncertainty remains
- repeated identical failure
- conflicting results across retries
- validation repeatedly fails on success
- no progress across retries
- oscillating outcomes
- high-risk uncertainty

---

### ESCALATION EFFECT

- step → BLOCKED
- workflow → BLOCKED
- user intervention required

---

### NO-PROGRESS SAFETY CEILING CLARIFICATION

* no-progress safety ceilings align with escalation semantics.
* max_iterations_exceeded results in BLOCKED.
* workflow becomes BLOCKED, not FAILED.
* user/operator intervention is required.

---

### DISTINCTION

FAIL = handled outcome  
ESCALATE = unsafe or uncertain outcome  

---

## FINAL DECISION FLOW

1. CHECK approval required  
   → BLOCK  

2. EXECUTE step via system_entry  

3. CHECK execution_result  
   → failure → FAILURE MODEL  
   → success → continue  

4. CHECK validation_result  
   → fail → VALIDATION FAILURE FLOW  
   → pass → continue  

5. CHECK confidence  
   → low → LOW CONFIDENCE FLOW  
   → sufficient → continue  

6. CHECK purpose_met  
   → false → RETRY  
   → true → COMPLETE  

---

## HARD GUARANTEES

- COMPLETE requires:
  - execution success
  - validation pass
  - purpose met

- BLOCK prevents execution or pauses flow

- ESCALATE always stops execution and requires user

- FAIL allows workflow continuation (depending on step importance and backend-validated user-control continuation path)

## SLICE 1 BACKEND DISPATCHER ALLOWANCE

For Sprint 7C Slice 1 only, operator-initiated force_step_retry may be applied through a backend validation + action-application dispatcher outside governance.py, provided the dispatcher does not modify governance decision authority, does not bypass lifecycle authority, does not bypass mutation legality, and emits required trace/audit events.

Future backend-created governance-loop override requests require a separate governance integration design.

Slice 1 does not decide that future design.

## FINAL PRINCIPLE

GOVERNANCE = predictable + explainable + safe

The governance layer MUST:
- remain deterministic in decisions
- remain transparent
- prevent unsafe execution
- enable controlled autonomy

---

## BOUNDED AGENT GOVERNANCE

Governance is the ONLY execution legality authority.

Governance MAY consume semantic signals from agents, planners, and validators.

Governance retains FINAL legality authority over all decisions.

Semantic systems (agents, planners, validators) remain advisory-only.

## SEMANTIC AUTHORITY ESCALATION PROHIBITION

Semantic systems MUST NOT escalate to runtime authority.

Semantic systems MUST NOT override execution_result.

Semantic systems MUST NOT claim lifecycle authority.

Semantic systems MUST NOT claim execution identity ownership.

## GOVERNANCE AUTHORITY SUPREMACY

Governance owns:
* retry authorization
* completion authorization
* failure authorization
* escalation authorization
* mutation legality authorization

No semantic system may independently own any of the above.
