# AI LAB — ARCHITECTURE LAW (ENFORCEMENT LAYER)

---

## PURPOSE OF THIS DOCUMENT

This document defines **non-negotiable enforcement rules** derived from `ARCHITECTURE_V2.txt`.

It exists to:

* Prevent architectural drift
* Enforce strict layer boundaries
* Block incorrect implementations before they occur
* Provide deterministic decision rules for development

---

# CORE EXECUTION MODEL (UPDATED)

system_entry is the ONLY execution interface.

Core pipeline consists of:

- input parsing (string → args)
- validation (structural only)
- execution (single-step)

Core MUST:

- remain deterministic
- remain single-step
- contain NO planning or intelligence

---

## ORCHESTRATOR BOUNDARY RULE

ORCHESTRATOR MUST NOT:

- inject arguments
- modify tool inputs at runtime
- reinterpret tool_call strings

---

## CORE PIPELINE CLARIFICATION

The following components define the core execution pipeline:

- system_entry
- validation layer
- execution layer

The core pipeline remains:

- strictly single-step
- fully deterministic
- stateless per execution

All previous laws enforcing single-step execution apply ONLY to the core pipeline.

---

## SYSTEM-LEVEL EXECUTION MODEL

The system as a whole now supports multi-step workflows through the Orchestrator layer.

- multi-step execution is NOT performed inside the core pipeline
- multi-step execution is achieved by orchestrating multiple independent single-step executions

---

## OVERRIDE RULE — MULTI-STEP EXECUTION

Multi-step execution is allowed ONLY at the Orchestrator layer.

Constraints:

- Each step MUST be executed independently via system_entry
- Each step MUST pass full validation before execution
- No step may bypass the core pipeline
- No chaining logic is allowed inside the core pipeline

---

## OVERRIDE RULE — ORCHESTRATOR ISOLATION

The Orchestrator MUST:

- operate strictly above system_entry
- treat system_entry as a black box execution engine
- NOT access parser, resolver, validation, or execution layers directly
- NOT modify pipeline data structures

This reinforces existing layer isolation laws.

---

## OVERRIDE RULE — GOVERNANCE AUTHORITY

Execution decisions are determined by governance within the Orchestrator layer.

- Validator provides advisory signals only
- Execution truth is defined by validated execution results
- Governance resolves:
  - retry vs continue decisions
  - conflict resolution between outputs
  - escalation decisions

Validator MUST NOT determine execution outcome.

---

## OVERRIDE RULE — GOVERNANCE AUTHORITY ENFORCEMENT

Governance decisions MUST be dynamically resolved at runtime.  
Static binding of governance decision functions is prohibited.  
Retry MUST ONLY occur when governance explicitly returns 'retry'.  
Any retry triggered outside governance decision is a violation of architecture law.

---

## ARCHITECTURE LAW — OUTPUT CONTRACT ENFORCEMENT

The system MUST return ONLY:

SUCCESS:
{"status": "success", "result": execution_result}

FAILURE:
{"status": "failure", "reason": string}

NO additional fields allowed.

This contract applies to:
- system_entry
- run_workflow

External interface (execute_from_input) applies layered wrapping.

Violation = contract breach (P0)

---

## OVERRIDE RULE — FINAL OUTPUT MODEL

Final output MUST originate from a single execution_result.
Orchestrator MUST NOT select between multiple outputs.

Constraints:

- Final output MUST originate from a single execution path
- Outputs MUST NOT be merged or synthesized
- If multiple outputs exist:
  - Orchestrator MUST select one OR
  - create a resolution step OR
  - escalate to the user

---

## COMPATIBILITY RULE

All existing laws remain valid UNLESS they explicitly conflict with:

- orchestrator-based multi-step execution
- governance-based decision authority

In case of conflict:

→ This evolution section takes precedence

---

## RELATIONSHIP TO ARCHITECTURE

* `ARCHITECTURE_V2.txt` defines **what the system is**
* `ARCHITECTURE_LAW.txt` defines **what must NEVER be violated**

---

## CRITICAL PRINCIPLES

* Laws MUST always align with `ARCHITECTURE_V2.txt`
* Laws MUST NOT reflect temporary implementations or bugs
* Laws change ONLY when architecture changes
* Laws are designed to **stop drift, not describe behavior**

---

# ARCHITECTURE LAW #1 — LAYER ISOLATION

Each layer has EXACTLY ONE responsibility:

* Agent → tool selection and task interpretation
* Orchestrator → control, governance, workflow management
* Core (system_entry) → parsing, validation, execution
* Tools → external action execution

NO layer may perform another layer’s responsibility.

If a layer performs multiple responsibilities, it is considered a SYSTEM VIOLATION.

This rule is PERMANENT.

---

## AGENT NON-DETERMINISM

Agents are non-deterministic and untrusted.

The system MUST assume:

- tool selection may be incorrect
- constraints may be ignored
- retry may not improve results

All correctness MUST be enforced outside the agent.

---

## NO SILENT CORRECTION

The system MUST NOT silently correct, substitute, or reinterpret invalid operations.

Invalid behavior MUST be surfaced via:

- validator signals
- governance decisions

NOT implicit correction.

---

## RUNTIME AUTHORITY CLARIFICATION

Runtime controls execution flow (loop, retry, override, pause) but MUST NOT make execution decisions.

All decisions originate from governance.

---

## SYSTEM ENTRY REJECTION RULE

If system_entry rejects execution:

* system MUST retry, adjust input, or escalate
* no alternative execution path allowed

---

# ARCHITECTURE LAW #2A — VALIDATOR AUTHORITY

Validator MUST NOT influence:

* retry decisions
* execution outcome
* step status

Validator outputs are strictly advisory.

---

# ARCHITECTURE LAW #2B — GOVERNANCE AUTHORITY

Governance decisions MUST be based solely on execution_result.

Retry MUST originate from governance based on execution_result failure.

---

# ARCHITECTURE LAW #3 — MODEL DECOUPLING

The system MUST function correctly regardless of the LLM used.

This means:

* The LLM may be replaced at any time
* System correctness MUST NOT depend on LLM accuracy
* All critical logic MUST be deterministic and outside the LLM

If changing the model breaks the system, the architecture is invalid.

This rule is PERMANENT.

---

# ARCHITECTURE LAW #4 — LAYER LOCKING PROTOCOL

A layer may ONLY be locked when ALL of the following are true:

1. Its responsibility matches `ARCHITECTURE.txt` exactly
2. It does NOT perform any other layer’s responsibility
3. It is fully testable in isolation
4. It produces deterministic outputs (if applicable)
5. It passes both:

   * manual tests
   * harness tests

Once locked:

* The layer MUST NOT be modified unless a P0 issue is found
* Any change must be explicitly approved at Head Dev level

Locking incorrect behavior is strictly forbidden.

---

# ARCHITECTURE LAW #5 — DEVELOPMENT CONTROL MODEL

There are NO permanent module owners.

* Head Dev owns architecture globally
* Sub Devs are temporary and task-scoped

A Sub Dev:

* MUST follow `ARCHITECTURE.txt`
* MUST follow `ARCHITECTURE_LAW.txt`
* MUST NOT introduce cross-layer behavior
* MUST NOT make assumptions outside its task

All decisions must be validated against architecture BEFORE implementation.

This prevents module isolation drift.

This rule is PERMANENT.

---

# ARCHITECTURE LAW #8 — CORE PIPELINE SINGLE-STEP ENFORCEMENT

Core pipeline (system_entry and below) is strictly single-step.

Multi-step execution is handled by orchestrator layer above system_entry.

---

# ARCHITECTURE LAW #9 — CONTROLLED DELETION

No module may be deleted during:

* architecture migration
* layer isolation
* pre-integration phases

Deletion is ONLY allowed when:

* verified unused through system-wide audit
* no runtime references exist
* removal does not violate system contracts

Premature deletion is a critical system risk.

This rule is PERMANENT.

---

# ARCHITECTURE LAW #10 — TOOL USAGE DISCIPLINE

Windsurf must ONLY be used for tasks that require code modification.

Tasks that MUST NOT use Windsurf:

* testing
* validation
* verification
* log analysis
* behavior confirmation

These tasks must be performed manually whenever possible.

Reason:

* reduces cost
* reduces unnecessary complexity
* prevents unintended code changes
* maintains control over system behavior

Windsurf is a coding tool, not a thinking tool.

This rule is PERMANENT.

---

# LAW — TOOL INDEX STRUCTURE (MANDATORY)

The tool index MUST be a dictionary keyed by tool name when passed into validation.

VALID FORMAT:
{
"tool_name": { ...tool_definition }
}

INVALID FORMAT:
[
{ "name": "tool_name", ... }
]

Violation of this rule will cause validation failure and system instability.

---

# FINAL PRINCIPLE

Architecture defines the system.
Laws enforce it.

If implementation conflicts with laws:

→ implementation must change
→ NOT the laws (unless architecture changes)

---

# ARCHITECTURE LAW #12 — FAIL-FAST EXECUTION BOUNDARY

Execution MUST NEVER occur if structural validation fails.

system_entry MUST enforce a strict fail-fast gate BEFORE execution:

- input must be a valid tool_call string
- tool must exist in registry
- argument count and types must match

If any condition fails:

→ system MUST return failure
→ execution MUST NOT start

This prevents invalid inputs from entering execution.

Violation = execution leakage (P0)

---

# ARCHITECTURE LAW #13 — ENTRY POINT ISOLATION

The entry layer (/system/entry) is responsible ONLY for:

* connecting pipeline stages
* passing data between layers

It MUST NOT:

* perform validation logic
* perform execution logic
* modify data
* contain business logic

Violation = layer contamination

---

# ARCHITECTURE LAW #14 — EXECUTION ISOLATION

Execution MUST exist as an isolated module.

It MUST:

* only execute validated plans
* not perform validation
* not perform planning
* not modify plan structure

Execution MUST be reusable independently of orchestration.

Violation = execution contamination

---

# ARCHITECTURE LAW #15 — TOOL REGISTRY ISOLATION

Validation and Execution MUST use separate registries.

- validation_registry → metadata only
- execution_registry → callable only

Entry MUST:

- receive BOTH registries
- pass them WITHOUT modification

PROHIBITED:

- shared registry
- transformation inside entry
- inference of registry structure

Violation = cross-layer contamination (P0)

---

# ARCHITECTURE LAW #16 — TOOL INDEX AUTHORITY

Tool Index is the ONLY source of truth for all tools.

* registry_builder MUST use tool_index
* NO alternative sources allowed
* NO filesystem scanning
* NO dynamic discovery
* NO inference

Violation = P0

---

# ARCHITECTURE LAW #18 — TOOL EXECUTION AUTHORITY

ALL tool execution MUST go through system_entry.

The orchestrator and agents MUST NOT execute tools directly.

The only valid path for tool execution is:

Orchestrator → system_entry → Validation → Execution → Tool

Violation = architectural bypass (P0)

This rule is PERMANENT.

---

# ARCHITECTURE LAW #19 — ORCHESTRATOR ISOLATION

The Orchestrator Layer MUST NOT bypass the core pipeline.

It MUST:
* sit above system_entry
* route execution through system_entry
* treat system_entry as a black box

It MUST NOT:
* access parser, resolver, validation, or execution directly
* modify pipeline data
* inject logic into pipeline layers

Violation = layer contamination (P0)

This rule is PERMANENT.

---

# ARCHITECTURE LAW #20 — AGENT CONSTRAINT

Agents MUST NOT execute tools directly.

Agents may:
* interpret input
* use LLM
* produce structured output

Agents MUST NOT:
* call tool functions directly
* bypass system_entry for tool execution
* control workflow state

Agent tool execution (USE_TOOL: path) routes through system_entry.

system_entry remains the ONLY execution authority.

---

# ARCHITECTURE LAW #21 — VALIDATOR ENFORCEMENT LAW

Validator outputs are advisory signals only.

If execution_result exists:
→ Governance MUST determine whether to accept, retry, or escalate.

Validator MUST NOT enforce final outcome.

---

# ARCHITECTURE LAW #22 — LLM NON-AUTHORITY LAW

LLM outputs MUST NOT override:

* execution_result
* validator decisions

---

# ARCHITECTURE LAW #23 — CONTRACT SEPARATION

Internal and external contracts MUST NOT be mixed.

- Internal tests use flat contract (run_workflow)
- Harness uses layered contract (execute_from_input)
- Each validation layer validates ONLY its own contract type

Violation = validation authority breach (P0)

---

# ARCHITECTURE LAW #24 — VALIDATION LAYER SEPARATION

Validation layers are separated:

- Harness validates external contract (what the system RETURNS)
- Internal tests validate behavior (how the system BEHAVES)

Harness MUST NOT test retry logic or lifecycle transitions.
Internal tests MUST NOT validate layered contract structure.

Violation = validation scope breach (P0)

---

# ARCHITECTURE LAW #25 — TOOL USAGE AUTHORITY (HAND CLARIFICATION)

At the Orchestrator layer:

- Tool usage requests MUST originate from agent_executor ONLY
- Planner MUST NOT imply tool execution semantics
- Invalid tool requests MUST be rejected or corrected via governance
