# AI LAB — PLAN CONTROL CONTRACT V1

---

## SCOPE

Defines how execution plans are:

- stored
- displayed
- edited
- validated
- executed

This contract governs the PLAN layer within the orchestrator.

Workflow Studio operational mutation semantics are governed by:
WORKFLOW_STUDIO_AND_OPERATIONAL_MUTATION_CONTRACT_V1

Workflow cancellation and terminalization semantics are governed by:
WORKFLOW_CANCELLATION_AND_TERMINALIZATION_CONTRACT_V1

---

## CORE PRINCIPLE

PLAN = source of execution  
USER = authority over plan  

System MUST NOT override explicit user plan edits.

---

## PLAN EXISTENCE

- A plan ALWAYS exists internally
- Plan is REQUIRED for all multi-step execution
- Plan is managed by orchestrator

---

## PLAN VISIBILITY MODES

---

### OFF (default)

- plan is hidden from user
- system executes autonomously
- user does NOT see steps

---

### ON (interactive mode)

- plan is visible
- user can inspect steps
- user can modify plan

---

## PLAN TOGGLE

- user can switch ON/OFF at any time
- toggle does NOT destroy or recreate plan
- toggle only affects visibility and control

---

## PLAN EDITING (CRITICAL)

When PLAN is ON:

User MAY:

- add steps  
- remove steps  
- reorder steps  
- modify step fields  

---

## EDIT AUTHORITY RULE

User edits are FINAL and MUST be respected.

System MUST NOT:

- overwrite user edits
- regenerate plan automatically
- modify step definitions without approval

---

## EDIT VALIDATION

After user edit:

System MUST:

- validate structure (STEP_SCHEMA_CONTRACT)
- validate tool_call (INTERFACE_CONTRACT)
- validate state consistency

System MUST NOT:

- re-plan
- reinterpret intent
- modify content

---

## INVALID EDIT HANDLING

If edit is invalid:

- system MUST reject edit
- system MUST explain why
- plan remains unchanged

---

## PLAN EDIT DEPENDENCY VALIDATION

Plan edits MUST preserve dependency correctness.

After ANY edit (add, remove, reorder, modify), the system MUST validate the dependency graph.

---

### INVALID EDITS

The following edits MUST be rejected:

- removing a step that is referenced in another step's "depends_on"
- reordering steps in a way that violates dependency constraints
- modifying a step such that its dependencies become invalid
- creating missing or broken dependency references

---

### VALIDATION RULES

After edit, system MUST ensure:

- all "depends_on" references exist
- no circular dependencies exist
- execution ordering remains valid
- dependency graph remains a valid DAG

---

### SYSTEM BEHAVIOR

If validation fails:

- edit MUST be rejected OR
- system MUST require user correction before execution

System MUST:

- provide clear explanation of failure
- identify affected steps
- NOT silently auto-correct dependency structure

---

### USER AUTHORITY

User MAY:

- modify dependencies explicitly
- resolve invalid graphs manually

System MUST NOT:

- override user intent without visibility
- auto-repair dependency graph without approval

---

## EXECUTION AFTER EDIT

After successful validation:

- execution resumes from updated plan
- current step may be re-evaluated
- retry_count may reset (implementation dependent)

---

## PLANNER ROLE (AFTER EDIT)

Planner becomes:

- advisory ONLY
- may suggest improvements
- MUST NOT apply changes automatically

---

## PLAN LOCKING

Once execution begins:

- steps already COMPLETED → locked
- ACTIVE step → editable with caution
- FUTURE steps → fully editable

---

## MID-EXECUTION EDIT RULES

If editing current ACTIVE step:

- step MUST restart execution
- previous execution result is discarded

If editing FUTURE steps:

- no impact on past steps
- future execution uses updated steps

---

## GOVERNANCE INTEGRATION

After edit:

- governance continues normally
- new steps must comply with:
  - risk model
  - approval model
  - retry model

---

## SAFETY CONSTRAINTS

System MUST prevent:

- invalid step structure
- multi-tool steps
- bypassing execution contract
- bypassing governance

---

## PLAN CONSISTENCY

Plan MUST always remain:

- valid (schema-compliant)
- executable (all steps valid)
- traceable (step order preserved)

---

## FINAL PRINCIPLE

PLAN = controlled execution blueprint  

USER = plan authority  

SYSTEM = validator and executor  

---

# ACTIVE EXECUTION MUTATION RULES

Plan mutation legality depends on runtime execution state.

---

## ACTIVE EXECUTION

During ACTIVE execution:

* direct plan mutation is prohibited
* execution-affecting mutation is prohibited
* dependency mutation is prohibited

Mutation requests during ACTIVE execution MUST:

* be rejected
  OR
* be deferred into future orchestrator-controlled mutation windows

---

## SAFE MUTATION WINDOWS

Plan mutation MAY occur during:

* QUEUED state
* PAUSED state
* BLOCKED state
* orchestrator-approved restart windows

---

## COSMETIC VS SEMANTIC MUTATION

Cosmetic mutation MAY include:

* labels
* descriptions
* UI-only metadata

Semantic mutation MAY include:

* dependency changes
* execution strategy changes
* purpose changes
* plan structure changes

Semantic mutation MUST trigger:

* derived-state invalidation
* dependency revalidation
* projection regeneration

Cosmetic mutation MUST NOT invalidate execution artifacts.

---

# FUTURE ADAPTIVE PLAN RECONCILIATION DIRECTION

Future-state direction for adaptive plan control is preserved per:
ADAPTIVE_RUNTIME_ORCHESTRATION_CONTRACT_V1

Future plan control MAY include:

* graph reconciliation direction
* subtree invalidation semantics
* preserved valid work semantics
* adaptive plan evolution direction
* branch healing plan mutation

Future adaptive plan control MUST preserve:

* ACTIVE immutability
* mutation legality windows
* execution identity isolation
* authority hierarchy

Current plan control remains deterministic execution oriented.

---

## RETRY LINEAGE SEMANTICS

Retry creates:
NEW execution lineage.

NOT:
stale execution resurrection.

Retry replaces:
previous active execution instance.

Retry does NOT replace:

* lifecycle state
* step identity
* workflow identity

Retry lineage semantics are governed by:
EXECUTION_IDENTITY_AND_REPLAY_CONTRACT_V1

## RECOVERABLE WORKFLOW SEMANTICS

FAILED is:
recoverable terminal state.

FAILED workflows MAY support:

* retry
* reconciliation
* adaptive continuation

COMPLETED is:
immutable terminal state.

Recoverable terminal semantics are governed by:
WORKFLOW_CANCELLATION_AND_TERMINALIZATION_CONTRACT_V1

## FUTURE RECONCILIATION DIRECTION

Future plan control MAY include:

* graph reconciliation direction
* subtree invalidation semantics
* preserved valid work semantics
* adaptive plan evolution direction
* branch healing plan mutation

Future adaptive plan control MUST preserve:

* ACTIVE immutability
* mutation legality windows
* execution identity isolation
* authority hierarchy

Future reconciliation direction per:

HUMAN_IN_THE_LOOP_WORKFLOW_RECONCILIATION_V1

## FUTURE BRANCH INVALIDATION DIRECTION

Future branch invalidation MAY support:

## FINAL RULE

ACTIVE runtime execution remains immutable.

Mutation flexibility MUST NOT compromise deterministic execution behavior.
