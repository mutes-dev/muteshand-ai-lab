**Status:** AUDIT COMPLETE

## 0. EXECUTIVE SUMMARY

The proposed ISSUE-072 implementation slice (typed agent registration + bounded tool-selection agent specialization + attribution metadata + observability integration) was subjected to a focused implementation-safety audit against 16 required grounding documents and 4 conditional documents. The audit examined contract fit, authority boundaries, regression risks, shape/compatibility, legacy dormant reconnection risks, validation adequacy, and scope reduction potential.

**Overall Finding:** The proposed slice preserves all AG1 authority boundaries and does not violate any architectural law. However, the slice carries a **MEDIUM regression risk** due to the non-trivial refactoring of `agent_executor.py` tool-selection logic into a new module. The observational-only enhancements (attribution metadata, trace integration, governance metadata enrichment) are low-risk but could be deferred to reduce implementation surface.

**Recommendation:** **IMPLEMENTATION APPROVED WITH REDUCTION** — approve the core operationalization (tool-selection agent extraction + typed registry), defer pure observability metadata enhancements to ISSUE-073 to minimize regression risk while still achieving AG1 initial operationalization.

## 2. AUTHORITY-BOUNDARY FINDINGS

**YES — for the active orchestrator path.**

The proposed slice does not change the execution path:
- tool_selection_agent produces USE_TOOL: strings
- agent_executor routes through tool_call_converter → system_entry
- system_entry remains the sole execution gateway

The baseline audit's finding remains valid: all active-path tool execution routes through system_entry.

### 2.2 Can any agent directly execute tools?

**NO — in the orchestrator path.**

The tool-selection agent remains bounded to producing USE_TOOL: strings. No direct tool execution capability is added.

### 2.3 Can any agent override execution_result?

**NO.**

execution_result is produced by system_entry inside the core pipeline. The agent embeds execution_result in its return dict but does not create or modify it.

### 2.4 Can any agent trigger retry independently?

**NO.**

Retry is decided by governance in orchestrator_runtime based on execution_result + validator signals. Agent attribution metadata is observational only and does not influence retry logic.

### 2.5 Can any agent alter lifecycle state?

**NO.**

Lifecycle transitions are managed by workflow_control.request_step_transition() and governance decisions. Agents have no access to lifecycle authority.

### 2.6 Can any agent mutate workflow state?

**NO.**

Agents receive input_data strings and optional context. They do not receive workflow dicts. The orchestrator controls all workflow state mutations.

### 2.7 Can any agent make governance decisions?

**NO.**

Governance decisions are made by the governance layer. Agent outputs are inputs to the process, not decision-makers. Attribution metadata enrichment in GovernanceDecision.metadata does not change decision logic.

### 2.8 Are agent outputs advisory-only and routed through orchestrator / governance / system_entry?

**YES.**

Agent outputs = tool-selection suggestions → converter → system_entry → execution_result → governance decision. The proposed slice does not change this routing.

### 2.9 Are trace/projection/observability surfaces read-only?

**YES.**

trace_collector enhancements are additive observational fields. No control flow influence.

### 2.10 Is there persistent agent identity or multi-agent coordination?

**NO.**

Each agent invocation uses a fresh agent config. No state is maintained across invocations. Only one agent type (tool_selection) is operationalized.

## 3. REGRESSION-RISK FINDINGS

### 3.1 agent_executor.py Refactoring Risk

**Risk Level: MEDIUM**

The proposed extraction of tool-selection logic from agent_executor.py into a new `system/orchestrator/agents/tool_selection_agent.py` module is the highest-risk change. The current agent_executor.py contains:

- Complex LLM prompt construction (lines 170-345)
- Single USE_TOOL: enforcement logic (lines 360-378)
- LLM error handling and fallback paths (lines 379-386, 388-414)
- finalize_output fallback for non-tool responses (lines 388-414, 416-434)
- Multiple system_entry call sites (lines 131, 400, 422, 450)
- The "USE_TOOL:" fast path for pre-resolved tool calls (lines 98-154)

Any bug in extraction could break:
- Tool selection accuracy (LLM prompt changes)
- Error handling paths (LLM_ERROR, missing USE_TOOL, multiple USE_TOOL)
- System_entry routing (missing call sites or incorrect arguments)
- The fast path for direct tool calls

**Mitigation Required:**
- Exact behavioral preservation tests: mock LLM and verify identical outputs before/after refactoring
- Verify all system_entry call sites are preserved
- Verify error handling paths (LLM_ERROR, no USE_TOOL, multiple USE_TOOL) produce identical results
- Verify the fast path (input_data starts with "USE_TOOL:") is preserved

### 3.2 agent_registry.py Enhancement Risk

**Risk Level: LOW-MEDIUM**

Adding type, capabilities, version validation to register_agent() could break bootstrap if the default_agent registration doesn't include these fields.

**Mitigation Required:**
- Make new fields optional in validation (backward compatible)
- Update bootstrap.py to register typed agents (included in proposed slice)

### 3.3 agent_output_validator.py Enhancement Risk

**Risk Level: LOW**

Adding attribution field validation could cause validation failures if existing code paths don't produce them.

**Mitigation Required:**
- Attribution fields must be OPTIONAL in validation
- Existing outputs without attribution must still pass validation

### 3.4 step_executor.py Enhancement Risk

**Risk Level: LOW**

Adding agent attribution tagging to step results involves adding new keys to the return dict. Existing consumers (parallel_executor.py, sequential_executor.py) use .get() for known keys and ignore unknown keys.

**Verification:** parallel_executor.py lines 265-304 use .get("blocked"), .get("execution_result"), .get("validator_output"), .get("step_result") — safe for additional keys.

### 3.5 trace_collector.py Enhancement Risk

**Risk Level: LOW**

Trace collector is already failure-isolated. Adding new parameters to record functions should preserve backward compatibility via optional parameters.

### 3.6 bootstrap.py Enhancement Risk

**Risk Level: LOW**

Registering typed tool_selection_agent at initialization is straightforward. Must ensure existing default_agent registration remains compatible.

### 3.7 New Module Import Risk

**Risk Level: LOW**

Creating `system/orchestrator/agents/tool_selection_agent.py` introduces a new import path. Must avoid circular imports with agent_executor.py. Since tool_selection_agent would import system_entry and tool_call_converter (not agent_executor), circularity is unlikely unless agent_executor imports tool_selection_agent and tool_selection_agent imports back from agent_executor.

**Mitigation:** Design the module boundary so tool_selection_agent is a leaf module (imports system_entry, tool_call_converter, llm_registry) and agent_executor imports it. No back-imports.

## 7. SCOPE REDUCTION ASSESSMENT

### 7.1 Can the slice be safely reduced?

**YES.**

The proposed slice contains both **core operationalization** changes and **observational enrichment** changes. The slice can be divided into:

**CORE (Behavior-Changing):**
1. Typed Agent Registration Enhancement (agent_registry.py)
2. Bounded Tool-Selection Agent Specialization (new tool_selection_agent.py + agent_executor.py refactor)
3. Bootstrap registration of typed agent (bootstrap.py)

**OBSERVATIONAL (Non-Behavior-Changing):**
4. Agent Output Tagging / Attribution (agent_executor.py, agent_output_validator.py, agent_output_interpreter.py)
5. Agent Observability Integration (trace_collector.py)
6. Governance-Routed Agent Output (step_executor.py metadata enrichment)

### 7.2 Recommended Reduced Slice

**Core operationalization only:**
- Implement typed agent registration in agent_registry.py (backward-compatible)
- Create tool_selection_agent.py with extracted tool-selection logic
- Refactor agent_executor.py to delegate to tool_selection_agent.py
- Update bootstrap.py to register tool_selection_agent

**Deferred to ISSUE-073:**
- Agent attribution metadata in agent output
- Attribution field validation in agent_output_validator.py
- Attribution extraction in agent_output_interpreter.py
- Agent attribution in trace_collector records
- Agent attribution tagging in step_executor.py
- GovernanceDecision metadata enrichment

### 7.3 Rationale for Reduction

- The core operationalization achieves the essential goal: AG1 has a specialized, typed, bounded tool-selection agent in the orchestrator path.
- The observational enhancements are valuable for debugging and monitoring but do not change runtime behavior.
- Deferring observational enhancements reduces the implementation surface, lowering regression risk.
- Attribution metadata can be added later without breaking changes if the core agent structure is already in place.
- The baseline audit's "What Is Missing for Initial Operationalization" list is aspirational. The truly minimum viable operationalization is: (1) a working specialized agent, (2) a registry that can hold its definition.

### 7.4 Risks of NOT Reducing

- Higher regression risk from more files changed
- More validation required before merge
- Higher chance of introducing bugs in the critical agent_executor.py path
- Attribution metadata adds complexity without functional benefit at this stage

## 8. FINAL RECOMMENDATION

### 8.1 Verdict

**IMPLEMENTATION APPROVED WITH REDUCTION**

Approve the core operationalization slice (typed registry + tool-selection agent specialization + bootstrap update). Defer pure observational enhancements (attribution metadata, trace integration, governance metadata enrichment) to ISSUE-073.

### 8.2 Rationale

1. **Authority boundaries are preserved.** The proposed slice does not violate any AG1 containment rule, authority model, or architecture law.
2. **No SA escalation required.** The registry enhancement is minimal and does not constitute an "agent registry" per AGENT_GOVERNANCE_CONTRACT_V1 Section 8.
3. **Regression risk is manageable with reduction.** The agent_executor.py refactoring is the highest-risk change. Limiting the slice to core operationalization minimizes the chance of introducing bugs in the critical tool-selection path.
4. **Observational enhancements are safe but unnecessary for initial operationalization.** Attribution metadata, trace enrichment, and governance metadata are valuable but do not change behavior. They can be added in ISSUE-073 with lower risk once the core agent module is stable.
5. **Validation requirements are clearer for the reduced slice.** Fewer files to test means faster validation and lower chance of missed regressions.

### 8.3 Approved Reduced Slice

**Files to change (reduced):**
1. `system/orchestrator/agent_registry.py` — Extend with typed registration (backward-compatible)
2. `system/orchestrator/agents/tool_selection_agent.py` — NEW FILE (extract tool-selection agent logic)
3. `system/orchestrator/agent_executor.py` — Refactor to use specialized agent module (preserve exact API)
4. `system/orchestrator/bootstrap.py` — Register typed tool_selection_agent at initialization

**Files that MUST NOT change:**
- All core pipeline files (system_entry, parser, resolver, validation, execution)
- system/orchestrator/governance.py (decision logic untouched)
- system/orchestrator/workflow_control.py (lifecycle authority untouched)
- system/orchestrator/orchestrator_runtime.py (runtime loop untouched)
- agents/ directory (legacy dormant agents untouched)
- core/agent_executor.py (legacy executor untouched)

**Deferred to ISSUE-073:**
- Agent output attribution metadata (agent_type, agent_version, capability_used, confidence)
- Agent output validator attribution field checks

- step_executor.py agent attribution tagging
