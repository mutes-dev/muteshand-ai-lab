### Current Agent-Related Architecture

**Two distinct agent paths exist in the codebase:**

1. **Orchestrator Path (ACTIVE, AG1-relevant):**
   ```
   user_input → execute_from_input() → plan_workflow() → run_workflow() → execute_step() → execute_agent() [LLM tool selection] → tool_call_converter() → system_entry() → tool execution → execution_result → governance decision → lifecycle update
   ```
   - Agent role: tool-selection / purpose-to-tool_call resolution
   - Agent scope: bounded to producing USE_TOOL: strings
   - Execution authority: NONE. Actual execution is delegated to system_entry.
   - Output format: structured dict with agent metadata, reasoning, execution_result

2. **Legacy Manager Path (DORMANT, NOT AG1-relevant):**
   ```
   manager → core/agent_executor.execute_agent() → AGENTS[agent_name](agent_input) → agent module.run() → direct tool execution OR file write
   ```
   - Used by: legacy manager pattern (not in current orchestrator)
   - Agents: code_agent, tester_agent, system_test_agent
   - These agents CAN bypass system_entry (tester_agent calls module.run() directly)
   - These agents CAN mutate filesystem (code_agent writes files directly)
   - NOT connected to the orchestrator runtime

```

  → agent_input = step.get("tool_call") or step.get("purpose") or step.get("input")
```

## 4. AUTHORITY BOUNDARY AUDIT

### 1. Does all tool execution still route through system_entry?

**YES** — for the orchestrator path.
- `system/orchestrator/agent_executor.py` lines 131, 400, 422, 450: ALL call `system_entry(tool_call)`
- `system/orchestrator/step_executor.py` line 11: imports system_entry, does not call tools directly

**NO** — for legacy agents (not in orchestrator path):
- `agents/tester_agent.py` line 148: `result = module.run(*final_args)` — bypasses system_entry
- `agents/code_agent.py` lines 315-317: `exec(code, namespace)` — bypasses system_entry

**Assessment:** The active orchestrator path preserves system_entry as the sole execution gateway. Legacy agent files in `agents/` bypass system_entry but are NOT invoked by the orchestrator.

### 2. Can any agent directly execute tools?

**NO** — in the orchestrator path. The agent only produces USE_TOOL: strings. `tool_call_converter.py` converts them, then `system_entry()` executes.

**YES** — legacy `agents/tester_agent.py` directly calls `module.run()`. Not in orchestrator path.

### 3. Can any agent bypass parser / resolver / validation / execution?

**NO** — in the orchestrator path. The full pipeline is: agent output → converter → system_entry → parser → resolver → validation → execution.

**YES** — legacy agents bypass the entire pipeline.

### 4. Can any agent produce or override authoritative execution_result?

**NO**. The agent returns a structured dict that CONTAINS the execution_result from system_entry, but the agent does not create or modify execution_result. execution_result is produced by `system/execution/executor.py` inside the core pipeline.

```python
# system/orchestrator/agent_executor.py line 131
execution_result = system_entry(tool_call)
# execution_result is then embedded in the agent's result dict
```

### 5. Can any agent trigger retry independently?

**NO**. Retry is decided by governance in `orchestrator_runtime.py` based on execution_result + validator signals. The agent's validator_output is advisory-only and stored in step metadata.

### 6. Can any agent alter lifecycle state?

**NO**. Lifecycle state transitions are managed by `workflow_control.request_step_transition()` and `governance` decisions. Agents have no access to lifecycle authority.

### 7. Can any agent mutate workflow state?

**NO**. Agents do not receive workflow dicts. They receive input_data strings and optional context. The orchestrator controls all workflow state mutations.

### 8. Can any agent own or write projection state?

**NO**. Projections are managed by `projection_manager.py`. Agents do not interact with projections.

### 9. Can any agent make governance decisions?

**NO**. Governance decisions are made by the governance layer in `orchestrator_runtime.py` based on execution_result. Agent outputs are inputs to the process, not decision-makers.

### 10. Are agent outputs advisory-only, or are they routed through orchestrator / governance / system_entry before execution?

**ADVISORY-ONLY and GOVERNANCE-ROUTED.**
- Agent outputs = tool-selection suggestions (USE_TOOL: strings)
- These suggestions are converted to tool_calls by `tool_call_converter.py`
- tool_calls are validated by system_entry's validation layer
- execution_result is produced by the core execution layer
- governance decides next action based on execution_result

### 11. Are trace/projection/observability surfaces read-only if agents touch them?

**YES.**
- `trace_collector` records events after execution (read-only observation)
- `projection_manager` emits lifecycle changes after governance decisions (read-only downstream)
- `signal_interpreter` stores analysis in step metadata (not read by governance)
- `drift_detector` stores drift signals in step metadata (not read by governance)

### 12. Is there any persistent agent identity?

**NO** in the orchestrator path. The agent is ephemeral — a dict with name="generic_agent" is constructed fresh per step. No state is maintained across invocations.

**YES** in legacy `memory/agent_registry.json` — but this is metadata for dormant agents.

### 13. Is there any multi-agent coordination?

**NO**. Only one agent (generic_agent) is invoked per step. There is no agent-to-agent communication or coordination.

### 14. Is there any adaptive orchestration path?

**NO**. The orchestrator uses deterministic planning, governance rules, and fixed step execution. No adaptive behavior is triggered by agents.
