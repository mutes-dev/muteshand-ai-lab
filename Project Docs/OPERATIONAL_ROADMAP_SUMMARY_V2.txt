## 2. WHY V2 EXISTS — THE STRATEGIC PIVOT

OPERATIONAL_ROADMAP_V1.txt correctly stabilized the core runtime and stopped architecture drift through Sprint 6. V1 delivered:
- single lifecycle authority
- governance-owned retry/failure/escalation
- projection-only frontend rendering
- Task Hub / History separation
- FAILED actionability metadata
- backend instance identity guard
- AG1 bounded containment and debug attribution visibility
- SSE event-hint transport without giving transport authority
- memory storage/API/GUI/trace/guardrail foundation

V1 drifted by treating architecture stabilization and operational hardening as the primary path of progress while the product-facing intelligence layer remained mostly missing. The system is architecturally aligned but at roughly 22% SYSTEM_GOALS_V2 functional completion.

V2 changes the roadmap center of gravity:

**Before (V1):** Architecture stabilization and operational hardening → main line  
**After (V2):** Product capability activation → main line. Production hardening → bounded parallel track.

This is NOT an architecture change. All frozen architecture rules are unchanged. V2 is a sequencing and priority change only.

## 3. CURRENT FUNCTIONAL REALITY SUMMARY

The system currently has:
- deterministic core execution pipeline and tool registry
- workflow planning/execution orchestration with governance decision layer
- parallel execution, dependency scheduling, and checkpointing
- runtime lifecycle registry and projection-driven GUI
- pause/resume/retry/cancel controls and FAILED actionability metadata
- AG1 bounded tool-selection agent with debug attribution visibility
- SSE event-hint transport (hint-only, non-authoritative)
- memory CRUD API and MemoryPanel (operator-managed display/manage only)
- test safety guard for destructive persistence paths

What the system does NOT yet have:
- memory used at runtime to influence agent or planner behavior
- learning that reads back into behavior
- GUI approval surface for step/workflow decisions
- in-app notifications
- user override / force execution path
- privacy/sensitivity enforcement
- operational purpose validation
- agent/tool coverage sufficient for real multi-step workflows
- sandbox or self-improvement path

## 4. PRODUCT CAPABILITY SEQUENCING (V2 SPRINT DIRECTION)

### Sprint 7 — Product Capability Activation + P0 Safety Baseline

**This is the immediate next sprint.**

Sprint 7 must deliver the minimum safe product activation slice:
- Instrument and measure PERF-036 trivial-prompt latency (P0 usability gate — must be measured before making responsiveness claims)
- Activate memory advisory influence: connect operator-managed memory into agent/planner context in an advisory-only, guardrailed bridge
- Add GUI approval surface for step or workflow decisions requiring operator confirmation
- Surface in-app notifications for workflow events
- Design workflow-scoped user override / force execution path
- Apply P0 safety hardening only where it prevents unsafe use or blocks product evaluation:
  - CORS origin restriction
  - admin/test endpoint gating
  - `/health` and `/ready` endpoints if process reliability work is touched
  - LLM timeout / circuit breaker before expanded LLM use

Sprint 7 must NOT:
- implement full memory/learning
- implement full override authority
- implement broad tool/agent expansion
- replace or redesign the core orchestration architecture
- treat production hardening as the primary sprint deliverable

### Sprint 8 — Learning / Preference Adaptation

- Activate learning: connect memory writes to behavior reads
- Implement preference tracking that influences agent/planner recommendations
- Preserve advisory-only status — learning does not override execution_result or governance
- Adversarially validate learning cannot escalate to authority

### Sprint 9 — Agent and Tool Expansion

- Expand AG1 tool coverage to support real multi-step workflows
- Evaluate additional bounded agent types within AG1 governance scope
- Each new agent requires adversarial containment validation before production
- No persistent agent identity, no multi-agent orchestration, no autonomous retry without SA escalation

### Sprint 10 — Plan Control / Workflow Repair

- Activate plan editing and workflow repair surfaces
- Implement operator-driven step mutation in legal mutation windows
- Integrate with approval UX from Sprint 7
- Preserve mutation legality per MUTATION_LEGALITY_AND_RUNTIME_ISOLATION_CONTRACT_V1

### Sprint 11 — Privacy and Local-First Data Enforcement

- Implement privacy/sensitivity classification for inputs and memory
- Enforce local-first data boundaries before external tool danger increases
- Define and implement data retention enforcement

### Sprint 12+ — Production Readiness Gate

- Declare full product readiness only after core product capability tracks are materially complete
- Infrastructure hardening (CI, auth hardening, monitoring, deployment reproducibility) may proceed earlier as bounded work but is not the final gate
- Final readiness requires: memory operationalized, learning operationalized, agents expanded, sandbox/self-improvement path established

## 5. PRODUCTION HARDENING TREATMENT

Production hardening is **parallel and bounded**, not a standalone sprint.

P0 hardening is allowed in Sprint 7 only where it prevents unsafe use or blocks product evaluation:
- CORS restriction to `["http://localhost:5173", "tauri://localhost"]`
- Admin/test endpoint gating (env-var or local token)
- `/health` and `/ready` endpoints if startup work is touched
- LLM timeout / circuit breaker before expanded LLM use

P1/P2/P3 hardening should not displace product capability unless it is a direct dependency.

The Production Platform Audit identified that AI Lab is not production-ready for LAN/network/multi-user exposure. This is acceptable for local-first single-operator desktop use only while CORS, admin endpoint exposure, and portability gaps remain bounded.

## 8. SUB-DEV ISSUE SIZING AND LIFECYCLE MODEL

### Issue Sizing Rules

Each sprint issue must be:
- **Bounded:** scoped to one capability slice or one validation target
- **Atomic:** completable without reopening other closed issues
- **Evidence-required:** marked complete only when harness/test evidence exists or manual validation is documented
- **Non-goals explicit:** every issue must define what it does NOT do

### Issue Lifecycle

1. **NOT STARTED** — defined in roadmap, not yet active
2. **IN PROGRESS** — active implementation; Sub-Dev has single assigned issue
3. **IMPLEMENTED** — code complete, awaiting validation
4. **VALIDATED** — harness/test evidence exists or manual validation documented by Head Dev
5. **COMPLETE** — validated and accepted; must not be reopened unless regression recurs
6. **DEFERRED** — descoped from current sprint; does not imply incomplete sprint

### Sub-Dev Rules

- Sub-Dev executes one issue at a time
- Sub-Dev must read the Required Grounding Documents listed under the issue in OPERATIONAL_ROADMAP_V2 before starting
- Sub-Dev must not alter frozen architecture rules
- Sub-Dev must not reopen closed issues without Head Dev authorization
- Sub-Dev must not mark an issue COMPLETE without validation evidence
- Sub-Dev must not merge implementation-state claims into SYSTEM_STATE_V2 until validated
- Sub-Dev must escalate to Head Dev at any uncertainty about scope, authority boundaries, or contract compliance
