# USER_CONTROL_CONTRACT_V2

## 1. Document Purpose

This contract defines AI Lab user control semantics for workflow actions, workflow-scoped override, force execution requests, and the relationship between user intent, approval, governance, lifecycle authority, mutation legality, dependency validity, projection/frontend display, and notifications.

This contract exists because user authority is a core product requirement, but user authority must be implemented without creating unsafe authority bypasses.

This contract defines:

- user control principles
- pause/resume/cancel/retry relationship
- approval vs override vs force execution
- workflow-scoped override
- step-scoped override
- force execution request semantics
- forbidden cases
- backend validation requirements
- GUI intent-capture rules
- trace/audit requirements
- staleness/expiry rules
- relationship to governance, lifecycle, mutation legality, approval, notification, and projection contracts

This contract does not implement override.

This contract does not grant frontend authority.

This contract does not grant agents, planners, memory, validators, notifications, or projections runtime authority.

---

## 2. Core Principle

User control is absolute as a product principle.

User control is not the same as direct mutation authority.

The user may request, approve, reject, retry, cancel, pause, resume, replan, or override within the legal backend-authorized control model.

The backend must validate whether the requested action is currently legal.

The correct authority chain is:

```text
user intent -> backend validation -> governance/runtime decision -> legal lifecycle/mutation action -> projection update
```

The incorrect authority chain is:

```text
user intent -> frontend/projection mutation -> workflow state changes
```

---

## 3. Authority Model

### 3.1 User Role

The user may express intent to:

- pause a workflow
- resume a workflow
- cancel a workflow
- retry a failed/retryable step
- approve a pending approval request
- reject a pending approval request
- request replan
- request workflow-scoped override
- request step-scoped override
- request force execution of a specific continuation path
- accept a clearly described risk
- provide missing input
- choose between backend-offered recovery options

### 3.2 Backend Role

The backend owns:

- control request identity
- control request validation
- approval/override request lifecycle
- legal action acceptance/rejection
- lifecycle transitions
- mutation legality
- retry/replan legality
- dependency validity
- tool safety enforcement
- privacy/sensitivity gates
- trace emission
- stale request rejection

### 3.3 Frontend Role

The frontend may:

- display controls
- display approval requests
- display override requests
- display notifications
- capture user intent
- send user intent to backend
- display backend-confirmed results

The frontend may not:

- mutate lifecycle truth directly
- mutate workflow state directly
- unblock workflows directly
- apply approval locally
- apply override locally
- treat notification dismissal as approval or override
- infer legal continuation from projection state
- synthesize lifecycle truth

## 4. Approval vs Override vs Force Execution

### 4.1 Approval

Approval means:

```text
The system requested permission for a specific pending action.
The user approves or rejects that requested action.
```

Approval is governed by `USER_APPROVAL_CONTRACT_V1.txt`.

Approval is not override.

Approval is not force execution.

### 4.2 Override

Override means:

```text
The system has blocked, failed, escalated, warned, or recommended against continuation.
The user explicitly requests a different continuation path.
```

Override is user intent.

Override is not authority.

Override must be backend-validated.

### 4.3 Force Execution

Force execution is a stronger form of override intent.

Force execution means:

```text
The user asks the system to proceed with a specific workflow/step action despite a non-terminal block, warning, escalation, or recoverable failure.
```

Force execution is not a blank check.

Force execution remains subject to:

- lifecycle legality
- mutation legality
- dependency validity
- governance safety
- tool safety
- privacy/sensitivity policy
- approval requirements
- backend acceptance

---

## 5. Scope Model

### 5.1 Workflow-Level Control

Allowed for legal workflow actions such as:

- pause
- resume
- cancel
- retry workflow recovery path
- replan workflow
- request override for a workflow-level block

Workflow-level override is allowed only for non-terminal workflows.

### 5.2 Step-Level Control

Allowed for legal step actions such as:

- retry failed/retryable step
- replan from failed or blocked step
- request override of a step-level low-confidence block
- accept a step-specific warning/risk
- supply missing step input

### 5.3 Approval-Request-Level Control

Allowed where a control action is tied to a specific approval request.

Example:

```text
approval_id -> user approves external call risk
```

### 5.4 Disallowed Scopes

The following are not approved:

- global override
- project-level blanket override
- frontend-only override
- projection-only override
- agent-owned override
- memory-owned override
- planner-owned override

---

## 6. Overrideable Outcomes

The following may be overrideable if backend validation passes.

### 6.1 BLOCK due to approval_required

Usually handled by normal approval, not override.

Override applies only if the user asks to proceed differently from a system block/recommendation beyond ordinary approval.

### 6.2 BLOCK due to low confidence

May be overrideable if:

- action is low/medium risk
- action is reversible or bounded
- no dependency failure is being ignored
- no mutation legality violation exists
- no privacy/tool safety hard block exists
- user confirms risk

### 6.3 ESCALATE

May be overrideable only if escalation is advisory/user-decision-oriented.

Not overrideable if escalation means architecture, lifecycle, mutation, privacy, safety, or tool-policy impossibility.

### 6.4 Retry Exhaustion / Failed Step

May support:

- force retry
- retry with same input
- retry with modified input
- replan from failure
- continue only if downstream dependencies do not require failed output

May not support:

- pretending the failed step succeeded
- fabricating output
- bypassing dependency requirements

### 6.5 No-Progress BLOCKED

May support:

- retry
- replan
- cancel
- operator-provided missing input
- force continuation only if no dependent step requires missing output

### 6.6 Planner / Pre-Step FAILED

Usually not force-continuable.

May support:

- retry planning
- replan with simpler constraints
- fallback planner mode
- conversational fast-path only if separately approved by SA

---

## 7. Categorically Non-Overrideable Cases

The following cannot be overridden unless SA explicitly changes architecture.

### 7.1 Mutation Legality Violations

Override cannot bypass mutation legality.

Examples:

- illegal ACTIVE execution mutation
- unsafe dependency edit during active execution
- direct runtime-owned state mutation
- mutation during terminalization
- mutation while runtime lock forbids it

### 7.2 Lifecycle Transition Illegality

Override cannot force illegal lifecycle transitions.

Lifecycle transitions remain committed only by Lifecycle Authority.

### 7.3 Terminal Lifecycle Resurrection

Override cannot resurrect terminal workflows.

Forbidden:

- COMPLETED -> ACTIVE
- CANCELLED -> ACTIVE
- QUARANTINED -> ACTIVE
- non-recoverable terminal state -> ACTIVE

Recoverable FAILED may use authorized retry/replan/re-execution mechanisms only.

### 7.4 execution_result Truth

Override cannot change execution_result truth.

The user cannot declare failed execution successful.

### 7.5 Dependency Failure Bypass

Override cannot ignore failed dependencies.

Allowed alternatives:

- retry failed dependency
- replan dependency chain
- user supplies replacement input through legal mechanism
- backend-approved replan declares dependency irrelevant
- cancel/skip branch only if schema and governance allow skip semantics

Forbidden:

- treating missing dependency output as present
- continuing dependent step with invalid input
- marking failed dependency successful by user instruction

### 7.6 Projection / Frontend-Originated Continuation

Projection and frontend cannot create continuation truth.

They may request.

Backend decides.

### 7.7 Governance Safety Hard Blocks

Override cannot bypass hard blocks caused by:

- missing mandatory approval
- privacy/sensitivity policy violation
- unsafe external call
- prohibited tool action
- path confinement violation
- shell/file/system action outside allowed scope
- sandbox boundary violation
- license/provenance violation

### 7.8 Adaptive Orchestration

Override cannot activate adaptive orchestration.

Adaptive orchestration remains quarantined unless SA explicitly approves activation.

---

## 8. External / API / High-Risk Tool Control

External/API/high-risk actions may use user control only as explicit risk acceptance.

Mandatory requirements:

- clear action description
- tool/provider/destination
- data that may leave local system
- risk level
- reversibility/side effects
- confirmation text
- backend validation
- approval/override trace
- privacy/sensitivity metadata
- no careless secret/token display
- rejection if tool policy forbids action

HIGH or CRITICAL external-data actions require explicit approval-style confirmation even if an override/force request exists.

## 9. Backend Model

A user override / force execution request should be modeled distinctly from ordinary approval.

Recommended object:

```json
{
  "override_id": "string",
  "workflow_id": "string",
  "step_id": "string|null",
  "requested_action": "override_governance_block|force_retry_after_failure|force_continue_after_warning|force_replan|accept_external_call_risk",
  "status": "PENDING|ACCEPTED|REJECTED|EXPIRED|CANCELLED|SUPERSEDED|APPLIED",
  "reason": "string",
  "original_decision": {},
  "risk_level": "LOW|MEDIUM|HIGH|CRITICAL",
  "actor": "user",
  "created_at": "timestamp",
  "expires_at": "timestamp|null",
  "execution_generation": "number|null",
  "retry_generation": "number|null",
  "confirmation_text": "string|null",
  "backend_decision": "string|null",
  "metadata": {}
}
```

Approval infrastructure may be reused for display/confirmation, but override semantics remain distinct.

## 10. Requested Action Model

Approved initial requested_action values:

```text
force_step_retry
force_workflow_replan
override_low_confidence_block
accept_external_call_risk
continue_after_warning
provide_replacement_input
cancel_blocked_branch
```

Not approved initially:

```text
force_success
force_lifecycle_transition
force_dependency_bypass
force_active_mutation
force_terminal_resurrection
global_override
project_override
agent_override
```

---

## 11. Lifecycle Rule

Override may never directly force lifecycle transition.

Allowed:

```text
override request accepted -> runtime schedules legal retry/replan/continue action -> Lifecycle Authority transitions if valid
```

Forbidden:

```text
override request accepted -> frontend/backend directly sets workflow ACTIVE
```

---

## 12. Mutation Legality Rule

Mutation legality remains absolute.

If the user requests a mutation, the backend must validate legality.

If mutation is illegal, override cannot make it legal.

Future queued mutation semantics may defer a request, but must not execute during an illegal mutation window.

---

## 13. Dependency Rule

Override cannot ignore failed dependencies.

Dependency repair must happen through legal retry, replan, replacement input, branch cancellation, or backend-approved dependency restructuring.

---

## 14. Expiry / Staleness Rules

A user control / override request becomes invalid if:

- workflow reaches terminal state
- step is replaced
- retry_generation changes
- execution_generation changes
- governance decision changes
- dependency state changes
- requested action no longer applies
- approval request is superseded
- timeout expires
- user cancels/rejects
- backend detects stale projection/frontend state

Stale requests must be rejected.

---

## 16. Notification Relationship

Notifications may surface user-control requests.

Notifications may not apply user-control decisions.

Notification dismissal does not approve, reject, override, retry, cancel, continue, fail, complete, or unblock.

---

## 17. Approval Relationship

Approval infrastructure may be reused for user confirmation, but approval and override remain semantically distinct.

Ordinary approval must not be treated as force execution.

Override/force execution must carry distinct requested_action and trace metadata.

---

## 18. Agent / Planner / Memory Relationship

Agents may recommend user-control actions.

Planners may propose recovery options.

Memory may provide advisory context.

None of these may:

- approve
- override
- force execution
- mutate lifecycle
- mutate workflow state
- bypass governance
- bypass mutation legality
- bypass privacy/safety gates

---

## 19. Legacy override_state Ruling

Legacy `override_state` language is not valid implementation authority.

Do not implement:

```text
override_state = ON -> FAIL + CONTINUE
```

unless rewritten under this contract.

Replacement concept:

```text
user_control_override_request
```

or:

```text
force_execution_request
```

These are backend-validated, scoped user intents.

## 20. Minimal Sprint 7C Model

Sprint 7C is design-first.

Implementation may proceed only after Head Dev/SA confirms contract alignment.

Allowed minimal first implementation:

- backend-authored override request object
- workflow_id / step_id scope
- requested_action
- backend validation
- accept/reject/expire/supersede
- trace events
- GUI captures intent only
- no lifecycle bypass
- no mutation bypass
- no dependency bypass
- no terminal resurrection

Recommended first allowed actions:

- force retry of failed/retryable step
- continue after low-confidence warning
- replan from BLOCKED/no-progress
- accept external-call risk through approval-linked requested_action

Not allowed first:

- continue past failed dependency
- force ACTIVE lifecycle transition
- force success
- override HIGH/CRITICAL tool hard block
- override mutation legality
- override privacy hard block
- project/global override

## 22. Contract Rules

1. User control is a product principle, not direct runtime authority.
2. Override is scoped user intent, not governance bypass.
3. Force execution is backend-validated continuation intent, not lifecycle bypass.
4. Lifecycle Authority remains sole lifecycle owner.
5. Mutation legality remains absolute.
6. execution_result truth cannot be overridden.
7. Failed dependencies cannot be ignored.
8. Frontend/projection/notification may request or display, not decide.
9. Approval and override remain separate concepts.
10. Stale control requests must be rejected.
11. All override/force execution actions must be traceable.
12. Legacy `override_state` is not implementation authority.
