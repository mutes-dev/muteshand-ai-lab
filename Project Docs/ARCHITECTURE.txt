# AI LAB — SYSTEM ARCHITECTURE (IMMUTABLE)

---

## SCOPE (CRITICAL)

This document defines the CORE EXECUTION ARCHITECTURE ONLY.

It applies strictly to:

- planner
- parser
- resolver
- validation
- execution
- system_entry

The Orchestrator Layer (HAND):

- exists ABOVE this architecture
- is NOT defined in this document
- MUST NOT influence or modify core pipeline behavior

Any orchestration, workflow logic, governance, or retry control:

→ belongs to HAND_ARCHITECTURE.txt  
→ MUST NOT be implemented or described here

---

## CORE PRINCIPLE

DETERMINISTIC SYSTEM + NON-DETERMINISTIC PLANNER

The system is divided into STRICT layers.

Each layer has ONE responsibility.

NO layer may take on responsibilities of another.

---

# LAYER DEFINITIONS

---

## 1. PLANNER (LLM — INTELLIGENCE ONLY)

RESPONSIBILITY:

* Interpret user goal
* Decompose into steps
* Select tools or agents
* Define execution order

OUTPUT FORMAT:

[
{
"type": "tool" | "agent",
"name": "tool_name",
"input_text": "raw instruction"
}
]

RULES:

* MUST NOT generate arguments
* MUST NOT insert PREVIOUS_RESULT
* MUST NOT validate structure
* MUST NOT enforce execution constraints

## PLANNER RESPONSIBILITY (STRICT)

Planner MUST:
- Output ONLY:
  - type
  - name
  - input_text

Planner MUST NOT:
- generate args
- reference PREVIOUS_RESULT
- perform validation on args
- call validate_plan()

Planner output is considered STRUCTURAL ONLY and INCOMPLETE by design.

## LLM USAGE CLARIFICATION

LLM usage exists in TWO locations:

1. Planner (primary intelligence layer)
2. LLM Adapter (optional secondary intelligence via llm_entry)

Rules:

- LLM Adapter is OPTIONAL and environment-dependent
- Core pipeline remains deterministic
- Validation layer remains authoritative
- Execution does NOT depend on LLM correctness

---

## 2. PARSER (DETERMINISTIC — TRANSLATION LAYER)

RESPONSIBILITY:

* Convert planner output into structured execution steps
* Extract numeric arguments and quoted strings deterministically
* No inference, no semantic interpretation

BEHAVIOR:

* Parser = token extraction only (numbers + quoted strings)
* Parser does NOT own argument construction
* Resolver = argument construction (positional mapping only)

OUTPUT FORMAT:

[
  {
    "type": "tool",
    "name": "tool_name",
    "input_text": "raw instruction",
    "clean_input": "stripped instruction",
    "args": [arg1, arg2, ...]
  }
]

Note: Parser preserves full planner step structure via step.copy(), adding "args" only.

RULES:

* MUST be fully deterministic
* MUST NOT use LLM
* MUST NOT infer missing values
* MUST NOT reorder arguments
* MUST NOT validate structure (validation layer responsibility)
* MUST NOT construct arguments (resolver responsibility)

Parser acts as a strict translation bridge between planner and system.
Parser extracts numbers; Resolver builds complete argument lists.

---

## 3. RESOLVER (DETERMINISTIC)

RESPONSIBILITY:

* Construct complete argument lists from parser output
* Perform positional mapping only

OUTPUT FORMAT:

[
  {
    "type": "tool",
    "name": "tool_name",
    "input_text": "raw instruction",
    "clean_input": "stripped instruction",
    "args": [arg1, arg2, ...]
  }
]

RULES:

* MUST be fully deterministic
* MUST NOT use LLM
* MUST NOT infer missing values
* MUST NOT reorder arguments
* MUST NOT validate structure (validation layer responsibility)

---

## 4. VALIDATION (STRUCTURAL ONLY)

RESPONSIBILITY:

* Validate plan schema
* Validate tool/agent existence
* Validate argument count against tool contract
* Validate argument types against tool contract

RUNTIME PLACEHOLDERS:

* Not applicable — system is single-step only

RULES:

* MUST NOT interpret intent
* MUST NOT evaluate correctness of plan
* MUST NOT modify plan
* MUST skip validation for runtime placeholder tokens

## CLARIFICATION

Validator layer MAY influence:
- retry behavior
- final output enforcement

This operates ABOVE execution and does NOT break determinism.

---

## 5. EXECUTION (DETERMINISTIC RUNTIME)

RESPONSIBILITY:

* Execute tools/agents
* Store results
* Pass outputs forward

RULES:

* MUST NOT modify plan
* MUST NOT perform reasoning
* MUST NOT correct errors
* MUST fail immediately if required runtime data is missing (e.g. PREVIOUS_RESULT with no prior result)
* MUST NOT execute tools if validation conditions are not met
* MUST return explicit failure for invalid execution state

Execution MUST be implemented as an isolated module
(e.g. /system/execution/executor.py)

Execution MUST NOT depend on manager or orchestration code.

---

## 6. AGENTS (OPTIONAL INTELLIGENCE MODULES)

RESPONSIBILITY:

* Perform specialized LLM tasks

RULES:

* Invoked by planner like tools
* Encapsulated intelligence
* NO control over system flow

---

## ENTRY (ORCHESTRATION ONLY)

Entry MUST:

* receive plan
* receive validation_registry
* receive execution_registry
* call validation
* enforce fail-fast
* call execution

Entry MUST NOT:

* perform parsing
* perform validation logic
* perform execution logic
* mutate data

---

# DATA FLOW

User Input
→ Planner (NON-DETERMINISTIC — external)
→ Parser (DETERMINISTIC — translation layer)
→ Entry
→ Validation (STRUCTURAL ONLY — FAIL-FAST GATE)
→ Execution (single-step only)
→ Result

---

# REGISTRY FLOW

Tool Index
→ Registry Builder
→ validation_registry + execution_registry
→ used by Validation and Execution respectively

---

# SYSTEM STRUCTURE (IMPLEMENTATION LAYERS)

The system is implemented across the following directories:

/core

* Contains deterministic logic layers
* planner, parser, resolver, validation

/system

* Contains runtime system implementation

/system/execution

* Execution engine (deterministic runtime loop)

/system/entry

* Entry point (pipeline orchestration ONLY)

/system/observability

* Trace system
* Validation (observability layer)
* Harness

---

# IMPLEMENTATION RULES

* /core contains LOGIC ONLY
* /system contains SYSTEM FLOW
* Execution logic MUST NOT exist in entry layer
* Entry layer MUST NOT contain business logic
* Observability MUST be read-only

---

## CHAIN RESOLVER DEFINITION (DEPRECATED)

Chain Resolver was removed. System supports single-step execution only.
PREVIOUS_RESULT is not supported in current architecture.

---

## POST-EXECUTION LAYER

Execution → Result → Orchestrator Layer:
- Validator (advisory only)
- Final Output Resolution (single-source, no synthesis)

---

# HARD RULES (NON-NEGOTIABLE)

1. Planner NEVER generates arguments
2. Parser ALWAYS produces execution-ready structured steps
3. All argument extraction MUST occur inside Parser
4. Validation NEVER interprets intent
5. Execution NEVER modifies plan
6. NO layer may take another layer's responsibility
7. ALL transformations must be explicit
8. System supports single-step execution only

---

# FAILURE MODEL

* Planner failure → stop
* Validation failure → stop
* Execution failure → contained and reported
* Execution failure MAY trigger controlled replanning

NO silent failures
NO partial states

---

# EXTENSIBILITY MODEL

System must support:

* multiple agents
* model swapping
* DAG execution (future)
* autonomous loops

WITHOUT changing core architecture

---

# FINAL PRINCIPLE

INTELLIGENCE IS REPLACEABLE
ARCHITECTURE IS PERMANENT
