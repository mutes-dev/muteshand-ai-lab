## Scope

Defines how the system logs, traces, and records:
- workflow execution
- step execution
- decisions (governance)
- tool execution
- errors and failures
- user-control events
- notification events
- retry/replan/recovery events

This contract ensures:
- full traceability
- debuggability
- auditability
- learning data consistency

---

## Core Principle

Trace is an append-only evidentiary/audit record, not lifecycle authority or execution truth.

System MUST be able to:
- reconstruct any execution for audit/debugging
- explain any decision from trace evidence

System MUST NOT:
- derive lifecycle truth from trace alone
- derive execution truth from trace alone
- derive governance decisions from trace alone

---

## Trace Authority Model

- execution_result owns execution truth.
- Lifecycle Authority owns lifecycle truth.
- Governance owns runtime decisions.
- Runtime Registry owns execution coordination state.
- Trace/logging does not originate lifecycle truth, execution truth, governance decisions, runtime coordination, projection truth, or persistence truth.
- Trace may record authoritative events but must not become authority.

---

## Trace Levels

---

### NORMAL

- minimal logs
- user-relevant events only

Includes:
- workflow start/end
- step completion
- failures
- approvals

---

### LIVE

- step-by-step visibility
- high-level internal state

Includes:
- step start/end
- governance decisions
- retry attempts
- validation outcomes

---

### DEBUG

- full system trace
- complete internal state

Includes:
- raw inputs
- parsed values
- validation details
- execution payloads
- errors/exceptions

DEBUG trace may include richer detail but must remain local and protected.

---

## Trace Structure

Every log entry MUST follow:

```json
{
  "timestamp": "<iso8601>",
  "workflow_id": "<id>",
  "step_id": "<id or null>",
  "level": "<NORMAL | LIVE | DEBUG>",
  "event": "<event_type>",
  "data": {...}
}
```

Prefer workflow_id over project_id.
project_id may be used as legacy alias for workflow_id where explicitly documented.

## Immutability Rule

- logs MUST NOT be modified after creation
- logs MUST be append-only
- corrections MUST be new entries

---

## Storage

- logs MUST be persisted locally
- logs MUST be structured (JSON or equivalent)
- logs MUST be queryable

---

## Replay Requirements

Trace may support audit reconstruction, debugging, and manual/authorized replay analysis.

Actual replay/re-execution is governed by EXECUTION_IDENTITY_AND_REPLAY_CONTRACT_V2 and must create new execution identity when authorized.

Recovery must not replay execution from logs automatically.

System MUST NOT support replaying a project/workflow from logs automatically or as authority.

---

## Privacy Rule

- sensitive data MUST NOT leave local storage
- logs MUST respect data classification rules
- secrets/tokens should be redacted or protected
- DEBUG trace may include richer detail but must remain local and protected

Logs may contain sensitive data.
Logs must respect privacy/sensitivity policy.

---

## Performance Rule

- logging MUST NOT block execution
- logging should be async where possible
- logging should not block lifecycle finalization
- logging failure must not redefine lifecycle/execution truth
- critical trace failure may emit warning/diagnostic but must not silently create authority drift

---

## Failure Logging

On ANY failure:
- error MUST be logged
- reason MUST be captured
- context MUST be preserved

---

## Final Principle

Trace is an append-only evidentiary/audit record.

execution_result owns execution truth.

Lifecycle Authority owns lifecycle truth.

Trace records what happened for audit, debugging, and learning evidence.

Trace does not become authority.

Logs MUST be:
- complete
- structured
- reliable
- append-only
