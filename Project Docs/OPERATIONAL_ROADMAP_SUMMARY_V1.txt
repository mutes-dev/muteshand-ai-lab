## 4. PRODUCTION-HARDENING SEPARATION CLARIFICATION

### Critical Distinction

**Production readiness ≠ Runtime correctness.**

OPERATIONAL_ROADMAP_V1.txt explicitly separates these in Section 6.

### Runtime Correctness

Runtime correctness is:
- deterministic execution
- governance supremacy
- lifecycle authority isolation
- execution_result truth
- mutation legality
- convergence correctness

Runtime correctness is VERIFIED and FROZEN (Section 1).

### Production Readiness

Production readiness is:
- CI/CD completeness
- authentication hardening
- CORS configuration
- monitoring infrastructure
- alerting infrastructure
- metrics collection
- deployment reproducibility
- environment isolation
- operational security
- performance baselines

Production readiness is ACTIVE WORK (Section 6).

### Why This Separation Matters

Production readiness gaps are NOT runtime instability.

A system can be:
- runtime-correct AND production-unready (current state)
- runtime-correct AND production-ready (target state)
- runtime-incorrect AND production-ready (dangerous state to avoid)

OPERATIONAL_ROADMAP_V1.txt preserves this separation to prevent:
- conflating operational gaps with architecture defects
- pressuring runtime redesign to fix operational gaps
- treating production hardening as license to modify frozen architecture

### Operational Rule

Section 6 NON-GOALS explicitly prohibit:
- altering deterministic runtime architecture
- modifying governance semantics
- changing transport-agnostic semantics
- weakening mutation legality
- weakening execution identity guarantees
- introducing reactive orchestration
- operationalizing adaptive orchestration

## 6. EXECUTION-ORDER RATIONALE

### Phase Order

1. GUI / operational refinement
2. Realtime observability transport refinement
3. AG1 bounded agent operationalization
4. AG1 validation & governance hardening
5. Production hardening
6. Deferred future evolution (quarantined)

### Why This Order

**Phase 1 before Phase 2:** GUI observability is prerequisite for operator trust. Transport refinement improves GUI freshness but GUI must exist first.

**Phase 2 before Phase 3:** Transport infrastructure must be stable before agent observability integration. Agent outputs need reliable delivery.

**Phase 3 before Phase 4:** Agents must be implemented before they can be validated. Validation requires implemented agents to test.

**Phase 4 before Phase 5:** Containment validation MUST pass before production hardening. Production hardening on unvalidated containment is unsafe.

**Phase 5 before Phase 6:** Production hardening closes current operational scope. Deferred evolution requires explicit SA escalation and is not part of normal execution flow.

### Dependency Chain

Each phase depends on the previous phase being substantially complete.
Skipping phases creates risk:
- Skip Phase 1 → operator confusion during later phases
- Skip Phase 2 → agent observability unreliable
- Skip Phase 3 → no agents to validate
- Skip Phase 4 → unvalidated agents in production
- Skip Phase 5 → production deployment unsafe

### Parallel Work

Within each phase, tasks may run in parallel where dependencies permit.
Between phases, strict ordering is mandatory.
