## Purpose

Defines the canonical projection architecture used for workflow rendering, synchronization, continuity, and interaction.

This contract formalizes:
- orchestrator-generated projections
- frontend projection rendering
- projection identity
- projection lifecycle
- projection mutation flow
- projection transport semantics
- canonical read-model architecture

---

## Core Principle

Canonical projections are synchronized read models.

Canonical projections provide:
- stable workflow visibility
- synchronized rendering
- editable plan visibility
- deterministic continuity behavior

Canonical projections are NOT:
- execution truth
- lifecycle authority
- execution state ownership

Lifecycle Authority owns lifecycle truth.

execution_result owns execution truth.

Projections synchronize AFTER authority commit per:
ORCHESTRATION_AND_EXECUTION_SEQUENCE_CONTRACT_V2.txt

Projections NEVER participate in mutation legality decisions per:
MUTATION_LEGALITY_AND_RUNTIME_ISOLATION_CONTRACT_V2.txt

Projections NEVER participate in lifecycle sequencing authority.

---

## 1. Projection Ownership

Canonical projections are generated by the backend/orchestrator.

Frontend consumes projections.

API transports projections.

Neither frontend nor API owns projection truth.

API is transport/schema/intent routing only.

GUI is renderer/interaction layer only.

Backend/orchestrator may generate canonical projections, but projection state remains downstream synchronized visibility only.

## 16. Terminal Projection Rules

Terminal workflow projections MUST remain stable after:
- COMPLETED (immutable terminal)
- CANCELLED (immutable terminal)
- FAILED (recoverable terminal)

COMPLETED = immutable terminal projection anchor.

CANCELLED = immutable terminal projection anchor.

FAILED = recoverable terminal projection anchor.

BLOCKED = recoverable non-terminal/wait visibility anchor, not terminal.

Projections must not synthesize retry legality, recovery authority, or execution identity.

Retry creates new execution lineage; projections may display lineage but may not authorize it.

Terminal projections MUST NOT disappear unless:
- explicitly invalidated
- re-executed through authorized recovery/retry/re-execution contracts
- removed by authoritative action

## 23. Queued Replan Required Projection Semantics

Projection MAY be absent for QUEUED_REPLAN_REQUIRED.

Missing projection for a replan-required planning shell:
- is NOT necessarily projection failure
- is expected when planning was interrupted before projection emission
- does NOT prove lifecycle corruption

Missing projection for QUEUED_REPLAN_REQUIRED may be expected and must not be treated as lifecycle corruption.

Projection seed SHOULD be emitted:
- on replan start
- when planning execution identity is created
- when planning begins producing output

Projection visibility MUST represent:
- backend-authored planning actionability state
- live planning status when planning is active
- replan-required status when planning is interrupted

Projection MUST NOT:
- synthesize live planning from persistence alone
- claim projection_not_found is recoverable runtime evidence
- infer planning actionability from missing projection

Replan projection semantics are governed by:
PLANNING_RECOVERY_AND_REPLAN_CONTRACT_V2.txt
