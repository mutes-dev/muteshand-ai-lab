------------------------------------------------------------
1. Purpose
------------------------------------------------------------

WebResearchProfile supports explicit bounded web research workflows that require more than a single web search or a single URL read.

It is intended for workflows such as:
- search the web for a topic;
- read one or more selected sources;
- summarize or answer from those web sources;
- provide source-aware/cited or evidence-backed output where supported by current evidence metadata.

WebResearchProfile is not:
- autonomous browsing;
- ResearchAgent;
- document Q&A;
- CSV/XLSX analysis;
- learning/adaptation;
- broad uncontrolled research loop.

------------------------------------------------------------
2. Authority boundaries
------------------------------------------------------------

WebResearchProfile does not own:

- lifecycle truth;
- execution truth;
- governance decisions;
- approval decisions;
- user-control authority;
- system_entry authority;
- projection/frontend authority;
- memory/learning authority;
- planner authority;
- autonomous agent authority.

AG1 remains the only active runtime tool-selection agent.

WebResearchProfile is a scoped tool/profile catalog and planner/AG1 narrowing mechanism only.

All tool execution still flows through existing runtime/governance/system_entry paths.

------------------------------------------------------------
3. Profile status
------------------------------------------------------------

Until implementation is explicitly opened and accepted:

- WebResearchProfile is defined by this contract only.
- WebResearchProfile is NOT enabled.
- WebResearchProfile is NOT selectable.
- WebResearchProfile must not be returned by profile_selector.
- WebResearchProfile must not be exposed to AG1 as active.
- WebResearchProfile must not be exposed in GUI as active.
- WebResearchProfile must not be exposed as a scoped profile.
- WebResearchProfile must not be used to claim web research is implemented.

After acceptance and implementation:
- WebResearchProfile may become active only within the allowed tools/routing/approval boundaries below.

------------------------------------------------------------
4. Allowed tools
------------------------------------------------------------

Future allowed tools for WebResearchProfile (subject to contract acceptance and implementation):

- web_search
- read_webpage
- finalize_output

No other tools are approved by default.

semantic_transform is NOT included in the initial WebResearchProfile unless Head Dev/SA separately approves its use for bounded summarize/explain/extract_key_points over web evidence.

File tools are not included.

Mutation tools are not included.

CSV/XLSX tools are not included.

Document Q&A tools are not included.

ResearchAgent is not included.

Any expansion of allowed tools requires contract patch or explicit Head Dev/SA approval.

------------------------------------------------------------
5. Relationship to WebSearchProfile
------------------------------------------------------------

WebSearchProfile is for pure explicit search-only workflows.

Example:
- "Search the web for FastAPI lifespan docs."

WebSearchProfile may use:
- web_search

WebSearchProfile should not automatically read pages or synthesize from multiple sources unless another profile/slice explicitly supports that behavior.

------------------------------------------------------------
6. Relationship to WebReadProfile
------------------------------------------------------------

WebReadProfile is for explicit URL read workflows.

Example:
- "Read https://example.com"
- "Summarize https://example.com" if supported by existing bounded web read / transform path.

WebReadProfile may use:
- read_webpage
- finalize_output

WebReadProfile must not expose web_search unless separately approved.

------------------------------------------------------------
7. Relationship to WebResearchProfile
------------------------------------------------------------

WebResearchProfile is for explicit search + read + source-aware synthesis workflows.

Examples that MAY route to WebResearchProfile after implementation:

- "Research FastAPI lifespan docs and summarize the best source."
- "Search the web for X, read the top result, and summarize."
- "Find sources about X and give a short cited answer."
- "Research X and provide a brief source-backed answer."

WebResearchProfile should require:
- explicit web/research/search intent;
- no unresolved local data references;
- no document Q&A intent;
- no CSV/XLSX analysis intent;
- no side-effectful action.

------------------------------------------------------------
8. Relationship to GeneralFallbackProfile
------------------------------------------------------------

GeneralFallbackProfile must not expose web_search by default unless a separate contract explicitly allows it.

Uncertain/mixed prompts that require web research must either:
- route to WebResearchProfile when clearly explicit and safe, once implemented and accepted;
- remain GeneralFallbackProfile with web_search unavailable;
- or block/ask for clarification if unresolved references make the query unsafe.

GeneralFallbackProfile must not become a loophole for uncontrolled web_search.

------------------------------------------------------------
9. Relationship to F4 local-reference resolution
------------------------------------------------------------

F4-resolved local-reference web_search remains a separate safe path.

Example:

User intent:
- "Search the web for the person in row 4."

Before resolution:
- "person in row 4" is an unresolved local data reference.
- It must not be sent to web_search as a literal query.

After F4/Data Reference resolution:
- row 4 may resolve to a concrete value, for example "Ada Lovelace."
- web_search may use the resolved value as query input if query provenance records the dependency.

WebResearchProfile must respect F4/Data Reference rules.

------------------------------------------------------------
10. Unresolved reference blocking
------------------------------------------------------------

Prompts like these must remain blocked/safe until resolution:

- "Search the web for the person in row 4."
- "Research the company in this spreadsheet."
- "Find more info about the client in row 2."
- "Research this document" when no document Q&A/document reference pipeline exists.

The system must not pass unresolved placeholders, row references, document references, or vague dependency refs directly to web_search.

Required safe outcomes:
- block;
- ask for clarification;
- require data-reference resolution;
- or route to a pending-step continuation path when implemented.

------------------------------------------------------------
11. AG1/tool visibility boundary
------------------------------------------------------------

It is acceptable for WebResearchProfile implementation to change AG1 scoped tool visibility only within this contract.

Allowed once implemented and accepted:
- AG1 may see web_search, read_webpage, finalize_output under WebResearchProfile.
- AG1 must not see unrelated file mutation, document Q&A, CSV/XLSX analysis, or broad tools under this profile.
- Out-of-profile tool selection must be rejected before system_entry.

Not allowed:
- exposing web_search broadly to GeneralFallbackProfile;
- expanding AG1 full tool universe for research;
- allowing AG1 to browse autonomously;
- adding ResearchAgent;
- adding learning/adaptation.

------------------------------------------------------------
12. Planner/compiler boundary
------------------------------------------------------------

WebResearchProfile may be implemented without planner prompt changes only if existing planner/compiler/profile machinery can produce safe steps and scoped tools.

If implementation requires planner prompt changes, system prompt changes, AG1 prompt changes, or planner-visible schema changes:
- STOP;
- escalate to Head Dev/Bryan/SA before implementation.

WebResearchProfile must not be implemented through broad prompt-specific hardcoded routes.

Capability routing may recommend WebResearchProfile for explicit bounded research intent only after this contract is accepted and a bounded implementation slice is opened. Capability routing must remain advisory/profile-recommender only.

Planner remains primary workflow decision-maker.

------------------------------------------------------------
13. Approval/user-control boundary
------------------------------------------------------------

Every external call still obeys existing approval/user-control rules.

web_search:
- external call;
- approval/user-control required if current runtime policy requires it.

read_webpage:
- external call;
- approval/user-control required if current runtime policy requires it.

finalize_output:
- not an external call;
- must not require external-call approval merely because it follows web_search/read_webpage.

Preserve F3C/FIX3.1 behavior:
- no duplicate approval prompts;
- no approval race regressions;
- approval resolution must remain authoritative;
- approval metadata must remain traceable.

------------------------------------------------------------
14. Evidence/provenance boundary
------------------------------------------------------------

Initial WebResearchProfile may rely on existing F3C additive metadata substrate:

- observations;
- evidence_refs;
- validator_results;
- query_provenance;
- source_summary;
- privacy_summary;
- grounding/advisory warnings.

A full Evidence Graph is not required for initial WebResearchProfile activation if F3C metadata exists and tests prove the output does not claim unsupported grounding.

However:
- full Evidence Graph remains future-owned / F2/F7+ depending on roadmap;
- claim-to-source mapping remains future-owned unless separately implemented;
- source citations/evidence must honestly reflect what metadata currently supports.

------------------------------------------------------------
15. Grounding boundary
------------------------------------------------------------

For initial WebResearchProfile:

- grounding validators are advisory-only unless existing governance contracts explicitly allow blocking behavior;
- advisory grounding warnings may be emitted in validator_results;
- final output may include warnings/limitations;
- grounding validators may not create new lifecycle states;
- grounding validators may not independently own COMPLETE/FAILED/BLOCKED;
- blocking finalization requires separate grounding/governance authority.

If Head Dev wants grounding validators to block finalization, this requires explicit contract/governance approval before implementation.

------------------------------------------------------------
16. Privacy/spend/source boundary
------------------------------------------------------------

Allowed initially:
- metadata-only privacy_summary;
- metadata-only source_summary;
- query provenance;
- source URL/title/snippet/timestamp metadata where available;
- advisory source/freshness warnings.

Not approved by this contract alone:
- true spend/cost/budget enforcement unless an existing spend/budget contract already governs it;
- autonomous external browsing;
- unlimited search/read loops;
- source quality as hard governance authority;
- source freshness as hard governance authority.

Privacy/spend/source policy remains advisory/metadata unless another governing contract makes it enforceable.
