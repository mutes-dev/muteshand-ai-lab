# VALIDATION SYSTEM ARCHITECTURE

**Version:** 1.1  
**Created:** April 2026  
**Last Updated:** 2026-05-18  
**Status:** ACTIVE

---

## PURPOSE

This document defines the formal separation between two distinct validation systems:

1. **Harness** — External contract validation
2. **Internal Tests** — Behavior validation

This separation prevents validation drift, ensures clear authority boundaries, and maintains system integrity.

---

## 1. VALIDATION LAYERS

### LAYER 1 — HARNESS (EXTERNAL)

**Entry Point:** `execute_from_input(user_input: str)`  
**Contract Type:** Layered (nested status/result structure)  
**Location:** `tests/harness_cases/`

**Responsibilities:**
- Contract enforcement (layered structure)
- Determinism validation (3-run comparison)
- External system correctness
- Output schema validation

**Scope:**
- Tests public API surface
- Validates what the system RETURNS
- No knowledge of internal implementation

**Output Contract (Layered):**
```python
{
    "status": "success",
    "result": {
        "status": "success",
        "result": <value>
    }
}

# OR

{
    "status": "failure",
    "reason": <string>
}
```

---

### LAYER 2 — INTERNAL TESTS (BEHAVIOR)

**Entry Point:** `run_workflow(workflow: dict, return_trace: bool = False)`  
**Contract Type:** Flat (direct status/result structure)  
**Location:** `system/tests/`

**Responsibilities:**
- Retry behavior validation
- Lifecycle behavior validation
- Failure propagation validation
- Internal state transitions

**Scope:**
- Tests internal orchestrator logic
- Validates how the system BEHAVES
- Uses controlled mocking (monkeypatch)
- Direct workflow construction

**Output Contract (Flat):**
```python
{
    "status": "success",
    "result": <value>
}

# OR

{
    "status": "failure",
    "reason": <string>
}
```

---

## 2. HARD BOUNDARIES

### HARNESS MUST NOT:

- ❌ Test retry logic directly
- ❌ Test lifecycle transitions (PENDING → RUNNING → COMPLETE)
- ❌ Access `run_workflow` directly
- ❌ Validate internal step states
- ❌ Use mocking to control behavior
- ❌ Test orchestrator internals

**Rationale:** Harness validates external contract. Retry and lifecycle are implementation details not visible through `execute_from_input`.

---

### INTERNAL TESTS MUST NOT:

- ❌ Validate layered contract structure
- ❌ Test `execute_from_input` behavior
- ❌ Duplicate harness validation logic
- ❌ Enforce external contract rules
- ❌ Use natural language input (strings)
- ❌ Validate determinism across runs

**Rationale:** Internal tests validate behavior. The layered contract is a transformation applied at the external boundary, not the internal layer.

---

## 3. CONTRACT SEPARATION

### run_workflow → Flat Contract

**Success:**
```python
{
    "status": "success",
    "result": <value>  # Direct value, no nesting
}
```

**Failure:**
```python
{
    "status": "failure",
    "reason": <string>  # Human-readable explanation
}
```

**No extra fields:** No `trace`, `steps`, or internal metadata in final output.

---

### execute_from_input → Layered Contract

**Success:**
```python
{
    "status": "success",
    "result": {
        "status": "success",
        "result": <value>  # Nested structure
    }
}
```

**Failure:**
```python
{
    "status": "failure",
    "reason": <string>
}
```

**Note:** The layering is applied by `execute_from_input` wrapping the `run_workflow` output.

---

### STRICT RULE

**NO crossover between contracts.**

- Internal tests NEVER see layered contract
- Harness NEVER uses flat contract
- Each layer validates ONLY its own contract type

---

## 4. VALIDATION AUTHORITY MODEL

### Harness = CONTRACT AUTHORITY

**Validates:** What the system RETURNS to external callers

**Authority:**
- Defines external API contract
- Enforces output schema
- Guarantees determinism
- Prevents regression

**Tools:**
- Strict schema validation
- 3-run determinism check
- Layered structure enforcement
- Expected vs actual comparison

---

### Internal Tests = BEHAVIOR AUTHORITY

**Validates:** How the system BEHAVES internally

**Authority:**
- Defines retry logic behavior
- Validates state transitions
- Tests failure modes
- Controls execution path (mocking)

**Tools:**
- pytest monkeypatch
- Call counting
- Direct workflow construction
- Flat contract assertions

---

## 5. SEPARATION PREVENTS DRIFT

### Without Separation (Risk):

```
Harness tests retry behavior → Implementation changes → Harness breaks
Internal tests layered contract → Layer changes → Internal tests break
Mixed concerns → Unclear ownership → Validation gaps
```

### With Separation (Protection):

```
Harness validates contract → Contract stable → Harness stable
Internal tests behavior → Behavior stable → Tests stable
Clear boundaries → Clear ownership → Complete coverage
```

## 7. MODIFICATION RULES

### Adding New Tests:

**Harness Tests:**
- Use `execute_from_input` ONLY
- Test external, user-facing behavior
- Validate layered contract
- NO mocking (except for failure injection)

**Internal Tests:**
- Use `run_workflow` ONLY
- Test internal behavior mechanisms
- Validate flat contract
- Mocking permitted for behavior control

## 8. TEST EXECUTION MODEL

This section defines how validation systems are executed in practice.

---

### 1. TEST SUITES

Two distinct test suites exist:

#### Harness (External Contract Validation)

* Location: `tests/harness_cases/`
* Entry point: `execute_from_input(input: str)`
* Validates:

  * Layered contract structure
  * Determinism (3-run consistency)
  * External system correctness

Run command:

```bash
pytest tests/harness_cases/
```

---

#### Internal Tests (Behavior Validation)

* Location: `system/tests/`
* Entry point: `run_workflow(workflow: dict)`
* Validates:

  * Retry behavior
  * Failure propagation
  * Orchestrator execution logic

Run command:

```bash
pytest system/tests/
```

---

#### Playwright Runtime Survivability Tests

* Location: `frontend/tests/e2e/`
* Entry point: GUI-driven orchestration validation
* Validates:

  * Pause/resume continuity under real runtime execution
  * ACTIVE mutation continuity
  * Retry lineage continuity
  * Recovery/restart continuity
  * Workflow isolation under concurrent execution
  * Projection convergence behavior
  * Hydration/reconnect continuity

Run command:

```bash
npx playwright test frontend/tests/e2e/
```

---

### 2. EXECUTION ORDER

Tests MUST be executed in the following order:

1. Internal tests (behavior validation)
2. Harness tests (contract validation)

Rationale:

* Behavior must be correct before contract validation is meaningful
* Harness assumes correct internal execution

---

### 3. WHEN TO RUN WHICH TESTS

| Change Type                  | Required Tests     |
| ---------------------------- | ------------------ |
| Core pipeline change         | Internal + Harness |
| Orchestrator behavior change | Internal tests     |
| Contract/output change       | Harness            |
| Validation logic change      | Both               |

---

### 4. STRICT RULES

* Harness tests MUST NOT depend on internal state
* Internal tests MUST NOT validate layered contract
* Both test suites MUST pass before system is considered valid
* Playwright runtime survivability tests validate real execution behavior; they complement but do not replace harness or internal tests

---

### 5. DETERMINISM REQUIREMENT

* Harness enforces determinism via repeated execution
* Internal tests may use controlled mocking
* Non-deterministic behavior MUST NOT affect final outputs

## PLANNER OUTPUT VALIDATION

### Purpose

Structural validation of planner output format.

**Scope:**
- JSON structure validation only
- Required field presence checking
- Type validation (no semantic validation)

### Location

`system/orchestrator/planner_output_validator.py`

### Validation Rules

1. **Structural only** — NO mutation of output
2. **Single retry allowed** — on parse failure only
3. **Advisory only** — does NOT block execution
4. **Format enforcement** — checks "steps" key exists

### Validation Flow

```
Planner Output → JSON Valid? → "steps" Key? → Fields Present? → Result
     ↓              ↓              ↓               ↓             ↓
  Invalid       Parse Error    Missing Key    Missing Field    Pass
  → Retry       → Retry        → Fail          → Fail          → Continue
```

### Authority

- Validation is **advisory**
- Governance makes final execution decisions
- Invalid format may trigger:
  - Retry (single attempt)
  - Escalation to user
  - Failure with reason

### Planner-Specific Validation

| Planner | Validation Type | Authority |
|---------|-----------------|-----------|
| Core (deterministic) | Structural | Enforced by parser |
| Orchestrator (LLM) | Structural + Format | Advisory, governance decides |

### Notes

- `planner_validation.py` exists at orchestrator layer
- Validation is NON-BLOCKING for orchestrator planner
- Format enforcement via prompt engineering (not hardcoded)
- Structural errors may trigger parse failure → retry

## CONSTRAINT PIPELINE

Constraint extraction and validation pipeline:

1. User input analyzed
2. LLM extracts format constraints (`_extract_constraints_llm`)
3. Structured LLM extraction supplements (`_extract_constraints_structured`)
4. `execution_result` validated against extracted constraints (`_validate_constraints`)

Outputs:

- `constraint_ok` — boolean: whether execution_result satisfies constraints
- `constraint_violation` — type string: which constraint was violated (if any)
- `extracted_constraints` — dict: the constraints extracted by LLM
- `structured_constraints` — list: additional structured constraint objects

---

## VALIDATOR OUTPUT STRUCTURE

Validator (`evaluate_intent`) returns:

```python
{
    "recommendation": "accept" | "retry",
    "reason": <string>,
    "meta": {
        "llm_semantic_judgment": <"YES" | "NO" | "UNKNOWN">,
        "extracted_constraints": <dict>,
        "structured_constraints": <list>
    },
    "signals": {
        "final_answer_correct": <boolean>,
        "constraint_ok": <boolean>,
        "constraint_violation": <string | None>
    }
}
```

All fields are advisory only.

---

## VALIDATOR SIGNAL LIMITATION

Validator signals are NOT used for:

- retry decisions (governance decides retry from `execution_result`)
- governance decisions (governance is sole decision authority)
- execution modification (execution is locked and unaffected)

They are observational only.

Signals are stored on step metadata and captured in trace for inspection. They do not enter the governance decision path.

## 9. RUNTIME SURVIVABILITY VALIDATION

This section centralizes the authority for orchestration runtime proving, Playwright runtime validation semantics, convergence interpretation, and runtime survivability testing philosophy.

---

### 9.1 PURPOSE

Runtime survivability validation exists to validate orchestration continuity under real runtime conditions — not cosmetic frontend behavior.

**Focus areas:**
- Lifecycle continuity across pause/resume/mutation/retry boundaries
- Convergence behavior (authority → projection → frontend)
- Orchestration safety and runtime coordination
- Workflow isolation under concurrent execution

**What this is NOT:**
- Cosmetic frontend testing
- Replay or event-sourcing validation system
- Architecture authority redefinition
- Lifecycle authority redesign

**Relationship to other validation:**
- Complements harness validation (external contract)
- Complements internal behavior validation (orchestrator logic)
- Does NOT replace either layer

---

### 9.2 PLAYWRIGHT RUNTIME VALIDATION ROLE

Playwright is used **selectively** for runtime execution behavior validation through GUI/runtime interaction.

**Validated surfaces:**
- Pause/resume continuity
- ACTIVE mutation continuity
- Retry lineage continuity
- Recovery/restart continuity
- Workflow isolation under concurrency
- Stale-owner suppression behavior
- Concurrency survivability
- Projection convergence validation
- Hydration/reconnect continuity

**Playwright is NOT:**
- Architecture authority
- Lifecycle authority
- Cosmetic UI testing authority
- Replay validation system

Playwright validates **real runtime execution behavior** by driving the GUI and observing downstream runtime effects. It does not claim authority over any layer.

---

### 9.3 AUTHORITATIVE RUNTIME INTERPRETATION

**Upper Workflow panel** reflects authoritative runtime execution visibility.

**Projection layers** are derived convergence-oriented representations — eventual-consistency layers, NOT authority.

**Temporary projection lag or divergence during the following is LEGAL:**
- Pause
- Resume
- Mutation
- Retry
- Reconnect

Projection corruption or divergence becomes a failure condition **only** when convergence fails persistently.

**Critical rule:** projection `BLOCKED` semantics alone MUST NOT be treated as orchestration failure evidence. BLOCKED is a projection-derived status; the runtime registry holds authoritative lifecycle truth.

---

### 9.4 COOPERATIVE ORCHESTRATION VALIDATION

Execution is **cooperative**, not globally serialized.

**Validated semantics:**
- `execution_generation` provides stale-owner invalidation
- Stale execution owners self-suppress
- ACTIVE mutation coordination is generation-coordinated
- Cooperative pause occurs at execution boundaries
- Active executing steps may complete before pause activates

**Validation principle:** temporary concurrent execution overlap during invalidation/replacement is legal if stale-owner suppression converges correctly.

This confirms the cooperative model is intentional architecture — not a race condition.

---

### 9.5 PLAYWRIGHT EXECUTION EXPECTATIONS

LLM-backed workflows may require long execution windows.

**Timing guidance:**
- Workflow tests may take 30–180 seconds
- SSE/event streams may keep network connections active
- `networkidle` is unreliable for long-running workflow streams
- `domcontentloaded` is preferred over `networkidle`

**Assertion philosophy:**
- Eventual convergence assertions preferred over transient timing assertions
- Authoritative runtime state should be validated before projection convergence
- Slow convergence alone is NOT orchestration failure

---

### 9.6 TEST ISOLATION REQUIREMENTS

Runtime survivability tests should isolate persistence state to prevent cross-test contamination.

**Isolation practices:**
- `memory/active_workflows/` cleanup may be required between tests
- Workflow identity tracking preferred over DOM-count assumptions
- Banner/runtime lifecycle visibility preferred over fragile CSS selectors
- Backend API used where DOM state is not authoritative (e.g., background workflow counts)

---

### 9.7 VALIDATED RUNTIME SURVIVABILITY SURFACES

The following runtime surfaces have been validated through Playwright runtime proving:

- Pause/resume continuity
- ACTIVE mutation continuity
- Retry lineage continuity
- Restart/recovery continuity
- Workflow isolation under concurrent execution
- Stale-owner suppression
- Persistence continuity
- Projection convergence continuity
- execution_generation invalidation
- Cooperative pause boundary semantics

**Important:** these validations provide **runtime confidence**, not permanent proof of correctness. They confirm the orchestration layer behaves safely under observed runtime conditions. They do not constitute formal verification.

---

### 9.8 RUNTIME OBSERVABILITY + DETERMINISTIC VALIDATION

The runtime survivability validation layer now includes deterministic runtime observability surfaces used for orchestration validation and convergence inspection.

These observability surfaces are:

* READ-ONLY
* NON-AUTHORITATIVE
* downstream from runtime authority
* validation/debugging infrastructure only

They do NOT:

* participate in orchestration control flow
* mutate runtime state
* synthesize lifecycle truth
* participate in retry decisions
* act as synchronization authority

The runtime registry remains the sole lifecycle authority.

Projection layers remain non-authoritative derived state.

---

#### Runtime Inspection Endpoints

The system now exposes lightweight runtime inspection endpoints for deterministic survivability validation.

Examples include:

* runtime workflow inspection
* runtime registry inspection
* execution_generation visibility
* retry lineage visibility
* projection metadata visibility

These endpoints exist solely to support:

* orchestration debugging
* deterministic validation
* survivability proving
* convergence inspection

They are NOT orchestration authority surfaces.

---

#### Deterministic Survivability Validation

Runtime survivability validation no longer relies solely on projection inference or GUI timing observation.

Validation may now directly inspect:

* execution_generation invalidation
* stale-owner suppression
* retry lineage continuity
* runtime registry lifecycle state
* projection freshness metadata
* workflow recovery continuity

This materially strengthens runtime survivability proving while preserving the authority hierarchy.

---

#### Runtime Authority Inspection vs Projection Observation

The validation architecture now explicitly distinguishes between:

1. Runtime authority inspection
2. Projection observation
3. GUI rendering validation

Runtime authority inspection validates authoritative orchestration state directly from the runtime registry.

Projection observation validates downstream convergence behavior.

GUI validation validates rendering and interaction behavior only.

This separation prevents projection layers or frontend rendering from being misinterpreted as orchestration authority.

---

#### Architectural Constraints

Observability infrastructure MUST remain:

* read-only
* downstream-only
* non-authoritative
* replay-free

The system does NOT introduce:

* event sourcing
* distributed tracing authority
* replay-driven recovery
* projection-derived lifecycle authority
* frontend-derived orchestration authority

Recovery remains reconstruction-based, not replay-based.
