## Amendment 2026-07-05 — Planner-First Tool-Gated Hybrid Architecture

### 0.1 Accepted architecture realignment

On 2026-07-05, the Planner-First, Tool-Gated Hybrid Architecture was accepted as the target architecture. This amendment applies that decision to capability routing.

### 0.2 Capability routing role (clarified)

- Capability routing is a deterministic closed-form fast path for high-confidence supported domains.
- Capability routing may also act as a tool/profile recommender by emitting profile metadata or narrowing the candidate tool set for the planner and AG1.
- Capability routing is NOT a replacement for planner-first workflow decision authority.
- For non-trivial workflows — especially document Q&A, targeted extraction, multi-step reasoning, and workflows where the route is uncertain — the general planner remains the primary workflow decision-maker.

### 0.3 Planner-first authority preserved

- The planner may accept, modify, or reject capability-emitted candidate workflows.
- The planning compiler and workflow validator remain mandatory gates.
- No capability route may inject a workflow directly into execution.
- No capability route may own execution_result truth, lifecycle truth, or governance decisions.

### 0.4 Tool/profile gating alignment

- Scoped tool/profile catalogs for planner and AG1 will be defined in `TOOL_PROFILE_GATING_CONTRACT_V1`.
- Capabilities may recommend a profile but may not grant a broader tool set than the profile allows.
- AG1 remains the only active runtime tool-selection agent for now.

### 0.5 Document Q&A quarantine

- `semantic_transform` `answer_question` and related Slice 007 document Q&A behavior are NOT approved under this contract.
- Capabilities must not emit workflows that rely on the rejected Q&A behavior.
- Multi-document Q&A is deferred to Sprint 15+.
- Evidence-backed single-document Q&A may be opened as a bounded future Sprint 11 MVP only after quarantine and tool-profile plumbing are stable.

### 0.6 No new autonomous agents

This amendment does not introduce new autonomous agents. AG1 remains the only active runtime tool-selection agent.

## 1. Purpose

This contract governs capability routing before general planning.

It allows high-confidence supported domains to be routed to bounded capability normalizers/compilers.

It does not grant capabilities execution, lifecycle, governance, projection, persistence, or learning authority.

Capability routing is an advisory, pre-runtime classification and normalization layer. It narrows the planning search space for known domains without replacing the general planner, the runtime, or any existing authority.

---

## 2. Core Architecture Decision

The first proposed model is:

```text
centralized capability_router / capability_registry
```

This model is intentionally not named:

```text
agent_index
agent_orchestrator
multi_agent_router
agent_scheduler
```

Reason:

```text
Capability routing is not autonomous multi-agent orchestration.
```

The router is a deterministic, bounded pre-planner gate. The registry is a metadata/lookup/factory surface. Neither is an agent. Neither owns execution. Neither coordinates agents autonomously.

---

## 3. Authority Boundary

### 3.1 What the capability router MAY do

- classify supported prompt domains
- route high-confidence prompts
- reject unsupported routes
- fall back to general planner
- attach route metadata
- call bounded capability normalizers/compilers

### 3.2 What a capability MAY do

- normalize domain-specific semantics
- emit candidate workflow/DAG structure
- declare explicit dependencies
- declare expected outcomes
- constrain allowed tool families / allowed tools
- attach capability metadata for observability and downstream tool narrowing

### 3.3 What the router / capabilities MAY NOT do

- execute tools
- bypass system_entry
- bypass planning compiler
- bypass workflow validator
- bypass governance
- bypass lifecycle authority
- mutate runtime registry
- mutate projection
- mutate persistence
- own execution_result truth
- create lifecycle truth
- coordinate agents autonomously
- activate learning/adaptation
- silently rewrite user intent
- perform hidden contained execution in Phase 1

Any violation of the MAY NOT list requires immediate escalation to SA and is outside the scope of this contract.

---

## 4. Relationship to Existing Authority Model

This contract references and preserves the following existing rules without modifying them:

- Lifecycle Authority owns lifecycle truth.
- Governance owns runtime decisions.
- Runtime Registry owns execution coordination state.
- system_entry remains sole execution gateway.
- Projection/frontend remain non-authoritative.
- execution_result remains execution truth.
- Planning compiler remains deterministic pre-runtime repair/normalization layer.
- Workflow validator remains final schema/DAG/safety gate before runtime.
- Learning/adaptation remains deferred until separately activated.

Capability routing is additive only. No existing authority boundary is moved, weakened, or shared.

---

## 5. Route Lifecycle and Route Outcomes

### 5.1 Defined route outcomes

```text
ROUTE_ACCEPTED
ROUTE_FALLBACK_TO_PLANNER
ROUTE_REJECTED_UNSUPPORTED
ROUTE_BLOCKED_UNSAFE
ROUTE_ERROR
```

### 5.2 Behavior per outcome

- **High-confidence supported route** may emit candidate workflow/DAG.
- **Low-confidence route** must fall back to general planner.
- **Mixed-domain prompt** must fall back unless the capability explicitly supports mixed-domain routing.
- **Unsafe route** must block or fall back depending on risk.
- **Route errors** must fail safe (fall back to planner or block, never proceed with unvalidated candidate workflow).

A route decision is advisory. The runtime is not required to honor a ROUTE_ACCEPTED outcome if downstream validation rejects the candidate workflow.

---

## 6. Conditions for Skipping plan_workflow

A capability may skip `plan_workflow` only if ALL of the following are true:

1. Route is high-confidence.
2. Domain is explicitly supported by contract or proposed registry metadata.
3. Domain normalizer/compiler is deterministic for the route.
4. Capability emits explicit candidate workflow/DAG.
5. Candidate workflow conforms to step schema.
6. Candidate workflow preserves original user intent.
7. Candidate workflow declares dependencies explicitly.
8. Candidate workflow is passed to planning compiler.
9. Candidate workflow is passed to workflow validator.
10. Runtime handoff happens only through the existing orchestrator/runtime path.
11. Tool execution happens only through system_entry.
12. Route metadata is visible for debug/audit.

If any condition is not satisfied, the router must fall back to `plan_workflow`.

---

## 7. Mandatory Compiler/Validator Handoff

This is non-negotiable:

```text
capability output
-> planning compiler
-> workflow validator
-> runtime handoff
```

No route may bypass the planning compiler.
No route may bypass the workflow validator.
No route may inject a candidate workflow directly into the execution loop.

The planning compiler may apply deterministic repairs to capability-emitted workflows exactly as it does to planner-emitted workflows. The workflow validator may reject capability-emitted workflows exactly as it rejects planner-emitted workflows. This symmetry is intentional and required.

`capability_registry` is defined as a metadata/lookup/factory surface only.

### 8.1 Allowed registry fields

```text

allowed_tool_families
allowed_tools

```

### 8.2 Registry MAY NOT

```text
own lifecycle
own execution
own governance
own persistence
own projection
own learning
coordinate agents
schedule execution
```

The registry is a read-only configuration surface at runtime. It does not execute code, manage state, or make dynamic decisions beyond the bounded policies defined in its entries.

## 9. Capability Router

`capability_router` responsibilities:

- consume user prompt and task classification result
- evaluate registered capabilities
- select at most one initial route in Phase 1
- return route decision
- return fallback decision
- return route metadata
- call capability only after route accepted

### 9.1 Phase 1 limitation

Phase 1 must not support autonomous multi-capability coordination.

A single prompt is evaluated against registered capabilities. At most one capability normalizer/compiler is invoked. Chained or mixed-capability routing is explicitly out of scope for Phase 1 and requires a separate contract amendment.

## 10A. Read-Only Document / Local-File Capability

The `document_local_read` is recorded as a proposed bounded capability domain in this draft.

### 10A.1 Capability identity

```text
capability_id: document_local_read
capability_name: Read-Only Document / Local-File Capability
domain: document_local_read
route_type: deterministic_preplanner
```

### 10A.2 Purpose

This capability supports deterministic pre-runtime routing for high-confidence read-only local-file/document intents where the user provides explicit local file/folder/path/pattern literals.

It exists to avoid routing simple local read/list requests through broad general planning when the intent is clear, while preserving all runtime, governance, validation, path-safety, and system_entry authority boundaries.

### 10A.3 What the capability MAY own

- read/show/open/display the contents of a specific explicitly named local file
- summarize a specific explicitly named local file
- list files in a specific explicitly named local folder
- emit explicit candidate workflow/DAG structure
- declare explicit depends_on relationships
- attach capability metadata for observability and tool narrowing
- narrow allowed tools to proposed read-only file tools and finalize_output

Deferred until after first-slice validation (unless Head Dev separately expands scope):
- grep/search within files using an explicit query or pattern
- glob/list matching files using an explicit pattern
- compare or summarize multiple explicitly named files only when all files are explicit and dependency construction is deterministic

### 10A.4 First implementation slice restriction

The first implementation slice is limited to:

```text
read_file
list_files
finalize_output
```

First-slice allowed deterministic DAG shapes:

```text
read_file -> finalize_output
read_file -> summarize/finalize_output
list_files -> finalize_output
```

Deferred until after first-slice validation (unless Head Dev explicitly expands scope):

```text
grep -> finalize_output
glob -> finalize_output
read_file A + read_file B -> finalize_output compare/summarize
```

Reason: grep/glob and multi-file workflows increase pattern-safety, dependency, and ambiguity risk. They are allowed by this amendment as future bounded extensions, but should not be included in the first implementation slice unless Head Dev explicitly expands scope.

### 10A.5 Allowed tools

First implementation slice allowed tools:

### 10A.8 Fallback requirements

The capability must fall back to the general planner for:

- ambiguous "the file" / "that file" with no explicit file context
- vague project exploration such as "find the best file"
- broad project exploration
- read + write/edit/update/delete in the same request
- any file mutation request
- external file/source/web/API requests
- semantic judgement over unknown file sets
- multi-step project refactor
- mixed-domain prompts such as file + web, file + email, file + arithmetic, file + calendar
- unsupported file/document operations
- low-confidence or partial matches
- prompts where the local path/folder/file literal cannot be preserved exactly

Fallback means `ROUTE_FALLBACK_TO_PLANNER`.

Unsafe mutation or sensitive-path cases may instead block safely with `ROUTE_BLOCKED_UNSAFE` if the router can determine the route is unsafe without executing tools.

### 10A.9 Literal preservation requirements

```text

```

The capability must not rewrite, normalize, infer, shorten, expand, autocorrect, or "clean up" file paths before tool execution.

The capability may copy exact literals into candidate workflow step inputs.

Path safety remains enforced by existing path validation and system_entry/tool handlers.

### 10A.10 Path safety requirements

The capability must rely on existing path safety enforcement and may not weaken it.

Requirements:

- base-dir confinement remains enforced by path_validator/system_entry/tool handlers

- sensitive-path denylist remains enforced
- sensitive filename blocking remains enforced
- empty/null paths remain blocked
- capability output must still pass planning compiler and workflow validator
- tool execution remains through system_entry only

Explicit rule:

```text
Capability routing approval is not path-access approval.
A route decision must never be interpreted as permission to bypass path safety, privacy, user-control, or tool-level validation.
```

## 12. Tool Narrowing / Allowlists

A capability may constrain allowed tool families / allowed tools.

Tool selection may only choose inside the capability-proposed candidate set.

Wrong-family tool selection must fail safe before system_entry.

### 12.1 Mechanism

The capability may attach `allowed_tool` or `allowed_tool_families` metadata to the candidate workflow or to individual steps. Downstream tool selection (AG1) must respect this constraint. If AG1 proposes a tool outside the allowed set, the proposal must be rejected before `system_entry` is invoked.

### 12.2 Fail-safe rule

If tool narrowing metadata is present and the selected tool violates it, the step must block with reason `tool_not_in_capability_allowlist` rather than proceed.

## 13. Global Guard Ownership

This section documents which existing global safety mechanisms remain global and which arithmetic-specific semantics move into arithmetic capability ownership.

### 13.1 Global safety that should remain global

- dependency preservation through resolver
- validator rejection of malformed depends_on
- validator rejection of self/future/nonexistent dependencies
- validator rejection of structurally under-declared explicit references
- validator rejection of unsafe ambiguity in emitted workflow structure
- final validation before runtime handoff

These mechanisms are domain-agnostic and must continue to protect all workflows regardless of origin (planner or capability).

### 13.2 Arithmetic semantics that should move into arithmetic capability ownership

- "the result" / "that result" meaning inside arithmetic chains
- bare continuation math operations
- arithmetic branch starts
- independent arithmetic branch handling
- arithmetic plural-reference resolution where deterministic
- math-specific final numeric formatting
- math-specific tool-family narrowing

The arithmetic capability owns deterministic normalization of these semantics into explicit DAG structure. It does not own validation; validation remains the workflow validator's authority.

### 14.2 Visibility requirements

- Route metadata must be present in workflow trace.
- Route metadata must be present in execution history events where feasible.
- Route metadata must be debug-log visible.

Hidden routing (routing decisions not recorded, route metadata stripped, or capability origin obscured) is prohibited.

## 15. Learning Boundary

```text
Learning/adaptation must not consume capability-routing outcomes until a separate learning contract is accepted.
```

Learning may only use validated successful route/tool/capability outcomes after explicit learning contract approval.

Failed, ambiguous, blocked, validator-repaired, or false-success routes must not be learned as success.

Capability routing outcomes are explicitly quarantined from learning/adaptation consumption until:
- capability routing is stable and validated,
- A separate learning contract is accepted, and
- An explicit learning activation milestone is reached.

## 16. Non-Goals

This contract explicitly rejects the following:

```text
- autonomous multi-agent orchestration
- persistent agent identity
- agent-to-agent communication
- adaptive runtime orchestration
- hidden subplan execution in Phase 1
- lifecycle/governance/projection/system_entry authority changes
- learning/adaptation activation
- direct tool execution from capabilities
- frontend authority
```

Any proposal introducing any of the above requires a new contract and SA escalation.
