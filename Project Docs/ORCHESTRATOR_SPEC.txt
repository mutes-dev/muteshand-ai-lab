# 🧠 AI LAB — ORCHESTRATOR SPEC (v1.0)

---

## 1. PURPOSE

This document defines the **Orchestrator (HAND) Layer**.

The Orchestrator (HAND) sits ABOVE the execution pipeline and is responsible for:

* Goal interpretation
* Workflow creation
* Step orchestration
* State management
* Failure handling
* Controlled adaptation
* Agent coordination

---

## 2. SYSTEM POSITION

```
User Goal
↓
Orchestrator (THIS LAYER)
↓
Workflow Engine
↓
Agents
↓
Execution Engine (existing system)
```

---

## 3. ORCHESTRATOR (HAND) PRINCIPLE

The Orchestrator (HAND) operates under **Controlled Autonomy**:

* The Orchestrator (HAND) executes tasks independently
* The Orchestrator (HAND) adapts within strict boundaries
* The Orchestrator (HAND) escalates when required
* The user retains ultimate control

The Orchestrator includes a governance function responsible for:

* ensuring alignment with the original goal
* resolving conflicting outputs
* determining safe continuation, adjustment, or escalation

---

## 6. EXECUTION LOOP (ORCHESTRATOR)

The Orchestrator controls execution using a deterministic loop:

```
WHILE workflow not complete:

    SELECT next PENDING step

    SET step → RUNNING

    CALL assigned agent

    IF success:
        SET step → COMPLETE
        STORE output

    IF failure:
        INCREMENT retries

        IF retries < max_retries:
            RETRY step

        ELSE:
            ATTEMPT adaptation

            IF adaptation succeeds:
                CONTINUE

            ELSE:
                SET step → BLOCKED
                ESCALATE to user
                STOP workflow
```

---

## 7. FAILURE POLICY (CONTROLLED AUTONOMY)

### Stage 1 — Retry

* Retry failed step automatically
* Use same strategy
* Limited attempts (default: 3)

---

### Stage 2 — Adaptation

Triggered after retries exhausted.

Allowed actions:

* Agent suggests alternative approach
* Orchestrator (HAND) may:

  * retry with modified input
  * switch agent
  * adjust execution method

---

### Stage 3 — Escalation

If adaptation fails:

* Step marked as BLOCKED
* Workflow paused
* User notified
* Await instruction

---

## 8. ADAPTATION MODEL

### Rule

Agents may **suggest**, but may NOT modify the workflow.

---

### Flow

```
Agent → Suggest change
Orchestrator (HAND) → Evaluate suggestion
Orchestrator (HAND) → Accept / Reject / Escalate
```

---

### Constraints

* Agents cannot:

  * reorder steps
  * modify workflow structure
  * override system decisions

* Orchestrator (HAND) is the ONLY authority that may modify workflows

---

## 9. CONTROL MODEL

### Ownership

| Component          | Responsibility                |
| ------------------ | ----------------------------- |
| Orchestrator (HAND) | Workflow ownership, decisions |
| Agents             | Execution + suggestions       |
| User               | Final authority               |

---

### Rules

* Orchestrator (HAND) MUST control all workflow changes
* Agents MUST NOT control system flow
* User MAY override at any time

---

## 10. AGENT INTERACTION

Agents:

* Receive step input
* Execute task via execution engine
* Return:

  * success / failure
  * output
  * optional suggestions

Agents do NOT:

* control workflow
* manage retries
* handle state transitions

### Parallel Output Handling

When multiple agents execute in parallel:

* each produces an independent output
* outputs MUST NOT be merged

The Orchestrator MUST:

* select one output
* OR create a resolution step
* OR escalate to the user

---

## LLM INTERACTION (CONSTRAINT)

Agents or orchestrator MAY use LLMs for:

- planning suggestions
- adaptation proposals

BUT:

- LLM output MUST NOT bypass validation
- LLM MUST NOT control workflow state
- LLM MUST NOT modify workflow directly

All LLM outputs are advisory only.
Orchestrator (HAND) remains authoritative.
LLM output is NON-AUTHORITATIVE and may be overridden.

* LLM outputs are NON-AUTHORITATIVE
* LLM does NOT determine execution truth
* LLM does NOT control workflow state

---

## 10A. VALIDATOR ROLE

Validator provides advisory signals only.

* It may recommend retry or escalation
* It does NOT enforce final decisions
* Final decisions are made by the Orchestrator within system constraints

---

## 11. FINAL OUTPUT RESOLUTION

The final output is determined by the Orchestrator (HAND) based on validated execution results.

Resolution priority:

1. If a step produces a valid, contract-compliant result aligned with the goal:
   → that step output becomes the final output

2. If multiple candidate outputs exist:
   → Orchestrator MUST:
      - select the output best aligned with the goal
      - OR create a new resolution step
      - OR escalate to the user

3. If no valid result exists:
   → return failure or escalate

Rules:

- Outputs MUST NOT be merged or synthesized
- Final output MUST be traceable to a single execution path
- Orchestrator determines which output is final, but does NOT alter execution truth

---

## 12. SUPERVISOR MODEL (OPTIONAL)

The Orchestrator (HAND) may invoke a Supervisor model for:

* plan improvement
* failure analysis
* output validation
* strategy adjustment

---

### Constraints

* Supervisor is NOT an agent
* Supervisor does NOT execute tasks
* Supervisor does NOT override Orchestrator (HAND)

---

## 13. PERSISTENCE (MANDATORY)

Workflows MUST be persisted:

* after each step completion
* after each state change

---

### Purpose

* crash recovery
* resume capability
* auditability
* debugging

---

## 14. RESUME LOGIC

On system restart:

* LOAD workflow state
* IF step was RUNNING → mark FAILED
* CONTINUE from last valid state

---

## 15. USER CONTROL

User may:

* pause workflow
* resume workflow
* cancel workflow
* override decisions

---

## 16. SYSTEM BEHAVIOR

Default behavior:

* Orchestrator (HAND) autonomous execution
* Silent retries
* Controlled adaptation

Escalation behavior:

* Notify user only when necessary
* Provide clear failure context

---

## 17. HARD RULES

* Workflows MUST be stateful
* Execution MUST be resumable
* No step may execute without state tracking
* No silent failures allowed
* No agent may modify workflow structure
* All changes MUST be traceable
* Orchestrator (HAND) controls all workflow changes
