# 🧠 AI LAB — ORCHESTRATOR SPEC (v1.0)

---

## 1. PURPOSE

This document defines the **Orchestrator (HAND) Layer**.

The Orchestrator (HAND) sits ABOVE the execution pipeline and is responsible for:

* Goal interpretation
* Workflow creation
* Step orchestration
* State management
* Failure handling
* Controlled adaptation
* Agent coordination

---

## 2. SYSTEM POSITION

```
User Goal
↓
Orchestrator (THIS LAYER)
↓
Workflow Engine
↓
Agents
↓
system_entry (execution boundary)
↓
Core Pipeline (deterministic execution)
```

---

## 3. ORCHESTRATOR IS NON-DETERMINISTIC (PLANNING LAYER)

Orchestrator uses LLM for planning and tool selection.

Expected behavior:

* Same input may produce different tool selections
* Retry loops may converge or diverge
* Output quality varies by LLM response
* Core pipeline remains deterministic regardless of orchestrator output

This is ACCEPTED and EXPECTED.

---

## 4. DETERMINISM

Orchestrator layer is NOT deterministic.

Retry behavior, tool selection, and convergence are LLM-dependent.

Only guaranteed determinism:

* Core validation layer (structure)
* Core execution layer (result correctness)
* Orchestrator controls but does not compromise deterministic core.

## 7. EXECUTION LOOP (ORCHESTRATOR)

The Orchestrator controls execution using a deterministic loop:

```
WHILE workflow not complete:

    SELECT next PENDING step

    SET step → RUNNING

    CALL assigned agent

    IF success:
        SET step → COMPLETE
        STORE output

    IF failure:
        CALL governance.decide_next_action(...)

        IF decision == "retry":
            INCREMENT retries
            RETRY step

        IF decision == "fail":
            IF retries >= max_retries:
                SET step → BLOCKED
            ELSE:
                SET step → FAILED
            STOP workflow

        IF decision == "complete":
            CONTINUE
```

Execution includes validation and enforcement of execution through system_entry.

---

## 8. FAILURE POLICY (CONTROLLED AUTONOMY)

### Stage 1 — Retry

* Retry failed step automatically
* Use same strategy
* Limited attempts (default: 3)

---

### Stage 2 — Adaptation

Triggered after retries exhausted.

Allowed actions:

* Agent suggests alternative approach
* Orchestrator (HAND) may:

  * retry with modified input
  * switch agent
  * adjust execution method

---

### Stage 3 — Escalation

If adaptation fails:

* Step marked as BLOCKED
* Workflow paused
* User notified
* Await instruction

---

## 9. ADAPTATION MODEL

### Rule

Agents may **suggest**, but may NOT modify the workflow.

---

### Flow

```
Agent → Suggest change
Orchestrator (HAND) → Evaluate suggestion
Orchestrator (HAND) → Accept / Reject / Escalate
```

---

### Constraints

* Agents cannot:

  * reorder steps
  * modify workflow structure
  * override system decisions

* Orchestrator (HAND) is the ONLY authority that may modify workflows

---

## 10. CONTROL MODEL

### Ownership

| Component          | Responsibility                |
| ------------------ | ----------------------------- |
| Orchestrator (HAND) | Workflow ownership, decisions |
| Agents             | Execution + suggestions       |
| User               | Final authority               |

---

### Rules

* Orchestrator (HAND) MUST control all workflow changes
* Agents MUST NOT control system flow
* User MAY override at any time

---

## 11. VALIDATOR ROLE

Validator provides advisory signals only (by design).

* Structural validation: mandatory (pass/fail)
* Semantic validation: advisory (retry/accept recommendation)
* Does NOT enforce final decisions
* ⚠️ May influence retry indirectly (behavioral drift — NOT intended architecture)

Final decisions are made by Governance within system constraints.

---

## 12. FINAL OUTPUT RESOLUTION

The final output is determined by the Orchestrator (HAND) based on validated execution results.

Resolution priority:

1. If a step produces a valid, contract-compliant result accepted by governance:
   → that step output becomes the final output

2. If multiple candidate outputs exist:
   → Orchestrator MUST:
      - select the output contract-compliant and accepted by governance
      - OR create a new resolution step
      - OR escalate to the user

3. If no valid result exists:
   → return failure or escalate

Rules:

- Outputs MUST NOT be merged or synthesized
- Final output MUST be traceable to a single execution path
- Orchestrator determines which output is final, but does NOT alter execution truth
- Final output MUST originate from execution_result.
- No synthesis or multi-source resolution is allowed.

---

## 13. SUPERVISOR MODEL (OPTIONAL)

The Orchestrator (HAND) may invoke a Supervisor model for:

* plan improvement
* failure analysis
* output validation
* strategy adjustment

---

### Constraints

* Supervisor is NOT an agent
* Supervisor does NOT execute tasks
* Supervisor does NOT override Orchestrator (HAND)

---

## 14. PERSISTENCE

**CURRENT IMPLEMENTATION: PARTIAL**

Workflows are persisted only when status = COMPLETED.

* Only COMPLETED workflows are saved to memory/workflows.json
* Active/running workflows are NOT persisted
* This is a known limitation — see KNOWN_ISSUES.txt

Planned future behavior:
* after each step completion
* after each state change

---

### Purpose

* crash recovery
* resume capability
* auditability
* debugging

---

## 15. RESUME LOGIC

**STATUS: NOT IMPLEMENTED**

Current system does NOT support resume on restart.

Planned future behavior:
* LOAD workflow state
* IF step was RUNNING → mark FAILED
* CONTINUE from last valid state

---

## 16. USER CONTROL

**STATUS: NOT IMPLEMENTED**

Current system does NOT support user intervention during workflow execution.

Planned future behavior:
* pause workflow
* resume workflow
* cancel workflow
* override decisions

---

## 17. SYSTEM BEHAVIOR

Default behavior:

* Orchestrator (HAND) autonomous execution
* Silent retries
* Controlled adaptation

Escalation behavior:

* Notify user only when necessary
* Provide clear failure context

---

## 18. HARD RULES

* Workflows MUST be stateful
* Execution MUST be resumable
* No step may execute without state tracking
* No silent failures allowed
* No agent may modify workflow structure
* All changes MUST be traceable
* Orchestrator (HAND) controls all workflow changes

---

## 19. DESIGN PRINCIPLES

* Control over chaos
* Determinism over guesswork
* Adaptation within boundaries
* Separation of concerns
* Persistence over re-execution
* Transparency over hidden logic

---

## 20. SYSTEM GOAL

To enable:

* long-running autonomous workflows
* controlled self-improvement
* scalable multi-agent coordination
* reliable recovery from failure
