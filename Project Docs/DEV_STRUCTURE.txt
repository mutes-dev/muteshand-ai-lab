# AI LAB — DEVELOPMENT STRUCTURE (LOCKED)

---

## CORE PRINCIPLE

Development is CONTROLLED, LAYERED, and HIERARCHICAL.

There is ONE source of truth:

→ ARCHITECTURE + HAND_ARCHITECTURE + ARCHITECTURE_LAW

All roles exist to PROTECT this.

---

# DOCUMENT CONTROL SYSTEM (MANDATORY)

The system is document-driven.

The following documents control development:

* ARCHITECTURE.txt → system design
* HAND_ARCHITECTURE.txt → system design
* ARCHITECTURE_LAW.txt → enforcement rules
* SYSTEM_STATE.txt → real system state (merged from CONTEXT.txt and CURRENT_PHASE_SPEC.txt)
* ROADMAP_MASTER.txt → long-term phases
* ROADMAP_ACTIVE.txt → current execution
* SYSTEM_CONTRACTS.txt → behavior definitions
* HARNESS_SPEC.txt → validation authority
* VALIDATION_ARCHITECTURE.txt → validation system design

Documents define intent. System (code + harness) defines current truth.

# ROLE DEFINITIONS

---

## 🧑‍💼 USER (OWNER)

ROLE:

* Final authority over system direction
* Provides goals, priorities, and constraints
* Owns architecture files and approvals

RESPONSIBILITIES:

* Provide clear objectives
* Approve architecture changes
* Trigger development tasks
* Review high-level outcomes

MUST NOT:

* Write or modify code directly inside system layers
* Override architecture impulsively
* Skip control layers (Head Dev)

---

## HEAD DEV (ARCHITECT / VALIDATOR)

ROLE:

* Owns system architecture
* Makes ALL technical decisions
* Defines tasks and system evolution
* Validates ALL Windsurf outputs
* Enforces execution discipline directly

RESPONSIBILITIES:

* Maintain ARCHITECTURE.txt and ARCHITECTURE_LAW.txt
* Define WHAT needs to be built or fixed
* Classify issues (P0 vs non-P0)
* Prevent architectural drift
* Design minimal, controlled changes
* Update ROADMAP_ACTIVE before any task
* Update CONTEXT after system changes
* Ensure all tasks align with SYSTEM_CONTRACTS
* Ensure every task is testable via HARNESS_SPEC

MUST:

* Think in systems, not code
* Enforce layer boundaries
* Avoid assumptions (audit when needed)

MUST NOT:

* Write code directly
* Skip validation of system understanding
* Allow cross-layer logic
* Delegate validation to external reviewers

---

## WINDSURF_EXECUTION_TEMPLATE (ONLY EXECUTION INTERFACE)

**Purpose:**
Structured prompt template for controlled code execution.

**Location:** Used by Head Dev to communicate with Windsurf

**Characteristics:**
- Strict task boundaries
- Explicit allowed/forbidden operations
- Validation requirements
- Report format specifications

**Process:**
1. Head Dev prepares execution template
2. Windsurf receives template via context
3. Windsurf executes ONLY as specified
4. Windsurf returns structured report
5. Head Dev validates against architecture

**Authority:**
- Windsurf has NO autonomy outside template
- Windsurf MUST NOT self-modify template
- Head Dev validates ALL outputs

---

## WINDSURF (EXECUTOR)

ROLE:

* Executes code changes ONLY

RESPONSIBILITIES:

* Read files
* Modify code
* Create files
* Run tests
* Return structured reports

MUST:

* Follow instructions EXACTLY
* Make minimal changes only
* Report ALL changes explicitly

MUST NOT:

* Think architecturally
* Redesign systems
* Add extra features
* Make assumptions
* Perform uncontrolled refactors
* Introduce execution before validation gates
* Allow invalid inputs to reach execution

# ENTRY LAYER CONSTRAINTS (Violation 1.1 Resolution)

Entry is PURE orchestration and MUST NOT perform transformation.

The Orchestrator (HAND) operates above system_entry and does not belong to the core execution pipeline.

- controls execution flow
- coordinates agents and steps
- executes governance decisions only
- operates within SYSTEM_CONTRACTS and ARCHITECTURE_LAW constraints

Orchestrator MUST NOT independently decide retry, continuation, or failure.  
All such decisions originate from governance.

Governance decisions MUST be based solely on execution_result.

It does NOT override validation or execution truth.

Structural logic belongs ONLY to:

* Resolver (construction)
* Validation (enforcement)

Entry MUST NEVER perform data transformation.

* Receive plan
* Pass to validation
* Pass to execution (if validation succeeds)
* Normalize final output

NO structural modification allowed.

# DECISION FLOW

Architecture decisions:
→ Head Dev (approved by User if major)

→ NONE (must follow instructions exactly)

Any ambiguity:
→ STOP → escalate to Head Dev

---

# FAILURE HANDLING

If ANY of the following occur:

* unexpected code changes
* architectural violations
* hidden logic
* scope expansion

Then:

→ Head Dev MUST reject and redefine task

⚠️ DRIFT ESCALATION RULE

If system behavior contradicts:

* ARCHITECTURE_LAW
* ORCHESTRATOR_CONTRACT

Then:

→ MUST be documented BEFORE fix
→ MUST NOT be silently corrected

# DEVELOPMENT RULES

1. NEVER skip layers of control
2. NEVER allow Windsurf autonomy
3. NEVER modify architecture during implementation
4. ALWAYS validate before approving
5. ALWAYS prefer small, testable changes
