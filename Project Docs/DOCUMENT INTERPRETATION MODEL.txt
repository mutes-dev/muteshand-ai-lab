### 10.1 Replay vs Recovery Semantics

Recovery is NOT replay.

* **Recovery** restores authoritative runtime state from persistence or reconstruction
* **Replay** creates a NEW execution identity
* **Retry** is a NEW execution attempt, NOT a continuation of a terminated execution
* Recovery MUST NOT automatically replay execution
* Replay MUST NOT resurrect a terminated execution
* Reconstruction restores authoritative runtime state WITHOUT creating new execution lineage

Per EXECUTION_IDENTITY_AND_REPLAY_CONTRACT_V1:
- replay is explicit-only, never automatic
- retry generates new execution identity
- reconstruction and replay are semantically distinct

Per SYSTEM_CONVERGENCE_AND_RECOVERY_CONTRACT_V1:
- recovery converges to authoritative lifecycle state
- recovery does NOT replay execution
- stale-state quarantine prevents stale persistence from overwriting authority

### Planning Recovery vs Replan Semantics

Planning Request Recovery is distinct from runtime Recovery, Replay, Retry, and Reconstruction.

* Recovery restores authoritative runtime/lifecycle state
* Replay creates new execution identity
* Retry creates new step/workflow execution attempt
* Replan creates a new planning attempt from persisted planning intent
* Replan MUST NOT be interpreted as planner thread resurrection
* Persisted QUEUED shell does NOT prove live planning
* Stale bg_id does NOT prove runtime recoverability
* Original prompt/user intent SHOULD be preserved once accepted

Reference:
PLANNING_RECOVERY_AND_REPLAN_CONTRACT_V1.txt

### Cancellation Semantics

Cancellation is distinct from failure.

Per WORKFLOW_CANCELLATION_AND_TERMINALIZATION_CONTRACT_V1.txt:

- CANCELLED represents intentional operator terminalization
- FAILED represents execution failure
- CANCELLED workflows are immutable terminal states
- CANCELLED workflows MUST NOT be replayed automatically
- retry semantics apply to FAILED execution recovery, not intentional cancellation

Cancellation preserves historical chronology and governance truth.

## 18. FALSE POSITIVE DRIFT PREVENTION

The following phenomena are NOT automatic drift:

* Eventual consistency lag
* Temporary projection divergence
* Observability gaps
* UX ambiguity
* Execution visibility gaps
* Advisory semantic limitations
* Transport timing windows
* Cache divergence
* Future-state architecture not yet implemented
* Implementation binding references inside contracts
* Accepted operational limitations
* Bounded agent infrastructure without persistent identity (stateless tool-selection is correct AG1 posture)
* Single-agent topology without multi-agent coordination (multi-agent is outside AG1 scope)
* Agent behavior boundaries not yet implementation-audited (AGENT_CONTRACT_V1.txt defines boundaries; implementation audit is a gap, not drift)
* Lack of dedicated agent governance subdomain (general signal hierarchy provides sufficient containment)
* Absence of agent lifecycle/identity model (stateless agents have no lifecycle; this is correct AG1 posture)
* Persisted QUEUED shell without live planner/runtime/stream may be valid replan-required state, not necessarily lifecycle corruption
* Missing projection for QUEUED_REPLAN_REQUIRED is not automatically projection drift
* Lack of planner thread recovery is not drift if replan semantics are implemented
* BLOCKED caused by max_iterations_exceeded is not automatic FAILED drift
* Non-terminal BLOCKED projection for runtime no-progress ceiling is correct behavior

**DRIFT EXISTS ONLY WHEN:**

* Explicit contract semantics are violated
* Authority ownership becomes ambiguous
* Lifecycle truth becomes synthesized outside authority
* Convergence direction is violated
* Sequencing legality is violated
* Mutation legality is violated
* Authoritative runtime truth is bypassed
* Semantic systems override execution_result
* Agents claim lifecycle, execution, or mutation authority
* Distributed orchestration topology emerges without SA escalation
* Adaptive orchestration is operationalized without SA escalation
* Agent outputs bypass governance decision flow

**CLASSIFICATION RULE:**

Before classifying any finding as drift:

1. Verify an explicit contract semantic is violated
2. Verify authority ownership is ambiguous or merged
3. Verify lifecycle truth is synthesized outside its authority
4. Verify convergence direction is upward or bidirectional
5. Verify sequencing legality is violated
6. Verify mutation legality is violated
7. Verify authoritative runtime truth is bypassed

If NONE of the above apply, the finding is NOT drift.

Document it as:
- temporary divergence
- observability gap
- UX limitation
- future-state gap
- accepted operational limitation

**PURPOSE:**

This section is CRITICAL for audit safety. It prevents:
- False-positive drift escalation
- Architecture downgrading to match bugs
- Future-state requirements being treated as current defects
- Observability gaps being treated as authority violations
