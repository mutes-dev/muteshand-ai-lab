> a well-engineered orchestration/runtime platform

toward:

> an intelligent, memory-backed, adaptive, agent-capable, user-controlled AI product.

- deterministic runtime authority
- governance supremacy

# 1. EXECUTIVE ROADMAP VERDICT

## 1.1 What OPERATIONAL_ROADMAP_V1 got right

V1 correctly stabilized the core runtime and stopped architecture drift. It established:
- single lifecycle authority
- governance-owned retry/failure/escalation
- projection-only frontend rendering
- retry/recovery legality
- Task Hub / History separation
- FAILED actionability metadata
- backend instance identity guard
- memory storage/API/GUI/trace/guardrail foundation
- AG1 bounded containment and debug attribution visibility
- SSE event-hint transport without giving transport authority

This was necessary foundational work. The runtime is structurally coherent, bounded, and far safer than earlier versions.

## 1.2 Where V1 drifted

V1 drifted by treating architecture stabilization and operational hardening as the main path of progress while the product-facing intelligence layer remained mostly missing.

The audits show that the system is still not a useful AI product in the SYSTEM_GOALS_V2 sense because:
- memory is stored but not used at runtime
- learning writes but does not read back into behavior
- AG1 is only a bounded tool selector
- tool coverage is too narrow for real workflows
- approval UX is terminal-only
- notifications do not reach the frontend
- user override / force execution was removed without replacement
- privacy/sensitivity enforcement is absent
- purpose validation is not operational
- drift detection does not correct or escalate
- operator-facing UX remains engineering-heavy
- sandbox/self-improvement has no activation milestone

V1 preserved architecture; V2 must now activate product capability.

## 1.3 What the audits proved

The Functional Product Gap Audit proved the system is architecturally aligned but functionally incomplete. It estimated overall SYSTEM_GOALS_V2 functional completion at roughly 22%, with runtime/orchestration far ahead of memory, learning, agents, privacy, and self-improvement.

The Performance Audit proved current scaling is moderate for single-operator use, but the reported trivial-prompt latency path was not explained and must not be hand-waved. PERF-036 has now been measured: LLM calls dominate warm/cold trivial-prompt latency. Raw threading overhead was not the primary cause. This removes the "unknown latency root cause" blocker but does not solve latency. LLM timeout/circuit breaker remains unresolved after rejected/reverted ISSUE-092A implementation.

The Risk Audit proved the highest operational risks are not architecture collapse; they are unbounded persistence, memory architecture separation, swallowed persistence failures, unauthenticated/admin exposure, wildcard CORS, non-persistent preference counts, duplicate workflow IDs, and known retry/recovery convergence anomalies.

The Production Platform Audit proved AI Lab is not production-ready for LAN/network/multi-user exposure. This is acceptable for a local-first single-operator desktop app only if CORS/auth/admin endpoint exposure is bounded and if portability/health/observability gaps are handled.

## 1.4 What V2 changes

V2 changes the roadmap center of gravity:

- Product capability becomes the main line.
- Production hardening becomes bounded parallel work, not the main roadmap.
- Memory activation becomes the first product capability milestone (Sprint 7A AG1-only advisory bridge now complete).
- GUI approval, notifications, and external-call user control become table-stakes workflow product work; ISSUE-098 external-call user-control implementation is functionally complete. ISSUE-098A defines override/force execution as governance-mediated user intent requiring USER_CONTROL_CONTRACT_V2 before implementation.
- PERF-036 latency measurement becomes a P0 usability gate.
- Planner / DAG / Final-Output Intelligence Stabilization becomes Sprint 8.
- Live Observability / Streaming / Testability becomes Sprint 9 — real-time planner/AG1/LLM visibility before learning.
- Learning/adaptation moves from indefinite future track to sequenced Sprint 10 work.
- Agent/tool expansion moves from vague future direction to Sprint 11.
- Plan control/workflow repair moves to Sprint 12.
- Privacy/local-first enforcement moves before expanded external tool danger increases (Sprint 13).
- Sandbox/self-improvement gets an explicit design milestone so it is not permanently forgotten (Sprint 14).

### Sprint 7A — Memory Activation Bridge

**Status: COMPLETE + VALIDATED for AG1-only advisory memory bridge (ISSUE-095B).**

Scope completed:
- AG1-only operator-memory advisory bridge implemented in `system/memory/advisory_bridge.py`.
- Bridge reads `memory_store.py` directly; does not use `global_memory.py`, `memory_adapter.py`, or `preference_tracker.py`.
- Memory is **read-only advisory injection only**: runtime reads memory entries and injects bounded advisory context into AG1/tool-selection prompt, but does not write/promote learning, mutate memory automatically, or adapt behavior outside the approved advisory prompt/context path.
- Memory activated as bounded, source-labeled, advisory context.
- Explicit user instruction precedence preserved in advisory framing.
- Project-scope isolation preserved (PROJECT memory included only when project/workflow lookup key available; `workflow_id` used as project lookup key when no separate `project_id`).
- Memory cannot affect lifecycle authority, execution_result truth, Task Hub/History membership, retry legality, recovery, replay, or governance decisions directly.
- Prompt-injection resistance and length/category/source filters implemented (source=user, behavior/preference/context, confidence >= 0.5, max entries bounded, prompt length bounded to 1000 chars).
- Memory can influence AG1 tool-selection wording only as advisory context.
- `MEMORY_CONTEXT_USED` trace event and event-bus/UI visibility implemented.
- Raw memory values excluded from `MEMORY_CONTEXT_USED` metadata.

Remaining follow-ups deferred:
- Planner memory bridge — deferred to future sprint.
- Learning, preference promotion, automatic memory writes, occurrence-count persistence, and adaptation decisions — Sprint 10.
- Semantic memory relevance/ranking — future design.
- AG1 tool-selection guardrails — separate active issue (ISSUE-090 in KNOWN_ISSUES_V2); memory bridge correctness does not guarantee tool-selection correctness.

# 10. CONTRADICTIONS / INTERPRETATION NOTES

## 9.1 No major audit contradiction blocks roadmap creation

The audits are directionally consistent:
- Functional Audit says product capability is missing.
- Performance Audit says latency and scaling risks must be measured/handled.
- Risk Audit says exposure/storage/memory split risks are real.
- Production Audit says the system is local-first and not production-ready.

## 9.2 The main tension is sequencing, not contradiction

There is a real tension between:
- production/platform P0 items, and
- product capability activation.

V2 resolves this by:
- allowing minimal P0 hardening in Sprint 7,
- forbidding a standalone hardening sprint unless an exposure blocker requires it,
- keeping memory/approval/notifications/override/latency as Sprint 7 center.

## 9.3 PERF-036 can alter Sprint 7 implementation detail

PERF-036 has now measured LLM-dominant latency. This removes the "unknown latency root cause" blocker but does not solve latency.

Conversational/trivial fast-path remains a future SA/Head Dev decision; it was not implemented by Sprint 7D. ISSUE-092B improved graceful planner/pre-step failure handling but does not implement a fast-path.

If future analysis proves full orchestration is inherently too slow for trivial/conversational prompts, the next decision is whether to allow a deterministic conversational fast-path. That requires SA/Head Dev review because it changes routing, even if not lifecycle authority.

## 9.4 Self-improvement remains quarantined but visible

V2 does not operationalize self-improvement directly. It adds a Sprint 12 design milestone to prevent permanent disappearance while preserving sandbox and approval requirements.

## 9.5 ISSUE-095B proves first active memory usage but does not make memory authoritative

ISSUE-095B implements the first active operator-memory advisory bridge. It proves memory can influence AG1 tool-selection context but does not make memory a guardrail, authority, planner input, or learning system. AG1 remains LLM-controlled and may misroute tools; guardrails remain future work.

## 9.7 ISSUE-096B implements approval/notification baseline but not full validation/product notification center

ISSUE-096B moved approval/notification from disconnected/partial infrastructure into a contract-safe MVP GUI baseline.
Approval remains backend-owned and frontend intent-only.
Notifications remain visibility-only.
Full real GUI E2E approval validation and richer notification UX remain deferred.
The dev-only approval fixture endpoint must be gated/disabled/removed before production hardening.

## 9.6 ISSUE-094 is an enabling latency/debuggability capability

ISSUE-094 is an enabling latency/debuggability capability, not a replacement for timeout/circuit breaker and not proof that cloud should become default.

OpenRouter is optional and local-first.
Ollama remains default/reset posture.
MutesHand budget guard is separate from OpenRouter key/account limit.
LLM usage ledger and History LLM Calls are read-only observability.
Provider/model telemetry does not influence lifecycle, governance, retry, projection, memory, or execution control flow.
Projection remains non-authoritative.
Frontend remains non-authoritative.
API key is never exposed, edited, or persisted through GUI.
No .env writes.
Timeout/circuit breaker remains deferred/redesign-required.
