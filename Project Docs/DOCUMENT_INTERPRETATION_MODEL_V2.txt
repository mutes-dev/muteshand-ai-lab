## 3C. DOCUMENT PRECEDENCE RULES

The following precedence hierarchy governs interpretation during audits, reconciliation, and drift classification.

PRECEDENCE (highest to lowest):
1. Runtime contracts override philosophical / meta-architecture guidance for runtime behavior
2. Lifecycle authority overrides projection interpretation
3. Runtime authority overrides observability interpretation
4. SYSTEM_STATE_V2 defines implementation truth
5. Harness validation defines behavioral validity
6. Current contracts override legacy documents
7. Roadmaps define progression, NOT implementation truth
8. Audit / support artifacts are non-authoritative

DOMAIN SEPARATION:
These domains are distinct and MUST NOT be conflated:
* Architecture intent — ideal design, authority model, philosophical boundaries
* Runtime authority — enforceable execution behavior, lifecycle ownership, coordination rules
* Implementation reality — actual verified behavior documented in SYSTEM_STATE_V2
* Roadmap progression — planned phases, future implementation targets, stabilization sequencing

Conflating these domains causes false-positive drift escalation and incorrect classification.

INTERPRETATION RULE:
When a document from a lower-precedence domain appears to conflict with a higher-precedence domain:
- The higher-precedence domain governs runtime behavior classification
- The lower-precedence domain may guide intent but does not override enforceable contracts
- Implementation gaps are NOT automatically architecture failures

- `finalize_output` remains a dumb identity final sink regardless of `final_action` value; semantic composition belongs to AG1 or explicitly authorized deterministic synthesis.

### 13.1 Replay vs Recovery Semantics

Recovery is NOT replay.
* Recovery restores authoritative runtime state from persistence or reconstruction
* Replay creates a NEW execution identity
* Retry is a NEW execution attempt, NOT a continuation of a terminated execution
* Recovery MUST NOT automatically replay execution
* Replay MUST NOT resurrect a terminated execution
* Reconstruction restores authoritative runtime state WITHOUT creating new execution lineage

Per EXECUTION_IDENTITY_AND_REPLAY_CONTRACT_V2:
- replay is explicit-only, never automatic
- retry generates new execution identity
- reconstruction and replay are semantically distinct

Per SYSTEM_CONVERGENCE_AND_RECOVERY_CONTRACT_V2:
- recovery converges to authoritative lifecycle state
- recovery does NOT replay execution
- stale-state quarantine prevents stale persistence from overwriting authority

### 13.2 Planning Recovery vs Replan Semantics

Planning Request Recovery is distinct from runtime Recovery, Replay, Retry, and Replan.
* Recovery restores authoritative runtime/lifecycle state
* Replay creates new execution identity
* Retry creates new step/workflow execution attempt
* Replan creates a new planning attempt from persisted planning intent
* Replan MUST NOT be interpreted as planner thread resurrection
* Persisted QUEUED shell does NOT prove live planning
* Stale bg_id does NOT prove runtime recoverability
* Original prompt/user intent SHOULD be preserved once accepted

Reference: PLANNING_RECOVERY_AND_REPLAN_CONTRACT_V2.txt

### 13.3 Cancellation Semantics

Cancellation is distinct from failure.

Per WORKFLOW_CANCELLATION_AND_TERMINALIZATION_CONTRACT_V2.txt:
- CANCELLED represents intentional operator terminalization
- FAILED represents execution failure
- CANCELLED workflows are immutable terminal states
- CANCELLED workflows MUST NOT be replayed automatically
- retry semantics apply to FAILED execution recovery, not intentional cancellation

Cancellation preserves historical chronology and governance truth.
