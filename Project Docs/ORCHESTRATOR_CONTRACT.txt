# ORCHESTRATOR CONTRACT

---

# 1. WORKFLOW CONTRACT

## STRUCTURE

{
  "id": string,
  "name": string,
  "status": "ACTIVE" | "PAUSED" | "COMPLETED" | "FAILED" | "BLOCKED",
  "steps": [...]
}

## RULES

- Workflow is top-level control container
- No execution logic allowed
- Status reflects aggregate step state
- If any step status = BLOCKED → Workflow status = BLOCKED
- If any step status = FAILED (and no retries remaining) → Workflow status = FAILED
- If all steps status = COMPLETE → Workflow status = COMPLETED
- Otherwise → Workflow status = ACTIVE

---

### NOTE — PARALLEL EXECUTION

Parallel execution may be implemented at orchestrator level in future phases.

Current implementation: Sequential execution only.

Future constraints (if parallel execution added):

- Each step remains independent
- Each execution still routes through system_entry
- Output resolution must follow defined priority rules

## 🔒 LAYER SCOPE — ORCHESTRATOR LAYER

This document defines the behavior of the Orchestrator Layer ONLY.

The Orchestrator Layer includes:

- workflows

- agents
- retry logic
- context handling
- decision and control logic

Characteristics:

- multi-step execution
- stateful
- partially non-deterministic (LLM-assisted)

## 🔗 RELATIONSHIP TO CORE PIPELINE

The system consists of two layers:

1. Orchestrator Layer (this document)
2. Core Execution Pipeline (defined in SYSTEM_CONTRACTS.txt)

Rules:

- The Orchestrator MUST use system_entry for ALL execution
- The Orchestrator MUST treat system_entry as a black box
- The Orchestrator MUST NOT access parser, resolver, validation, or execution layers directly
- The Orchestrator MUST NOT modify execution data
- The Core Pipeline defines execution truth
- The Orchestrator defines execution flow

# 2. STEP CONTRACT

## STRUCTURE

{
  "id": string,
  "name": string,
  "agent": string,
  "status": "PENDING" | "RUNNING" | "COMPLETE" | "FAILED" | "BLOCKED",
  "retries": int,
  "max_retries": int,
  "input": any,
  "output": any,
  "error": string | null
}

### NOTE — step["output"] field

The step["output"] field is for internal step storage ONLY.
It MUST NOT be used as final workflow output.

## RULES

- One step = one execution unit
- retries increment on failure only
- output on success, error on failure
- agent is metadata only (no control)
- Step MUST be strictly atomic
- Step performs one or more execution attempts until governance returns "complete" or retries are exhausted
- Step may trigger multiple system_entry calls during retry loop (within max_retries limit)

---

### NOTE — STEP EXECUTION REALITY

A step is logically atomic, but may perform multiple execution attempts (retries).

- Each retry triggers a new system_entry call
- Execution is single-step per attempt
- Multi-attempt behavior exists within step boundary

This preserves core pipeline constraints while enabling recovery.

---

## TASK CLASSIFICATION NOTE

Task classification is advisory and may exist independently of runtime integration.

Current implementation:
- Task classifier exists as `classify_task()` in task_classifier.py
- Provides: classification, autonomy_level, approval_required, reasoning, confidence
- Classification types: simple, complex, critical
- Pure rule-based function (deterministic, no side effects)

Integration status:
- Current runtime uses `plan_workflow()` (LLM-based planning)
- Classifier is used in `create_workflow()` but NOT in `execute_from_input` flow
- Task classification is currently not integrated into main execution path

# 4. STEP EXECUTION CONTRACT

## DEFINITION

- One step = one logical execution unit
- Step execution is triggered once per decision cycle
- Repeated execution requires explicit governance decision

## FLOW

input → agent_executor → system_entry → execution_result → validator (advisory) → governance.decide_next_action()
         ↑                                                                                       ↓
         └──────────────────────────── retry if governance returns "retry" ←─────────────────────┘

## RULES

- No batching across steps
- No chaining across step boundaries
- Validation may augment agent context (last_result) but does not modify execution contract
- Governance decision determines retry vs failure vs continuation
- Output stored exactly as returned
- Orchestrator MUST NOT modify input before passing to system_entry
- Input MUST be passed exactly as defined in step.input

### STEP INPUT ISOLATION RULE

step["input"] MUST be derived from step["purpose"] only.

- Full user input MUST NOT be passed to individual steps
- Each step MUST execute using isolated step-level context
- Cross-step input leakage is prohibited

### GOVERNANCE AUTHORITY RULE

Governance is the single decision authority.
Orchestrator MUST NOT infer or initiate retry based on state, counters, or validation output.

### DYNAMIC AUTHORITY RULE

Governance decision functions must be dynamically resolved at runtime.
Static binding of governance logic is prohibited.

# 5. FAILURE HANDLING CONTRACT

## DEFINITION

- Governance evaluates execution_result ONLY
- Validator signals are advisory metadata and MUST NOT influence decisions

If decision == "retry":
→ INCREMENT retries
→ retry (RUNNING)

Retries occur ONLY via governance decisions.
Orchestrator MUST NOT initiate retries independently.

If decision == "fail":
→ If retries >= max_retries: BLOCKED
→ Else: FAILED

If decision == "complete":
→ COMPLETE

## RULES

- No infinite retries
- Error must be captured
- Escalation when max retries reached
- Escalation on repeated identical failure
- Escalation on invalid system_entry response
- Retry occurs ONLY when governance returns "retry"
- FAILED → RUNNING is ONLY allowed when governance returns "retry"
- FAILED → BLOCKED is ONLY allowed when governance returns "fail" and retries >= max_retries

### MAX RETRY ENFORCEMENT

If retries >= max_retries:

- Step MUST transition to BLOCKED
- Workflow MUST reflect BLOCKED state (if applicable)
- No further execution attempts allowed

# 6. STATE TRANSITION TABLE

## ALL VALID TRANSITIONS

PENDING → RUNNING
RUNNING → COMPLETE
RUNNING → FAILED
FAILED → RUNNING (retry)
FAILED → BLOCKED
PENDING → BLOCKED
RUNNING → BLOCKED
COMPLETE → terminal
BLOCKED → terminal

## RULES

- No implicit transitions
- Terminal states cannot transition further

# 9. AGENT RULES

Agents may:
- interpret input
- use LLM
- request tool usage via USE_TOOL: prefix

Agents MUST NOT:
- execute tools directly outside the sandbox
- control workflow flow
- bypass output validation

Agent-discovered tool execution (USE_TOOL) routes through system_entry.
Direct tool execution via tool_executor is not used for core tools.
system_entry is the sole execution authority.

---

# 10. LLM RULES

- LLM is non-authoritative
- LLM output MUST NOT bypass output validation
- LLM failure MUST degrade safely (LLM_ERROR fallback)
- LLM provider is selected via registry (default_llm / ollama_llm)
- Provider switching MUST NOT affect execution contract
- System MUST remain functional without LLM

---

# 11. PERSISTENCE RULES

- Persistence is read-only influence on execution
- Only COMPLETED workflows are stored
- Persistence MUST NOT alter execution flow
- Persistence MUST NOT inject hidden data into execution
- Context injection is prompt-only — does not affect logic or state
- Persistence failure MUST NOT crash execution

---

# 12. DECISION LAYER RULES

### ORCHESTRATOR DECISION AUTHORITY

Governance Layer (Orchestrator):

* Makes final decisions: retry, fail, complete
* Controls execution flow
* Evaluates execution_result ONLY

Validator Layer:

* Advisory only (structural and semantic signals)
* Provides signals only
* No execution control
* No output authority

Rule:
Decision ≠ control
Validator ≠ control
Governance = control

---

Validator provides advisory signals only.

Governance evaluates execution_result ONLY and determines all decisions.
Validator signals are advisory metadata and MUST NOT influence decisions.
