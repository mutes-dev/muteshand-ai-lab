---

Applies to:

- workflows (projects)
- planning
- step execution control
- agents
- governance
- approval handling
- learning influence

# ⚙️ EXECUTION CONTROL

---

## PARALLEL EXECUTION

Allowed ONLY if:

- no dependencies  
- no shared state conflicts  

NEVER parallel:

- installs  
- system changes  
- environment changes  
- destructive file actions  

## SEQUENTIAL ENFORCEMENT

Critical steps MUST execute in order

Before executing any step:

- resource_targets MUST be evaluated
- conflict detection MUST run
- execution MUST respect conflict resolution contract

---

## LIFECYCLE INTERACTION RULE

Orchestrator coordinates execution but does NOT own lifecycle truth.

Orchestrator coordinates sequencing per:
ORCHESTRATION_AND_EXECUTION_SEQUENCE_CONTRACT_V1

Orchestrator uses runtime registry coordination per:
RUNTIME_REGISTRY_AND_EXECUTION_COORDINATION_CONTRACT_V1

Orchestrator obeys execution identity isolation per:
EXECUTION_IDENTITY_AND_REPLAY_CONTRACT_V1

Orchestrator MUST:

* request lifecycle transitions through Lifecycle Authority
* consume authoritative lifecycle state

Orchestrator MUST NOT:

* directly mutate workflow or step lifecycle state
* maintain competing lifecycle truth
* override orchestration sequencing authority
* bypass mutation legality windows
* perform replay-style recovery
* bypass execution identity boundaries

---

## ACTIVE EXECUTION EDIT BEHAVIOR

During ACTIVE execution:

* edit requests MAY be rejected
* edit requests MAY be deferred
* execution-affecting edits MUST NOT apply immediately

Mutation legality is governed by:
MUTATION_LEGALITY_AND_RUNTIME_ISOLATION_CONTRACT_V1

Orchestrator MUST enforce mutation legality windows.

Orchestrator sequencing is governed by:
ORCHESTRATION_AND_EXECUTION_SEQUENCE_CONTRACT_V1

Frontend MUST NOT assume mutation success before orchestrator confirmation.

Frontend MUST render:

* rejection state
  OR
* deferred mutation state

based on authoritative runtime response.

---

## CANONICAL PROJECTION RESPONSIBILITY

Orchestrator Runtime owns canonical projection generation and emission.

Projection generation follows the commit ordering defined in:
ORCHESTRATION_AND_EXECUTION_SEQUENCE_CONTRACT_V1

Orchestrator MUST:

* generate synchronized canonical projections
* emit projection updates deterministically
* maintain workflow-scoped projection isolation

Orchestrator MUST NOT:

* delegate projection ownership to frontend
* allow uncontrolled projection mutation
* allow projection generation to block lifecycle authority

## OBSERVABILITY PROJECTION EXPOSURE

### ORCHESTRATOR MAY EXPOSE OBSERVABILITY PROJECTIONS

Orchestrator MAY expose observability projections for:

* dashboard rendering
* runtime monitoring
* orchestration topology visualization
* websocket/event stream consumption

Orchestrator observability projections:

* originate from orchestrator-owned canonical projection generation
* remain orchestrator-owned
* remain non-authoritative for consumers

---

### ORCHESTRATOR REMAINS AUTHORITATIVE COORDINATION OWNER

Observability exposure does NOT delegate orchestration authority.

Orchestrator remains:

* authoritative coordination owner
* authoritative sequencing owner
* authoritative lifecycle transition requester

Dashboard, websocket, and frontend layers remain:

* passive consumers
* non-authoritative
* downstream-only

---

### OBSERVABILITY EXPOSURE DOES NOT DELEGATE ORCHESTRATION AUTHORITY

Frontend systems consuming orchestrator observability feeds:

* MAY render, group, filter, aggregate
* MUST NOT synthesize orchestration authority
* MUST NOT derive lifecycle truth from projections
* MUST NOT infer workflow ownership from visibility

Orchestrator MUST NOT:

* delegate projection ownership to frontend
* allow uncontrolled projection mutation
* allow frontend to reconstruct authority from projections

## RETRY LINEAGE REPLACEMENT SEMANTICS

NEW execution lineage.
