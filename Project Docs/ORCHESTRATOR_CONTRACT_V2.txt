# AI LAB — ORCHESTRATOR CONTRACT V2 (CONTROL LAYER)

---

## 🔒 SCOPE — ORCHESTRATOR LAYER ONLY

This document defines the behavior of the Orchestrator Layer ONLY.

Applies to:

- workflows (projects)
- planning
- step execution control
- agents
- governance
- approval handling
- learning influence
- memory usage

Does NOT apply to:

- core execution pipeline (system_entry)
- tool execution logic

---

## 🧠 CORE PRINCIPLE

ORCHESTRATOR = intelligent control layer

The orchestrator:

- defines WHAT should be done
- controls execution flow
- adapts based on context and learning
- NEVER executes actions directly

---

## 🔗 SYSTEM RELATIONSHIP

- Core Pipeline = execution authority  
- Orchestrator = flow + decision authority  
- User = absolute authority  

---

## ⚖️ AUTHORITY MODEL

Priority:

1. USER  
2. SYSTEM PLAN  
3. MEMORY  

Rules:

- user always overrides  
- system may warn or temporarily block  
- user can force execution  

---

# 🧩 WORKFLOW (PROJECT) MODEL

---

## DEFINITION

Each task runs as a PROJECT.

Projects are:

- independent  
- stateful  
- parallelizable  
- non-blocking  

---

## STATES

- QUEUED  
- ACTIVE  
- PAUSED  
- BLOCKED  
- COMPLETED  
- FAILED  

---

## RULES

- no cross-project blocking  
- conflict detection required for shared resources  
- user can control any project at any time  

---

# 🧠 STEP MODEL

---

## STEP TYPES

- ANALYZE  
- RESEARCH  
- PLAN  
- PROPOSE  
- EXECUTE_API  
- EXECUTE_LOCAL  
- EXECUTE_FILE  
- EXECUTE_INSTALL  
- EXECUTE_SYSTEM_SETTINGS_SERVICES  
- EXECUTE_ENVIRONMENT  
- VALIDATE  
- GENERATE  
- BUILD  

---

## STEP RULES

- one step = one logical action  
- one step = one system_entry call per attempt  
- retries allowed within limits  
- steps are atomic at execution level  

---

## STEP COMPLETION

A step is COMPLETE ONLY if:

- execution succeeded  
- purpose achieved  
- validation passed  

---

## FAILURE MODEL

- retry (risk-based limits)  
- escalate when exhausted  

Risk behavior:

- LOW → more retries  
- MEDIUM → limited  
- HIGH → minimal  

---

# 🧠 PLAN MODEL

---

## RULE

- plan ALWAYS exists internally  
- visibility is optional  

---

## MODES

OFF → autonomous  
ON  → visible + editable  

---

## USER CONTROL

User can:

- edit steps  
- reorder steps  
- add/remove steps  

Edits MUST:

- respect system constraints  
- not bypass core contracts  

---

# ⚙️ EXECUTION CONTROL

---

## PARALLEL EXECUTION

Allowed ONLY if:

- no dependencies  
- no shared state conflicts  

NEVER parallel:

- installs  
- system changes  
- environment changes  
- destructive file actions  

## SEQUENTIAL ENFORCEMENT

Critical steps MUST execute in order

Before executing any step:

- resource_targets MUST be evaluated
- conflict detection MUST run
- execution MUST respect conflict resolution contract

---

## LIFECYCLE INTERACTION RULE

Orchestrator coordinates execution but does NOT own lifecycle truth.

Orchestrator MUST:

* request lifecycle transitions through Lifecycle Authority
* consume authoritative lifecycle state

Orchestrator MUST NOT:

* directly mutate workflow or step lifecycle state
* maintain competing lifecycle truth

---

## CANONICAL PROJECTION RESPONSIBILITY

Orchestrator Runtime owns canonical projection generation and emission.

Orchestrator MUST:

* generate synchronized canonical projections
* emit projection updates deterministically
* maintain workflow-scoped projection isolation

Orchestrator MUST NOT:

* delegate projection ownership to frontend
* allow uncontrolled projection mutation
