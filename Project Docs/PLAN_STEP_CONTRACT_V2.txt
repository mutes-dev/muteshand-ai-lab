## PURPOSE

Defines the structure of a PLAN STEP.

A PLAN STEP represents intent (WHAT), not execution (HOW).

Plan steps are candidate / pre-runtime structure until validated.
Plan steps are NOT execution truth.
Plan steps do NOT imply execution authority.

---

## CORE PRINCIPLE

PLAN STEP = human-readable, editable, non-executable, candidate structure

## FINAL PRINCIPLE

PLAN STEP defines WHAT must be done.
It does NOT define HOW.

---

## PLAN FINALIZATION AND EDIT RULES

---

### EDITABLE STATES

Plan is FULLY EDITABLE when project state is:

* QUEUED
* PAUSED
* BLOCKED

---

### RESTRICTED STATE

When project state is ACTIVE:

* Plan edits are RESTRICTED
* Edits MUST go through controlled update process
* Edits MUST trigger full validation
* Edits MUST NOT bypass mutation legality per MUTATION_LEGALITY_AND_RUNTIME_ISOLATION_CONTRACT_V2

---

### EDIT IMPACT RULES

If a plan edit affects existing steps:

* affected steps MUST be invalidated or reset
* dependency graph MUST be revalidated per DEPENDENCY_MODEL_CONTRACT_V2
* invalid steps MUST NOT continue execution

---

### USER CONTROL

User MAY edit plan at any time, but:

* system MUST enforce validation rules
* system MUST prevent invalid execution states
* user edits represent intent, not runtime authority
* backend MUST validate and may reject invalid edits

---

### FINAL RULE

Plan flexibility MUST NOT break execution correctness.

Plan steps remain candidate structure until validated, resolved, and governed.
