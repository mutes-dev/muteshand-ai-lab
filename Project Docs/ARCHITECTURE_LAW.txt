# AI LAB — ARCHITECTURE LAW (ENFORCEMENT LAYER)

---

## PURPOSE OF THIS DOCUMENT

This document defines **non-negotiable enforcement rules** derived from `ARCHITECTURE.txt`.

It exists to:

* Prevent architectural drift
* Enforce strict layer boundaries
* Block incorrect implementations before they occur
* Provide deterministic decision rules for development

---

## RELATIONSHIP TO ARCHITECTURE

* `ARCHITECTURE.txt` defines **what the system is**
* `ARCHITECTURE_LAW.txt` defines **what must NEVER be violated**

---

## CRITICAL PRINCIPLES

* Laws MUST always align with `ARCHITECTURE.txt`
* Laws MUST NOT reflect temporary implementations or bugs
* Laws change ONLY when architecture changes
* Laws are designed to **stop drift, not describe behavior**

---

# ARCHITECTURE LAW #1 — ARGUMENT OWNERSHIP

Arguments MUST be created ONLY by the **ARGUMENT RESOLVER** layer.

The PLANNER is strictly forbidden from:

* generating arguments
* formatting arguments
* inserting `PREVIOUS_RESULT`
* performing any argument-related logic

The PARSER is strictly limited to token extraction and MUST NOT create arguments.

Any system behavior that derives arguments from the planner or parser is a violation of architecture.

This rule is PERMANENT and NON-NEGOTIABLE.

---

# ARCHITECTURE LAW #2 — LAYER ISOLATION

Each layer has EXACTLY ONE responsibility:

* Planner → structure only
* Parser → token extraction only
* Argument Resolver → positional argument mapping only
* Validation → structural validation only
* Execution → runtime execution only (single-step)

NO layer may perform another layer’s responsibility.

If a layer performs multiple responsibilities, it is considered a SYSTEM VIOLATION.

This rule is PERMANENT.

---

# ARCHITECTURE LAW #3 — MODEL DECOUPLING

The system MUST function correctly regardless of the LLM used.

This means:

* The LLM may be replaced at any time
* System correctness MUST NOT depend on LLM accuracy
* All critical logic MUST be deterministic and outside the LLM

If changing the model breaks the system, the architecture is invalid.

This rule is PERMANENT.

---

# ARCHITECTURE LAW #4 — LAYER LOCKING PROTOCOL

A layer may ONLY be locked when ALL of the following are true:

1. Its responsibility matches `ARCHITECTURE.txt` exactly
2. It does NOT perform any other layer’s responsibility
3. It is fully testable in isolation
4. It produces deterministic outputs (if applicable)
5. It passes both:

   * manual tests
   * harness tests

Once locked:

* The layer MUST NOT be modified unless a P0 issue is found
* Any change must be explicitly approved at Head Dev level

Locking incorrect behavior is strictly forbidden.

---

# ARCHITECTURE LAW #5 — DEVELOPMENT CONTROL MODEL

There are NO permanent module owners.

* Head Dev owns architecture globally
* Sub Devs are temporary and task-scoped

A Sub Dev:

* MUST follow `ARCHITECTURE.txt`
* MUST follow `ARCHITECTURE_LAW.txt`
* MUST NOT introduce cross-layer behavior
* MUST NOT make assumptions outside its task

All decisions must be validated against architecture BEFORE implementation.

This prevents module isolation drift.

This rule is PERMANENT.

---

# ARCHITECTURE LAW #6 — ARGUMENT RESOLUTION LAYER

Raw parsing is NOT equivalent to usable arguments.

The system MUST include an Argument Resolver layer between:

Parser → Execution

Responsibilities:

* Convert raw tokens into tool-ready arguments via positional mapping
* NO filtering of tokens
* NO type conversion
* Preserve deterministic behavior

The Parser remains a token extractor ONLY.

The Resolver performs positional argument mapping ONLY.

This separation is PERMANENT and NON-NEGOTIABLE.

---

# ARCHITECTURE LAW #7 — ARGUMENT RESOLVER IMMUTABILITY

The Argument Resolver layer is LOCKED.

Responsibilities:

* Convert parser tokens → tool-ready arguments via positional mapping
* NO filtering of tokens
* NO type conversion
* Preserve input order
* Return deterministic output

Constraints:

* MUST remain fully deterministic
* MUST NOT use LLM
* MUST NOT infer semantics
* MUST NOT reorder arguments
* MUST NOT filter tokens
* MUST NOT depend on planner, validation, or execution logic
* MUST NOT expand scope without Head Dev approval

The `tool_name` parameter MUST remain unused unless explicitly required by future architecture.

No changes are allowed unless:

* A P0 issue is identified
* A new Architecture Law explicitly requires modification

This layer is considered STABLE and COMPLETE.

---

# ARCHITECTURE LAW #8 — CHAIN RESOLVER (REMOVED)

Chain Resolver was removed from architecture.

System supports single-step execution only.

No multi-step chaining or PREVIOUS_RESULT support.

---

# ARCHITECTURE LAW #9 — NO PREMATURE DELETION

No module or file may be deleted during:

* architecture migration
* layer isolation
* pre-integration phases

Deletion is ONLY allowed when:

1. The system is fully integrated with new layers
2. The module is confirmed unused via audit
3. A replacement exists and is active
4. Removal has ZERO impact on execution

Premature deletion is a critical system risk.

This rule is PERMANENT.

---

# ARCHITECTURE LAW #10 — TOOL USAGE DISCIPLINE

Windsurf must ONLY be used for tasks that require code modification.

Tasks that MUST NOT use Windsurf:

* testing
* validation
* verification
* log analysis
* behavior confirmation

These tasks must be performed manually whenever possible.

Reason:

* reduces cost
* reduces unnecessary complexity
* prevents unintended code changes
* maintains control over system behavior

Windsurf is a coding tool, not a thinking tool.

This rule is PERMANENT.

---

# LAW — TOOL INDEX STRUCTURE (MANDATORY)

The tool index MUST be a dictionary keyed by tool name when passed into validation.

VALID FORMAT:
{
"tool_name": { ...tool_definition }
}

INVALID FORMAT:
[
{ "name": "tool_name", ... }
]

Violation of this rule will cause validation failure and system instability.

---

# ARCHITECTURE LAW — VALIDATION TIMING

Validation MUST occur ONLY after:

1. Argument Resolver has created arguments

Validation MUST NEVER run on planner output.

Violation results in guaranteed system failure.

---

# LAW — SINGLE-STEP EXECUTION

System supports single-step execution only.

Multi-step plans are rejected at entry layer.

NO runtime dependency resolution.

---

# LAW — SINGLE-STEP CONSTRAINT

System enforces single-step execution.

Entry layer MUST reject multi-step plans.

Expected failure: multi_step_not_supported

---

# ARCHITECTURE LAW #11 — SEMANTIC PATTERN MAPPING

The Planner MAY include a deterministic semantic mapping layer.

Purpose:

- Map known input phrases to valid tool names
- Reduce LLM dependency for common operations
- Enable direct tool accessibility

Rules:

- Mapping MUST be deterministic (explicit patterns only)
- Mapping MUST NOT use fuzzy matching or AI inference
- Mapping MUST verify tool exists in registry before routing
- Mapping MUST NOT extract arguments from input
- Mapping MUST preserve input_text unchanged
- One pattern MUST map to exactly one tool
- Patterns MUST NOT overlap or create ambiguity

Execution Order:

1. Normalize input (basic: strip, lowercase)
2. Direct tool match (exact name lookup)
3. Semantic pattern match (controlled regex)
4. Else → structured failure

Regex Usage:

- ALLOWED: deterministic pattern matching in semantic mapping ONLY
- FORBIDDEN: normalization, parsing, argument handling, inference

This layer is OPTIONAL but if present MUST follow these constraints.

Violation = uncontrolled routing behavior

---

# LAW — INPUT NORMALIZATION IS PRE-PLANNER ONLY

Input Normalization is positioned BEFORE the Planner layer.

Purpose:
- Remove noise tokens (e.g., "please", "hey", "bro")
- Normalize casing (lowercase)
- Trim whitespace

MUST:
- Remove noise and normalize casing
- Preserve valid argument tokens
- Maintain token order

MUST NOT:
- Create arguments
- Reorder tokens
- Modify argument values
- Introduce inference

---

# ARCHITECTURE LAW #17 — SINGLE-STEP EXECUTION MODEL

System is single-step only.

Multi-step execution is NOT supported.

Entry layer enforces this constraint.

Expected behavior:
- Single-step plans: processed normally
- Multi-step plans: rejected with multi_step_not_supported

---

# FINAL PRINCIPLE

Architecture defines the system.
Laws enforce it.

If implementation conflicts with laws:

→ implementation must change
→ NOT the laws (unless architecture changes)

---

# ARCHITECTURE LAW #12 — FAIL-FAST EXECUTION BOUNDARY

Execution MUST NEVER occur if structural validation fails.

The system entry layer MUST enforce a strict fail-fast gate BEFORE execution:

- planner_output must be a list
- planner_output must not be empty
- each step must contain:
  - type
  - name
  - input_text

If any condition fails:

→ system MUST return "invalid_input"
→ execution MUST NOT start

This prevents invalid plans from entering runtime.

Violation = execution leakage (P0)

---

# ARCHITECTURE LAW #13 — ENTRY POINT ISOLATION

The entry layer (/system/entry) is responsible ONLY for:

* connecting pipeline stages
* passing data between layers

It MUST NOT:

* perform validation logic
* perform execution logic
* modify data
* contain business logic

Violation = layer contamination

---

# ARCHITECTURE LAW #14 — EXECUTION ISOLATION

Execution MUST exist as an isolated module.

It MUST:

* only execute validated plans
* not perform validation
* not perform planning
* not modify plan structure

Execution MUST be reusable independently of orchestration.

Violation = execution contamination

---

# ARCHITECTURE LAW #15 — TOOL REGISTRY ISOLATION

Validation and Execution MUST use separate registries.

- validation_registry → metadata only
- execution_registry → callable only

Entry MUST:

- receive BOTH registries
- pass them WITHOUT modification

PROHIBITED:

- shared registry
- transformation inside entry
- inference of registry structure

Violation = cross-layer contamination (P0)

---

# ARCHITECTURE LAW #16 — TOOL INDEX AUTHORITY

Tool Index is the ONLY source of truth for all tools.

* registry_builder MUST use tool_index
* NO alternative sources allowed
* NO filesystem scanning
* NO dynamic discovery
* NO inference

Violation = P0
