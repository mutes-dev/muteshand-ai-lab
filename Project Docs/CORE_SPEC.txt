# 🧠 CORE SYSTEM SPEC (v1.0)

---

## 1. SYSTEM PRINCIPLE

The system is built around a deterministic Core Execution Pipeline controlled by an Orchestrator layer.

The Core Execution Pipeline is responsible for deterministic execution and contract enforcement.

The Orchestrator (HAND) sits above the Core and is responsible for:

- planning
- workflow control
- governance (decision authority)

All functionality is achieved through specialized Agents controlled by the Orchestrator.

### SINGLE SOURCE OF TRUTH

tool_index defines ALL tool identity via tool["name"].
Registry_builder is the ONLY consumer of tool_index.
Both validation and execution registries are derived from tool_index.

---

## ⚠ IMPLEMENTATION STATUS

* Core pipeline: implemented and active
* Orchestrator (HAND): partially implemented; behavior-critical components (retry, execution flow) are active and validated
* Agent lifecycle, memory, workflow engine: defined but not fully implemented

---

## TERMINOLOGY CLARIFICATION

- "Core Pipeline" refers to the deterministic execution system (system_entry and below)
- "Orchestrator Layer (HAND)" refers to the control layer above the core pipeline

The orchestrator is NOT part of the core pipeline.

---

## ENTRY POINTS

* run_workflow → internal orchestrator execution (flat contract)
* execute_from_input → external interface (layered contract)

---

## VALIDATION SPLIT

* Harness → contract validation (external behavior via execute_from_input)
* Internal tests → behavior validation (orchestrator logic via run_workflow)

---

## OUTPUT AUTHORITY

execution_result is the single source of truth for all step outputs.

- LLM-generated output MUST NOT override execution_result
- Any mismatch MUST resolve in favor of execution_result

---

## CONTEXT PASSING

The Orchestrator MUST maintain context:

- last_result stores the most recent execution_result
- context stores raw values only (NOT full execution_result objects)

---

## RETRY CONSISTENCY

On retry:

- executed_input MUST be reused
- tool inputs MUST NOT be regenerated via LLM

---

## 2. ORCHESTRATOR (HAND)

### Pipeline Order (Core Pipeline):

Planner → Parser → Resolver → Validation → Execution

NOTE: system_entry is the execution boundary (orchestrator layer) that routes to this core pipeline. It is NOT part of the core deterministic pipeline itself.

### Responsibilities:

* Task intake
* Goal interpretation
* High-level planning (WHAT to do)
* Agent selection or creation
* Workflow orchestration
* Permission and risk enforcement
* Execution tracking (state management)
* Logging and auditing
* Supervisor model invocation (when required)

### Decision Authority

Governance (within HAND) performs decision-making.  
Orchestrator executes governance decisions only.

### Constraints:

* The Core pipeline is deterministic and single-step only
* The Core does NOT perform multi-step workflows
* The Core does NOT perform chaining
* The Core does NOT make LLM-driven decisions
* Multi-step logic, retry loops, and workflow control belong to the Orchestrator layer above system_entry

---

## 3. AGENT MODEL

### Definition:

Agents are specialized, domain-focused execution units.

### Responsibilities:

* Execute assigned tasks
* Determine HOW tasks are performed
* Use tools to complete work
* Maintain domain-specific memory
* Suggest improvements to the Core

### Rules:

* Agents are created and managed by the Orchestrator (HAND layer)
* Agents must have:

  * Unique name
  * Defined role
  * Clear scope
* Agents must not duplicate responsibilities unnecessarily
* Agents cannot modify the Core directly
* Agents may propose changes, but Core approves

---

## 4. DYNAMIC AGENT CREATION

The Orchestrator layer (HAND) may create new agents when no suitable agent exists.

### Requirements:

* Each agent must include:

  * Name
  * Role
  * Scope definition
* Creation must be logged
* Redundant agent creation should be avoided

NOTE: This is an Orchestrator layer capability, NOT a Core pipeline function.

---

## 5. AGENT LIFECYCLE MANAGEMENT

**STATUS: NOT IMPLEMENTED**

Agent lifecycle states are defined but not yet implemented in the current codebase.

### Planned States:

* ACTIVE: Recently used
* IDLE: Not used for moderate period
* STALE: Not used for extended period
* MARKED_FOR_DELETION: Requires user approval
* ARCHIVED (optional): Stored but inactive

### Current Implementation:

The agent_registry module provides basic agent registration and lookup only. Lifecycle management is not active.

---

## 6. EXECUTION MODEL (RISK-BASED CONTROL)

All agent actions must pass through a Permission & Validation Layer.

### Risk Levels:

#### LOW RISK:

* Read operations
* Analysis
* Logging
* Sandboxed generation

→ Auto-execute UNLESS complexity is high

---

#### MEDIUM RISK:

* File creation
* Sandboxed execution
* Low-cost API usage
* File organization

→ REQUIRE explicit user approval

---

#### HIGH RISK:

* System modifications
* File deletion
* Software installation/uninstallation
* External spending (APIs, RunPod)
* Core/system changes
* Self-modification

→ REQUIRE explicit user approval

---

**Complexity Rule:**

Complexity is evaluated alongside risk.

- Low risk + high complexity → approval REQUIRED
- Confidence may further restrict auto-execution

---

## POST-EXECUTION LAYER

Execution results are returned to the Orchestrator layer.

The Orchestrator:

- evaluates outputs
- applies governance decisions
- determines final output

**Validator Role:**

Validator is advisory only.

- Validates contract compliance and step correctness
- May recommend retry or escalation
- Does NOT determine execution outcome

All final decisions are made by the Orchestrator within system constraints.

**Rules:**

- Outputs MUST NOT be synthesized or merged
- Final output MUST be traceable to a single execution path

LLM outputs are NON-AUTHORITATIVE

---

## 7. WORKFLOW ENGINE (STATEFUL EXECUTION)

**ORCHESTRATOR LAYER ONLY — NOT CORE PIPELINE**

The Orchestrator layer (HAND) operates as a stateful workflow engine above the core pipeline.

### Core Pipeline (Single-Step Only):

Planner → Parser → Resolver → Validation → Execution

The core pipeline is strictly single-step with no chaining.

### Orchestrator Layer Capabilities:

* Multi-step task execution
* Step tracking (pending, running, completed, failed)
* Retry loops with governance decisions
* Context passing between steps (last_result)

### Requirements (Orchestrator):

* State must be persisted after each step
* System must support interruption recovery (e.g. power loss)

### IMPORTANT:
The Core Execution Pipeline (below system_entry) does NOT support multi-step or chaining. All multi-step logic is implemented in the Orchestrator layer.

## 8. PLANNING MODEL (HYBRID)

### Core:

* Responsible for high-level planning (WHAT)
* Defines phases and assigns agents

### Agents:

* Responsible for execution planning (HOW)
* Optimize methods within their domain

### Rules:

* Agents cannot alter global workflow
* Agents may propose improvements

---

## 11. TOOL MODEL

Tools are external systems used by agents.

### Examples:

* File system
* ComfyUI
* RunPod
* Git
* APIs
* Browser automation

### Rules:

* Agents use tools
* Tools are executed through the Core Execution Pipeline
* Agents request execution, but all tool usage MUST pass through the Core pipeline
* No direct tool execution is allowed outside the pipeline
* All execution MUST pass through the core pipeline (system_entry)
* The Core pipeline is the sole execution authority
* No component may bypass this pipeline
* Tool usage follows risk model

---

## 12. GOVERNANCE & SAFETY

### Core Protection:

* Core modification requires:

  * User approval
  * Backup
  * Rollback mechanism

### Agent Autonomy:

* Allowed within defined scope
* All actions logged

### System Integrity:

* No silent critical changes
* Full traceability required

---

## 13. SUPERVISOR MODEL (OPTIONAL EXTENSION)

The system may use a higher-level model for:

* Planning improvement
* Output validation
* Strategic reasoning
* Agent refinement

### Rules:

* Supervisor is used by the Core
* It is not an independent agent
* It does not override governance rules

---

## 14. SYSTEM GOAL

To create a flexible, extensible AI system capable of:

* Autonomous task execution
* Controlled self-improvement
* Multi-domain specialization via agents
* Deep personalization through memory
* Efficient use of local and external compute
* Long-running workflow orchestration

---

## 15. DESIGN PRINCIPLES

* Separation of concerns (Core vs Agents vs Tools)
* Controlled autonomy (freedom with governance)
* Scalability through modular agents
* Safety through risk-based execution
* Persistence and evolution over time
* User remains in ultimate control
