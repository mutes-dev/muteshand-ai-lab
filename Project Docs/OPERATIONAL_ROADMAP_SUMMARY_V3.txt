## 2. WHY V2 EXISTS — THE STRATEGIC PIVOT

OPERATIONAL_ROADMAP_V1.txt correctly stabilized the core runtime and stopped architecture drift through Sprint 6. V1 delivered:
- single lifecycle authority
- governance-owned retry/failure/escalation
- projection-only frontend rendering
- Task Hub / History separation
- FAILED actionability metadata
- backend instance identity guard
- AG1 bounded containment and debug attribution visibility
- SSE event-hint transport without giving transport authority
- memory storage/API/GUI/trace/guardrail foundation

V1 drifted by treating architecture stabilization and operational hardening as the primary path of progress while the product-facing intelligence layer remained mostly missing. The system is architecturally aligned but at roughly 22% SYSTEM_GOALS_V2 functional completion.

V2 changes the roadmap center of gravity:

**Before (V1):** Architecture stabilization and operational hardening → main line  
**After (V2):** Product capability activation → main line. Production hardening → bounded parallel track.

This is NOT an architecture change. All frozen architecture rules are unchanged. V2 is a sequencing and priority change only.

## 8. SUB-DEV ISSUE SIZING AND LIFECYCLE MODEL

### Issue Sizing Rules

Each sprint issue must be:
- **Bounded:** scoped to one capability slice or one validation target
- **Atomic:** completable without reopening other closed issues
- **Evidence-required:** marked complete only when harness/test evidence exists or manual validation is documented
- **Non-goals explicit:** every issue must define what it does NOT do

### Issue Lifecycle

1. **NOT STARTED** — defined in roadmap, not yet active
2. **IN PROGRESS** — active implementation; Sub-Dev has single assigned issue
3. **IMPLEMENTED** — code complete, awaiting validation
4. **VALIDATED** — harness/test evidence exists or manual validation documented by Head Dev
5. **COMPLETE** — validated and accepted; must not be reopened unless regression recurs
6. **DEFERRED** — descoped from current sprint; does not imply incomplete sprint

### Sub-Dev Rules

- Sub-Dev executes one issue at a time
- Sub-Dev must read the Required Grounding Documents listed under the issue in OPERATIONAL_ROADMAP_V3 before starting
- Sub-Dev must not alter frozen architecture rules
- Sub-Dev must not reopen closed issues without Head Dev authorization
- Sub-Dev must not mark an issue COMPLETE without validation evidence
- Sub-Dev must not merge implementation-state claims into SYSTEM_STATE_V2 until validated
- Sub-Dev must escalate to Head Dev at any uncertainty about scope, authority boundaries, or contract compliance
