# PART 1 — AUDIT RESULTS

---

## PHASE 1 — CORE EXECUTION ENGINE

Status: PARTIALLY BUILT — MISALIGNED

What exists:

- system/entry/system_entry.py — functional, handles full pipeline
- system/parser/parser.py — deterministic token extraction
- system/resolver/argument_resolver.py — positional arg mapping
- system/observability/validator.py — structural validation
- system/execution/executor.py — single-step execution
- system/registry/registry_builder.py — builds validation + execution registries
- system/tool_index/tools.json — tool definitions with production flags
- tools/ — 27 tool implementations

Issues:

- system_entry still uses internal planner (deterministic_planner) inside core
  - CONTRACTS say: core = no planning, no intelligence
  - planner should be called by orchestrator, not inside system_entry
- system_entry accepts string but internally routes through planner
  - should accept pre-parsed tool call string and execute directly
- router.py inside entry/ makes routing decisions (planner vs direct)
  - routing logic belongs in orchestrator, not core
- normalize_input called inside system_entry
  - normalization is orchestrator responsibility
- llm_entry.py exists in system/entry/ — LLM has no place in core
- core/ directory exists as legacy duplicate (entry.py, parser.py, planner.py, etc.)
  - creates confusion about which pipeline is authoritative
- pipeline_entry.py (build function) is a passthrough with no purpose

## PHASE 2 — ORCHESTRATOR CONTROL LAYER

Status: BUILT — HEAVILY TANGLED

What exists:

- orchestrator_runtime.py — run_workflow + execute_from_input (1065 lines)
- orchestrator_planner.py — LLM-based workflow planning
- agent_executor.py — agent execution with LLM
- task_classifier.py — rule-based + keyword classification
- workflow_validator.py — workflow structure validation
- memory_controller.py — runtime context management
- escalation_controller.py — retry + escalation handling
- user_control.py — pause/resume/override
- user_approval.py — approval gate (placeholder)
- persistence.py — workflow save
- planner_soft_guard.py — atomic step enforcement

Issues:

- orchestrator_runtime.py is monolithic (1065 lines)
  - mixes: step selection, agent execution, validation, result propagation,
    chaining logic, constraint extraction, trace capture, governance calls
  - should be decomposed into focused modules
- agent_executor.py directly calls system_entry
  - correct per contract, but agent output (USE_TOOL:) prefix stripping
    is buried inside agent_executor, not a clean conversion layer
- operand injection logic in runtime (lines 344-386) is runtime intelligence
  - violates separation: runtime should not parse purpose strings
- constraint extraction via LLM happens in runtime (extract_constraints_llm)
  - LLM calls inside runtime loop violate deterministic control principle
- duplicate function: inject_result_into_purpose defined twice (lines 36-49)
- step schema does not match STEP_SCHEMA_CONTRACT_V1
  - missing: type, purpose, tool_call, expected_outcome, risk, importance, resource_targets
  - current steps only have: id, name, agent, status, retries, max_retries, input
- workflow built in main.py (build_workflow) uses minimal schema
  - no classification, risk, importance, or purpose fields
- no project system — single workflow per execution
  - no project states (QUEUED, ACTIVE, PAUSED, BLOCKED, COMPLETED, FAILED)
  - workflow["status"] used but not aligned with STATE_TRANSITIONS_CONTRACT

## PHASE 3 — GOVERNANCE & DECISION ENGINE

Status: MINIMAL — INCOMPLETE

What exists:

- governance.py — resolve_decision + decide_next_action
- decide_next_action returns: retry / complete / escalate / fail
- execution_result is sole decision driver (correct per contract)
- validator signals stored as advisory metadata (correct)

Issues:

- governance does not evaluate purpose_met
  - CONTRACT says: COMPLETE = success AND purpose_met AND validation_passed
  - current: COMPLETE = execution success only
- no confidence model implemented
- no risk-based retry limits
  - current: flat max_retries per step (default 2-3)
  - CONTRACTS say: LOW = more retries, HIGH = minimal
- no approval integration in governance
  - approval gate exists but governance doesn't trigger it based on risk
- governance does not return BLOCK decision
  - only returns: retry, complete, escalate, fail
  - CONTRACT defines: COMPLETE, RETRY, FAIL, BLOCK, ESCALATE

# PART 3 — REALIGNMENT PLAN

---

## APPROACH

Realign from the inside out:

1. Fix core first (smallest, most critical)
2. Clean orchestrator (largest, most tangled)
3. Enforce contracts (connect the two)
4. Build missing layers (incremental)

Each step preserves working functionality.
No big-bang rewrites.

---

## STEP 1 — PURIFY CORE PIPELINE

Priority: CRITICAL
Risk: LOW (isolated changes)
Effort: SMALL

Actions:

1.1 — Remove planner from system_entry
  - system_entry should receive a tool call string and execute it
  - no routing, no planning, no normalization inside core
  - move router.py logic to orchestrator

1.2 — Remove llm_entry.py from system/entry/
  - LLM has no place in core

1.3 — Remove pipeline_entry.py passthrough
  - or give it actual purpose (currently does nothing)

1.4 — Clean system_entry to:
  - accept string: "<tool_name> <arg1> <arg2>"
  - parse with shlex.split
  - validate against registry
  - execute
  - return normalized result

1.5 — Delete or archive core/ directory
  - confirm system/ is sole authority
  - remove to prevent confusion

Result: Core becomes a pure, deterministic execution engine.

---

## STEP X — ENFORCE EXECUTION BOUNDARY

Priority: CRITICAL
Risk: LOW
Effort: SMALL

Actions:

- remove operand injection logic from orchestrator runtime
- remove purpose string parsing for execution input
- ensure orchestrator passes ONLY explicit tool_call strings
- ensure no runtime mutation of execution input
- ensure system_entry receives ONLY validated tool_call string

Result:

- strict separation between:
  - orchestrator (decision layer)
  - core (execution layer)
- no intelligence leakage into execution
