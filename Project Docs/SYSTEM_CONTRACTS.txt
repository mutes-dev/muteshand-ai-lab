This document defines the behavior of the Core Execution Pipeline ONLY.

The Core Execution Pipeline includes:

- parser
- resolver
- validation layer
- execution layer
- entry layer (system_entry)

Characteristics:

- deterministic
- single-step execution only
- stateless per execution
- contract-enforced

This layer is the SOLE authority for execution truth.

---

## 🔗 LAYER RELATIONSHIP

The system consists of two layers:

1. Core Execution Pipeline (this document)
2. Orchestrator Layer (defined in ORCHESTRATOR_CONTRACT.txt)

- The Orchestrator executes governance decisions to control execution flow

- The Orchestrator MUST use the Core Pipeline for ALL execution
- system_entry is the ONLY execution interface between layers

# 🔀 ARGUMENT RESOLVER CONTRACT

## PURPOSE

Construct final execution-ready plan structure.

Resolver is the STRUCTURAL CONSTRUCTION LAYER — final authority on step format.

## INPUT

Parser output:

[
  { "name": string, "args": [...], "clean_input": optional, "input_text": string, "type": "tool" }
]

Note: "name" is the canonical tool identifier field.

## OUTPUT

### RESOLVER OUTPUT CONTRACT (EXPLICIT)

Resolver MUST output:

[
  {
    "name": string,
    "args": [...]
  }
]

No additional fields allowed.

Resolver constructs NEW dicts — this is the FINAL structural transformation in the pipeline.

## RULES

* MUST perform positional mapping of tokens to arguments
* MUST NOT filter tokens
* MUST NOT type convert
* MUST NOT infer values
* MUST NOT reorder arguments
* MUST NOT access registry
* MUST NOT access execution results
* MUST be deterministic

# � VALIDATION CONTRACT (PHASE 2)

---

## PURPOSE

Defines strict behavior for the validation layer.

Validation is a FAIL-FAST structural gate between:

Argument Resolver → Execution

---

## INPUT

Validation MUST accept:

- Fully structured plan
- Tool registry (dictionary format)

Plan format:

[
  {
    "name": "tool_name",
    "args": [...]
  }
]

Note: Execution layer accepts both "name" (canonical) and "tool" (legacy) for backward compatibility.

Tool registry MUST be the SINGLE source of truth for:

- tool existence
- argument count
- argument types

Validation MUST NOT:

- infer tool contracts
- define tool schemas internally
- depend on external sources

---

## OUTPUT

### SUCCESS

Validation MUST return:

{
  "status": "success"
}

---

### FAILURE

Validation MUST return:

{
  "status": "failure",
  "reason": "error_type"
}

---

## VALIDATION RULES

Validation MUST:

- Validate plan is a list
- Validate plan is not empty
- Validate each step contains:
  - "name" (canonical tool identifier)
  - "args"
- Validate tool exists in registry
- Validate argument count matches tool contract
- Validate argument types match tool contract

---

## RUNTIME PLACEHOLDER RULE

Validation MUST:

- IGNORE runtime placeholders (e.g. PREVIOUS_RESULT)
- NOT type-check placeholders
- NOT resolve placeholders

---

## PROHIBITIONS

Validation MUST NOT:

- Execute tools
- Modify plan
- Infer missing arguments
- Reorder arguments
- Perform planning
- Access execution results
- Transform data (read-only validation only)

## STRUCTURAL RESPONSIBILITY

Validation layer role:

- Verifies structure against registry contracts
- Enforces contract compliance via rejection (not correction)
- Authoritative gate — may reject invalid structure
- MUST NOT modify data to make it valid

---

## VALIDATION AUTHORITY GUARANTEE

Validation MUST enforce complete argument correctness.

- Argument count MUST match tool contract exactly
- Argument types MUST match tool contract
- Invalid arguments MUST result in failure

Execution layer assumes:

- Arguments are structurally valid

No semantic validation exists. Validation is strictly structural.

Execution MUST NOT:

- Validate arguments
- Correct arguments
- Perform fallback validation

---

## TOOL CONTRACT AUTHORITY

Tool registry definitions are the ONLY source of truth for argument requirements.

- Validation MUST use registry-defined contracts
- Function signatures MUST NOT be used for validation

---

## STRUCTURAL GATE GUARANTEE

Validation is the COMPLETE structural gate.

No structurally invalid plan may reach execution.

---

## FAIL-FAST RULE

Validation MUST:

- STOP on first failure
- Return structured failure output
- PREVENT execution from starting

---

## DETERMINISM RULE

Validation MUST:

- Be fully deterministic
- Produce identical output for identical input

---

## STRUCTURAL PURITY

Validation is:

- Structural only
- Non-semantic
- Non-intelligent

NOTE:

Core validation layer is strictly structural and non-semantic.

Semantic validation (partial, advisory) exists ONLY at the orchestrator layer and is NOT part of this contract.

---

## CONSTRAINTS

- NO side effects
- NO hidden logic
- NO cross-layer behavior

---

## FIELD LIFECYCLE TABLE

| Field       | Layer Scope      | Status                         |
| ----------- | ---------------- | ------------------------------ |
| type        | Planner only     | removed before resolver output |
| input_text  | Planner/Parser   | not passed beyond resolver     |
| clean_input | Planner/Resolver | internal only                  |
| args        | Resolver onward  | execution contract             |
| name        | pipeline-wide    | canonical                      |

---

## CLEAN_INPUT SPECIFICATION

clean_input is a STRUCTURAL TRANSFORMATION field (NOT normalization).

**Generation:**
- Created by planner at `system/planner/deterministic_planner.py:261`
- Derived from `input_text` after phrase matching and stripping

**Usage:**
- Used by resolver for argument construction
- Resolver accesses via `step.get("clean_input", input_text)`

**Contract Status:**
- NOT part of execution contract
- NOT part of validation contract
- NOT passed to execution layer
- Internal to planner/resolver boundary only

clean_input is a structural transformation field and MUST remain within planner scope.

    "types": [type, ...]

Used by execution layer.

- Execution MUST use execution_registry ONLY  

---

## ENTRY RESPONSIBILITY

Entry MUST:

- Receive BOTH registries  
- Pass validation_registry to validation  
- Pass execution_registry to execution  

---

## PROHIBITIONS

- No shared registry between layers  
- No transformation inside Entry  
- No inference of registry structure  
- No runtime mutation of registries  

---

## CONSTRAINTS

- Registries must be deterministic  
- Registries must be explicit  
- Registries must not contain hidden logic

---

## STRUCTURE

---

## RULES

* MUST be deterministic
* MUST be explicit
* MUST NOT include logic
* MUST NOT include execution behavior
* MUST NOT be modified at runtime

---

## RELATIONSHIP

registry_builder MUST:

* read tool_index
* construct validation_registry
* construct execution_registry

NO other source allowed.

---

## PROHIBITIONS

* NO directory scanning
* NO dynamic imports from filesystem
* NO fallback logic
* NO inference

# �🚪 ENTRY CONTRACT (PHASE 2)

---

## PURPOSE

Defines strict behavior of the system entry layer.

The entry layer is responsible ONLY for orchestrating pipeline stages.

---

## RESPONSIBILITY

Entry MUST:

- Receive input (structured plan + validation_registry + execution_registry)
- Call validation layer
- Enforce fail-fast behavior
- Call execution layer ONLY if validation succeeds
- Return final system output

---

## INPUT

Entry MUST accept:

{
  "plan": [...],
  "validation_registry": {...},
  "execution_registry": {...}
}

---

## OUTPUT

Entry MUST return EXACTLY one of:

### SUCCESS

{
  "status": "success",
  "result": <final_result>
}

Note: "trace" and "steps" are NOT present in final output. Entry layer's `_normalize_output()` enforces strict contract with ONLY status + result/reason.

### FAILURE

{
  "status": "failure",
  "reason": "error_type"
}

---

## SCOPE NOTE

This contract applies ONLY to system_entry.

The system MUST return ONLY contract-compliant output:

Success:
{"status": "success", "result": ...}

Failure:
{"status": "failure", "reason": ...}

No raw strings allowed.

---

## PIPELINE FLOW (STRICT ORDER)

1. Receive input  
2. Call parser.parse(input) → structured plan
3. Call resolver.resolve(plan, input_text) → resolved plan with positional mapping
4. Call validation.validate(resolved_plan, validation_registry)  
5. If validation fails → RETURN failure immediately  
6. If validation succeeds → call execution.execute(resolved_plan, execution_registry)
7. Call _normalize_output(raw_result) → enforce strict contract
8. Return normalized result (ONLY status + result/reason, no trace/steps)  

---

## FAIL-FAST RULE

Entry MUST:

- NEVER call execution if validation fails  
- NEVER continue after failure  
- RETURN immediately on failure  

---

## PROHIBITIONS

Entry MUST NOT:

- Execute tools directly  
- Perform validation logic internally  
- Modify plan  
- Modify arguments  
- Perform planning  
- Infer missing data  
- Reorder steps  

---

## DETERMINISM RULE

Entry MUST:

- Be deterministic  
- Produce identical outputs for identical inputs  

---

## DATA PASS-THROUGH RULE

Entry MUST:

- Pass plan unchanged to validation  
- Pass plan unchanged to execution  
- NOT transform data  

---

## CONSTRAINTS

- NO side effects  
- NO hidden logic  
- NO cross-layer behavior  

---

# PARSER CONTRACT

## PURPOSE

Translate planner output into execution plan.

Parser is a STRICT, deterministic translation layer.

It MUST NOT:

- infer meaning
- interpret natural language freely
- guess missing data
- access external systems
- modify system state
- own arguments
- validate arguments
- access registries

Parser extracts tokens deterministically, including numbers and quoted strings. No semantic interpretation.
Argument ownership remains with Argument Resolver

Parser is NOT intelligent.  
Parser is NOT a fallback layer.  
Parser is NOT optional.

---

## INPUT

Planner output:

EITHER:

1. List of steps:

[
  {
    "type": "tool" | "agent",
    "name": string,
    "input_text": string
  }
]

OR

2. Failure object:

{
  "status": "failure",
  "reason": string
}

---

## OUTPUT

EITHER:

1. Execution plan:

[
  {
    "name": string,
    "args": [any, ...]
  }
]

OR

2. Failure object (PASSTHROUGH):

{
  "status": "failure",
  "reason": string
}

---

## RULES

### 1. FAILURE PASSTHROUGH

If input is failure object:

→ RETURN AS-IS  
→ DO NOT MODIFY  

---

### 2. STEP TYPE HANDLING

If step["type"] == "tool":

→ MUST translate to execution step  

If step["type"] != "tool":

→ RETURN failure:

{
  "status": "failure",
  "reason": "unsupported_step_type"
}

---

### 3. NAME MAPPING

step["name"] → execution["name"]

EXACT match required. "name" is the canonical tool identifier field.

---

### 4. ARGUMENT EXTRACTION (STRICT)

Arguments MUST be extracted using deterministic rules ONLY.

Allowed patterns (STRICT):

- integers in input_text
- floats in input_text (e.g., 3.14, -0.5)
- order of appearance defines argument order

Example:

"add 2 and 3" → [2, 3]  
"multiply 4 by 5" → [4, 5]  
"divide 10.5 by 2.5" → [10.5, 2.5]

---

### 5. INVALID INPUT_TEXT

If:

- ambiguous structure
- cannot extract arguments deterministically

→ RETURN step with empty args:

[
  {
    "name": "tool_name",
    "args": []
  }
]

Parser returns [] when no numbers found.
Parser NEVER fails for missing arguments.
Validation handles argument correctness.

---

### 6. NO INFERENCE

Parser MUST NOT:

- guess missing numbers
- assume defaults
- reorder arguments beyond appearance
- interpret synonyms
- use NLP techniques

---

### 7. OUTPUT STRUCTURE

Each step MUST produce:

{
  "name": string,
  "args": list
}

NO additional fields allowed.

---

### 8. DETERMINISM

Same input MUST always produce same output.

No randomness allowed.

---

### 9. ISOLATION

Parser MUST:

- NOT call execution layer
- NOT call validation layer
- NOT access tool registry
- NOT modify input

---

## PROHIBITED

- AI / LLM usage
- fuzzy matching
- regex heuristics beyond numeric extraction
- external dependencies
- hidden logic
- fallback behavior

---

## FAILURE CONTRACT

Parser MUST return ONLY:

{
  "status": "failure",
  "reason": "<specific_reason>"
}

Allowed reasons:

- "unsupported_step_type"
- "argument_parse_error"

NO other failure formats allowed.

---

# EXECUTION CONTRACT (PHASE 1)

---

### EXECUTION AUTHORITY

Execution layer is the final authority for:

- tool execution
- result generation

It assumes:

- inputs are structurally valid
- validation has already passed

Execution MUST NOT:

- perform validation
- perform planning
- infer missing data

---

## INPUT

Executor MUST accept:

```json
[
  {
    "name": "tool_name",
    "args": [arg1, arg2]
  }
]
```

---

## OUTPUT

Executor returns (internal format):

```json
{
  "status": "success",
  "result": <final_result>
}
```

Note: "steps" is for internal observability only. Entry layer's `_normalize_output()` strips this before returning to caller.

---

## FAILURE OUTPUT

```json
{
  "status": "failure",
  "reason": "error_type"
}
```

---

## EXECUTION RULES

* MUST NOT validate input
* MUST NOT modify plan structure
* MUST NOT perform planning
* MUST be deterministic
* MUST execute steps in order
* System supports single-step execution only

---

## FAILURE PROPAGATION RULE (MANDATORY)

If a tool returns:

```json
{
  "status": "failure",
  "reason": "<string>"
}
```

Execution MUST:

- return the failure object immediately
- NOT wrap the result
- NOT continue execution
- NOT modify the failure object

This behavior MUST match executor.py implementation.

Tool-level failures are PASSTHROUGH only.

Execution MUST exist as an isolated module:

/system/execution/executor.py

Execution MUST NOT depend on:

* manager
* orchestration logic
* validation layer

# LLM ENTRY CONTRACT (PHASE 3)

## PURPOSE

Define the LLM entry layer contract for optional intelligence integration.

LLM entry operates as a pre-planner intelligence layer that is OPTIONAL and environment-dependent.

---

## INPUT

Natural language instruction (string)

---

## OUTPUT (DUAL-MODE)

### MODE 1 — SAFE MODE (NO ENV)

Output: input_text (string passthrough)

Condition:
- LLM_MODEL not configured
- LLM adapter returns failure
- LLM output invalid

### MODE 2 — INTELLIGENT MODE (ENV ENABLED)

Output: structured plan (list of steps)

[
  {
    "type": "tool",
    "name": "tool_name",
    "input_text": "original instruction"
  }
]

Condition:
- LLM_MODEL configured
- LLM adapter returns valid structured output
- Validation layer accepts output

---

## CONFIGURATION

Environment variables:

- LLM_MODEL: Model identifier (required for intelligent mode)
- LLM_API_KEY: API key (required for external providers)
- OLLAMA_MODEL: Override for local Ollama models

---

## RULES

1. LLM entry MUST function without LLM (passthrough)
2. LLM output is NOT trusted
3. Validation layer remains authoritative
4. Failure MUST result in passthrough (never crash)
5. Structured output MUST match planner output format
6. Tool names MUST exist in tool_index

---

## FAILURE CONTRACT

On adapter failure or invalid output:

{
  "status": "failure",
  "reason": "llm_not_available" | "llm_invalid_output"
}

Behavior: llm_entry returns input_text (passthrough)

# DOMAIN ERROR CONTRACT

Rules:

- Invalid numeric domains MUST return failure.

Standard format:

```json
{
  "status": "failure",
  "reason": "invalid_domain"
}
```

Applies to:

- factorial of negative numbers
- square root of negative numbers
- fibonacci with invalid (e.g. negative or non-integer) input

This rule is MANDATORY and overrides tool-specific behavior if domain is invalid.

}

# 📐 SINGLE-STEP EXECUTION CONTRACT (PIPELINE-LEVEL)

Rules:

- The Core Execution Pipeline supports single-step execution only
- Each execution call processes exactly one resolved plan
- Multi-step execution is NOT supported within the pipeline

### NOTE

Multi-step workflows may exist at the Orchestrator layer.

These are implemented as multiple independent single-step executions.

The pipeline itself remains strictly single-step.

---

Multi-step plans are rejected at the Core Pipeline entry layer.

This applies ONLY to direct pipeline usage.

Multi-step execution is handled by the Orchestrator layer,
which calls the pipeline multiple times.
