## Amendment 2026-07-05 — Planner-First Tool-Gated Hybrid Architecture GUI Visibility

### Profile / Tool Decision Visibility

GUI MUST provide debug-mode visibility for the Planner-First Tool-Gated Hybrid Architecture:

- Selected tool/profile context for planner and AG1.
- Scope of available tools per profile.
- Selected tool per step and why it was selected.
- Validation warnings when a tool is outside the active profile.
- Capability route metadata including capability_id, recommended profile, and fallback reason.

### Future Document Q&A Evidence Visibility

When a future evidence-backed document Q&A step is implemented, GUI MUST display:

- Source document identity (path or URL, acquisition tool, workflow_id).
- Result classification: `found | not_found | ambiguous | unsupported`.
- Evidence snippets and chunk IDs.
- Limitations and warnings.
- No unsupported plain-text answer may be presented as authoritative.

### Q&A Quarantine

- GUI MUST NOT expose controls, actions, or prompts that invoke `semantic_transform` `answer_question` or Slice 007 Q&A behavior.
- GUI staging remains limited to Read/Summarize/Extract key points/Explain only.

## Core Principle

GUI = interaction layer ONLY

GUI MUST:
- reflect backend/orchestrator/projection state
- send user intent
- include required execution context

GUI MUST NOT:
- execute tools
- make decisions
- modify execution logic
- bypass mutation legality boundaries
- assume synchronization completion authority
- own retention classification
- own archival semantics

GUI controls request backend actions only; backend validates; Lifecycle Authority commits any legal lifecycle transition.

## 1. Interaction Modes

DEFAULT MODE — CHAT
- user enters requests
- system responds conversationally
- system MAY suggest creating a workflow

PROJECT MODE
- activated when task becomes structured
- displays workflow (steps, states, outputs)
- allows user control actions

DEBUG MODE (OPTIONAL)
- shows trace logs
- shows detailed system signals
- does NOT affect execution

---

## 2. Core GUI Components

CHAT PANEL
- accepts user input
- displays system responses

WORKFLOW LIST
- shows all active workflows
- supports switching between workflows

WORKFLOW VIEWER
- displays workflow state
- displays steps and states

STEP DETAIL PANEL
- shows purpose, result, output, retry status

EXECUTION OUTPUT PANEL
- shows tool outputs and logs

CONTROL PANEL (CONTEXT-SCOPED)
- shows valid actions for current workflow

PLAN VIEW (TOGGLE)
- ON -> editable plan
- OFF -> hidden

Plan View displays PLAN STEP (not execution STEP).

NOTIFICATIONS
- approvals
- failures
- completion

## 3. Control Actions

ALL control actions MUST include context.

REQUIRED CONTEXT:
- workflow_id
- step_id (when applicable)

ACTIONS:

START WORKFLOW -> workflow_id
PAUSE WORKFLOW -> workflow_id
RESUME WORKFLOW -> workflow_id
STOP WORKFLOW -> workflow_id

APPROVE STEP -> workflow_id + step_id
REJECT STEP -> workflow_id + step_id
RETRY STEP -> workflow_id + step_id

EDIT PLAN -> workflow_id

RULE:
GUI MUST NOT send actions without required context.

GUI action names may use workflow instead of project, with project as legacy UI wording where needed.

## 8. Explicit Workflow Attachment and Observability Boundaries

### Explicit Workflow Attachment Semantics

Frontend workflow attachment is:
- explicit
- operator-initiated
- context-bound

Frontend tracks:
- workflows it starts
- workflows it restores
- workflows explicitly selected/attached

This is:
intentional architecture.

NOT:
a defect.

---

### Focused Workflow Interaction Boundaries

Focused workflow screens:
- are explicit attachment surfaces
- are workflow-scoped
- are interaction-oriented

Focused workflow screens are NOT:
- global runtime discovery dashboards
- auto-discovery surfaces

Focused workflow UI does NOT automatically discover arbitrary runtime workflows.

---

## Planning vs Replan-Required UI Semantics

GUI MUST distinguish:
- live planning (QUEUED_LIVE_PLANNING)
- replan-required planning request (QUEUED_REPLAN_REQUIRED)
- recoverable runtime execution

For QUEUED_REPLAN_REQUIRED:
- UI must NOT show as live/restorable runtime
- UI may show Resume Planning / Replan action
- UI must NOT require operator to retype persisted original prompt
- UI must NOT poll stale bg_id indefinitely
- UI must consume backend-authored planning actionability

For QUEUED_LIVE_PLANNING:
- UI may show planning in progress
- UI may allow stream polling for workflow_id resolution
- UI may show pending/progress indicators

Frontend MUST NOT infer:
- live planning from persistence alone
- actionability from Task Hub visibility alone
- recoverability from stale bg_id

Replan UI semantics are governed by:
PLANNING_RECOVERY_AND_REPLAN_CONTRACT_V2.txt

## Dashboard vs Interaction Layer Distinction

Dashboard / Observability Layer:
- passive read-only visibility
- subscribes to runtime feeds
- groups, filters, aggregates

Focused Workflow Interaction Layer:
- explicit workflow attachment required
- scoped interaction controls
- mutation requests
- execution inspection

These layers are:
- architecturally separate
- MUST NOT be conflated
- MUST NOT be substituted for one another

## 10. Operational Mutation and Terminal Semantics

### Recoverable Failed Semantics

GUI MUST recognize:
- FAILED is a recoverable terminal state
- FAILED workflows MAY support retry controls
- FAILED workflows MAY support reconciliation controls

GUI MUST NOT:
- treat FAILED as immutable terminal
- disable retry for FAILED workflows arbitrarily
- synthesize retry legality locally

GUI may show retry controls for FAILED only when backend-authored actionability allows it.

---

## Task Hub Contract

Task Hub represents recoverable / actionable work.

GUI MUST include in Task Hub:
- ACTIVE workflows
- PAUSED workflows
- BLOCKED/actionable workflows
- QUEUED_REPLAN_REQUIRED workflows (as actionable planning items)
- recoverable FAILED workflows

GUI MUST NOT include in Task Hub:
- COMPLETED workflows
- CANCELLED workflows
- archived workflows
- historical workflows

Task Hub is NOT historical storage.

Task Hub may include ACTIVE, PAUSED, BLOCKED/actionable, QUEUED_REPLAN_REQUIRED, and recoverable FAILED where backend says actionable.

Task Hub must exclude immutable terminal COMPLETED/CANCELLED unless a separate non-actionable history/archive view is used.

---

## History Contract

History represents previously existing workflows.

History is observability-oriented and inspection-oriented.

History is NOT recoverability-oriented.

History MAY include:
- COMPLETED workflows
- CANCELLED workflows
- archived FAILED workflows
- historical workflows

History may show immutable terminal and historical workflows, but not as actionable.

History MUST NOT:
- suggest retry legality
- imply recoverability
- override lifecycle authority

---

## Retention Visibility Direction

GUI MAY eventually support:
- retention controls
- archival controls
- dismiss controls
- delete controls

Retention actions do NOT alter lifecycle truth.

Lifecycle state and retention state are independent.

---

## Recoverability Visibility Direction

GUI SHOULD expose recoverable terminal workflows in actionable surfaces.

GUI SHOULD NOT expose immutable terminal workflows in actionable surfaces.

Recoverability visibility is governed by:
LIFECYCLE_AUTHORITY_CONTRACT_V2.txt

BLOCKED = recoverable non-terminal/wait.
FAILED = recoverable terminal.
COMPLETED/CANCELLED = immutable terminal.

---

## Retry Surface Visibility

GUI SHOULD expose retry controls for:
- FAILED workflows
- recoverable terminal workflows

GUI must not show retry/continue controls for CANCELLED.

Retry controls MUST:
- include required context (workflow_id, step_id)
- request retry through orchestrator
- not assume retry success before authority confirmation

GUI must not synthesize FAILED from BLOCKED/no-progress.

---

## Cancellation Controls

GUI MAY expose cancellation controls for:
- ACTIVE workflows
- PAUSED workflows
- QUEUED workflows

Cancellation controls MUST:
- request cancellation through orchestrator
- not synthesize cancellation authority locally
- not bypass lifecycle authority

Cancellation semantics are governed by:
WORKFLOW_CANCELLATION_AND_TERMINALIZATION_CONTRACT_V2.txt

---

## Blocked No-Progress Ceiling GUI Interpretation

For workflows BLOCKED due to max_iterations_exceeded/no_progress_ceiling:
- show as BLOCKED / intervention required
- keep actionable/recoverable surfaces visible
- keep in Task Hub unless archived/dismissed
- do not move to History by default
- do not display as terminal FAILED
- retry/resume/cancel controls depend on backend-authored actionability

Frontend must not synthesize FAILED from BLOCKED reason.

---

## Focused Workflow Persistence

Focused workflow attachment SHOULD persist:
- until explicitly detached
- or another workflow explicitly attached

Task Hub navigation MUST NOT implicitly sever:
foreground workflow interaction context.

GUI MUST distinguish:
- observability context (passive viewing)
- interaction attachment context (active control)

---

## Lightweight Mutation Boundaries

GUI edit mode supports:
- purpose
- expected_outcome
- risk
- importance
- operator annotations
- semantic correction hints

GUI edit mode does NOT support:
- dependency rewiring
- topology mutation
- structural orchestration mutation

Lightweight mutation requests must be backend-validated and mutation-legal.

GUI must not infer retry legality, approval validity, user-control legality, recoverability, or lifecycle state from projection alone.

GUI must not infer:
- live planning from persistence alone

- recoverability from stale bg_id
