## CORE PRINCIPLE

Execution instances are isolated runtime coordination entities.

Recovery restores authority state.

Replay is explicit re-execution behavior.

# 1. EXECUTION IDENTITY MODEL

## EXECUTION IDENTITY

Every execution attempt has a distinct execution identity.

Execution identity includes:

* execution instance identifier
* step reference
* attempt number
* execution context reference
* worker assignment

Execution identity is:

* runtime coordination metadata
* NOT lifecycle authority
* NOT projection truth

## EXECUTION INSTANCE SEMANTICS

An execution instance represents:

* a single attempt to execute a step
* a single worker assignment
* a single execution context

Multiple execution instances may exist for the same step across retries.

Each execution instance is:

* independent
* isolated
* separately identifiable

## PLANNING EXECUTION IDENTITY

Planning execution identity is separate from step execution identity.

Each planning attempt has a distinct planning execution identity.

If the planner is interrupted and replanned:

* replan creates a NEW planning execution identity
* replan is NOT replay
* replan is NOT retry
* replan does NOT rewrite historical execution lineage

Planning execution identity includes:

* planning attempt number
* planning input context
* planning interruption state if applicable

Replan semantics are governed by:
PLANNING_RECOVERY_AND_REPLAN_CONTRACT_V1.txt

## RETRY EXECUTION IDENTITY

Retry creates a NEW execution instance.

Retry execution identity:

* is distinct from previous execution identity
* references the same step
* increments attempt context
* establishes fresh isolation boundaries

Retry is NOT:

* continuation of previous execution
* resurrection of previous execution state
* reuse of previous execution context

## EXECUTION LINEAGE

Execution lineage traces:

* execution attempts for a step
* retry ancestry
* replay ancestry

Execution lineage is:

* observability metadata
* coordination metadata
* NOT lifecycle authority

## EXECUTION SCOPING

Execution instances are scoped to:

* a specific step
* a specific workflow
* a specific runtime session

Execution instances MUST NOT:

* cross workflow boundaries
* cross step boundaries without explicit re-dispatch
* persist as lifecycle authority

# 2. RETRY IDENTITY SEMANTICS

## RETRY LINEAGE

Retry creates a new entry in execution lineage.

Retry lineage includes:

* parent execution instance reference
* retry attempt number
* new execution instance identity

Retry lineage is:

* observability metadata
* audit trail support
* NOT lifecycle authority

## RETRY INVALIDATION

On retry authorization:

* previous execution instance is invalidated
* previous execution artifacts are quarantined
* new execution instance is created

Invalidation applies to:

* execution instance identity
* execution worker assignment
* execution context

## RETRY REPLACEMENT SEMANTICS

Retry replaces:

* previous active execution instance
* previous worker assignment
* previous execution context

Retry does NOT replace:

* lifecycle state
* step identity
* workflow identity

## RETRY OBSERVABILITY EXPECTATIONS

Retry observability includes:

* new execution instance identity
* retry attempt number
* lineage reference

Projections MAY display:

* retry attempt count
* current execution instance
* historical execution instances

Projections MUST NOT:

* synthesize execution identity
* restore stale execution instances
* define replay legality

## RETRY SYNCHRONIZATION BEHAVIOR

Retry synchronization:

* invalidates previous execution projections
* generates new execution projections
* updates execution lineage

Retry synchronization follows:
ORCHESTRATION_AND_EXECUTION_SEQUENCE_CONTRACT_V1

## RETRY EXECUTION ISOLATION

Retry execution is isolated from prior execution runtime state.

Isolation boundaries include:

* new worker assignment
* new execution context
* fresh execution artifacts
* independent coordination locks

Prior execution state:

* is quarantined
* is NOT resurrected
* is NOT continued

# 3. REPLAY VS RECONSTRUCTION

## REPLAY DEFINITION

Replay is:

* intentional re-execution behavior
* explicit user or system authorized re-execution
* a NEW execution instance with new execution identity

Replay creates:

* a new execution instance
* a new execution attempt
* new execution artifacts

## RECONSTRUCTION DEFINITION

Reconstruction is:

* authority/state restoration behavior
* recovery of authoritative lifecycle state
* recovery of runtime coordination state

Reconstruction restores:

* Lifecycle Authority state
* Runtime Registry coordination state
* projection visibility

Reconstruction does NOT:

* create new execution instances
* replay execution behavior
* resume execution automatically

## REPLAY VS RECONSTRUCTION DISTINCTION

Replay:

* creates NEW execution instances
* requires explicit authorization
* is runtime behavior

Reconstruction:

* restores EXISTING authority state
* is recovery behavior
* does NOT create new execution instances

## EXPLICIT PROHIBITION

Recovery systems MUST NOT behave like replay systems.

Reconstruction MUST NOT:

* automatically replay failed executions
* create new execution instances during recovery
* resume execution without explicit authorization
* synthesize execution replay behavior

---

# 4. REPLAY LEGALITY

## REPLAY LEGALITY CONDITIONS

Replay is LEGAL when:

* workflow is in a state that permits re-execution
* explicit authorization exists
* mutation legality windows are satisfied
* no conflicting active execution exists

Replay is ILLEGAL when:

* workflow is actively executing
* terminalization is in progress
* mutation legality windows are violated
* no explicit authorization exists

## REPLAY AUTHORITY

Replay authority belongs to:

* Lifecycle Authority (state transition authorization)
* Runtime Governance (execution semantics validation)
* User Authority (explicit authorization)

Replay does NOT belong to:

* projections
* streams
* frontend
* persistence layer

## REPLAY VISIBILITY SEMANTICS

Replay visibility includes:

* new execution instance identity
* replay attempt number
* lineage reference

Projections MAY display replay execution instances.

Projections MUST NOT:

* synthesize replay state
* define replay legality
* restore replay authority

## REPLAY INVALIDATION SEMANTICS

On replay:

* previous execution instances remain in lineage
* new execution instance is created
* previous execution artifacts are NOT overwritten

Replay invalidation applies to:

* stale execution projections
* outdated execution visibility

## REPLAY PROJECTION BEHAVIOR

Projections during replay:

* display new execution instance
* maintain historical lineage
* update execution visibility

Projections MUST NOT:

* synthesize replay state
* define replay legality
* restore replay execution context

## REPLAY DOES NOT REDEFINE AUTHORITATIVE HISTORICAL LIFECYCLE TRUTH

Replay creates NEW execution instances.

Replay does NOT modify:

* historical lifecycle transitions
* historical execution results
* historical execution artifacts

Historical execution instances remain in lineage.

New execution instances are appended to lineage.

# 5. EXECUTION LINEAGE

## EXECUTION ANCESTRY

Execution ancestry traces:

* initial execution attempt
* retry attempts
* replay attempts

Execution ancestry is:

* observability metadata
* audit trail support
* coordination metadata

## RETRY ANCESTRY

Retry ancestry includes:

* parent execution instance
* retry attempt number
* retry authorization context

Retry ancestry is:

* append-only
* immutable historical records
* non-authoritative metadata

## REPLAY ANCESTRY

Replay ancestry includes:

* original execution instance
* replay authorization context
* new execution instance

Replay ancestry is:

* append-only
* immutable historical records
* non-authoritative metadata

## EXECUTION OBSERVABILITY LINEAGE

Execution observability lineage provides:

* execution history
* retry history
* replay history
* execution outcome records

Execution observability lineage is:

* projection-rendered
* stream-transported
* frontend-displayed

Execution observability lineage is NOT:

* lifecycle authority
* governance input
* replay trigger

## INVALIDATION PROPAGATION LINEAGE

Invalidation propagates through lineage:

* retry invalidates previous execution instance
* replay does NOT invalidate previous execution instances
* terminalization invalidates all active execution instances
* cancellation invalidates all active execution instances

## RETRY LINEAGE REPLACEMENT CLARIFICATION

Retry is:
execution lineage replacement.

NOT:
terminal state reversal.

NOT:
stale execution resurrection.

Retry creates a NEW execution instance.

Retry does NOT:

* resurrect stale execution
* continue previous execution context
* rewind lifecycle state

## FAILED RETRY SEMANTICS

FAILED workflows MAY support retry under:

* mutation legality rules
* execution identity isolation rules
* runtime coordination rules

Retry for FAILED workflows:

* creates NEW execution lineage
* is NOT stale execution continuation
* is NOT terminal state reversal

## CANCELLATION LINEAGE SEMANTICS

CANCELLED workflows create:

* terminalized execution lineage
* immutable terminal state

CANCELLED workflows do NOT support:

* retry
* continuation
* resurrection

Cancellation invalidates:
all active execution instances.

Cancellation semantics are governed by:
WORKFLOW_CANCELLATION_AND_TERMINALIZATION_CONTRACT_V1

## RETRY != RESURRECTION CLARIFICATION

Retry is NEVER:

* resurrection of previous execution state
* continuation of previous execution context
* reuse of previous execution artifacts
* stale execution continuation

Retry is ALWAYS:

* new execution instance creation
* fresh isolation boundary establishment
* execution lineage replacement
* explicit re-execution behavior

Invalidation propagation is:

* coordination behavior
* runtime behavior
* NOT lifecycle authority modification

# 7. RECONSTRUCTION BOUNDARIES

## RECOVERY RESTORATION LEGALITY

Recovery restoration is LEGAL when:

* system restarts
* system reconnects
* system recovers from failure

Recovery restoration restores:

* Lifecycle Authority state
* Runtime Registry coordination state
* projection visibility

Recovery restoration does NOT:

* replay execution
* create new execution instances
* resume execution automatically

## RUNTIME RECONSTRUCTION LEGALITY

Runtime reconstruction restores:

* execution tracking
* worker mappings
* coordination locks

Runtime reconstruction does NOT:

* replay execution
* create new execution instances
* resume execution automatically

Runtime reconstruction is governed by:
RUNTIME_REGISTRY_AND_EXECUTION_COORDINATION_CONTRACT_V1

## STALE EXECUTION INVALIDATION

Stale execution instances MUST be invalidated during reconstruction when:

* execution instance has no corresponding lifecycle state
* execution instance references invalid worker
* execution instance is orphaned

Stale execution invalidation:

* is coordination cleanup
* is NOT lifecycle transition
* is NOT projection update

## PROJECTION RECONSTRUCTION BOUNDARIES

Projection reconstruction:

* regenerates from authoritative state
* rebuilds execution visibility
* restores execution lineage display

Projection reconstruction does NOT:

* synthesize execution identity
* authorize replay
* restore execution context

## RECONSTRUCTION RESTORES AUTHORITY STATE, NOT EXECUTION REPLAY

Reconstruction restores:

* authoritative lifecycle state
* runtime coordination state
* projection visibility

Reconstruction does NOT:

* replay execution behavior
* create new execution instances
* resume execution automatically
* synthesize execution replay
