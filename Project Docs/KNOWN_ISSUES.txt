Classification:
ARCHITECTURAL LIMITATION

Behavior:
* Orchestrator: SYNCHRONOUS
* API Layer: ASYNC WRAPPER (thread executor)
* Streaming: POLLING-BASED

Execution Flow:
API → run_in_executor → orchestrator_runtime (blocking) → events stored → UI polls

Implications:
* No true async streaming
* No progressive updates during resume
* UI receives final state after completion

Status:
ACCEPTED LIMITATION (Future improvement candidate)

[ISSUE_029]
Title: LLM Validation and Constraint Overhead Causes Excessive Per-Step Execution Cost

Root Cause:
System performs multiple LLM calls per execution step due to:

* duplicate semantic validation (multiple semantic checks per step)
* duplicate constraint extraction (LLM + structured extraction)
* lack of conditional validation gating
* validation executed regardless of step complexity

Evidence:
Audit results show:

* ~20 LLM calls per run
* ~50% of calls from semantic validation alone
* Constraint extraction executed twice per step
* Structured constraint extraction output is not used anywhere in system
* Semantic validation executed multiple times per step with overlapping purpose

Repro:
Run multi-step workflow (e.g. add 2 and 3 then multiply by 4)
Observe LLM trace logs and count calls per step

Expected:

* Minimal LLM usage per step
* Single validation pass per step
* No redundant constraint extraction
* Conditional validation based on step complexity

Actual:

* ~6–7 LLM calls per step
* Multiple semantic validation calls with overlapping purpose
* Duplicate constraint extraction (one unused)
* Linear performance degradation with step count

Impact:
CRITICAL — system performance degrades linearly with step count and is significantly slower than necessary

Priority:
CRITICAL
