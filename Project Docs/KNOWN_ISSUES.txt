# ⚠️ ACTIVE NON-P0 ISSUES

---

## 1. PARSER NUMERIC-ONLY LIMITATION

Parser extracts numeric arguments ONLY.

### STATUS

✔ By design
⚠ Known limitation

### EXPLANATION

Parser is intentionally limited to deterministic numeric extraction.
String arguments, file paths, URLs require explicit handling.

### ACTION

Future phases may expand argument types while maintaining determinism.

---

## 2. PLANNER RULE-BASED LIMITATION

Planner uses simple keyword matching:

* substring detection
* " then " splitting
* TOOL_RULES lookup

### STATUS

✔ By design
⚠ Known limitation

### EXPLANATION

Deterministic behavior is enforced.
No NLP, no inference, no semantic understanding.

### ACTION

Planner Hardening phase will expand coverage while maintaining determinism.

---

## 3. LLM NON-DETERMINISM (CONTROLLED)

LLM output may vary between executions when enabled.

### STATUS

✔ Controlled via validation layer
⚠ Known limitation

### EXPLANATION

LLM is non-deterministic by nature.

System mitigates this via:

- strict prompt constraints
- JSON-only output requirement
- validation layer enforcement
- fail-safe fallback (passthrough)

### ACTION

Future phases may introduce:

- response caching
- retry strategies
- stricter prompt templates

---

## 4. DOCUMENTATION DRIFT (BEING RESOLVED)

System behavior exceeded documented contracts.

### STATUS

⚠ IN PROGRESS

### EXPLANATION

- Contracts being realigned to implementation
- Multiple recent fixes applied
- Documentation updates in progress
- Harness limitations identified

### ACTION

Documentation alignment ongoing. System is FUNCTIONAL but requires contract hardening.

---

## 5. INPUT NORMALIZATION LIMITATION

Input normalization has architectural placement issues.

### STATUS

⚠ Known limitation

### EXPLANATION

- Normalization exists INSIDE planner (not pre-planner layer)
- No dedicated pre-planner normalization layer exists
- No noise word removal implemented ("please", "hey", "can you")
- Partial casing normalization (inconsistent behavior observed)

### ACTION

Architecture realignment required:
- Extract normalization to pre-planner layer
- Implement noise word removal
- Standardize casing normalization

---

## 6. HARNESS CONTRACT VALIDATION GAP

Harness does not fully validate tool return schemas.

### STATUS

⚠ Known limitation (P0 Blocker)

### EXPLANATION

- Harness validates behavior not structure
- Subset matching may miss contract violations
- Tool return schemas not strictly enforced
- Contract violations may pass harness

### ACTION

Harness hardening required:
- Add strict schema validation
- Enforce tool output contracts
- Validate failure structures

---

## 7. FLOAT SUPPORT CONTRACT GAP

Float support exists in parser/execution but not in contracts.

### STATUS

⚠ Known limitation

### EXPLANATION

- Parser extracts floats
- Execution processes floats
- Registry supports float type
- Contracts do not explicitly define float behavior

### ACTION

Update SYSTEM_CONTRACTS.txt to formalize float support:
- Define numeric type as int | float
- Document float validation rules
- Document float execution rules

---

## 8. RESOLVER PHRASE STRIPPING COMPLEXITY

Resolver now performs command phrase stripping.

### STATUS

⚠ Known limitation

### EXPLANATION

- Resolver behavior expanded beyond original scope
- Phrase stripping adds complexity
- Dependency on TOOL_PHRASES mapping
- Potential for drift between planner and resolver

### ACTION

Monitor for consistency:
- Ensure planner/resolver phrase alignment
- Document phrase stripping behavior
- Consider consolidation in future
