## 15. FORMATTER MAY PRODUCE INCORRECT OUTPUTS

Response formatter uses LLM — output is not trusted.

### STATUS

⚠ Known limitation — by design

### EXPLANATION

- `_format_tool_output` calls `ollama_llm` to convert raw output to human-readable text
- LLM may hallucinate or produce unrelated responses
- Formatter failure falls back to raw output (safe fallback exists)
- Formatted output is never validated for correctness

### ACTION

Formatter is advisory only. Future improvement: add confidence scoring or skip formatter for math results.

---

## 16. MEMORY SYSTEM CAN LEARN INCORRECT NOISE TOKENS

Execution memory learns from failure→success pairs but may learn valid tokens as "noise".

### STATUS

⚠ Known limitation

### EXPLANATION

- If LLM adds a word that happens to differ between attempts, it may be learned as a bad token
- Filters prevent numeric, quoted, and path tokens — but word tokens are still at risk
- Example: "hello" was learned as a bad token for `subtract_numbers`

### ACTION

Future improvement: require minimum usage_count threshold before applying a learned token.

### HAND ISSUE — STEP EXECUTION MODEL

Step performs multiple executions (retries), not single-call.

### STATUS

⚠ Accepted behavior — documented in ORCHESTRATOR_CONTRACT.txt

### EXPLANATION

- orchestrator_runtime.py implements governance-controlled retry (lines 269+)
- Step may trigger multiple system_entry calls when governance returns "retry"
- Governance decision determines retry vs failure vs continuation
- last_result updated only after successful validation

### ACTION

Retry behavior must be governed by governance decisions. Any implicit retry logic is considered drift.

- Non-tool execution paths may not properly validate context usage
- Context is ephemeral — not persisted to workflow state until step completion

Monitor during chaining validation. Document edge cases.

- Governance authority lock implemented

- All signal-related control issues resolved

## 18. PLANNER OUTPUT INSTABILITY

Planner outputs non-deterministic JSON (extra text, multiple JSON blocks, explanations).

### STATUS

⚠️ OPEN — Observed during testing

### EXPLANATION

- Planner returns valid JSON followed by additional text
- Causes JSON parse failures (Extra data errors)
- Forces fallback to agent execution
- Planner does not enforce strict JSON-only output

### IMPACT

- Planner becomes unreliable for structured planning
- Multi-step orchestration degraded
- System relies on fallback behavior instead of structured planning

### ACTION

Planner must enforce strict JSON-only output with no additional text.

## 19. MULTI-STEP TASK COLLAPSE

Multi-step tasks collapse into single-step execution.

### STATUS

⚠️ OPEN — Observed during testing

### EXPLANATION

- Planner fails to produce structured steps for multi-step tasks
- Agent executes only first tool
- Remaining logical steps are hallucinated in LLM output rather than executed

Example:
- "get my name from file and greet me"
- → only read_file executed
- → greeting generated by LLM (not system execution)

### IMPACT

- Orchestration model broken for multi-step workflows
- System cannot reliably execute chained operations
- Dependent on planner reliability (Issue #18)

### ACTION

Fix planner JSON output stability first. Then validate multi-step workflow execution.

## 21. INVALID INPUT HANDLING (NON-RETRYABLE FAILURES)

System retries deterministic failures that cannot succeed on retry.

### STATUS

⚠️ OPEN — Observed during testing

### EXPLANATION

- division_by_zero triggers retry loop
- invalid_domain (sqrt negative) triggers retry loop
- These failures are deterministic — retry will never succeed

### IMPACT

- Wasted execution cycles
- Unnecessary resource consumption
- Poor user experience (delay before eventual failure)

### ACTION

Implement failure classification: retryable vs non-retryable.
Non-retryable failures should fail immediately without retry attempts.
