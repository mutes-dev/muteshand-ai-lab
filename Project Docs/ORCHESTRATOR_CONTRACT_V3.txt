## Scope — Orchestrator Layer Only

This document defines the behavior of the Orchestrator Layer ONLY.

Applies to:
- workflows (projects)
- planning
- step execution control
- agents
- governance coordination
- approval handling
- learning influence
- memory usage

Does NOT apply to:
- core execution pipeline (system_entry)
- tool execution logic

## Core Principle

ORCHESTRATOR = coordination and control executor.

The orchestrator:
- coordinates execution flow
- adapts based on context and learning
- NEVER executes actions directly
- is NOT the runtime decision authority

Authority stack:
- execution_result = execution truth only
- Core/system_entry = deterministic execution gateway
- Governance = runtime decision authority
- Lifecycle Authority = lifecycle truth
- User = final authority through backend-validated control paths
- Orchestrator = coordination/control executor, not decision authority

## Authority Model

Priority (operational, not override hierarchy):

1. User (through backend-validated control paths)
2. Governance (runtime decision authority)
3. Orchestrator (coordination and control executor)

Rules:
- user intent flows through backend validation -> governance/runtime decision -> legal lifecycle/mutation action -> projection update
- system may warn or temporarily block
- user may request override; override is subject to USER_CONTROL_CONTRACT_V2 and backend validation
- force execution remains subject to lifecycle legality, mutation legality, dependency validity, governance safety, tool safety, privacy/sensitivity rules, approval requirements, and backend acceptance

## Workflow (Project) Model

### Definition

Simple queries may remain chat answers. Meaningful, complex, long-running, reusable, multi-step, or stateful work becomes a project/workflow.

Projects/workflows are:
- independent
- stateful
- parallelizable
- non-blocking

### States

- QUEUED
- ACTIVE
- PAUSED
- BLOCKED
- COMPLETED
- FAILED
- CANCELLED

### Rules

- no cross-project blocking
- conflict detection required for shared resources
- user can control any project at any time (through backend-validated paths)

## Step Model

### Step Types

- ANALYZE
- RESEARCH
- PLAN
- PROPOSE
- EXECUTE_API
- EXECUTE_LOCAL
- EXECUTE_FILE
- EXECUTE_INSTALL
- EXECUTE_SYSTEM_SETTINGS_SERVICES
- EXECUTE_ENVIRONMENT
- VALIDATE
- GENERATE
- BUILD

### Step Rules

- one step = one logical action
- one step = one system_entry call per attempt
- retries allowed within limits
- steps are atomic at execution level

### Step Completion

A step is COMPLETE ONLY if:
- execution succeeded
- purpose achieved
- validation passed
- required approvals obtained
- mutation legality confirmed
- lifecycle transition legally allowed

### Failure Model

- retry (risk-based limits)
- escalate when exhausted
- block when recoverable stall

Risk behavior:
- LOW -> more retries
- MEDIUM -> limited
- HIGH -> minimal

## Execution Control

### Parallel Execution

Allowed ONLY if:
- no dependencies
- no shared state conflicts

NEVER parallel:
- installs
- system changes
- environment changes
- destructive file actions

### Sequential Enforcement

Critical steps MUST execute in order.

Before executing any step:
- resource_targets MUST be evaluated
- conflict detection MUST run
- execution MUST respect conflict resolution contract

## Observability Projection Exposure

### Orchestrator MAY Expose Observability Projections

Orchestrator MAY expose observability projections for:
- dashboard rendering
- runtime monitoring
- orchestration topology visualization
- websocket/event stream consumption

Orchestrator observability projections:
- originate from orchestrator-owned canonical projection generation
- remain orchestrator-owned
- remain non-authoritative for consumers

### Orchestrator Remains Coordination Executor

Observability exposure does NOT delegate orchestration authority.

Orchestrator is:
- the coordination/control executor
- the lifecycle transition requester (requests through Lifecycle Authority, does not own lifecycle truth)

Runtime Registry owns runtime execution coordination state.

Orchestration sequencing semantics are governed by ORCHESTRATION_AND_EXECUTION_SEQUENCE_CONTRACT_V2.

Lifecycle Authority owns lifecycle truth.

Governance owns runtime decisions.

Dashboard, websocket, and frontend layers remain:
- passive consumers
- non-authoritative
- downstream-only

### Observability Exposure Does Not Delegate Orchestration Authority

Frontend systems consuming orchestrator observability feeds:
- MAY render, group, filter, aggregate
- MUST NOT synthesize orchestration authority
- MUST NOT derive lifecycle truth from projections
- MUST NOT infer workflow ownership from visibility

Orchestrator MUST NOT:
- delegate projection ownership to frontend
- allow uncontrolled projection mutation
- allow frontend to reconstruct authority from projections
