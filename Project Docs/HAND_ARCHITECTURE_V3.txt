## Product Identity

AI Lab / MutesHand is a local-first, project-based autonomous AI operating environment.

It is NOT only a chatbot. It uses chat as the primary entry interface, but meaningful work becomes governed projects/workflows.

It is also NOT:
- a cloud-only service
- an ungoverned autonomous agent
- a general-purpose AI assistant without boundaries

It IS:
- a controlled autonomous AI system
- a local-first execution environment with optional cloud augmentation
- a project/workflow-centric platform
- a system with strict execution control, validation, and governance
- a system that balances autonomy with explicit user authority

## Architecture Layers

```
USER (Authority)
  |
  v
ORCHESTRATOR (Intelligence + Coordination)
  |
  v
GOVERNANCE (Runtime Decision Authority)
  |
  v
LIFECYCLE AUTHORITY (Lifecycle Truth)
  |
  v
CORE / system_entry (Deterministic Execution)

Derived / Downstream Layers (non-authoritative):

Advisory Context Layers:
- MEMORY / LEARNING (Advisory Persistence — never authority)

## Authority Stack

### 1. USER = Final Authority

- User can override any decision subject to safety, legality, and system-integrity gates
- System may warn or temporarily block unusual actions
- User can always force execution through proper backend-validated channels
- User instruction overrides learned behavior
- User is the owner/admin for the initial build (Bryan)

### 2. ORCHESTRATOR = Intelligence + Coordination

Responsibilities:
- workflow creation and management
- step planning and decomposition
- execution sequencing and control
- memory usage coordination
- learning adaptation coordination
- approval request generation
- user control request handling
- retry handling (under governance authorization)
- parallel execution coordination (where safe)
- conflict detection

Constraints:
- MUST NOT execute tools directly
- MUST NOT modify tool inputs
- ALL execution MUST go through system_entry
- MUST NOT claim lifecycle authority
- MUST NOT claim governance authority
- MUST NOT claim execution truth

### 3. GOVERNANCE = Runtime Decision Authority

Governance owns:
- retry authorization
- completion authorization
- failure authorization
- escalation authorization
- approval handling and validation
- user-control validation
- privacy gate decisions
- budget/spend gate decisions
- mutation legality decisions
- self-development gate decisions

Governance decisions:
- COMPLETE — step/workflow is finished
- RETRY — step may be retried (with limits)
- FAIL — step/workflow has failed
- BLOCK — step/workflow is blocked (recoverable)
- ESCALATE — requires human / SA intervention

Governance constraints:
- MUST NOT execute tools
- MUST NOT modify execution_result
- MUST NOT claim lifecycle authority
- MUST NOT bypass system_entry
- MUST validate stale/expired approvals

### 4. LIFECYCLE AUTHORITY = Lifecycle Truth

Lifecycle Authority owns:
- authoritative workflow lifecycle state
- authoritative lifecycle transitions
- authoritative workflow state ownership

Canonical lifecycle states:
- QUEUED
- ACTIVE
- PAUSED
- BLOCKED
- COMPLETED
- FAILED
- CANCELLED

Additional transitional runtime states (orchestration-only, NOT durable lifecycle truth):
- ACTIVATING
- RESTORING
- PENDING_RECOVERY
- REHYDRATING

Lifecycle Authority is the ONLY source of lifecycle truth.

### 5. CORE / system_entry = Deterministic Execution

See CORE_SYSTEM_ENTRY_PIPELINE_ARCHITECTURE_V1.txt for full specification.

Summary:
- deterministic
- single-step only
- no reasoning
- no learning
- no inference
- no governance
- no lifecycle awareness

All execution MUST go through system_entry.

### 6. PROJECTIONS / GUI / OBSERVABILITY = Downstream / Non-Authoritative

Projections:
- are synchronized read-model layers
- are NOT authoritative
- do NOT define lifecycle truth
- do NOT gate execution
- do NOT gate terminalization

Observability:
- is passive visibility only
- is advisory analysis only
- does NOT mutate runtime behavior
- does NOT override governance

GUI:
- is a thin, context-aware interaction layer
- consumes projections
- sends intent WITH context
- does NOT synthesize authority
- does NOT reconstruct execution truth

## Project / Workflow Model

### Model

Simple queries may remain chat answers.
Meaningful, complex, long-running, reusable, multi-step, or stateful work becomes a project/workflow.

### Properties

- independent (one project failing does not block unrelated projects)
- parallel (where no dependency or shared-state conflicts exist)
- stateful (has persistent state across sessions)
- long-running (can continue for hours or days)

### States

Canonical lifecycle states:
- QUEUED
- ACTIVE
- PAUSED
- BLOCKED
- COMPLETED
- FAILED
- CANCELLED

Rules:
- no cross-project blocking (unless shared resource conflicts)
- conflict detection required for shared resources

## Orchestrator Role

The orchestrator is the intelligence and coordination layer.

It is responsible for:
- interpreting user intent
- planning and decomposing tasks into steps
- selecting tools (via AG1 bounded agent or capability routing)
- sequencing execution
- coordinating parallel execution (where safe)
- handling retries (under governance authorization)
- managing memory context
- coordinating learning and adaptation
- generating approval requests
- handling user control requests

It is NOT responsible for:
- executing tools directly
- making governance decisions
- owning lifecycle state
- modifying execution_result
- bypassing system_entry

### Execution Rule

ALL execution MUST go through system_entry.

### Step Model

Each step:
- has a type
- has a purpose
- triggers system_entry for execution
- receives execution_result
- is governed by governance decisions

Step types (from SYSTEM_GOALS_V2):
- ANALYZE
- RESEARCH
- PLAN
- PROPOSE
- EXECUTE_API
- EXECUTE_LOCAL
- EXECUTE_FILE
- EXECUTE_INSTALL
- EXECUTE_SYSTEM_SETTINGS_SERVICES
- EXECUTE_ENVIRONMENT
- VALIDATE
- GENERATE
- BUILD

### Step Completion

A step is complete only if:
execution success AND purpose met AND validation passed

## Governance Role

Governance is the runtime decision authority. It is NOT a placeholder.

Governance owns:
- retry authorization (when and how many retries)
- completion authorization (when a step/workflow is truly complete)
- failure authorization (when to declare FAILED)
- escalation authorization (when to escalate to user/SA)
- approval handling (validation of user approvals, rejection of stale/expired approvals)
- user-control validation (backend validation of user override/force requests)
- privacy gate decisions (whether data may leave local system)
- budget/spend gate decisions (whether financial obligations may be incurred)
- mutation legality decisions (whether a mutation is legal in current state)
- self-development gate decisions (whether a self-development proposal may proceed)

Governance decisions are deterministic and based on:
- execution_result
- step type and risk level
- user configuration
- learned patterns (advisory only)
- safety rules
- legal constraints

It owns:
- workflow lifecycle state

- workflow state ownership

It does NOT own:

## Planning / Capability / Agent Boundary

### Planners

The system implements TWO distinct planners:

1. **Core Planner (deterministic)**
   - Location: `core/planner.py`
   - Type: Rule-based, deterministic phrase matching
   - Scope: Core pipeline execution
   - Output: List of tool steps with type, name, input_text

2. **Orchestrator Planner (LLM-based)**
   - Location: `system/orchestrator/orchestrator_planner.py`
   - Type: LLM-assisted workflow planning
   - Scope: Orchestrator layer above system_entry
   - Output: Workflow with steps containing name, purpose, agent, estimated_complexity

Separation Rule:
- Core planner -> pipeline execution
- Orchestrator planner -> workflow decomposition
- NO cross-layer planner access

### Capability Routing

Capability routing is:
- advisory and pre-runtime
- bounded by AGENT_CAPABILITY_ROUTING_CONTRACT_V1
- NOT autonomous orchestration
- NOT lifecycle authority
- NOT execution authority

Valid authority chain:
```
user prompt -> capability router -> capability normalizer/compiler -> candidate workflow/DAG -> planning compiler -> workflow validator -> runtime/governance/system_entry -> execution_result truth -> output aggregation/final display
```

### Agents (AG1)

AG1 agents are:
- bounded intelligence infrastructure
- NOT runtime authority
- advisory-only
- stateless (tool-selection agent)
- non-authoritative for lifecycle, governance, execution, projection, or mutation

See AGENT_GOVERNANCE_CONTRACT_V2.txt for full AG1 containment rules.

## Memory and Learning Governance

### Memory Types

- global memory (user behavior, preferences, habits)
- project memory (project-specific context)
- workflow memory (execution history, tool preferences)

### Memory Rules

- Memory persists across sessions
- Memory is editable, reviewable, and resettable by the user
- Memory updates are suggestable, approvable, rejectable, and editable
- Memory MUST NEVER override explicit user instruction
- Memory is advisory-only for governance and orchestration

### Learning Rules

- System learns preferences, approvals, and patterns over time
- Low-risk actions may become autonomous sooner
- High-impact actions always require approval
- Learning is bounded and governed
- Learned autonomy may be revoked by the user at any time

### Learning Governance

- Memory/learning proposals require approval (except low-risk, pre-configured categories)
- The system may suggest memory updates based on observed patterns
- New memory suggestions do NOT silently become permanent
- The system should challenge habits when research suggests better patterns
- All learning is reversible

## Privacy and Cloud Routing

### Sensitivity Levels

- LOW — public or non-sensitive data
- MEDIUM — general personal or project data
- HIGH — sensitive personal, financial, health, identity, family, or source-code data
- CRITICAL — data that must never leave local system without explicit approval

### Cloud Routing Rules

- The system MUST classify data sensitivity before sending to cloud
- HIGH and CRITICAL sensitivity data MUST require explicit approval before leaving local system
- The system SHOULD prefer local models/tools for sensitive context
- The system MUST support redaction or summarization before cloud routing where possible
- User must be able to define and edit privacy rules
- Future restricted users must never gain access to private memory or local files unless explicitly granted

### Local-First Principle

- Core operation should work locally and offline where possible
- Cloud is optional augmentation
- Reduced capability offline is acceptable
- Core execution should not be dependent on the internet

---

## Spending and Budget Governance

### Financial Obligation Rule

The system MUST NEVER create a new financial obligation without explicit user approval.

Examples of new financial obligations:
- new purchases or subscriptions
- unbounded spending
- creating new paid service accounts

### Prepaid / Budget Envelope Rule

- Prepaid or preloaded balances MAY be used under learned or configured budget rules
- Budget envelopes MUST have clear limits, service scope, and visibility
- The system MUST NOT waste prepaid credits
- Early-stage paid service use SHOULD default to approval until patterns are learned
- The user MUST be able to revoke learned budget autonomy at any time

### Budget Visibility

- Dashboard shows remaining budget, recent spend, active jobs, estimated cost
- Stop controls must be available
- Cost estimates should be provided before paid execution

```
PROPOSAL -> APPROVAL -> SANDBOX DEVELOPMENT -> TESTS -> REPORT -> INTEGRATION APPROVAL -> INTEGRATION -> ROLLBACK PATH

### Constraints

- Approval REQUIRED before development
- Sandbox execution ONLY during development

- Approval REQUIRED before integration

- Rollback path REQUIRED
- Integration must not break existing functionality

### Governance

- Self-development proposals require governance approval
- Development happens in isolated sandbox
- Tests must pass before integration approval
- Integration approval requires explicit user consent
- Rollback must be possible if integration causes issues

## Failure / Retry / Validation Model

### Failure Model

- retry within limits
- escalate when needed
- risk-based retry limits

Retry rules:
- LOW risk -> more retries
- MEDIUM -> limited retries
- HIGH -> minimal retries

Retry behavior:
- first retry = same input (SAME enforcement)
- subsequent retries = variation (if governance authorizes)

### Validation Model

Validation strength depends on:
- step type
- risk level

COMPLETE = success AND purpose_met AND validated

If any fail -> step is NOT complete
