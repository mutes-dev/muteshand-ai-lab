## Scope

Defines how step dependencies are represented, validated, and used for execution ordering.

This contract ensures:
- correct step sequencing
- safe parallel execution
- deterministic execution order
- reliable multi-step workflows

Dependency invalidation propagation is governed by:
MUTATION_LEGALITY_AND_RUNTIME_ISOLATION_CONTRACT_V2

Orchestration sequencing is governed by:
ORCHESTRATION_AND_EXECUTION_SEQUENCE_CONTRACT_V2

Mutation legality is governed by:
MUTATION_LEGALITY_AND_RUNTIME_ISOLATION_CONTRACT_V2

---

## Core Principle

DEPENDENCIES = explicit execution constraints

System MUST rely ONLY on:
- explicitly defined dependencies
- resource_target conflicts

System MUST NOT:
- infer dependencies from purpose
- infer dependencies from natural language
- apply heuristic ordering

Planner/compiler may declare or bind dependencies before validation, but runtime execution uses only declared validated dependencies and resource_target conflicts.

Runtime must not infer dependencies from natural language at execution time.

---

## 1. Step Dependency Field

### Definition

Each STEP MAY define:

"depends_on": ["<id>", ...]

### Rules

depends_on is REQUIRED when:
- step relies on output from another step
- step modifies or depends on shared resources
- execution order cannot be determined by isolation

depends_on MAY be omitted ONLY if step is fully independent.

Empty or absent = no dependency

### Validity

Each dependency MUST:
- reference an existing id
- not reference itself
- not create circular dependency

---

## Step Identifier Requirement

Each STEP MUST include:

"id": "<unique_identifier>"

Rules:
- MUST be unique within the plan
- MUST be stable across execution
- MUST NOT change during execution lifecycle
- MUST be used as the sole reference for dependencies

Dependencies MUST reference "id" ONLY.

---

## 2. Dependency Graph

### Definition

Steps form a Directed Acyclic Graph (DAG)

Nodes = steps
Edges = dependencies

### Rules

Graph MUST:
- be acyclic (no loops)
- be resolvable (no missing nodes)
- allow at least one valid execution path

---

## 3. Execution Order

### Principle

Execution order is derived from dependency graph.

Rules:
- step may execute ONLY when all dependencies are COMPLETED
- dependency completion = governance COMPLETE
- FAILED dependencies block dependent steps.

Override behavior MUST be defined by GOVERNANCE_CONTRACT_V3.

Scheduling and dependency model MUST NOT define override logic.

---

## 4. Parallel Eligibility

A step is eligible for parallel execution ONLY if:
- all dependencies satisfied
- no resource conflict
- not excluded by type/risk

---

## 5. Plan Validation

Plan MUST validate dependency graph:

Checks:
- no circular dependencies
- all referenced steps exist
- dependency ordering is valid

If invalid:
- plan MUST be rejected OR flagged for correction

---

## 6. Runtime Responsibility

Runtime step construction layer MUST:
- ensure all steps have valid dependency structure
- validate all dependency references exist

Runtime MUST NOT:
- resolve missing dependencies
- infer missing links
- auto-correct dependency structure

---

## 7. Validation Integration

Validation MUST include:
- dependency graph correctness
- dependency resolution readiness

Validation failure MUST:
- block execution
- trigger correction or escalation

---

## 8. Scheduling Integration

Scheduler MUST:
- use dependency graph as primary ordering mechanism
- combine with resource_target conflict checks
- NOT infer missing dependencies

---

## 9. State Integration

Step may transition to ACTIVE ONLY if:
- dependencies are satisfied

Dependency failure:
- dependent step remains BLOCKED or FAILED
- per GOVERNANCE_CONTRACT_V3

---

## 10. Dependency Consistency During Execution

### Principle

Dependencies MUST remain valid throughout execution.

Execution MUST respect dependency integrity at all times.

### Failure Propagation

If a dependency step:
- FAILS
- is RETRIED
- is INVALIDATED after completion

Then:
- all dependent steps MUST be re-evaluated

### Dependent Step Behavior

If dependency becomes invalid:

Dependent steps MUST:
- transition to BLOCKED, be re-evaluated, or follow authorized governance/replan path
- NOT continue execution based on stale results

Dependency invalidation routes through governance, scheduling, mutation legality, and lifecycle authority.

Do not mention INVALID state unless STATE_TRANSITIONS_CONTRACT_V2 defines it.

### Retry Integration

When a dependency is retried:
- dependent steps MUST NOT execute until dependency resolves again
- previously completed dependent steps MAY require re-execution
- re-execution decision is governed by GOVERNANCE_CONTRACT_V3
- retry invalidation sequencing follows:
ORCHESTRATION_AND_EXECUTION_SEQUENCE_CONTRACT_V2

### No Stale Execution

System MUST NOT allow:
- dependent steps to execute using outdated dependency results
- continuation of execution after dependency invalidation
- stale dependency execution during retry invalidation propagation
- scheduler continuing with stale evaluation results after invalidation

Stale dependency rejection is governed by:
MUTATION_LEGALITY_AND_RUNTIME_ISOLATION_CONTRACT_V2

### Governance Authority

Governance determines:
- whether dependent steps retry
- whether workflow continues or fails
- whether user intervention is required

Dependency model MUST NOT override governance decisions.

Scheduler re-evaluation boundaries are governed by:
ORCHESTRATION_AND_EXECUTION_SEQUENCE_CONTRACT_V2

### CANCELLED/Terminal State Alignment

If a dependency step is CANCELLED:
- dependent steps MUST be re-evaluated
- dependent steps MAY transition to BLOCKED or FAILED per GOVERNANCE_CONTRACT_V3
- dependent steps MUST NOT continue based on stale results

CANCELLED/terminal states must align with STATE_TRANSITIONS_CONTRACT_V2.

Execution order MUST be explicit, deterministic, and validated.

Dependencies define structure.
Scheduling defines grouping.
Governance defines decisions.

Dependency invalidation propagation is governed by:
