# TEST METADATA CONTRACT

**Version:** 1.0  
**Created:** May 2026  
**Status:** ACTIVE — AUTHORITATIVE TEST METADATA GOVERNANCE

---

## PURPOSE

Every test must declare intent.

Every test must declare authority layer.

Every test must declare category.

Every test must declare entrypoint usage.

Hidden validation semantics are architectural drift.

Metadata exists to preserve validation governance.

---

### UNCLEAR TESTS ARE INVALID

**Unclear tests are invalid.**

A test without clear metadata represents architectural drift.

**Definition of Unclear Test:**
- No category declaration
- No authority layer declaration
- No entry point declaration
- Direct internal calls without intent declaration
- Monkeypatch usage without declaration
- Mixed concerns without separation

**Consequence:**
Unclear tests must be rejected during code review.

---

### UNDECLARED DIRECT CALLS ARE INVALID

**Undeclared direct calls are invalid.**

Direct internal calls without explicit intent declaration represent architectural drift.

**Definition of Undeclared Direct Call:**
- Direct import of internal module without metadata declaration
- Direct call to internal function without metadata declaration
- Direct access to internal state without metadata declaration

**Consequence:**
Tests with undeclared direct calls must be rejected during code review.

---

### UNDECLARED MONKEYPATCHING IS INVALID

**Undeclared monkeypatching is invalid.**

Monkeypatch usage without explicit declaration represents architectural drift.

**Definition of Undeclared Monkeypatching:**
- Use of `monkeypatch` without MONKEYPATCH_USAGE field
- Use of `patch` without MONKEYPATCH_USAGE field
- Use of `MagicMock` without MONKEYPATCH_USAGE field
- Runtime state manipulation without MONKEYPATCH_USAGE field

**Consequence:**
Tests with undeclared monkeypatching must be rejected during code review.

---

### UNDECLARED CATEGORY MIXING IS INVALID

**Undeclared category mixing is invalid.**

Mixed-category files without explicit declaration represent architectural drift.

**Definition of Undeclared Category Mixing:**
- Single file testing multiple categories without declaration
- Single file using multiple entry points without declaration
- Single file with mixed authority layers without declaration

**Consequence:**
Tests with undeclared category mixing must be rejected during code review.

---

## 2. REQUIRED TEST METADATA

Every test file MUST include the following metadata fields in its header docstring.

---

### CATEGORY

**Purpose:** Defines the validation category of the test

**Allowed Values:**
- `HARNESS_CONTRACT` — External contract validation
- `INTERNAL_RUNTIME` — Internal behavior validation
- `INTEGRATION` — Component integration validation
- `ADVERSARIAL` — Authority stress testing
- `REGRESSION` — Historical bug prevention
- `STABILIZATION` — Temporary architectural hardening
- `GOVERNANCE` — Decision authority validation
- `LIFECYCLE` — State transition validation
- `PROJECTION` — Projection synchronization validation
- `VALIDATION` — Structural validation
- `OBSERVABILITY` — Trace and event validation
- `PERFORMANCE` — Performance validation
- `DEBUG_REPRO` — Debug reproduction

**Examples:**
```
CATEGORY: HARNESS_CONTRACT
CATEGORY: INTERNAL_RUNTIME
CATEGORY: REGRESSION
```

**Enforcement Meaning:**
- Determines allowed entry points
- Determines allowed direct internal calls
- Determines allowed monkeypatching
- Determines architectural scope

---

### AUTHORITY_LAYER

**Purpose:** Defines which authority layer the test validates

**Allowed Values:**
- `External Observable Truth` — Harness tests validate external API
- `Runtime Behavioral Truth` — Internal tests validate behavior
- `Component Integration Truth` — Integration tests validate integration
- `Authority Stress Testing` — Adversarial tests stress authority
- `Historical Bug Prevention` — Regression tests prevent recurrence
- `Temporary Architectural Hardening` — Stabilization tests harden system
- `Decision Authority Validation` — Governance tests validate decisions
- `Lifecycle State Transition Validation` — Lifecycle tests validate transitions
- `Projection Synchronization Validation` — Projection tests validate sync
- `Structural Validation Truth` — Validation tests validate structure
- `Observability Validation` — Observability tests validate logging
- `Performance Validation` — Performance tests validate timing
- `Debug Reproduction` — Debug tests reproduce bugs

**Examples:**
```
AUTHORITY_LAYER: External Observable Truth
AUTHORITY_LAYER: Runtime Behavioral Truth
AUTHORITY_LAYER: Decision Authority Validation
```

**Enforcement Meaning:**
- Defines what architectural truth the test protects
- Defines how the test enforces that truth
- Aligns with VALIDATION_SYSTEM_MAP.txt authority definitions

---

### VALIDATES

**Purpose:** Defines what the test specifically validates

**Allowed Values:** Free-form list of validation targets

**Examples:**
```
VALIDATES:
  - External API contract compliance
  - Layered output structure
  - Determinism across runs
```

```
VALIDATES:
  - Retry logic behavior
  - State transition correctness
  - Failure propagation
```

```
VALIDATES:
  - Projection schema correctness
  - Projection identity stability
  - Stale overwrite prevention
```

**Enforcement Meaning:**
- Documents specific validation targets
- Enables test coverage analysis
- Enables duplicate detection

---

### ENTRYPOINT

**Purpose:** Defines the primary entry point used by the test

**Allowed Values:**
- `execute_from_input` — External API entry point
- `run_workflow` — Internal orchestrator entry point
- `system_entry` — Core execution entry point
- `step_executor` — Step execution entry point
- `projection_manager` — Projection management entry point
- `governance.decide_next_action` — Governance decision entry point
- `create_execution_group` — Scheduler entry point
- `validate_workflow` — Validation entry point
- Component-specific entry points

**Examples:**
```
ENTRYPOINT: execute_from_input
ENTRYPOINT: run_workflow
ENTRYPOINT: projection_manager.build_projection_identity
```

**Enforcement Meaning:**
- Enables entry point validation
- Enables category/entry point consistency checking
- Prevents entry point violations

---

### DIRECT_INTERNAL_CALLS

**Purpose:** Declares all direct internal calls used by the test

**Allowed Values:** List of direct internal function calls, or `NONE`

**Examples:**
```
DIRECT_INTERNAL_CALLS:
  - projection_manager.build_projection_identity
  - projection_manager.build_step_projection
```

```
DIRECT_INTERNAL_CALLS:
  - governance.decide_next_action
  - governance.resolve_decision
```

```
DIRECT_INTERNAL_CALLS: NONE
```

**Enforcement Meaning:**
- Enables direct call validation
- Enables category/direct call consistency checking
- Prevents illegal architectural bypasses

---

### MONKEYPATCH_USAGE

**Purpose:** Declares all monkeypatch usage in the test

**Allowed Values:** List of monkeypatch targets, or `NONE`

**Examples:**
```
MONKEYPATCH_USAGE:
  - system_entry (to control execution outcomes)
  - agent_executor (to control tool selection)
```

```
MONKEYPATCH_USAGE:
  - _workflow_state_registry (for state manipulation)
  - checkpoint_manager (for recovery tests)
```

```
MONKEYPATCH_USAGE: NONE
```

**Enforcement Meaning:**
- Enables monkeypatch validation
- Enables category/monkeypatch consistency checking
- Prevents illegal monkeypatching

---

### MOCKING_POLICY

**Purpose:** Defines the mocking approach used by the test

**Allowed Values:**
- `REAL_EXECUTION` — No mocking, real execution
- `FAILURE_INJECTION` — Simulate failures only
- `BEHAVIORAL_CONTROL` — Control execution behavior
- `EXECUTION_RESULT_SIMULATION` — Simulate execution results
- `SIGNAL_SIMULATION` — Simulate advisory signals
- `STATE_MANIPULATION` — Direct state manipulation
- `REAL_PROJECTION_SYSTEM` — Real projection system
- `EXTERNAL_SERVICE_MOCKING` — Mock external services
- `AS_PER_HISTORICAL_BUG` — Preserve historical reproduction

**Examples:**
```
MOCKING_POLICY: REAL_EXECUTION
MOCKING_POLICY: FAILURE_INJECTION
MOCKING_POLICY: BEHAVIORAL_CONTROL
MOCKING_POLICY: AS_PER_HISTORICAL_BUG
```

**Enforcement Meaning:**
- Documents mocking approach
- Enables mocking policy validation
- Prevents inappropriate mocking

---

### TEST_INTENT

**Purpose:** Defines the high-level intent of the test

**Allowed Values:**
- `UNIT_LEVEL_VALIDATION` — Validate specific component
- `INTEGRATION_LEVEL_VALIDATION` — Validate component integration
- `CONTRACT_VALIDATION` — Validate contract compliance
- `AUTHORITY_VALIDATION` — Validate authority boundaries
- `BEHAVIORAL_VALIDATION` — Validate behavioral correctness
- `HISTORICAL_BUG_PREVENTION` — Prevent historical bug recurrence
- `TEMPORARY_HARDENING` — Temporary edge case hardening
- `EDGE_CASE_REPRODUCTION` — Reproduce specific edge case
- `DEBUG_REPRODUCTION` — Reproduce specific bug for investigation

**Examples:**
```
TEST_INTENT: UNIT_LEVEL_VALIDATION
TEST_INTENT: INTEGRATION_LEVEL_VALIDATION
TEST_INTENT: HISTORICAL_BUG_PREVENTION
```

**Enforcement Meaning:**
- Documents test purpose
- Enables intent validation
- Enables duplicate detection

---

### ARCHITECTURAL_SCOPE

**Purpose:** Defines the architectural scope of the test

**Allowed Values:** Free-form description of architectural scope

**Examples:**
```
ARCHITECTURAL_SCOPE: External API contract only
```

## 3. REQUIRED HEADER FORMAT

Every test file MUST include a header docstring with the following format:

```python
"""
CATEGORY: <category>
AUTHORITY_LAYER: <authority_layer>
VALIDATES:
  - <validation_target_1>
  - <validation_target_2>
ENTRYPOINT: <entrypoint>
DIRECT_INTERNAL_CALLS:
  - <direct_call_1>
  - <direct_call_2>
MONKEYPATCH_USAGE:
  - <monkeypatch_target_1>
  - <monkeypatch_target_2>
MOCKING_POLICY: <mocking_policy>
TEST_INTENT: <test_intent>
ARCHITECTURAL_SCOPE: <architectural_scope>
"""
```

## 4. CATEGORY RULES

### HARNESS_CONTRACT

**Required Entrypoints:**
- `execute_from_input` — PRIMARY
- `system_entry` — For entry point contract validation
- `llm_entry` — For LLM entry contract validation
- `router` — For routing contract validation

**Forbidden Entrypoints:**
- `run_workflow` — Internal orchestrator entry point
- Direct orchestrator module imports
- Direct governance module imports
- Direct scheduler module imports
- Direct projection manager imports

**Allowed Direct Calls:**
- `system_entry` — For entry point contract tests
- Tool functions — For tool contract validation
- Validation functions — For validation contract validation

**Forbidden Direct Calls:**
- `run_workflow` — Violates harness authority
- Direct orchestrator internals — Violates harness authority
- Direct governance internals — Violates harness authority
- Direct scheduler internals — Violates harness authority
- Direct projection internals — Violates harness authority

**Allowed Monkeypatching:**
- Failure injection (simulate tool failure)
- Network failure simulation
- Resource unavailability simulation

**Forbidden Monkeypatching:**
- Behavioral mocking (control retry logic)
- State manipulation
- Direct function replacement (except failure injection)
- Monkeypatching internal orchestrator logic

---

### INTERNAL_RUNTIME

**Required Entrypoints:**
- `run_workflow` — PRIMARY
- Direct workflow construction (for controlled scenarios)

**Forbidden Entrypoints:**
- `execute_from_input` — External harness entry point

**Allowed Direct Calls:**
- `workflow_control` functions — For lifecycle state manipulation

**Allowed Monkeypatching:**

## 5. DIRECT INTERNAL CALL POLICY

### WHEN DIRECT INTERNAL CALLS ARE LEGITIMATE

**Direct internal calls are legitimate when:**
1. Test category explicitly permits direct calls
2. TEST_INTENT is `UNIT_LEVEL_VALIDATION`
3. DIRECT_INTERNAL_CALLS field declares the calls
4. Calls align with category rules in VALIDATION_SYSTEM_MAP.txt

**Examples of Legitimate Direct Calls:**

**PROJECTION Unit Tests:**
```python
CATEGORY: PROJECTION
TEST_INTENT: UNIT_LEVEL_VALIDATION
DIRECT_INTERNAL_CALLS:
  - projection_manager.build_projection_identity
```
**Legitimate:** PROJECTION category permits direct projection_manager calls for unit-level validation.

**GOVERNANCE Unit Tests:**
```python
CATEGORY: GOVERNANCE
TEST_INTENT: UNIT_LEVEL_VALIDATION
DIRECT_INTERNAL_CALLS:
  - governance.decide_next_action
```
**Legitimate:** GOVERNANCE category permits direct governance calls for unit-level validation.

**SCHEDULER Unit Tests:**
```python
CATEGORY: INTERNAL_RUNTIME
TEST_INTENT: UNIT_LEVEL_VALIDATION
DIRECT_INTERNAL_CALLS:
  - execution_scheduler.create_execution_group
```
**Legitimate:** INTERNAL_RUNTIME category permits direct scheduler calls for unit-level validation.

---

### WHEN DIRECT INTERNAL CALLS ARE ARCHITECTURE VIOLATIONS

**Direct internal calls are architecture violations when:**
1. Test category forbids direct calls
2. TEST_INTENT is not `UNIT_LEVEL_VALIDATION`
3. DIRECT_INTERNAL_CALLS field is missing or incorrect
4. Calls violate category rules in VALIDATION_SYSTEM_MAP.txt

**Examples of Illegal Direct Calls:**

**HARNESS Tests Using Orchestrator Internals:**
```python
CATEGORY: HARNESS_CONTRACT
DIRECT_INTERNAL_CALLS:
  - governance.decide_next_action
```
**Illegal:** HARNESS_CONTRACT category forbids direct governance calls.

**HARNESS Tests Using run_workflow:**
```python
CATEGORY: HARNESS_CONTRACT
DIRECT_INTERNAL_CALLS:
  - run_workflow
```
**Illegal:** HARNESS_CONTRACT category forbids run_workflow usage.

**INTERNAL Tests Using execute_from_input:**
```python
CATEGORY: INTERNAL_RUNTIME
DIRECT_INTERNAL_CALLS:
  - execute_from_input
```
**Illegal:** INTERNAL_RUNTIME category forbids execute_from_input usage.

---

### UNIT-LEVEL VALIDATION SEMANTICS

**Unit-level validation means:**
- Test validates specific component in isolation
- Test may use direct component calls
- Test does not validate integration
- Test does not validate end-to-end behavior

**Category + Intent Combination:**
- `PROJECTION` + `UNIT_LEVEL_VALIDATION` = Direct projection_manager calls legitimate
- `GOVERNANCE` + `UNIT_LEVEL_VALIDATION` = Direct governance calls legitimate
- `INTERNAL_RUNTIME` + `UNIT_LEVEL_VALIDATION` = Direct orchestrator internals legitimate

---

### INTEGRATION-LEVEL VALIDATION SEMANTICS

**Integration-level validation means:**
- Test validates component integration
- Test should use entry points, not direct calls
- Test validates end-to-end behavior
- Test should use real components

**Category + Intent Combination:**
- `INTEGRATION` + `INTEGRATION_LEVEL_VALIDATION` = Use entry points, minimal direct calls
- `HARNESS_CONTRACT` + `CONTRACT_VALIDATION` = Use execute_from_input, no direct internals
- `INTERNAL_RUNTIME` + `INTEGRATION_LEVEL_VALIDATION` = Use run_workflow, minimal direct calls

---

### EXPLICIT POLICY

**PROJECTION unit tests MAY directly call projection_manager:**
- Projection is read-only synchronization layer
- Direct calls are legitimate for unit-level validation
- Must declare TEST_INTENT: UNIT_LEVEL_VALIDATION
- Must declare DIRECT_INTERNAL_CALLS

**GOVERNANCE unit tests MAY directly call governance:**
- Governance is decision authority layer
- Direct calls are legitimate for unit-level validation
- Must declare TEST_INTENT: UNIT_LEVEL_VALIDATION
- Must declare DIRECT_INTERNAL_CALLS

**SCHEDULER unit tests MAY directly call scheduler internals:**
- Scheduler is execution scheduling layer
- Direct calls are legitimate for unit-level validation
- Must declare TEST_INTENT: UNIT_LEVEL_VALIDATION
- Must declare DIRECT_INTERNAL_CALLS

**HARNESS tests MUST NOT directly call orchestrator internals:**
- Harness validates external contract only
- Direct internal calls violate harness authority
- Must use execute_from_input as entry point
- Must declare DIRECT_INTERNAL_CALLS: NONE

## 6. MONKEYPATCH DECLARATION POLICY

### ALL MONKEYPATCH USAGE MUST BE DECLARED

**All monkeypatch usage must be declared in MONKEYPATCH_USAGE field.**

**Definition of Monkeypatch Usage:**
- Use of `monkeypatch` fixture
- Use of `patch` from unittest.mock
- Use of `MagicMock` or `Mock`
- Direct state manipulation (workflow state, registry state)
- Direct registry manipulation
- Direct checkpoint manipulation

**Consequence:**
Tests with undeclared monkeypatching are invalid.

---

### UNDECLARED MONKEYPATCHING IS INVALID

**Undeclared monkeypatching is invalid.**

**Examples of Undeclared Monkeypatching:**
```python
def test_something(monkeypatch):
    monkeypatch.setattr("system_entry", mock_function)
    # Missing MONKEYPATCH_USAGE field
```

**Consequence:**
Test must be rejected during code review.

---

### MONKEYPATCHING INTENT MUST BE DOCUMENTED

**Monkeypatching intent must be documented in MONKEYPATCH_USAGE field.**

**Examples of Documented Intent:**
```python
MONKEYPATCH_USAGE:
  - system_entry (to control execution outcomes)
  - agent_executor (to control tool selection)
```

```python
MONKEYPATCH_USAGE:
  - _workflow_state_registry (for state manipulation)
  - checkpoint_manager (for recovery tests)
```

**Consequence:**
Monkeypatch usage without intent documentation is invalid.

---

### BEHAVIORAL CONTROL VS FAILURE INJECTION DISTINCTION

**Behavioral Control:**
- Monkeypatching to control execution behavior
- Used in INTERNAL_RUNTIME tests
- MOCKING_POLICY: BEHAVIORAL_CONTROL

**Failure Injection:**
- Monkeypatching to simulate failures
- Used in HARNESS_CONTRACT tests
- MOCKING_POLICY: FAILURE_INJECTION

**Examples:**

**Behavioral Control (Internal):**
```python
CATEGORY: INTERNAL_RUNTIME
MONKEYPATCH_USAGE:
  - system_entry (to control execution outcomes)
MOCKING_POLICY: BEHAVIORAL_CONTROL
```

**Failure Injection (Harness):**
```python
CATEGORY: HARNESS_CONTRACT
MONKEYPATCH_USAGE:
  - system_entry (to simulate tool failure)
MOCKING_POLICY: FAILURE_INJECTION
```

---

### HARNESS MONKEYPATCHING RESTRICTIONS

**HARNESS tests MUST NOT:**
- Monkeypatch to control retry logic — Violates harness authority
- Monkeypatch to control lifecycle — Violates harness authority
- Monkeypatch internal orchestrator logic — Violates harness authority
- Monkeypatch that bypasses entry point — Violates harness authority

**HARNESS tests MAY:**
- Monkeypatch for failure injection — Simulate tool failure, network failure, resource unavailability
- Mock external dependencies — Simulate unavailable external services

**Example:**
```python
CATEGORY: HARNESS_CONTRACT
MONKEYPATCH_USAGE:
  - system_entry (to simulate tool failure)
MOCKING_POLICY: FAILURE_INJECTION
```

---

### INTERNAL RUNTIME MONKEYPATCH ALLOWANCES

**INTERNAL tests MAY:**
- Monkeypatch `system_entry` — To control execution outcomes
- Monkeypatch agent executor — To control tool selection
- Monkeypatch governance — To test decision logic
- Direct workflow state manipulation — For state transition tests

**INTERNAL tests MUST NOT:**
- Monkeypatch `run_workflow` itself — Violates entry point authority
- Monkeypatch that invalidates behavioral validation — Violates test purpose

**Example:**
```python
CATEGORY: INTERNAL_RUNTIME
MONKEYPATCH_USAGE:
  - system_entry (to control execution outcomes)
  - agent_executor (to control tool selection)
MOCKING_POLICY: BEHAVIORAL_CONTROL
```

---

### STABILIZATION MONKEYPATCH ALLOWANCES

**STABILIZATION tests MAY:**
- Use any monkeypatching required for stabilization scenario
- Use direct state manipulation
- Use direct registry manipulation

**STABILIZATION tests MUST NOT:**
- Be treated as permanent — Should eventually graduate/merge/archive/retire

**Example:**
```python
CATEGORY: STABILIZATION
MONKEYPATCH_USAGE:
  - _workflow_state_registry (state manipulation)
  - projection_manager.invalidate_projection
MOCKING_POLICY: STATE_MANIPULATION
CREATED: 2026-05-01
GRADUATION_CRITERIA: Zombie state permanently resolved
```

---

### REGRESSION PRESERVATION EXCEPTIONS

**REGRESSION tests MAY:**
- Preserve ugly historical reproductions
- Use original monkeypatching from bug discovery

**REGRESSION tests MUST NOT:**
- Change reproduction if it invalidates historical bug capture

**Example:**
```python
CATEGORY: REGRESSION
MONKEYPATCH_USAGE:
  - _update_workflow_state (historical reproduction)
  - _update_runtime_registry_only (historical reproduction)
MOCKING_POLICY: AS_PER_HISTORICAL_BUG
```

## 7. CATEGORY MIXING POLICY

### ONE PRIMARY CATEGORY PER TEST FILE

**One primary category per test file.**

**Definition of Primary Category:**
- Single CATEGORY field value
- Single AUTHORITY_LAYER field value
- Single TEST_INTENT field value

**Consequence:**
Mixed-category files are architectural drift.

---

### MIXED-CATEGORY FILES ARE ARCHITECTURAL DRIFT

**Mixed-category files are architectural drift.**

**Definition of Mixed-Category File:**
- Single file testing multiple categories without declaration
- Single file using multiple entry points without declaration
- Single file with mixed authority layers without declaration

**Examples of Mixed-Category Files:**
```python
CATEGORY: HARNESS_CONTRACT, INTERNAL_RUNTIME  # INVALID
```

```python
CATEGORY: HARNESS_CONTRACT
ENTRYPOINT: execute_from_input, run_workflow  # INVALID
```

```python
AUTHORITY_LAYER: External Observable Truth, Runtime Behavioral Truth  # INVALID
```

**Consequence:**
Mixed-category files must be rejected during code review.

---

### EXCEPTIONS REQUIRE EXPLICIT DECLARATION

**Exceptions require explicit declaration.**

**Valid Exception: INTEGRATION tests may bridge categories:**
```python
CATEGORY: INTEGRATION
TEST_INTENT: INTEGRATION_LEVEL_VALIDATION
ENTRYPOINT: execute_from_input (end-to-end integration)
VALIDATES:
  - External contract compliance
  - Internal orchestrator behavior
ARCHITECTURAL_SCOPE: End-to-end integration across layers
```

**Valid Exception: REGRESSION tests may preserve historical mixing:**
```python
CATEGORY: REGRESSION
TEST_INTENT: HISTORICAL_BUG_PREVENTION
ENTRYPOINT: execute_from_input (historical reproduction)
VALIDATES:
  - Historical bug across multiple layers
ARCHITECTURAL_SCOPE: Historical bug reproduction
HISTORICAL_NOTE: Original test mixed categories, preserved for accuracy
```

---

### HOW INTEGRATION TESTS MAY BRIDGE CATEGORIES

**Integration tests may bridge categories when:**
- TEST_INTENT is `INTEGRATION_LEVEL_VALIDATION`
- ARCHITECTURAL_SCOPE explicitly declares cross-layer scope
- VALIDATES explicitly declares multi-layer validation targets

**Example:**
```python
CATEGORY: INTEGRATION
TEST_INTENT: INTEGRATION_LEVEL_VALIDATION
ARCHITECTURAL_SCOPE: End-to-end integration across layers
VALIDATES:
  - External contract compliance
  - Internal orchestrator behavior
  - Component integration
```

**Consequence:**
Integration tests with explicit cross-layer scope are valid.

---

### HOW REGRESSION TESTS MAY PRESERVE HISTORICAL MIXING

**Regression tests may preserve historical mixing when:**
- TEST_INTENT is `HISTORICAL_BUG_PREVENTION`
- HISTORICAL_NOTE explicitly declares historical mixing
- ARCHITECTURAL_SCOPE explicitly declares historical reproduction scope

**Example:**
```python
CATEGORY: REGRESSION
TEST_INTENT: HISTORICAL_BUG_PREVENTION
ARCHITECTURAL_SCOPE: Historical bug reproduction
HISTORICAL_NOTE: Original test mixed categories, preserved for accuracy
```

**Consequence:**
Regression tests with explicit historical mixing declaration are valid.
