## 1. VALIDATION PHILOSOPHY

### CORE PRINCIPLE: LAYERED VALIDATION

Validation is intentionally layered.

Different test categories validate different authority layers.

Not all tests share the same entry point requirements.

Contract tests and internal runtime tests are fundamentally different.

Regression/stabilization tests may intentionally violate normal purity for historical protection.

Validation architecture exists to preserve authority boundaries.

---

### AUTHORITY LAYER DEFINITIONS

#### HARNESS = EXTERNAL OBSERVABLE TRUTH

**Purpose:** Validate what the system RETURNS to external callers

**Authority:**
- Defines external API contract
- Enforces output schema
- Guarantees determinism
- Prevents regression

**Scope:**
- Tests public API surface
- Validates externally observable behavior
- No knowledge of internal implementation
- Contract enforcement only

**Entry Point:** `execute_from_input(user_input: str)`

**Contract Type:** Layered (nested status/result structure)

**Location:** `tests/harness/`

---

#### INTERNAL = RUNTIME BEHAVIORAL TRUTH

**Purpose:** Validate how the system BEHAVES internally

**Authority:**
- Defines retry logic behavior
- Validates state transitions
- Tests failure modes
- Controls execution path (mocking permitted)

**Scope:**
- Tests internal orchestrator logic
- Validates behavioral correctness
- Uses controlled mocking (monkeypatch)
- Direct workflow construction

**Entry Point:** `run_workflow(workflow: dict)`

**Contract Type:** Flat (direct status/result structure)

**Location:** `system/tests/`

---

#### REGRESSION = HISTORICAL BUG PREVENTION

**Purpose:** Preserve architectural lessons, prevent recurrence of historical bugs

**Authority:**
- Historical bug reproduction is legitimate
- Some regression tests intentionally bypass ideal architecture
- Regression value overrides aesthetic purity

**Scope:**
- Reproduces specific historical failure states
- Preserves architectural lessons
- May use ugly reproductions if they accurately capture the bug

**Entry Points:** Original entry point used when bug was discovered

**Contract Type:** As per original test

**Location:** `tests/regression/`

---

#### STABILIZATION = TEMPORARY ARCHITECTURAL HARDENING

**Purpose:** Temporary hardening tests during architectural convergence

**Authority:**
- Stabilization tests are temporary
- Stabilization tests exist to harden specific edge cases
- Stabilization tests should eventually graduate, merge, archive, or retire

**Scope:**
- Complex edge case reproduction
- Zombie state cleanup validation
- Recovery path testing
- Pause/resume stability

**Entry Points:** As required for specific stabilization scenario

**Contract Type:** As per scenario

**Location:** `tests/stabilization/`

---

#### ADVERSARIAL = AUTHORITY STRESS TESTING

**Purpose:** Stress test authority boundaries, detect edge case failures

**Authority:**
- Validates system under adversarial conditions
- Tests malformed inputs, dependency failure chains, security attempts
- Ensures authority boundaries hold under stress

**Scope:**
- Edge case validation
- Malformed input handling
- Dependency failure scenarios
- Security boundary testing

**Entry Points:** `execute_from_input`, `run_workflow` (as appropriate)

**Contract Type:** As per scenario

**Location:** `tests/adversarial/`

---

#### PROJECTION = SYNCHRONIZATION VALIDATION

**Purpose:** Validate canonical projection behavior and synchronization

**Authority:**
- Projection layer is read-only synchronization
- Projection tests may directly validate projection layer behavior
- Projection tests may use direct projection manager calls

**Scope:**
- Projection schema validation
- Projection ordering (monotonic versioning)
- Workflow isolation (no cross-workflow contamination)
- Projection lifecycle states
- Stale overwrite prevention

**Entry Points:** `run_workflow` + direct projection calls (unit-level validation)

**Contract Type:** Projection-specific

**Location:** `tests/projection/`

---

#### GOVERNANCE = DECISION AUTHORITY VALIDATION

**Purpose:** Validate governance as sole decision authority

**Authority:**
- Governance is sole decision authority
- Validator signals are advisory only
- execution_result is sole decision driver

**Scope:**

- Retry decision logic

**Entry Points:** `run_workflow` + direct governance calls (unit-level validation)

**Contract Type:** Governance-specific

**Location:** `tests/governance/`

---

#### LIFECYCLE = STATE TRANSITION VALIDATION

## 2. VALIDATION CATEGORY DEFINITIONS

### HARNESS_CONTRACT

**Purpose:** Validate external API contract compliance

**Authority Layer:** External observable truth

**Allowed Entry Points:**
- `execute_from_input(user_input: str)` — PRIMARY
- `system_entry(tool_call: str)` — For entry point contract validation
- `llm_entry()` — For LLM entry contract validation
- `router()` — For routing contract validation

**Forbidden Entry Points:**
- `run_workflow` — Internal orchestrator entry point
- Direct orchestrator module imports
- Direct governance module imports
- Direct scheduler module imports
- Direct projection manager imports

**Allowed Mocking:**
- Failure injection (simulate tool failure)
- Network failure simulation
- Resource unavailability simulation

**Forbidden Mocking:**
- Behavioral mocking (control retry logic)
- State manipulation
- Direct function replacement (except failure injection)
- Monkeypatching internal orchestrator logic

**Acceptable Direct Calls:**
- `system_entry` — For entry point contract tests
- Tool functions — For tool contract validation
- Validation functions — For validation contract validation

**Architectural Intent:**
Harness tests validate the EXTERNAL contract. They must not test internal implementation details. They use the same entry point as external callers and validate the layered output structure.

---

### INTERNAL_RUNTIME

**Purpose:** Validate internal orchestrator behavior

**Authority Layer:** Runtime behavioral truth

**Allowed Entry Points:**
- `run_workflow(workflow: dict)` — PRIMARY
- Direct workflow construction (for controlled scenarios)

**Forbidden Entry Points:**
- `execute_from_input` — External harness entry point
- Natural language input strings

**Allowed Mocking:**
- `monkeypatch` on `system_entry` — To control execution outcomes
- `monkeypatch` on agent executor — To control tool selection
- `monkeypatch` on governance — To test decision logic
- Direct workflow state manipulation (for state transition tests)

**Forbidden Mocking:**
- Mocking of `run_workflow` itself
- Mocking of orchestrator runtime internals (unless testing specific component)
- Mocking that bypasses the entry point entirely

**Acceptable Direct Calls:**
- `workflow_control` functions — For lifecycle state manipulation
- `governance.decide_next_action` — For governance unit tests
- `execution_scheduler.create_execution_group` — For scheduler unit tests
- `projection_manager` functions — For projection unit tests

**Architectural Intent:**
Internal tests validate BEHAVIOR. They may use monkeypatching to control execution paths and test specific behavioral scenarios. They use `run_workflow` as the entry point to test the orchestrator layer.

---

### INTEGRATION

**Purpose:** Validate integration between system components

**Authority Layer:** Component integration truth

**Allowed Entry Points:**
- `execute_from_input` — For end-to-end integration
- `run_workflow` — For orchestrator integration

**Forbidden Entry Points:**
- None (integration tests may use any appropriate entry point)

**Allowed Mocking:**
- Minimal (integration tests should use real components)

**Forbidden Mocking:**
- Mocking of components under test
- Mocking that invalidates integration validity

**Acceptable Direct Calls:**
- Any component calls appropriate for integration scenario

**Architectural Intent:**
Integration tests validate that components work together correctly. They should use real components and minimal mocking to ensure integration validity.

## 3. ENTRYPOINT AUTHORITY MODEL

### execute_from_input

**Intended Usage:** External API entry point for user-facing execution

**Allowed Validation Categories:**
- HARNESS_CONTRACT — Primary category
- INTEGRATION — End-to-end integration tests
- ADVERSARIAL — External adversarial testing
- PERFORMANCE — External performance tests

**Forbidden Categories:**
- INTERNAL_RUNTIME — Should use `run_workflow`
- GOVERNANCE — Governance is internal layer
- LIFECYCLE — Lifecycle is internal layer

**Architectural Meaning:**
This is the external boundary. It wraps `run_workflow` and applies layered contract transformation. Tests using this entry point validate the external API contract.

---

### run_workflow

**Intended Usage:** Internal orchestrator entry point for workflow execution

**Allowed Validation Categories:**
- INTERNAL_RUNTIME — Primary category
- INTEGRATION — Orchestrator integration tests
- ADVERSARIAL — Internal adversarial testing
- GOVERNANCE — Governance integration tests
- LIFECYCLE — Lifecycle integration tests
- PROJECTION — Projection integration tests
- OBSERVABILITY — Trace integration tests
- PERFORMANCE — Internal performance tests

**Forbidden Categories:**
- HARNESS_CONTRACT — Should use `execute_from_input`

**Architectural Meaning:**
This is the orchestrator layer entry point. It executes workflows with flat contract output. Tests using this entry point validate internal orchestrator behavior.

---

### system_entry

**Intended Usage:** Core execution pipeline entry point for single tool execution

**Allowed Validation Categories:**
- HARNESS_CONTRACT — Entry point contract validation
- VALIDATION — Execution validation
- ADVERSARIAL — Execution adversarial testing

**Forbidden Categories:**
- INTERNAL_RUNTIME — Orchestrator tests should use `run_workflow`
- GOVERNANCE — Governance is orchestrator layer

**Architectural Meaning:**
This is the core execution boundary. It executes single tool calls with deterministic behavior. Tests using this entry point validate core pipeline correctness.

---

### step_executor

**Allowed Validation Categories:**
- INTERNAL_RUNTIME — Step execution unit tests

**Forbidden Categories:**

This is the step-level execution entry point. Tests using this entry point validate individual step execution behavior. This is a legitimate unit-level validation target.

## 4. MOCKING + MONKEYPATCH POLICY

### WHEN MOCKING IS ALLOWED

**Harness Tests:**
- Failure injection (simulate tool failure, network failure, resource unavailability)
- External dependency simulation (simulate unavailable external services)

**Internal Tests:**
- `monkeypatch` on `system_entry` — To control execution outcomes
- `monkeypatch` on agent executor — To control tool selection
- `monkeypatch` on governance — To test decision logic
- Direct workflow state manipulation — For state transition tests

**Integration Tests:**
- External service mocking (for dependencies)
- Minimal mocking (integration should use real components)

**Governance Tests:**
- Execution result simulation (for governance decision tests)
- Signal simulation (for advisory signal tests)

**Lifecycle Tests:**
- Direct workflow state manipulation (for state transition tests)
- Checkpoint manipulation (for recovery tests)

---

### WHEN MONKEYPATCHING IS ALLOWED

**Internal Tests:**
- `monkeypatch` on `system_entry` — To control execution outcomes
- `monkeypatch` on agent executor — To control tool selection
- `monkeypatch` on governance — To test decision logic

**Lifecycle Tests:**
- Direct workflow state manipulation — For state transition tests

**Stabilization Tests:**
- Any monkeypatching required for stabilization scenario

---

### WHEN MONKEYPATCHING BECOMES ARCHITECTURE VIOLATION

**Harness Tests:**
- Monkeypatching to control retry logic — Violates harness authority
- Monkeypatching to control lifecycle — Violates harness authority
- Monkeypatching internal orchestrator logic — Violates harness authority
- Monkeypatching that bypasses entry point — Violates harness authority

**Internal Tests:**
- Monkeypatching `run_workflow` itself — Violates entry point authority
- Monkeypatching that invalidates behavioral validation — Violates test purpose

---

### ACCEPTABLE RUNTIME ISOLATION

**Harness Tests:**
- Failure injection is acceptable runtime isolation
- External dependency simulation is acceptable

**Internal Tests:**
- `monkeypatch` on `system_entry` is acceptable runtime isolation
- Controlled workflow construction is acceptable

**Integration Tests:**
- External service mocking is acceptable

---

### UNACCEPTABLE RUNTIME MANIPULATION

**Harness Tests:**
- Direct state manipulation — Unacceptable
- Direct registry manipulation — Unacceptable
- Direct function replacement (except failure injection) — Unacceptable

**Internal Tests:**
- Monkeypatching that bypasses the entry point entirely — Unacceptable
- Monkeypatching that invalidates behavioral validation — Unacceptable

---

### HARNESS MOCKING POLICY

**HARNESS SHOULD:**
- Avoid monkeypatching
- Use failure injection only for simulating failures
- Test real execution paths

**HARNESS MUST NOT:**
- Monkeypatch to control behavior
- Monkeypatch internal orchestrator logic
- Monkeypatch to bypass entry point

---

### INTERNAL MOCKING POLICY

**INTERNAL MAY:**
- Monkeypatch execution boundaries
- Monkeypatch for behavior control
- Use direct workflow construction

**INTERNAL MUST NOT:**
- Monkeypatch `run_workflow` itself
- Monkeypatch that invalidates behavioral validation

---

### STABILIZATION MOCKING POLICY

**STABILIZATION MAY:**
- Require state manipulation
- Use direct registry manipulation
- Use any approach to harden system

**STABILIZATION MUST NOT:**
- Be treated as permanent

---

### REGRESSION MOCKING POLICY

**REGRESSION MAY:**
- Preserve ugly historical reproductions
- Use original monkeypatching from bug discovery

**REGRESSION MUST NOT:**
- Change reproduction if it invalidates historical bug capture

## 5. REGRESSION TEST PRESERVATION POLICY

### REGRESSION TESTS ARE HISTORICAL PROTECTION

**Regression tests preserve architectural lessons.**

Regression tests are historical protection against bug recurrence.

---

### REGRESSION TESTS MUST NOT BE DELETED SOLELY FOR UGLINESS

**Regression value overrides aesthetic purity.**

If a regression test accurately captures a historical bug, it must be preserved even if the reproduction is ugly.

---

### REGRESSION TESTS MAY INTENTIONALLY REPRODUCE HISTORICAL DRIFT/FAILURE STATES

**Historical bug reproduction is legitimate.**

Regression tests may reproduce the exact failure state from the historical bug, even if that state violates ideal architecture.

---

### REGRESSION TESTS PRESERVE ARCHITECTURAL LESSONS

**Regression tests preserve architectural lessons.**

Each regression test encodes an architectural lesson about what went wrong and how to prevent it.

---

### REGRESSION TESTS MAY INTENTIONALLY BYPASS IDEAL ARCHITECTURE

**Some regression tests intentionally bypass ideal architecture.**

If the historical bug was caused by a specific architecture violation, the regression test may reproduce that violation to ensure it doesn't recur.

---

### HISTORICAL BUG REPRODUCTION IS LEGITIMATE

**Historical bug reproduction is legitimate.**

Regression tests are allowed to reproduce the exact conditions that caused the historical bug.

---

### REGRESSION VALUE OVERRIDES AESTHETIC PURITY

**Regression value overrides aesthetic purity.**

The value of preventing bug recurrence is more important than having clean, aesthetically pleasing test code.

---

### REGRESSION TEST LIFECYCLE

**Regression tests are permanent unless:**
- The architectural lesson is no longer relevant
- The component being tested has been completely removed
- The test has been superseded by a more comprehensive test

**Regression tests must NOT be deleted for:**
- Ugliness
- Complexity
- Non-ideal architecture (if that non-ideal architecture is what caused the historical bug)

---

## 6. STABILIZATION TEST LIFECYCLE

### STABILIZATION TESTS ARE TEMPORARY HARDENING TESTS

**Stabilization tests are temporary.**

Stabilization tests exist during architectural convergence to harden specific edge cases.

---

### STABILIZATION TESTS EXIST DURING ARCHITECTURAL CONVERGENCE

**Stabilization tests exist during architectural convergence.**

Stabilization tests are created when specific edge cases need hardening during architectural development.

---

### STABILIZATION TESTS SHOULD EVENTUALLY:

**Graduation Criteria:**
- Test graduates to permanent suite when:
  - Edge case is stabilized and becomes permanent requirement
  - Test provides ongoing architectural value
  - Test is cleaned up to meet permanent suite standards

**Merge Criteria:**
- Test merges into permanent suite when:
  - Test scenario is covered by existing permanent test
  - Test adds no unique value
  - Test is redundant

**Archive Criteria:**
- Test archives when:
  - Edge case is no longer relevant
  - Architecture has evolved past the edge case
  - Test is no longer needed but provides historical value

**Retirement Criteria:**
- Test retires when:
  - Edge case is permanently resolved
  - Test provides no ongoing value
  - Test is safe to remove

---

### STABILIZATION TESTS ARE NOT AUTOMATICALLY PERMANENT

**Stabilization tests are NOT automatically permanent.**

Stabilization tests must be reviewed for graduation, merge, archive, or retirement.

---

### STABILIZATION TESTS MUST NOT BE REMOVED CASUALLY

**Stabilization tests must NOT be removed casually.**

Stabilization tests must go through formal review before retirement.

---

### STABILIZATION TEST LIFECYCLE PROCESS

**1. Creation:**
- Stabilization test created during architectural convergence
- Test marked as STABILIZATION category
- Test documents purpose and temporary nature

**2. Review:**
- Periodic review of stabilization tests
- Assessment of ongoing relevance
- Decision on graduation, merge, archive, or retirement

**3. Action:**
- Graduate: Move to permanent suite, clean up to meet standards
- Merge: Merge into existing permanent test, remove duplicate
- Archive: Move to archive folder with historical notes
- Retire: Remove test with documentation of removal reason

### STABILIZATION TEST DOCUMENTATION REQUIREMENTS

**Each stabilization test must document:**
- Purpose (what edge case is being hardened)
- Creation date
- Architectural context (what convergence phase this is part of)

## 9. ENFORCEMENT PRINCIPLES

### FUTURE TESTS MUST DECLARE CATEGORY

**Every new test MUST declare its category.**

Test category declaration must include:
- Primary category (e.g., HARNESS_CONTRACT, INTERNAL_RUNTIME)
- Authority layer (e.g., external observable truth, runtime behavioral truth)
- Intended validation scope

**Declaration Format:**
```python
"""
Category: HARNESS_CONTRACT
Authority Layer: External Observable Truth
Validates: External API contract compliance
Entry Point: execute_from_input
"""
```

---

### FUTURE TESTS MUST DECLARE AUTHORITY LAYER

**Every new test MUST declare its authority layer.**

Authority layer declaration must include:
- Which authority layer the test validates
- What architectural truth the test protects
- How the test enforces that truth

**Declaration Format:**
```python
"""
Authority Layer: External Observable Truth
Architectural Truth: System returns correct layered contract
Enforcement: Validates status + result/reason structure
"""
```

---

### FUTURE TESTS MUST DECLARE INTENDED ENTRY POINT

**Every new test MUST declare its intended entry point.**

Entry point declaration must include:
- Primary entry point (e.g., execute_from_input, run_workflow)
- Why this entry point is appropriate for the test category
- Whether direct internal calls are intentional

**Declaration Format:**
```python
"""
Entry Point: execute_from_input
Rationale: Harness tests must use external entry point
Direct Internal Calls: None (prohibited for harness)
"""
```

---

### FUTURE TESTS MUST DECLARE WHETHER DIRECT INTERNAL CALLS ARE INTENTIONAL

**Every new test using direct internal calls MUST declare intent.**

Direct internal call declaration must include:
- Which internal functions are called directly
- Why direct calls are necessary
- Which category justifies the direct calls (unit-level validation)

**Declaration Format:**
```python
"""
Direct Internal Calls: projection_manager.build_projection_identity
Rationale: Unit-level validation of projection schema
Justification: PROJECTION category permits direct projection calls
"""
```

---

### UNCLEAR TESTS ARE ARCHITECTURAL DRIFT

**Unclear tests are architectural drift.**

Tests without clear category, authority layer, or entry point declarations represent architectural drift.

**Definition of Unclear Test:**
- No category declaration
- No authority layer declaration
- No entry point declaration
- Direct internal calls without intent declaration
- Mixed concerns (multiple categories without separation)

**Consequence:**
Unclear tests must be reviewed and reclassified before being accepted.

---

### VALIDATION WITHOUT TAXONOMY CAUSES AUTHORITY COLLAPSE

**Validation without taxonomy causes authority collapse.**

Without clear taxonomy:
- Authority boundaries blur
- Tests drift between layers
- Entry point violations go undetected
- Duplicate coverage accumulates
- Architectural lessons are lost

**Consequence:**
Validation system becomes ineffective at protecting architectural boundaries.

---

### ENFORCEMENT MECHANISM

**New test review MUST check:**
1. Category declaration present and correct
2. Authority layer declaration present and correct
3. Entry point declaration present and correct
4. Direct internal calls declared with intent
5. Test location matches category (e.g., harness tests in tests/harness/)
6. No mixed concerns (single category per test file)

**Failure to meet any criterion = test rejected.**
