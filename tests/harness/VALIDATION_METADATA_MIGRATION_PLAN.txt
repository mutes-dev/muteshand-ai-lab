## 1. MIGRATION PHILOSOPHY

### GOVERNANCE BEFORE CLEANUP

**Governance before cleanup.**

Metadata governance must be established before any cleanup actions.

**Rationale:**
- Without governance, cleanup is speculative
- Without governance, deletion is dangerous
- Without governance, consolidation is unsafe

**Consequence:**
No cleanup, deletion, or consolidation until metadata governance is established.

---

### CLASSIFICATION BEFORE DELETION

**Classification before deletion.**

Tests must be classified before deletion decisions.

**Rationale:**
- Classification reveals test value
- Classification reveals test intent
- Classification reveals historical significance
- Classification reveals duplication

**Consequence:**
No test deletion without prior classification.

---

### MIGRATION BEFORE ENFORCEMENT

**Migration before enforcement.**

Metadata migration must precede enforcement activation.

**Rationale:**
- Enforcement without migration is unfair to historical tests
- Enforcement without migration causes unnecessary failures
- Enforcement without migration loses historical context

**Consequence:**
No CI enforcement until metadata migration is complete.

---

### METADATA BEFORE RESTRUCTURING

**Metadata before restructuring.**

Metadata headers must exist before folder reorganization.

**Rationale:**
- Metadata enables correct categorization
- Metadata enables correct folder placement
- Metadata prevents misclassification during moves
- Metadata preserves intent during restructuring

**Consequence:**
No folder moves until metadata headers are added.

---

### HISTORICAL PRESERVATION OVER AESTHETIC PURITY

**Historical preservation over aesthetic purity.**

Regression tests preserve architectural lessons.

**Rationale:**
- Ugly tests may still be strategically essential
- Historical reproductions may require non-ideal patterns
- Regression value overrides aesthetic cleanup
- Architectural lessons must not be lost

**Consequence:**
Regression tests are preserved even if aesthetically non-ideal.

---

### TESTS ARE HISTORICAL ARCHITECTURAL KNOWLEDGE

**Tests are historical architectural knowledge.**

Every test encodes:
- What was broken
- How it was fixed
- What architectural lesson was learned
- What boundary was established

**Rationale:**
- Tests are executable documentation
- Tests are architectural memory
- Tests are boundary enforcement
- Tests are lesson preservation

**Consequence:**
Test deletion must consider historical knowledge loss.

---

### REGRESSION TESTS PRESERVE LESSONS

**Regression tests preserve lessons.**

Regression tests encode:
- Historical bug patterns
- Architectural drift patterns
- Authority violation patterns
- Failure mode patterns

**Rationale:**
- Regression tests prevent recurrence
- Regression tests preserve architectural wisdom
- Regression tests encode hard-learned lessons
- Regression tests are architectural insurance

**Consequence:**
Regression tests are protected assets, not cleanup targets.

---

### STABILIZATION TESTS PRESERVE CONVERGENCE HISTORY

**Stabilization tests preserve convergence history.**

Stabilization tests encode:
- Edge cases discovered during convergence
- Temporary hardening requirements
- Architectural instability patterns
- Recovery path requirements

**Rationale:**
- Stabilization tests document convergence journey
- Stabilization tests preserve hardening lessons
- Stabilization tests enable future convergence
- Stabilization tests are architectural history

**Consequence:**
Stabilization tests are preserved during migration, then evaluated for graduation.

---

### CLEANUP WITHOUT CLASSIFICATION IS UNSAFE

**Cleanup without classification is unsafe.**

**Rationale:**
- Without classification, cleanup is speculative
- Without classification, deletion is dangerous
- Without classification, consolidation loses context
- Without classification, archival loses history

**Consequence:**
No cleanup action without prior classification.

---

### MIGRATION IS SEMANTIC, NOT COSMETIC

**Migration is semantic, not cosmetic.**

**Rationale:**
- Migration preserves validation intent
- Migration preserves architectural knowledge
- Migration preserves historical context
- Migration preserves test value

**Consequence:**
Metadata addition must NOT alter test behavior or intent.

---

### MIGRATION PRESERVES VALIDATION INTENT

**Migration preserves validation intent.**

**Rationale:**
- Test intent is architectural knowledge
- Test intent is historical context
- Test intent is boundary definition
- Test intent is lesson encoding

**Consequence:**
Metadata must accurately reflect original test intent, not reinterpret it.

## 3. MIGRATION PHASES

### PHASE 1 — INVENTORY + CLASSIFICATION

**Define:**
- Classify all tests
- Assign categories
- Assign authority layers
- Assign intended entrypoints
- Identify violations
- Identify stabilization tests
- Identify obsolete tests

**Explicit Definition:**
- NO test modification yet
- NO deletion yet
- NO folder movement yet

**Deliverables:**
- Complete test classification matrix
- Violation identification report
- Stabilization test inventory
- Obsolete test inventory
- High-priority authoritative test list

**Process:**
1. Read each test file
2. Analyze entry point usage
3. Analyze direct internal calls
4. Analyze monkeypatch usage
5. Analyze test intent from code and comments
6. Assign CATEGORY based on VALIDATION_SYSTEM_MAP.txt
7. Assign AUTHORITY_LAYER based on category
8. Assign ENTRYPOINT based on actual usage
9. Assign DIRECT_INTERNAL_CALLS based on imports
10. Assign MONKEYPATCH_USAGE based on code
11. Assign STATUS (AUTHORITATIVE, ACTIVE, STABILIZATION, REGRESSION, OBSOLETE, DUPLICATE, REVIEW_REQUIRED)
12. Assign ACTION (KEEP, RECLASSIFY, MOVE, ARCHIVE, MERGE, REVIEW, RETIRE)

**Criteria:**
- Use VALIDATION_SYSTEM_MAP.txt as authoritative interpretation model
- If uncertain, mark REVIEW_REQUIRED
- DO NOT guess
- DO NOT assume old means obsolete
- DO NOT assume direct calls mean violation

**Timeline:**
- Phase 1: Complete classification matrix (this document)

---

### PHASE 2 — METADATA HEADER MIGRATION

**Define:**
- Add metadata headers incrementally
- Prioritize authoritative tests first

**Priority Order:**
1. HARNESS_CONTRACT — External contract validation is critical
2. REGRESSION — Historical bug prevention is critical
3. GOVERNANCE — Decision authority validation is critical
4. LIFECYCLE — State transition validation is critical
5. PROJECTION — Projection synchronization validation
6. INTERNAL_RUNTIME — Internal behavior validation
7. STABILIZATION — Temporary hardening (lower priority)
8. DEBUG_REPRO — Debug reproduction (lowest priority)

**Explicit Definition:**
- Migration is additive only
- Metadata addition must NOT alter behavior
- Metadata addition must NOT alter test execution
- Metadata addition must NOT alter imports

**Deliverables:**
- All HARNESS_CONTRACT tests with metadata headers
- All REGRESSION tests with metadata headers
- All GOVERNANCE tests with metadata headers
- All LIFECYCLE tests with metadata headers
- All PROJECTION tests with metadata headers
- All INTERNAL_RUNTIME tests with metadata headers
- All STABILIZATION tests with metadata headers
- All DEBUG_REPRO tests with metadata headers

**Process:**
1. For each test in priority order
2. Add metadata header docstring
3. Fill CATEGORY based on Phase 1 classification
4. Fill AUTHORITY_LAYER based on Phase 1 classification
5. Fill VALIDATES based on test code analysis
6. Fill ENTRYPOINT based on actual usage
7. Fill DIRECT_INTERNAL_CALLS based on imports

11. Fill ARCHITECTURAL_SCOPE based on test boundaries
12. Add additional fields as needed (CREATED, GRADUATION_CRITERIA for stabilization)
13. Verify test still executes correctly
14. Commit metadata addition

**Criteria:**
- Metadata must accurately reflect test intent
- Metadata must align with VALIDATION_SYSTEM_MAP.txt
- Metadata must align with TEST_METADATA_CONTRACT.txt
- If uncertain during migration, mark REVIEW_REQUIRED in metadata

**Timeline:**
- Phase 2: Add metadata headers (incremental, by priority)

**Timeline:**

### PHASE 5 — CONTROLLED CLEANUP

**Define:**
- Duplicate consolidation
- Obsolete archival
- Debug repro retirement
- Stabilization graduation

**Explicit Definition:**
- Cleanup requires metadata classification first
- Cleanup requires enforcement visibility first
- Cleanup must preserve historical lessons

**Deliverables:**
- Duplicate test consolidation
- Obsolete test archival
- Debug repro retirement
- Stabilization test graduation/merge/archive/retire
- Final cleanup report

**Process:**
1. Use enforcement data to identify duplicates
2. Use enforcement data to identify obsolete tests
3. Review each duplicate for consolidation
4. Review each obsolete test for archival
5. Review each stabilization test for graduation
6. Review each debug repro test for retirement
7. Consolidate duplicates (merge into canonical test)
8. Archive obsolete tests (move to tests/archive/)
9. Graduate stabilization tests (move to permanent suite)
10. Retire debug repro tests (delete with documentation)
11. Document all cleanup actions
12. Commit cleanup

**Criteria:**
- Cleanup must be data-driven (based on enforcement visibility)
- Cleanup must preserve historical lessons
- Cleanup must not delete regression tests without review
- Cleanup must not delete stabilization tests without graduation evaluation
- Cleanup must be documented

**Timeline:**
- Phase 5: Controlled cleanup (after Phase 4 complete)
